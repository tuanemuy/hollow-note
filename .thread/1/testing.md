## 確認環境

### 検証環境の起動

- 開発サーバー: リポジトリルートで `pnpm dev` を実行し、`http://localhost:3000` を開く（`apps/web/vite.config.node.ts` の `server.port: 3000`）。
- DB マイグレーションは不要。永続化は in-memory アダプターで、migrate スクリプトは本 Issue で削除される（steps.md 手順1）。
- **データはプロセス内メモリのみ**: dev サーバーを再起動するとユーザー・ノートはすべて消える。以下の確認項目は 1 プロセス内で通しで実行し、テストユーザーは都度サインアップで作成する。
- **確認メールの受け取り**: memory の `mailSender` は送信内容を logger に出力する（steps.md 手順6「dev では確認 URL をログで拾える」）。確認リンクの URL は `pnpm dev` を実行しているターミナルのサーバーログから取得する。
- 本番ビルドの確認（確認項目「既存機能への影響確認」で使用）: `pnpm build` → `pnpm start`。待ち受け URL は起動ログの `[listen.node] listening on http://...` 行で確認する（`apps/web/scripts/listen.node.ts`）。
- 静的検証: `pnpm typecheck && pnpm lint:fix && pnpm format && pnpm test:unit`（plan.md テスト方針。root の `test` / `test:integration` の最終形はステップ8 で確定するため、本計画は実装後も確実に存在する `test:unit` を基準にする）。

### デプロイ方法

なし（Node ランタイム一本化、ローカル起動のみで検証する）。

## 確認項目

各項目は上から順に同一の dev サーバープロセス内で実行する（in-memory のため）。ブラウザは通常ウィンドウを「ユーザー A」、シークレットウィンドウを「ユーザー B / 未認証」として使い分ける。

### 1. サインアップの基本フロー

- **対応する受け入れ基準:** AC-16（P-01）、AC-8
- **目的:** 未登録メールでのサインアップが受理され、確認メールが発行されること
- **手順:**
  1. `http://localhost:3000/` を開き、登録への導線（「はじめる」相当）を選ぶ
  2. サインアップ画面（`/signup`）で メール `user-a@example.com` / パスワード `Passw0rd123` / 表示名を入力する
  3. 利用規約への同意にチェックを入れ、送信する
  4. サーバーログを確認する
- **期待結果:** 送信完了状態（確認メールを送った旨の案内）に切り替わる。サーバーログに `user-a@example.com` 宛の確認メール（確認 URL 付き）が出力される。
- **確認ポイント:** パスワード入力中に強度メーターが反応する。この時点で `/notes` を直接開くとサインイン画面へ弾かれる（未確認のためサインイン状態ではない）。

### 2. サインアップの項目エラーと送信抑止

- **対応する受け入れ基準:** AC-16（P-01）、AC-2（PlainPassword 8–128 + 英数）
- **目的:** 項目エラーが入力中に検出され、不正な状態では送信できないこと
- **手順:**
  1. `/signup` で メール欄に不正な形式（`foo@`）を入力する
  2. パスワード欄に 7 文字（`Pass123`）、次に数字のみ（`12345678`）を入力する
  3. 規約同意のチェックを外したまま送信を試みる
- **期待結果:** 各項目に項目エラーが表示され、エラーがある間・同意がない間は送信が抑止される。
- **確認ポイント:** エラーを解消して同意すると送信可能な状態へ戻る。

### 3. メール確認リンクでサインイン状態になりノート一覧へ着地

- **対応する受け入れ基準:** AC-17、AC-15（Cookie 属性）
- **目的:** AC-01 の e2e が確認リンクで完結し、セッション Cookie が仕様どおり発行されること
- **手順:**
  1. 項目1 のサーバーログから確認 URL を取得し、ユーザー A のウィンドウで開く
  2. 開発者ツールの Network タブを開いたまま遷移を観察する
  3. 遷移完了後、開発者ツールでセッション Cookie を確認する
- **期待結果:** 確認ページが処理中の状態を表示した後、ノート一覧（`/notes`）へ遷移し、サインイン状態になる（上部バーのアカウントメニューに表示名が出る）。
- **確認ポイント:**
  - トークン消費は GET のページ表示ではなく、マウント後の **POST**（server function）で行われている（Network タブで確認 — ADR-007 の状態変更 GET 禁止）
  - セッション Cookie: `HttpOnly`、`SameSite=Lax`、`Path=/`、有効期限が約 30 日後。**dev（http）では `Secure` が付かないのは計画どおりの縮退**（plan.md「縮退の記録」）であり失敗ではない

### 4. ノート一覧の空状態と白紙ノート作成 → 詳細閲覧

- **対応する受け入れ基準:** AC-18、AC-12
- **目的:** 新規作成で白紙ノートが作られ、詳細が閲覧できること（ED-01 最小 / OR-11）
- **手順:**
  1. ユーザー A で `/notes` を開き、空状態の表示を確認する
  2. 空状態の CTA または「新規作成」機能で白紙ノートを作成する
  3. 作成後に遷移したノート詳細（`/notes/:noteId`）の表示を確認する
  4. ノート一覧へ戻る
- **期待結果:** ノート 0 件では新規作成への導線を含む空状態が表示される（**アップロード導線は本スライス外のため無くて正しい** — plan.md の account.md TC-02 縮退）。作成すると詳細へ遷移し、タイトルは既定の「無題」、visibility 表示（非公開）が出る。一覧に戻るとタイトルと更新時刻を持つ 1 件が表示される。
- **確認ポイント:** 詳細の本文領域は Shadow DOM で描画される（開発者ツールの Elements で `#shadow-root` を確認）。遷移中にスケルトンが表示される。詳細から一覧へ再作成すると別のノートが増える。

### 5. サインアウト

- **対応する受け入れ基準:** AC-15、AC-18（AppShell アカウントメニュー）、ADR-008
- **目的:** サインアウトでセッション Cookie が破棄され、未認証状態へ戻ること
- **手順:**
  1. ユーザー A のアカウントメニューからサインアウトを実行する（Network タブを開いておく)
  2. `/notes` を再度開く
- **期待結果:** 未認証状態へ戻り、`/notes` はサインイン画面へリダイレクトされる。セッション Cookie が削除されている。
- **確認ポイント:** サインアウトは **POST** の server function で実行される（GET リンクではない — ADR-008 の CSRF 規律）。

### 6. サインインの成功

- **対応する受け入れ基準:** AC-16（P-02）、AC-9
- **目的:** 確認済みユーザーがメール + パスワードでサインインできること
- **手順:**
  1. サインイン画面（`/signin`）で `user-a@example.com` / `Passw0rd123` を送信する
- **期待結果:** ノート一覧（`/notes`）へ遷移し、項目4 で作成したノートが表示される（in-memory でもプロセス内では永続していること）。

### 7. 未認証ガードと元の遷移先への復帰

- **対応する受け入れ基準:** AC-15
- **目的:** 認証ガードが未認証アクセスをサインインへ誘導し、認証後に元のページへ戻すこと
- **手順:**
  1. サインアウトした状態（またはシークレットウィンドウ）で、項目4 で作成したノートの詳細 URL（`/notes/:noteId`）を直接開く
  2. サインイン画面へ遷移したら、ユーザー A の資格情報でサインインする
- **期待結果:** 手順1 でサインイン画面（`redirect` パラメータ付き）へ遷移する。サインイン成功後、`/notes` ではなく元のノート詳細 URL へ復帰する。

### 8. 認証失敗の共通文言（アカウント存在の秘匿）

- **対応する受け入れ基準:** AC-9、AC-16（P-02）
- **目的:** 資格情報エラーがアカウントの存在を漏らさないこと
- **手順:**
  1. サインアウト状態で `/signin` から `user-a@example.com` / 誤ったパスワード を送信する
  2. 続けて 未登録の `nobody@example.com` / 任意のパスワード を送信する
- **期待結果:** どちらも**同一の**認証失敗の共通文言が表示される（登録有無で表示が変わらない）。

### 9. 段階待機（THROTTLED）とロック（LOCKED）の状態分離

- **対応する受け入れ基準:** AC-9、AC-16（P-02）、AC-15（429）
- **目的:** 失敗の累積で待機 → ロックへ遷移し、それぞれ専用の状態表示になること
- **手順:**
  1. 新しいメールアドレスでサインアップ + メール確認まで済ませたテストユーザー（またはユーザー A）に対し、`/signin` で誤ったパスワードを連続送信する
  2. 3 回目の失敗以降の表示を確認する
  3. さらに失敗を重ね、通算 10 回に達した後の表示を確認する（Network タブでレスポンスの HTTP ステータスも確認）
- **期待結果:** 3 回目以降は待機中の状態（待機秒数の表示）になり、待機中の再送信はブロックされる。10 回でロック中の状態になり、解除時刻が表示される。待機中/ロック中のレスポンスは HTTP 429。
- **確認ポイント:** ロック中の「パスワード再設定への導線」は**文言のみ**（P-04 は本スライス外 — plan.md の縮退）であり、リンクが無いのは失敗ではない。待機秒数経過後に正しいパスワードで再試行するとサインインできる（成功で失敗記録がクリアされる）。

### 10. 未確認ユーザーのサインイン（EMAIL_NOT_VERIFIED の分離）

- **対応する受け入れ基準:** AC-9、AC-16（P-02）
- **目的:** メール未確認のアカウントが認証失敗とは別の状態で表示されること
- **手順:**
  1. シークレットウィンドウで `pending@example.com` を新規サインアップする（確認リンクは開かない）
  2. `/signin` から `pending@example.com` / 登録したパスワード を送信する
- **期待結果:** 認証失敗の共通文言ではなく、メール未確認である旨の専用状態が表示される。
- **確認ポイント:** 確認メール再送の導線は本スライス外（PAGE-p02-006 見送り）のため表示されなくて正しい。

### 11. 他人のノートへのアクセス収斂（NOTE_NOT_FOUND → P-46）

- **対応する受け入れ基準:** AC-13、AC-19（P-46）
- **目的:** 他人の非公開ノート・不在ノートが同一の「見つかりません」表示に収斂し、存在が漏れないこと
- **手順:**
  1. シークレットウィンドウで別ユーザー（ユーザー B）をサインアップ + メール確認し、サインイン状態にする
  2. ユーザー B で、ユーザー A のノート詳細 URL（項目4 の `/notes/:noteId`）を開く
  3. 続けて、存在しないノート ID をでっち上げた URL（例: 末尾を書き換えた `/notes/xxxx`）を開く
- **期待結果:** 手順2 と手順3 が**区別のつかない同一の**共通表示（P-46）になる。表示には安全な再試行とトップ / 一覧への導線が含まれる。
- **確認ポイント:** 再試行・導線が機能する（一覧へ戻れる）。

### 12. トップページのサインイン状態分岐

- **対応する受け入れ基準:** AC-16（導線）、steps.md `routes/index.tsx`
- **目的:** `/` が未サインインでは公開トップ、サインイン済みではノート一覧へのリダイレクトになること
- **手順:**
  1. サインイン済みのウィンドウで `/` を開く
  2. シークレット（未認証）ウィンドウで `/` を開く
- **期待結果:** 手順1 は `/notes` へリダイレクトされる。手順2 は公開トップが表示され、登録への導線から `/signup` へ遷移できる。
- **確認ポイント:** サインアップ画面とサインイン画面が相互に導線を持つ（P-01 → サインインへ、P-02 → サインアップへ）。

### 13. 静的ページ（P-47）

- **対応する受け入れ基準:** AC-19
- **目的:** 利用規約とプライバシーポリシーが静的表示されること
- **手順:**
  1. 未認証状態で `/terms` と `/privacy` を開く
  2. 開発者ツールの Network タブでレスポンスヘッダーを確認する
- **期待結果:** どちらも静的本文が表示される（認証不要）。レスポンスに `X-Content-Type-Options: nosniff` と `Referrer-Policy` ヘッダーが付与されている。

## エッジケース・異常系

### 1. 登録済みメールでの再サインアップ（応答同一性）

- **目的:** サインアップ応答からアカウントの存在が漏れないこと（AC-8）
- **手順:** 確認済みのユーザー A のメール（`user-a@example.com`）で再度サインアップを送信し、画面表示とサーバーログを確認する
- **期待結果:** 画面は未登録時と**同一の**送信完了状態。サーバーログには確認メールではなく**既存アカウント通知メール**が出力される。
- **注記（誤判定防止）:** spec/scenario/account.md AC-01 異常系には「確認前の再サインアップ → 確認メール再送」とあるが、これは spec 内部の不整合であり、本実装は usecase / TC-identity-255 側（Pending / Active を区別せず既存アカウント通知メール）を正とする（plan.md リスク欄）。**確認メールが再送されないことを失敗と判定しない。** 未確認ユーザー（`pending@example.com`）での再サインアップも同じ挙動（通知メール）で正しい。

### 2. 使用済み・無効な確認リンク

- **目的:** 確認トークンの再利用・改竄が拒否されること（AC-17）
- **手順:** 1. 項目3 で使用済みの確認 URL をもう一度開く 2. URL のトークン部分を書き換えて開く
- **期待結果:** どちらも `/notes` へは遷移せず、確認ページ上に使用済み / 無効である旨のエラー状態が表示される。エラーは POST の応答として返る（GET でサーバー状態は変わらない）。

### 3. オープンリダイレクト防止

- **目的:** サインイン後の復帰先が同一オリジンのパスに制限されていること（AC-15、plan.md リスク欄）
- **手順:** 未認証状態で `/signin?redirect=https://example.com` を開き、正しい資格情報でサインインする
- **期待結果:** 外部サイトへは遷移せず、既定の `/notes` （または安全なフォールバック先）へ着地する。

### 4. サインイン画面に見送り機能の UI が出ていないこと

- **目的:** 見送り行の placeholder 禁止方針の確認（plan.md スコープ）
- **手順:** `/signup` と `/signin` の画面を目視確認する
- **期待結果:** Google OAuth ボタン、パスワード再設定リンク、確認メール再送導線が**表示されない**（無効ボタンの placeholder も無い）。

### 5. サーバー再起動でデータが消える（仕様の確認）

- **目的:** in-memory 前提の把握（walking skeleton の仕様であり不具合ではない）
- **手順:** dev サーバーを再起動し、既存セッションのウィンドウで `/notes` を再読み込みする
- **期待結果:** ユーザー・ノートが消えており、セッションも無効になってサインイン画面へ誘導される（エラーやクラッシュにならず、未認証として整然と扱われる）。

## 既存機能への影響確認

- `pnpm typecheck && pnpm lint:fix && pnpm format && pnpm test:unit` がすべて成功する（AC-20）。
- `pnpm build` が成功し、`pnpm start` で起動した本番ビルド（URL は `[listen.node] listening on ...` ログで確認）でも、サインアップ → メール確認 → ノート作成 → 閲覧の主要動線が dev と同様に動作する。特に各フォーム送信（signup / signin / verify / createBlankNote / サインアウト）が **404 にならない**こと — root への server function side-effect import 漏れはビルド後にのみ 404 として顕在化する（plan.md リスク欄の gotcha）。
- 削除済みの todo 参照実装のルート（`/todo`）が存在しない（アクセスすると P-46 の共通表示になり、旧 UI が残っていない）。
- `pnpm dev` の起動時に libSQL / `DATABASE_URL` / wrangler 関連のエラー・警告が出ない（他ランタイム削除とスクリプト整理が完了している — AC-14）。
