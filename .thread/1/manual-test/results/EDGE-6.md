# EDGE-6: サーバー再起動でデータが消える（仕様の確認）

**結果**: PASS
**目的**: 永続化が in-memory であり、プロセス再起動で全データが失われることを確認する（`.thread/1/testing.md` エッジケース6）

実行者: メインエージェント（サーバーの停止・起動権限を持つため、テスト実行エージェントからは SKIP として引き継いだ）

## 実行ログ

| # | 操作 | 期待結果 | 実際の結果 | 判定 |
|---|------|---------|-----------|------|
| 1 | 再起動前のサーバー疎通確認（`GET /`） | 200 | 200 | PASS |
| 2 | dev サーバーを停止（PID kill）、ポート解放を確認 | ポート 3000 が解放される | 「ポート3000 解放」を確認 | PASS |
| 3 | 同じコマンドで dev サーバーを再起動し、ヘルスチェック | 応答する | 「サーバー再起動OK」 | PASS |
| 4 | 再起動前に作成した user-a のノート詳細 `/notes/019feb0e-e2a8-7703-b022-9a8f8745dafd` を開く（Cookie なし） | 未認証ガードで `/signin` へ | 307 → `/signin?redirect=%2Fnotes%2F019feb0e-…` | PASS |
| 5 | `/signup` を開き、**再起動前に登録済みだった** `user-a@example.com` で再度サインアップする | データが消えていれば「新規登録」として扱われる | フォーム送信が成立 | PASS |
| 6 | サーバーログの `mail.sent` テンプレートを確認 | 新規登録なら `emailVerification`、アカウントが残っていれば `email_already_registered` | **`template: 'emailVerification'`**、`actionUrl` も 1 件出力 | PASS |

## 判定の根拠

手順6が決め手。EDGE-1（登録済みメールでの再サインアップ）では同じ操作で `email_already_registered` テンプレートが記録され確認 URL は発行されなかったのに対し、再起動後は `emailVerification` テンプレート＋確認 URL の発行になった。つまり `user-a@example.com` のアカウントはプロセス再起動によって消えており、**永続化が in-memory であるという仕様どおりの挙動**である。

手順4は Cookie を持たない curl からの確認なので、単独ではデータ消失の証拠にはならない（未認証リダイレクトは正常時も同じ）。補助的な確認として記録する。

## 備考

この挙動は不具合ではなく、本スライス（walking skeleton）が in-memory アダプターのみを配線している設計どおりの縮退。永続化は後続スライス（Issue #11 の Cloudflare D1）で入る。
