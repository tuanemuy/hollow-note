## ラウンド2指摘の修正確認

**6 件すべて、意図どおりに入っていることを実装・テスト両面で確認した。** 差分は `ea0fddb` に集約されている。

- **R2-UA-W-001（ダミーハッシュの rejected 恒久キャッシュ）** — `signInWithPassword.ts:53-79`。モジュール変数 → `WeakMap<PasswordHasher, Promise<PasswordHash>>` へ移り、`verifyAgainstDummy` 全体が `try/catch` で `false` 固定、失敗時は `dummyHashes.delete(hasher)` で memo を空に戻す。**4 点を個別に確認した**:
  - *失敗時のキャッシュ削除*: `hash()` の reject も `verify()` の reject も同じ catch に入り、必ず `delete` が走る。テスト「a failing dummy hash still answers INVALID_CREDENTIALS and is not memoized」が 1 回目だけ throw する hasher を同一オブジェクトのまま 3 回使い、`hashCalls` が 2 になる（＝スロットが解放されて再導出された）ことを固定している。
  - *hasher インスタンス寿命*: `createMemoryRuntime` が `passwordHasher` を runtime 単位の 1 個に引き上げ（`memoryRuntime.ts:95-99`）、`serverNode.ts:66-72` の `globalThis` pin でプロセス寿命に一致する。ADR-034 の「per-request 生成は均等化コストが DoS 面になる」判断とコードが一致。
  - *並行呼び出し*: `get` → `set` → `await` が同期区間で連続するため、同一 hasher への並行 N 本は同じ promise を共有し、全員がハンドラーを貼ってから reject が配送される。unhandled rejection は生じない。A が delete した後に B が古い promise を set し直す interleaving も、B の `get`/`set` が A の delete より前に完了しているため起きない。
  - *ダミー値の妥当性*: `DUMMY_PASSWORD = "timing-equalizer-0nly"` は `PlainPassword` の規則（8–128 / 英字あり / 数字あり）を満たす。ここが不正なら `create` が毎回 throw して scrypt が 1 度も走らず均等化が無音で消えるが、テスト「the unregistered and registered failure paths run the same number of hash verifications」が両側 1 回で一致することを assert しているので退行も検知される。
- **R2-UA-W-002（UoW スイートの memory 固有順序）** — `conformance/unitOfWork.ts:145-192` から順序 assert が消え、「両方が commit する / relay kick が各 1 回」「片方が失敗しても他方の書き込みだけが残り kick は 1 回」という観測可能な結果に置き換わった。順序 assert は `adapters/memory/__tests__/unitOfWork.test.ts` へバックエンド固有テストとして移設され、冒頭コメントが「共有スイートではない」根拠（ADR-014 / Issue #11）を明記している。ADR-035 の決定と一致。
- **R2-UA-W-003（IdempotencyStore と WorkerContainer の矛盾）** — `di/types.ts:142-148` に「`idempotencyStore` は現在どの worker ロールからも到達しない」「非可換 consumer が来た時点で UoW プロバイダーを本 container に載せる」「不在を回避するために UoW 外で `markProcessed` を呼ぶな」の 3 文が入り、矛盾が解消。`markProcessed` の呼び出し元がリポジトリに存在しないことも再確認した。
- **R2-UA-W-004（OUTBOX_* env の未配線）** — `server.node.ts:91-101` が `nodeServerEnvToTuningEnv(env)` を経由して `readRelayTuning` / `readPruneTuning` を `createNodeWorkerRunner` の `tuning` に渡す形になった。`RelayTuning`（`batchSize` / `leaseMs` / `maxAttempts`）は `ProcessOutboxEventsOptions` の同名フィールドにそのまま乗り、`outboxRetentionMs` は `pruneOutbox` に渡る（`runner.ts:64-70, 89-93, 106-112`）。`decoderRegistry` を渡していないのは正しい — `processOutboxBatch` が `defaultEventDecoderRegistry`（identity + note）に倒れる。4 変数すべてが実際に効くようになり、`.env.example` / `docs/runtime_node.md` の記載が有効な設定になった。
- **R2-UA-W-005（`matchedIdentity` の null ガード空振り）** — `signInWithPassword.ts:81-84, 137-171` で `VerificationOutcome = { verified: false } | { verified: true; user; identity }` の直和になり、IIFE が値を返す形へ。`let` の可変キャプチャと実行時 null ガードが両方消え、`if (!outcome.verified) throw …` の後に `const { user, identity: matched } = outcome` が型で通る。下流の version 再検査（:191-199）は挙動不変。
- **R2-UA-W-006（stale JSDoc 2 箇所）** — `runner.ts:49-51` は「Node ランタイムの 4 つの背景ロール」へ、`support.ts:93-97` は「`expiresAt <= now` は述語であって整列キーではない。整列・ページングは表キー単独」へ書き換わり、どちらも実装（`deleteExpiredPage`）と一致した。

あわせて、指示にあった 3 点も個別に検証した。

- **`signUpWithPassword` の `reserve` ConflictError 捕捉の広さ** — 捕捉条件は `isConflictError(error) && error.code === "EMAIL_ALREADY_USED"` で、`reserve` が投げうる ConflictError はメモリ実装では `heldByAnother`（kind=email → `EMAIL_ALREADY_USED`）のみ、`UNIQUE_RESERVATION_NOT_FOUND` は `activate` 側にしか存在しない。`SystemError` は素通しされる。`UserRepository` 側の `ConflictError("EMAIL_ALREADY_USED")`（spec/domains/identity.md:369）は UoW 内で起きるため、この `try` の範囲外。**飲み込みすぎていない**。spec のエラー表（「email reservation の競合 → `ConflictError("EMAIL_ALREADY_USED")`」）との乖離は ADR-033 の明示的判断で、TC-identity-261 の改訂も progress.md の spec-sync 集約に記録済み。
- **ADR-033/034/035/036 とコードの整合** — 033: 一意性はポート契約として保持（適合スイートで `expectConflict("EMAIL_ALREADY_USED")` 継続）、畳み込みはユースケース側 1 箇所。034: 上述のとおり。035: 順序 assert の移設先・残した 5 ケースまで決定どおり。036: `noteRouteStore.resolveMany` が `SystemError(DatabaseError)` へ、造語 `NOTE_ROUTE_BATCH_TOO_LARGE` は grep で全消滅、両ポートの `Error contract:` 行に上限超過の記述が追加。いずれも**コードと ADR が一致**。
- **Node runner への tuning 配線の正しさ** — 上記 R2-UA-W-004 のとおり。`nodeServerEnvToTuningEnv` が `undefined` を明示的に落として `TuningEnv` へ写すため、未設定の env が zod の `.default()` に正しく倒れる（`""` として渡って `z.coerce.number()` が 0 になる事故は起きない）。

## Use Case / Adapter

### Blockers

なし。

AC-1 / AC-8〜14 に対応する契約は、ラウンド1・2 で精読した範囲と本ラウンドで新たに精読した範囲のいずれでも spec からの逸脱を検出しなかった。今回追加で確認した主な点:

- 二平面 UoW: `MemoryTransactionController` は両平面で 1 個を共有し、`inTransaction()` によるネスト禁止が同一平面・平面横断の両方を覆う。`MemTable.set/delete` の undo ログは「行は不変スナップショット、書き込みは常に新オブジェクトを `set`」という前提で正しく、in-place 変更は全メモリリポジトリで 0 件（今回 `noteProjection` / `scopeCleanupAdmissionStore` / `globalMaintenanceRunStore` / `authTokenRepository` / `sessionRepository` / `oauthStateStore` / `loginAttemptStore` / `noteRouteStore` を再確認）。
- UoW 外書き込みの境界: `loginAttemptStore.get/recordFailure/clear` はすべて `globalUnitOfWorkProvider.run` の外で呼ばれ（`signInWithPassword.ts:127-135, 174-178`）、UoW のロールバックに巻き込まれない。`noteRouteStore` の reserve→activate サガ、`identityUniqueDirectory` の reserve→activate/release サガも同様に UoW 外。`RequestContainer` の JSDoc（`di/types.ts:77-85`）が「UoW 外に置くポートは spec がトランザクション外に置いたものだけ」と列挙しており、実装と一致。
- outbox 整合: `collectEvents` で採番したイベントは同一トランザクション内で `outboxRepository.save` に流れ、`dispatched` が立ったときだけ commit 後に `relayTrigger.kick()`。ロールバック時は undo ログで outbox 行ごと巻き戻る。適合スイートが commit/rollback 両方の kick 回数を固定している。
- エラー翻訳と透過: ドメインエラー（`BusinessRuleError`）は `signInWithPassword` の `PlainPassword.create` だけが意図的に潰し（INVALID_CREDENTIALS へ収斂、理由コメントあり）、それ以外は素通し。アダプターは driver 相当の失敗を `SystemError(DatabaseError)` / `ConflictError` に翻訳しており、`ValidationError` を投げるアダプターは存在しない。
- `authenticateSession` は spec/usecases/identity.md 手順 1〜5 と逐語一致（best-effort delete の範囲・`UNAUTHENTICATED` 収斂を含む）。plan の「完全読み取り専用」は spec 本文（「セッションを書き換えない」＋「古い Session 行の削除は best effort」）の要約であり、実装が spec に反しているわけではない。
- DI: `createMemoryRuntime` が唯一の composition root で、request / worker / 適合テスト / ユースケーステストがすべてこれを共有する。`passwordHasher` / `mailSender` / `sessionRepository` / `authTokenRepository` / `loginAttemptStore` / `oauthStateStore` / ShareToken key ring が runtime 単位、それ以外が per-request 生成という寿命の切り分けも意図どおり（ADR-026 / ADR-034）。

### Warnings

- **[W-001]** `GlobalMaintenanceRunStore` に「リース失効した lane を回収する」経路が存在せず、`claimed` のまま残った lane は永久に作業不能になる — 場所: `packages/core/src/adapters/memory/repositories/globalMaintenanceRunStore.ts:88-112`（`beginOrResumeKind` の resume 分岐）、`:154-176`（`claimLanes`）、`:274-291`（`recoverLease`）/ 理由: `claimLanes` は `status === "pending"` の lane しか返さず、`beginOrResumeKind` の resume も `recoverLease` も `leaseOwner` / `leaseUntil` を差し替えるだけで lane の `status` に触れない。したがって、あるオーナーが lane を claim したまま落ちる（プロセス落ち・invocation タイムアウト・W-002 の throw 経路）と、その lane はリースが失効しても誰も claim できない。run は全 lane が `done` になるまで `completed` にならないため、(a) その shard/table のスイープが二度と進まない、(b) `beginOrResumeKind` が同じ run を最古の `asOf` のまま無限に resume し続ける、(c) `pruneCompleted` の回収対象にもならない、という**恒久的な liveness 障害**になる。これはポート自身の JSDoc（`application/ports/globalMaintenanceRunStore.ts:28-29`「`recoverLease` lets an owner reclaim a lapsed lease」）と `pruneExpiredAuthState.ts:102-106` の docstring（「a crashed invocation's claimed lane is recovered by re-invoking the continuation input after the next `cron` re-leases the lapsed run」）の両方に反する — re-lease しても `claimLanes` はその lane を返さないし、continuation 入力を生成する経路は本スライスに無い（plan のスコープ外）。CLAUDE.md の「crashed worker's claim is reclaimable once the lease lapses」という outbox 側の規律とも非対称。ラウンド1 の W-005 で足した解放は**ユースケース側の best-effort** であり、ストア側の回収手段が無いことがこの穴の本体。/ 提案: `claimLanes`（または `beginOrResumeKind` の resume 分岐 / `recoverLease`）で、リースが失効していた run の `claimed` lane を `pending` へ戻す。`checkpointLane` が cursor を保存済みなので、状態を戻すだけで同じ keyset から再開できる。あわせて適合スイートに「リース失効後、前オーナーが claim したままの lane を新オーナーが `claimLanes` で取り直せる」ケースを足す（現行スイートは `recoverLease` のリース所有権だけを見ており、lane の回収可能性を検証していない）。**本スライスに実行経路は無い（`pruneExpiredAuthState` はスケジューラー未配線）ため Blocker にはしないが、D1 実装者はこの適合スイートを契約として写すので、Issue #11 に持ち越すと同じ穴が実バックエンドに複製される。**

- **[W-002]** `runCron` に、claim 済み lane を解放せずに抜ける経路が 2 つ残っている（W-001 と重なると恒久化する）— 場所: `packages/core/src/application/identity/pruneExpiredAuthState.ts:302-315 / 319-325 / 366-372`（`checkpointLane` / `advanceOrAck` の throw）と `:339-360`（`SWEEP_ORDER_HINT` が次表を名指せない場合）/ 理由: (1) 末尾の解放ループ（`:398-406`）は `try/finally` ではないので、ループ本体の `checkpointLane` / `advanceOrAck` が throw すると**スキップされる**。`requireLeasedRun` はリース失効・foreign lease で `ConflictError` を投げるため、10 分リースを跨ぐ長い invocation では現実に起こる。このとき現在の lane と `laneQueue` に残った lane がすべて claimed のまま残る。(2) `SWEEP_ORDER_HINT`（`:421-426`）は run store の表順を**コード側で複製した第二の正本**で、`run.tables` は run 生成時にスナップショットされる（`globalMaintenanceRunStore.ts:132-140`）。表構成を変更したデプロイが古い run を resume すると両者がずれ、`SWEEP_ORDER_HINT.indexOf(table) + 1` が範囲外になった場合は `nextTable === undefined` → **push も解放もせず `laneDone = true`**（`:341-359`）で lane が静かに漏れる。順序だけがずれた場合は誤った表名で `checkpointLane` を呼び `ConflictError("MAINTENANCE_LANE_TABLE_MISMATCH")` になり、(1) の経路に合流する。/ 提案: (1) は lane 走査全体を `try { … } finally { 残った lane を release }` で囲む（`advanceOrAck` 自体の失敗は握り潰してログに落とす）。(2) は次表を推測しないのが本筋 — 同一 shard の advance 後も `claimLanes` で位置を取り直す（`:362-375` の別 shard 経路と同じ形に揃える）か、`nextTable === undefined` のとき `advanceOrAck(completed:false)` で解放してから `laneDone` にする。少なくとも後者の 1 分岐は今すぐ入れておく価値がある。
