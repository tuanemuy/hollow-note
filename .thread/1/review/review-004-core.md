### 最重要検証対象の判定

1. **`globalMaintenanceRunStore` の lane 回収** — 妥当。`reclaimLapsedLanes` は `claimed` のみを `pending` に戻し、`tableIndex` / `cursor` / `commandKey` をそのまま保持する（`globalMaintenanceRunStore.ts:32-37`）。`beginOrResumeKind`（:111-126）と `recoverLease`（:299-311）はどちらも `lapsed` を計算してから分岐しており、生きたリースの lane には触れない。二重実行はリース方式に内在する範囲（失効後に旧 owner が生きていた場合の同一 keyset 再 DELETE）にとどまり、旧 owner の後続 `checkpointLane` / `advanceOrAck` は `requireLeasedRun` の foreign lease 判定で確実に弾かれる。ポート JSDoc（`ports/globalMaintenanceRunStore.ts:29-37`）・実装・適合スイート（`adapters/conformance/globalMaintenanceRunStore.ts:215-291` の ADP-common-030 3 ケース。うち :255-258 が「生きたリースでは同一 owner の再 begin でも lane を返さない」を固定）は三者一致。ただし W-004 の残存条件がある。
2. **`runCron` の `try/finally`** — 解放漏れ・二重解放ともに無し。`inFlight` は各分岐で確実に `null` 化され（:293, :432）、失敗解放（:319）・予算切れ解放（:424）・`nextTable === undefined` 解放（:377）のいずれも、その後 `finally` が同じ lane を再解放することはない。`advanceOrAck` が投げた場合だけ `inFlight` が残るが、その場合は解放が実際に行われていないので再試行が正しい。`released` セットによる重複除去も安全側。例外の握り潰しは `releaseLane`（:245-254）と cron 冒頭の `pruneCompleted`（:205-209）の 2 箇所のみで、いずれも理由がコメント化されており、元例外は `finally` を素通りして伝播する。`nextTable === undefined` 分岐は lane を解放して `workRemains = true` を立てており、テスト（`pruneExpiredAuthState.test.ts:558-582`）が次 cron での完走まで固定している。
3. **`Excerpt.fromText` の `create` 経由化** — 例外は漏れない。`Math.max(0, Math.min(max, EXCERPT_MAX_LENGTH))` により切り詰め長は常に `[0, 200]` で、`truncateWithoutSplittingPair` はサロゲート境界で 1 減らす方向にしか動かないので `create` の `length > 200` は成立し得ない。`fromText` は全域関数のまま。
4. **共有 UoW スイートの隔離性ケース** — 偽陽性・偽陰性なし。`adapters/conformance/unitOfWork.ts:171-205` は「1 を観測したら中間状態が見えた」という all-or-nothing だけを assert し、memory の mutex 直列化（常に 0 のみ、または 2 のみ）でもトランザクション隔離（スナップショット）でも通る。書き手側に 5 回の中断点を挟んでいるので、コミット前に書き込みを公開するバックエンドは確実に落ちる。順序依存の assert は backend-local テスト（`adapters/memory/__tests__/unitOfWork.test.ts`）に隔離されており、R2-UA-W-002 の意図どおり。
5. **TC-identity-174 の書き換え** — spec の期待「同じ run/table/cursor position を claim し、重複 run を作らず完了まで進める」（`spec/inventory/test.md:313`）を、150 件 seed → 1 ページ掃引 → 11 分経過 → 次 cron が残り 50 件を掃いて run が `completed`、という形で厳密に固定できている。旧版（continuation を手で 4 回叩く）より強い。唯一 spec 文言の「新 owner」だけは、`PRUNE_LEASE_OWNER` がモジュール定数のため同一 owner で再現している。ただし別 owner による失効回収はポート適合スイート（ADP-common-030）が直接カバーしており、usecase 側の挙動は同一 owner / 別 owner で変わらない（どちらも `"resumed"`）ので、実質的な穴ではない。

### 補足（指摘ではない）

`pnpm test:unit` が一時的に 3 件失敗する事象を観測したが（`memory global unit of work serialization` / `ADP-common-003: a concurrent run never observes a half-written run` / `verifyEmail` 並行ケース / 一度は `TC-identity-174`）、他のレビュー担当が同一リポジトリで並行して `vitest` を走らせていた時間帯に限られ、以後 11 回連続で全緑（447 passed）。CPU 高負荷下でも再現しなかったため、vite キャッシュを共有した並行実行に起因するものと判断し、指摘には含めていない。`pnpm typecheck` は緑。
