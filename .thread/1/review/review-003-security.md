# Review 003 — PR #12 (issue/1/account-to-blank-note-skeleton)

### Security

#### Blockers

- **[B-301]** `/verify-email` の自動 POST が「強制ログイン（login CSRF / セッション注入）」として成立する — 場所: `apps/web/app/components/auth/VerifyEmailPanel/index.tsx:33-65` / `apps/web/app/components/auth/VerifyEmailPanel/action.ts:26-32` / `packages/core/src/application/identity/verifyEmail.ts:64,90-100,112` / 理由: 確認トークンは URL クエリで運ばれ、ページはマウント直後に**利用者の操作を一切介さず** `verifyEmailFn` を POST し、応答の `Set-Cookie` でセッション Cookie を**無条件に上書き**したうえ `/notes` へ遷移する。攻撃者は自分のメールでサインアップして自分の確認トークン `T` を入手し、`https://<app>/verify-email?token=T` を被害者に踏ませるだけでよい。トップレベル遷移なので `SameSite=Lax` は素通りし、POST を発するのは自オリジンのページ自身なので `Origin` 検証も CSRF トークンも原理的に効かない。結果、被害者のブラウザーは**攻撃者のアカウントでサインインした状態**になる（既存セッションがあれば破棄される）。本サービスはノートを書くためのものなので、被害者がそのまま書いた内容は攻撃者のアカウントに保存され、攻撃者が後から自分でサインインして読める — 直接のデータ流出経路。AC-15 の CSRF 規律は「状態変更 GET を作らない」という**文面**は満たしているが、GET ナビゲーションが無条件に状態変更 POST を発火する以上、規律が守ろうとした性質（リンクを踏ませるだけでは状態が変わらない）は成立していない。ADR-007 が挙げた効能（プリフェッチ・リンクプレビューでの誤消費防止）は残るが、強制ログインは検討されていない。/ 提案: 状態機械（処理中 / 成功 / 期限切れ / 使用済み / 無効）を変えずに塞げる最小形は「確認要求を出したブラウザーに束縛する」こと。`signUpWithPassword` の応答で短命・`HttpOnly`・`SameSite=Lax` の確認用 Cookie（対象 `userId` かノンス）を焼き、`verifyEmailFn` はそれが**トークンの持ち主と一致したときだけ**セッション Cookie を発行する。不一致なら（メール確認自体は成功させたうえで）セッションを出さず既存の `alreadyVerified` 相当の「確認できました。サインインしてください」へ倒す。攻撃者のブラウザーにしかその Cookie が無いため、リンクを踏ませても被害者はサインインしない。次善策として最低限、**既にセッション Cookie を持つ要求で別利用者のトークンを消費した場合に既存セッションを上書きしない**ことは即座に入れられる。どちらも採らない場合は「被害者のノートが攻撃者のアカウントに入りうる」ことを受容リスクとして ADR-007 に明記し、Issue 化すること（黙って残す選択肢は無い）。

#### Warnings

- **[W-301]** メール確認リンク（＝セッション発行に足る資格情報）が平文でサーバーログに出続ける — 場所: `packages/core/src/adapters/memory/mailSender.ts:38-42`（`logger.info("mail.sent", { …, actionUrl })`）/ `packages/core/src/application/di/memoryRuntime.ts:94` / 理由: `actionUrlOf` は `emailVerification` の `verifyUrl`（`?token=<生トークン>`）をそのまま返し、`ConsoleLogger` が **info レベルで無条件に** stdout へ書く。dev の導線として意図されたものだが、この memory ランタイムは `pnpm start`（NODE_ENV=production・`scripts/listen.node.ts`）でも同じ配線で動くため、本番相当の実行でも生トークンがログに残る。トークンは 24 時間有効で、消費するとその利用者のセッションが発行される（`verifyEmail.ts:112`）＝ログ閲覧権限がそのまま新規アカウントの乗っ取りになる。ログ収集基盤・共有端末・CI のジョブログへ流れれば範囲はさらに広がる。B-301 と組み合わせると「ログを見た者が任意の新規利用者になりすます」まで一直線。/ 提案: `actionUrl` の出力を非 production に限る（`process.env.NODE_ENV !== "production"`）か、既定では `template.kind` と `to` だけを出して URL は `sent()` の in-memory 記録にとどめる。実メール送信アダプターが入るまでの間、`docs/runtime_node.md` に「このランタイムは確認リンクをログに出す。本番運用しない」と明記するのも併せて欲しい。
- **[W-302]** Node ランタイムの `clientKey` がソケット IP のみで、リバースプロキシ配下では全クライアントが 1 つの鍵に潰れる — 場所: `apps/web/app/presentation/clientKey.ts:11-13` / `packages/core/src/domain/identity/valueObject.ts:246-247`（`signIn:{email}:{clientKey}`）/ `packages/core/src/domain/identity/services/loginThrottlePolicy.ts:36-37` / 理由: スロットル鍵が「メール × 発信元」なのは、攻撃者の失敗が被害者を巻き込まないための設計（spec/domains/identity.md#LoginAttemptKey、spec/presentation/index.md レート制限）。ところが `getRequestIP()` は接続元ソケットの IP を返すため、TLS 終端やロードバランサーが前段に立つと**全要求が同じ `clientKey`** になる。Cookie の `Secure` が production でのみ付く実装（`session.ts:36`）が示すとおり production は TLS 前提であり、素の Node を直接インターネットに晒す構成はむしろ例外。この状態では、攻撃者が任意の既知メールに 10 回失敗させるだけでそのアカウントを **15 分間 `LOCKED`**（`lockThreshold: 10` / `lockDurationMs: 15分`）にでき、繰り返せば無期限にサインインを封じられる — スロットルが防御から攻撃手段に反転する。`X-Forwarded-For` を使わない判断自体は正しい（コメントのとおり詐称可能）が、「使わない」と「潰れたことに気づかない」は別問題。/ 提案: 信頼するプロキシを明示的な設定にする（例: `TRUSTED_PROXY_HOPS` が設定されているときだけ `X-Forwarded-For` の右から N 番目を採る）。最低でも、`clientKey` が全要求で同一になっていることを起動時 / 定期に検出して warn を出すか、`docs/runtime_node.md` に「前段にプロキシを置く場合は `clientKey` の供給を差し替えること。さもないとアカウントロックの DoS になる」と運用条件として書くこと。CF スライスで `CF-Connecting-IP` に置き換わるまでの間に本番配備される可能性がある以上、無記載のままは危険。
- **[W-303]** `safeRedirectPath` が制御文字（タブ・改行）を弾かない — 場所: `apps/web/app/presentation/redirect.ts:9-19` / 理由: URL パーサーは `\t` / `\n` / `\r` を除去してから解釈するため、`"/\n/evil.example"` はこのガードを通過したあと `//evil.example` として解釈される。**現時点では悪用不能**（唯一の消費先が `router.history.push` → `history.pushState` で、ブラウザーがクロスオリジンを `SecurityError` で拒否する — `SignInForm/index.tsx:129`）。ただしこの関数は「オープンリダイレクトの唯一のガード」として独立モジュール化され、docstring も「same-origin absolute paths だけが通る」と保証を明言している。将来 `Location` ヘッダーや `<a href>` に同じ関数の戻り値が載った時点で素通りする。/ 提案: 条件に「値が制御文字（U+0000..U+001F と U+007F）を含むなら弾く」判定を 1 行足し、`redirect.test.ts` に `"/\n/evil.example"` / `"/\t/evil.example"` のケースを追加する（他のケースは既にテスト済みで、追加コストはほぼゼロ）。

#### ラウンド 2 指摘の修正検証

- **[R2-SC-W-201] サインアップのタイミング列挙 — 修正済み。** `passwordHasher.hash(password)` が `identityUniqueDirectory.resolve` の**前**（`signUpWithPassword.ts:116`）へ移り、既登録・新規の両分岐が必ず scrypt を 1 回だけ通る。テストが hash 呼び出し回数の一致を assert している（`__tests__/signUpWithPassword.test.ts:244-265`）。他の分岐差も確認: `termsAccepted` / `Email.create` / `PlainPassword.create` / `DisplayName.create` はいずれも「登録済みか否か」に依存しない前段の拒否なので列挙材料にならない。残る非対称は hash 後の**書き込み量**（既登録: 通知メール 1 通で終了 / 新規: reserve → UoW → activate → メール）だが、scrypt（N=16384）が支配的で桁が違い、オラクルとしての実用性は無い。記録のみ。
- **[R2-SC-W-202] / [R2-UA-W-001] ダミーハッシュの reject 恒久キャッシュ — 修正済み。** `verifyAgainstDummy` は `try/catch` で必ず `false` を返す契約になり、失敗時は `dummyHashes.delete(hasher)` でスロットを空へ戻す（`signInWithPassword.ts:71-81`）。恒久 500（＝ステータスコードによる列挙）は消えた。
  - 個別に確認した点: (a) **並行呼び出し** — `get` → `hash()` → `set` が同期区間で閉じているため、同時到達した 2 本が二重に scrypt を起こすことはない（後発は前発の promise を共有する）。(b) **失敗の自己回復** — 一過性の scrypt 失敗後、次の呼び出しが再導出する。(c) **hasher のランタイム単位シングルトン化の副作用** — `createScryptPasswordHasher()` は `createMemoryRuntime` 直下（`memoryRuntime.ts:99`）に移り、`memoryRuntime()` 自体が `globalThis` の `Symbol.for` スロット固定（`serverNode.ts:70-80`）なので、リクエストをまたいで同一インスタンス。`WeakMap` のキーが生きるのでメモが効く。hasher は**状態を持たない純粋なアダプター**（`randomBytes` / `scrypt` のみ）なので、共有によるリクエスト間の情報混入は無い。SSR / RSC の別モジュールグラフでは `dummyHashes` が別実体になるが、キーが同一 hasher なのでグラフごとに 1 回余分に導出されるだけで、オラクルにはならない。(d) `DUMMY_PASSWORD = "timing-equalizer-0nly"` は `PlainPassword` 規則を満たすので `create` は投げない。回帰テスト（`signInWithPassword.test.ts` の verify 回数 assert と hash 失敗ケース）も入っている。
- **[R2-SC-W-203] `Cache-Control` — 修正済み（適用は妥当）。** `SECURITY_HEADERS` に `["Cache-Control", "private, no-store"]` が入り（`server.node.ts:69`）、`withSecurityHeaders` は `if (!response.headers.has(name))` なので既存値を上書きしない。SSR HTML・GET の server function（`sessionUserFn` / `renderNoteList` / `renderNoteDetail` / `loadAppContext`）・`/verify-email?token=…` の HTML がすべて中間キャッシュ対象外になり、狙いどおり。
  - 静的アセットとの共存について事実確認: 追加コメントは「静的アセットはフレームワークが自前の `Cache-Control` を付ける」と書いているが、`@tanstack/start-server-core` / `@tanstack/start-plugin-core`（dev 用の `no-store` を除く）/ `@vitejs/plugin-rsc` の production 経路に `Cache-Control` を設定するコードは**無い**。ただし `scripts/listen.node.ts` は `booted.fetch` を渡すだけで静的配信ミドルウェアを持たず、フレームワーク側にも静的ハンドラーが無い＝**このプロセスはハッシュ付きアセットを配っていない**（前段の CDN / プロキシが担う構成）ため、結果として衝突は起きない。実害は無いのでこの巡では指摘に挙げないが、コメントの根拠は事実と違うので、将来この Node プロセスに静的配信を足すときは同時にアセット経路の除外が要る。
- **[R2-SC-W-204] サインアップ応答同一化の競合窓 — 修正済み。一意性の担保は弱まっていない。** `reserve` の `ConflictError("EMAIL_ALREADY_USED")` を `signUpWithPassword.ts:140-151` で捕捉し、既登録経路（`existingAccountNotice` + decoy userId）へ畳む。ADR-033 の層分担が実装で守られていることを確認した:
  - ポート側は従来どおり衝突で投げる（`adapters/memory/repositories/identityUniqueDirectory.ts:49-67`、`heldByAnother`）。**一意性の強制はアダプターに残っており**、捕捉はユースケースの応答表現に閉じている。ユーザー行は作られない（`reserve` 失敗時点で return するため `userRepository.insert` に到達しない）。
  - 適合スイートが `EMAIL_ALREADY_USED` を契約として検証し続けている（`adapters/conformance/identityUniqueDirectory.ts:57`）ので、アダプター差し替え時に一意性が抜け落ちれば検知される。
  - 捕捉範囲は `isConflictError && code === "EMAIL_ALREADY_USED"` に限定され、`UNIQUE_RESERVATION_NOT_FOUND` などは素通し。`Unique key already held: email <正規化済みメール>` がクライアントへ届く経路も消えた。
  - 残る縮退（新規指摘には挙げない）: 直前のサインアップが UoW 失敗で reservation を残した場合、同じメールの正当な新規登録が最大 10 分間「既にアカウントがあります」の通知メールに倒れ、アカウントが作られない。攻撃者が任意に誘発できる経路は無い（reservation は同一要求内で必ず `activate` か `release` に収束する）ため列挙・DoS には使えないが、`EMAIL_RESERVATION_TTL_MS` を縮める余地はある。
- **エラー文言の辞書化（R2-FE-W-001 由来）— 内部情報の露出は確かに減っている。** `renderErrorMessage` が読むのは `kind` と `code` だけで、サーバー由来の `message` は表示経路から完全に切れた（`errorDisplay.ts:80-83`）。辞書に無い `code` は kind 共通文言へ倒れるので英語も漏れない。漏れる経路が残っていないかを個別に追った結果:
  - `SignInForm` が読む `fieldErrors` は `waitSeconds` / `unlockAt` のみで、いずれもサーバーが自分で組み立てた数値・ISO 時刻（`signInWithPassword.ts:33-43`）。zod の英語文言（`INVALID_INPUT` の `fieldErrors`）を画面に出す経路は無い（`SignUpForm` も `displayError` 経由のみ）。
  - `system` / `unknown` は `errorResponseMiddleware`（`errorResponseMiddleware.ts:41-47`）と `renderServerFragment`（`serverFragment.tsx:43-47`）の 2 か所で `redactForClient` を通り、生ペイロードは `logServerError` にだけ渡る。`AppServerError` は `delete this.stack` でスタックも落とす。
  - `notFound` / `conflict` は非 redaction だが、辞書化後は message が画面に出ないため露出しない（`scopeRouter.ts:26-31` の `No externally resolvable route for note <id>` も要求者自身の id のみ）。
  - `sanitizeRouteError` は DEV 以外で `console.error("Route error")` のみ。

#### その他の再確認（新規指摘なし）

- Cookie 属性: `HttpOnly` / `SameSite=Lax` / `Path=/` / `Domain` 無し / `Expires = now + Session.ttlMs`、`Secure` は production のみ（縮退は plan.md 記載どおり）。`clearSessionCookie` は発行時と同じ属性で消す — `presentation/session.ts:31-48`
- CSRF: ミューテーション（signUp / signIn / verifyEmail / signOut / createBlankNote）はすべて JSON POST の server function。`FormData` を受ける経路は無し。GET の server function（`sessionUserFn` / `renderNoteList` / `renderNoteDetail` / `loadAppContext`）は読み取り専用（`authenticateSession` の best-effort delete は「既に無効な行」限定 — `authenticateSession.ts:41-66`）。**唯一の例外が B-301**
- セッション固定: サインイン・メール確認とも新規トークンを発行して上書きするため、攻撃者が事前に固定したトークンを有効化する古典的な固定化は不能（B-301 は逆方向 — 攻撃者のトークンを被害者に押し付ける形）
- オープンリダイレクト: `beforeLoad` の `location.href` と `/signin?redirect=`（zod `max(2048)` → `safeRedirectPath`）の双方を通す。消費先は `history.pushState` のみ（W-303 参照）
- 認可: `getNote` は route → scope → `NoteAccessPolicy.evaluate` で不在・他人の非公開・権限なしがすべて `NOTE_NOT_FOUND` に収斂。`listNotes` / `createBlankNote` はセッションの `userId` から scope を導き、クライアント指定の owner を受けない。`workspace` 分岐は `WORKSPACE_NOT_FOUND` で閉じ、`placeholderWorkspaceAuthorization` は到達したら `SystemError` で落ちる（黙って allow しない）— `application/note/accessControl.ts:18-35`
- トークン取り扱い: セッション / 確認トークンはどちらも `base64url(userId).<32B CSPRNG>`、保存は SHA-256 のみ（`secureTokenGenerator.ts`）。共有トークンは AES-256-GCM + 版付き鍵束、鍵はランタイム寿命（`shareTokenProtector.ts`、`memoryRuntime.ts:83`）。共有トークンハッシュの比較は定数時間（`noteAccessPolicy.ts` の `constantTimeHashEquals`）。`AuthToken` の単回消費は pending 行への条件付き更新（`authTokenRepository.ts:44-55`）
- ステータスマッピング: `UNAUTHENTICATED`→401 / `THROTTLED|LOCKED|RATE_LIMITED`→429 / `NOTE_GONE`→410、それ以外は kind 既定 — `errorResponse.ts:102-137`
- DoS 面: transport 境界の zod（email≤254 / password≤128 / displayName≤50 / token≤512 / noteId≤128 / redirect≤2048）、`listNotes` の limit clamp（1..100）、scrypt パラメータ上限（`passwordHasher.ts:85-103`）。サインアップにレート制限が無い点は plan.md でスコープ外（CF スライス）と明記済み — R2-SC-W-201 の修正で既登録メールも scrypt を通るようになったが、元々ランダムな新規メールで同じコストを引けたため増悪はしていない
- 秘密情報: `.env.example` に残骸なし（DB 認証情報・暗号鍵の項目は削除済み）。`config.ts` に秘密の混入なし。`loadAppContext` がクライアントへ返す `AppConfig` は `appUrl` / `siteName` / メタ文言のみ
