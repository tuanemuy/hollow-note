# 動作確認計画 — Issue #3: ワークスペースとメンバーを管理・公開する

## 確認環境

この Issue の変更を確認するために必要な手順のみ記載（`pnpm install` などプロジェクト全体のセットアップは省略）。

### 環境変数（起動前に必須）

`apps/web/.env` が無ければ `cp apps/web/.env.example apps/web/.env` で作る。`.env.example` は**サインイン手段を 2 つともコメントアウトした状態で配布される**ため、そのままでは起動が拒否される（`apps/web/.env.example` 19〜36 行）。以下の 3 行が有効になっていること。

```
APP_URL=http://localhost:3000
OAUTH_DEV_MODE=true
MEMORY_MAIL_LOG_ACTION_URL=true
```

- `OAUTH_DEV_MODE=true` — アプリ内の dev 同意画面（`/dev/oauth/authorize`）で 3 アカウントを Google 資格情報なしに作るためのスイッチ。`NODE_ENV=development` でしか受理されず、これを設定するのは `vite dev` だけなので `pnpm dev` 前提（`.env.example` 22〜29 行）。
- `MEMORY_MAIL_LOG_ACTION_URL=true` — in-memory の `MailSender` が `mail.sent` ログ行に `actionUrl` を出す。**招待リンクの取得に必須**で、既定は off。off のままだと WS-03 / WS-04 の確認が実行できない（`.env.example` 56〜62 行）。
- `DELETION_TICKET_KEY` は未設定でよい（本計画ではアカウント削除を扱わない）。

### 検証環境の起動

- 開発サーバー: リポジトリルートで `pnpm dev` を実行し、`http://localhost:3000` を開く（root `package.json` の `dev` → `@repo/web` の `dev:node` → `vite dev --config vite.config.node.ts`。`vite dev` は `APP_URL` のポートに strict bind するので、3000 が塞がっていると起動が失敗する）。
- **DB のプロビジョニング・マイグレーション・シードはすべて不要**。永続化は in-memory アダプターのみで、マイグレーションコマンドは存在しない（README「Persistence is in-memory, so there is no schema to generate and no migration command.」）。
- **データはプロセス内メモリのみ**。本計画の確認項目は **1 プロセス内で上から順に通しで実行**する。途中でサーバーを再起動すると全アカウント・全ワークスペースが消え、作り直しになる。
- **メール本文の取得**: `pnpm dev` を実行しているターミナルの `mail.sent` ログ行を読む。`actionUrl` フィールドが招待リンクの URL。
- **削除・除名の進捗**: 継続タスクランナーが dev サーバーと同一プロセスで動く。`deleteWorkspace` は受理後に非同期で manifest 構築 → cleanup と進むので、画面の表示を最大 60 秒待って判定する。
- 本番ビルドの確認（「既存機能への影響確認」で使用）: `pnpm build` → `pnpm start`。待ち受け URL は起動ログの `[listen.node] listening on http://...` 行で確認する（`apps/web/scripts/listen.node.ts`）。
- 静的検証: `pnpm typecheck` / `pnpm lint:fix` / `pnpm format` / `pnpm test:unit`（`pnpm test:node` / `pnpm test:workers` で片方ずつも実行できる。root `package.json` の scripts）。

### デプロイ方法

なし（Node ランタイム一本でローカル起動のみ。Cloudflare 側の実行環境は本 Issue の対象外）。

### ブラウザーの使い分け

3 つの独立したブラウザーコンテキストを使う（セッション Cookie を共有しないこと）。

- **ウィンドウ A** = ユーザー A（owner 役、主操作）
- **ウィンドウ B** = ユーザー B（editor / 招待の受け手役）
- **ウィンドウ C** = シークレットウィンドウ（ユーザー C 役、および未サインインの外部閲覧者役）

### 事前に作るアカウント

すべて dev IdP（`/signin` の「Google で続ける」→ 同意画面でメールアドレスと表示名を入力し `email_verified` を ON）で作る。メール確認の往復が不要になる。

| 役 | メールアドレス | 表示名 | 作る場所 |
|---|---|---|---|
| ユーザー A（owner） | `user-a@example.com` | `ユーザーA` | ウィンドウ A |
| ユーザー B（editor / 招待の受け手） | `user-b@example.com` | `ユーザーB` | ウィンドウ B |
| ユーザー C（viewer / 非メンバー） | `user-c@example.com` | `ユーザーC` | ウィンドウ C |

## 確認項目

上から順に、同一の `pnpm dev` プロセス内で実行する。各項目は前の項目が作った状態を引き継ぐ。

作るワークスペース:

| 名前 | スラッグ | 構成 |
|---|---|---|
| `設計チーム` | `design-team` | A が owner、B が editor、C が viewer |
| `個人検証` | （未設定 → 途中で設定） | A が唯一の owner。項目 14 で削除する |

### 1. WS-01 — ワークスペースを作成して owner として参加した状態になる

- **対応する受け入れ基準:** AC-2
- **検証手段:** browser
- **目的:** 作成の基本フローが通り、作成直後の状態（自分が唯一の owner / 非公開 / 招待導線）が正しいこと
- **前提:** ウィンドウ A でユーザー A としてサインイン済み
- **手順:**
  1. 上部バーのスコープトークンを開き、「ワークスペースを作成」を選ぶ
  2. 名前に `設計チーム`、説明に `テスト用`、スラッグに `design-team` を入力する
  3. 作成する
  4. メンバー管理を開く
  5. 公開設定を開く
- **期待結果:** 手順 1 で作成画面が開く。手順 2 でスラッグが使用可能であることが示される。手順 3 で `設計チーム` の文脈に切り替わり、メンバー招待への導線が表示される。手順 4 で自分が owner として 1 名だけ表示される。手順 5 で非公開になっている。
- **確認ポイント:** 作成直後の公開ステータスが非公開であること（WS-01 の異常系）。スコープトークンの表示が `設計チーム` に変わっていること。

### 2. WS-01 — スラッグと名前の検証・境界値

- **対応する受け入れ基準:** AC-2
- **検証手段:** browser
- **目的:** 重複検出・予約語・文字種・正規化・文字数境界が入力時点で働くこと
- **前提:** 項目 1 で `design-team` が使用済みになっている
- **手順:**
  1. 作成画面でスラッグに `design-team`（項目 1 と同じ値）を入力する
  2. スラッグに `new` を入力する
  3. スラッグに `チーム` を入力する
  4. スラッグに 2 文字、3 文字、30 文字、31 文字を順に入力する
  5. スラッグを `My-Team` にして、名前を空にしたまま作成を試みる
  6. 名前に 80 文字、81 文字を順に入力する
  7. 名前を `個人検証` に、スラッグを空にして作成する
- **期待結果:** 手順 1 で使用済みである旨と代替候補が示され、作成できない。手順 2 で予約語である旨が示される。手順 3 で使用できる文字種（英小文字・数字・ハイフン・アンダースコア）が示される。手順 4 は 2 文字で「3 文字以上」、31 文字で「30 文字以内」の制約が示され、3 / 30 文字は受け付けられる。手順 5 で名前が必須である旨が示される。手順 6 は 80 文字が通り 81 文字で「80 文字以内」が示される。手順 7 で `個人検証` が作成される。
- **確認ポイント:** `My-Team` が小文字 `my-team` に正規化されること（手順 5 で作成まで進めた場合）。手順 7 のようにスラッグ未設定でも作成できること（公開時に初めて必須になる）。

### 3. WS-01 — 所有数の上限（20 件）

- **対応する受け入れ基準:** AC-2
- **検証手段:** browser
- **目的:** 1 人あたり 20 件の上限が働くこと
- **前提:** ユーザー A が項目 1・2 で 2 件所有している
- **手順:**
  1. 名前だけを変えて 18 件のワークスペースを追加で作成する（計 20 件）
  2. 21 件目を作成しようとする
- **期待結果:** 手順 1 の 20 件目までは作成できる。手順 2 で所有できるのは 20 件までである旨が示され、作成されない。
- **確認ポイント:** 上限に達したときの文言が理由を示していること（WS-01「理由を示して拒否する」）。**この項目を実行すると以降のスコープトークンに 20 件が並ぶ**ので、項目 4 のページングの確認と兼ねてよい。18 件を手で作るのが現実的でなければ、件数を減らして「上限に達していない」ことだけ確認し、上限の合否は自動テスト（TC-workspace-062 / 063 / 068）に委ねた旨を記録する。

### 4. WS-02 — 文脈の切り替えと URL・再訪時の引き継ぎ

- **対応する受け入れ基準:** AC-3
- **検証手段:** browser
- **目的:** 参加中のワークスペースが一覧され、選択が URL と次回訪問に反映されること
- **手順:**
  1. 上部バーのスコープトークンを開く
  2. 一覧の末尾までスクロールして続きを読み込む（項目 3 で 20 件以上ある場合）
  3. `設計チーム` を選ぶ
  4. URL を確認する
  5. ノート一覧で検索語かタグの絞り込みを 1 つ入れてから、個人の文脈に切り替える
  6. ウィンドウ A を閉じて開き直し、`http://localhost:3000/` を開く
- **期待結果:** 手順 1 で「個人」と参加中のワークスペースが並ぶ。手順 2 で次の 20 件が追加され、既に表示したものが重複しない。手順 3 でその文脈のノート一覧に切り替わる。手順 4 の URL にワークスペースの文脈が反映されている。手順 5 で絞り込み条件が解除される。手順 6 で前回の文脈が引き継がれている。
- **確認ポイント:** 手順 5 の絞り込み解除は「タグが文脈ごとに独立しているため」の仕様（WS-02）。タグ機能は #8 なので、確認できるのは検索語の解除まででよい。

### 5. WS-03 — メンバーを招待し、保留中の一覧と有効期限を確認する

- **対応する受け入れ基準:** AC-4
- **検証手段:** browser
- **目的:** 招待が発行され、メールにリンクが載り、保留中として一覧されること
- **前提:** ウィンドウ A で `設計チーム` の文脈。`pnpm dev` のターミナルを見られる状態
- **手順:**
  1. `設計チーム` のメンバー管理で招待を開始する
  2. `user-b@example.com` を入力し、ロールに editor を選んで送信する
  3. `pnpm dev` のターミナルで `mail.sent` 行を確認する
  4. 保留中の招待の有効期限を確認する
  5. 続けて `user-c@example.com` を viewer で招待する
  6. 招待リンクのコピーを実行する
- **期待結果:** 手順 1 でメールアドレスとロールの入力欄が出る。手順 2 で保留中の招待として一覧に表示される。手順 3 のログ行に招待リンクを含む `actionUrl` が出る。手順 4 の有効期限が発行から 14 日後になっている。手順 6 でコピーされたことが示される。
- **確認ポイント:** 送信直後に楽観的に一覧へ追加され、失敗したら巻き戻ること（`CLAUDE.md`「Frontend」の三層）。ロールに owner を選ぶと権限の重さを説明する確認が挟まること（WS-03）。

### 6. WS-04 — 招待リンクから参加する（サインイン済み / リンクをコピーして共有）

- **対応する受け入れ基準:** AC-5
- **検証手段:** browser
- **目的:** 招待の preview が出て、受諾でメンバーになり、そのワークスペースへ遷移すること
- **手順:**
  1. 項目 5 手順 3 で得た `user-b@example.com` 宛のリンクを、ウィンドウ B（ユーザー B でサインイン済み）で開く
  2. 表示内容を確認する
  3. 「参加する」を選ぶ
  4. 項目 5 手順 6 でコピーした `user-c@example.com` 宛のリンクをウィンドウ C（ユーザー C でサインイン済み）で開き、受諾する
  5. ウィンドウ A でメンバー管理を再読み込みする
- **期待結果:** 手順 2 でワークスペースの名前・説明・付与されるロール・招待者が表示される。手順 3 で `設計チーム` のノート一覧に遷移する。手順 5 でユーザー B が editor、ユーザー C が viewer として一覧に表示される（計 3 名）。
- **確認ポイント:** 受諾後、ユーザー B / C のスコープトークンに `設計チーム` が現れること。受諾済みのリンクをもう一度開くとエッジケース 3 の扱いになること。

### 7. WS-04 — 未サインインから招待リンクを開き、サインアップして招待へ戻る

- **対応する受け入れ基準:** AC-5
- **検証手段:** browser
- **目的:** 未サインインの経路で認証後に招待の確認画面へ復帰すること（PAGE-p06-004）
- **手順:**
  1. ウィンドウ A で `invitee@example.com` を editor として招待する
  2. `mail.sent` 行から `actionUrl` を取り出す
  3. **新しいシークレットウィンドウ**（未サインイン）でそのリンクを開く
  4. 表示された新規登録の導線から、dev IdP で `invitee@example.com` / 表示名 `招待ユーザー` / `email_verified` ON で登録する
  5. 遷移先を確認し、招待を受諾する
- **期待結果:** 手順 3 で未サインインでも招待の preview（ワークスペース名・説明・ロール・招待者）が表示され、サインイン / サインアップを求められる。手順 4 の完了後、**招待の確認画面に戻る**（`/notes` へ直行しない）。手順 5 で `設計チーム` のノート一覧へ遷移し、メンバーになる。
- **確認ポイント:** 招待メールの受信をもって到達性が確認できているため、メール確認を省いてそのままサインインされること（WS-04 基本フロー 3）。dev IdP を使う場合はこの分岐が観測しづらいので、`email_verified` を OFF にして登録し、それでも確認待ちにならないことを見る。

### 8. WS-03 — 招待の再送と取り消し

- **対応する受け入れ基準:** AC-4
- **検証手段:** browser
- **目的:** 再送で新しいリンクが発行されて旧リンクが失効し、取り消しで一覧から消えること
- **前提:** 保留中の招待を 2 件作る（未使用のメールアドレス `pending-1@example.com` / `pending-2@example.com` を editor で招待）
- **手順:**
  1. `pending-1@example.com` の招待の**旧リンク**を `mail.sent` から控える
  2. その招待を再送する
  3. `mail.sent` の新しい `actionUrl` を控える
  4. 手順 1 の旧リンクをシークレットウィンドウで開く
  5. 手順 3 の新リンクを開く
  6. `pending-2@example.com` の招待を取り消す
  7. 取り消した招待のリンクを開く
- **期待結果:** 手順 2 で再送されたことが示され、有効期限が更新される。手順 3 で新しいリンクを含むメールがログに出る。手順 4 の旧リンクは無効である旨が表示される。手順 5 の新リンクは有効な preview が表示される。手順 6 で保留中の一覧から消える。手順 7 で取り消し済みである旨が表示される。
- **確認ポイント:** 取り消しは**一覧メンバーシップの変更**なので、楽観的な削除が親（一覧の所有者）で行われ、失敗時に行が戻ること。

### 9. WS-05 — メンバーのロールを変更する

- **対応する受け入れ基準:** AC-6
- **検証手段:** browser
- **目的:** ロールセレクターでの変更が即座に反映され、対象の権限が実際に変わること
- **手順:**
  1. ウィンドウ A のメンバー管理でユーザー B のロールセレクターを開く
  2. viewer を選ぶ
  3. ウィンドウ B で `設計チーム` のノートを開き、編集の操作を探す
  4. ウィンドウ A でユーザー B のロールを editor に戻す
  5. ウィンドウ B を再読み込みして編集の操作を探す
- **期待結果:** 手順 1 で owner / editor / viewer が並ぶ。手順 2 で即座に反映され、変更完了が示される。手順 3 で編集の操作が表示されない。手順 5 で再び表示される。
- **確認ポイント:** 手順 2 が楽観的に反映され、サーバー応答後に `router.invalidate()` で整合すること。降格に伴う実行中ジョブの取り消し（TC-06 手順 5〜10）は #5 / #6 のため対象外。

### 10. WS-05 — メンバーを除名する

- **対応する受け入れ基準:** AC-6
- **検証手段:** browser
- **目的:** 除名で対象がアクセスを失い、作成したノートは残ること
- **前提:** ウィンドウ C のユーザー C（viewer）が `設計チーム` にノートを 1 件作成しておく（スコープトークンで `設計チーム` に切り替えてから新規作成）
- **手順:**
  1. ウィンドウ C でユーザー C が `設計チーム` にノートを 1 件作る（viewer では作れない場合は、先に editor へ昇格させてから作り、viewer に戻す）
  2. ウィンドウ A でユーザー C の除名を開始する
  3. 確認を確定する
  4. ウィンドウ C で `設計チーム` のノート一覧を再読み込みする
  5. ウィンドウ C のスコープトークンを開く
  6. ウィンドウ A で手順 1 のノートを開く
- **期待結果:** 手順 2 でノートにアクセスできなくなることを伝える確認が表示される。手順 3 でメンバー一覧から消える。手順 4 で見つからない旨が表示される。手順 5 に `設計チーム` が並ばない。手順 6 でノートはワークスペースに残っている。
- **確認ポイント:** 除名は一覧メンバーシップの変更なので、**削除の楽観更新は一覧の所有者側で走る**（葉が先にアンマウントされる形になっていないこと）。除名の反映が directory に伝わるまで数秒かかる場合があるので、手順 5 は最大 60 秒まで再読み込みして判定する。

### 11. WS-06 — ワークスペースを脱退する / 最後の owner を保護する

- **対応する受け入れ基準:** AC-7
- **検証手段:** browser
- **目的:** 脱退できること、および最後の owner の降格・除名・脱退が禁じられること
- **手順:**

  3. `設計チーム` の設定から脱退を試みる
  4. ユーザー B を owner に昇格させてから、もう一度自分のロールセレクターを開く
  5. ウィンドウ B でユーザー B が `設計チーム` から脱退する
  6. ウィンドウ B のスコープトークンを確認する
- **期待結果:** 手順 1 で降格の選択肢が無効になっており、理由（最後の owner は変更できない）が示される。手順 2 で自分の除名の操作は出ない（脱退を使う）。手順 3 で他のメンバーを owner にするかワークスペースを削除する必要がある旨が示され、脱退できない。手順 4 では owner が 2 名になるので降格が選べるようになる（ただし自分自身のロール変更は無効のまま）。手順 5 で脱退の確認を経て個人の文脈へ遷移する。手順 6 に `設計チーム` が並ばない。

### 8. サーバー再起動でデータが消える（仕様の確認）

- **検証手段:** browser
- **目的:** in-memory 前提の把握（不具合ではない）
- **手順:** すべての確認を終えたあとに `pnpm dev` を再起動し、サインイン済みだったウィンドウで `/notes` とワークスペース URL を再読み込みする
- **期待結果:** アカウント・ワークスペース・メンバーシップ・招待がすべて消え、セッションも無効になってサインイン画面へ整然と誘導される（例外画面やクラッシュにならない）
- **注記:** `deleteWorkspace` の recovery（応答喪失・worker 停止からの再開 — TC-workspace-103 / 105 / 109 / 115）は **in-memory ランタイムでは実機確認できない**。再起動で `scheduled_tasks` ごと消えるため、ユニットテスト側の担保に委ねる旨を記録する
