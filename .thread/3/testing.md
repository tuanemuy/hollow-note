# 動作確認計画 — Issue #3: ワークスペースとメンバーを管理・公開する

## 確認環境

この Issue の変更を確認するために必要な手順のみ記載（`pnpm install` などプロジェクト全体のセットアップは省略）。

### 環境変数（起動前に必須）

`apps/web/.env` が無ければ `cp apps/web/.env.example apps/web/.env` で作る。`.env.example` は**サインイン手段を 2 つともコメントアウトした状態で配布される**ため、そのままでは起動が拒否される（`apps/web/.env.example` 19〜36 行）。以下の 3 行が有効になっていること。

```
APP_URL=http://localhost:3000
OAUTH_DEV_MODE=true
MEMORY_MAIL_LOG_ACTION_URL=true
```

- `OAUTH_DEV_MODE=true` — アプリ内の dev 同意画面（`/dev/oauth/authorize`）で 3 アカウントを Google 資格情報なしに作るためのスイッチ。`NODE_ENV=development` でしか受理されず、これを設定するのは `vite dev` だけなので `pnpm dev` 前提（`.env.example` 22〜29 行）。
- `MEMORY_MAIL_LOG_ACTION_URL=true` — in-memory の `MailSender` が `mail.sent` ログ行に `actionUrl` を出す。**招待リンクの取得に必須**で、既定は off。off のままだと WS-03 / WS-04 の確認が実行できない（`.env.example` 56〜62 行）。
- `DELETION_TICKET_KEY` は未設定でよい（本計画ではアカウント削除を扱わない）。

### 検証環境の起動

- 開発サーバー: リポジトリルートで `pnpm dev` を実行し、`http://localhost:3000` を開く（root `package.json` の `dev` → `@repo/web` の `dev:node` → `vite dev --config vite.config.node.ts`。`vite dev` は `APP_URL` のポートに strict bind するので、3000 が塞がっていると起動が失敗する）。
- **DB のプロビジョニング・マイグレーション・シードはすべて不要**。永続化は in-memory アダプターのみで、マイグレーションコマンドは存在しない（README「Persistence is in-memory, so there is no schema to generate and no migration command.」）。
- **データはプロセス内メモリのみ**。本計画の確認項目は **1 プロセス内で上から順に通しで実行**する。途中でサーバーを再起動すると全アカウント・全ワークスペースが消え、作り直しになる。
- **メール本文の取得**: `pnpm dev` を実行しているターミナルの `mail.sent` ログ行を読む。`actionUrl` フィールドが招待リンクの URL。
- **削除・除名の進捗**: 継続タスクランナーが dev サーバーと同一プロセスで動く。`deleteWorkspace` は受理後に非同期で manifest 構築 → cleanup と進むので、画面の表示を最大 60 秒待って判定する。
- 本番ビルドの確認（「既存機能への影響確認」で使用）: `pnpm build` → `pnpm start`。待ち受け URL は起動ログの `[listen.node] listening on http://...` 行で確認する（`apps/web/scripts/listen.node.ts`）。
- 静的検証: `pnpm typecheck` / `pnpm lint:fix` / `pnpm format` / `pnpm test:unit`（`pnpm test:node` / `pnpm test:workers` で片方ずつも実行できる。root `package.json` の scripts）。

### デプロイ方法

なし（Node ランタイム一本でローカル起動のみ。Cloudflare 側の実行環境は本 Issue の対象外）。

### ブラウザーの使い分け

3 つの独立したブラウザーコンテキストを使う（セッション Cookie を共有しないこと）。

- **ウィンドウ A** = ユーザー A（owner 役、主操作）
- **ウィンドウ B** = ユーザー B（editor / 招待の受け手役）
- **ウィンドウ C** = シークレットウィンドウ（ユーザー C 役、および未サインインの外部閲覧者役）

### 事前に作るアカウント

すべて dev IdP（`/signin` の「Google で続ける」→ 同意画面でメールアドレスと表示名を入力し `email_verified` を ON）で作る。メール確認の往復が不要になる。

| 役 | メールアドレス | 表示名 | 作る場所 |
|---|---|---|---|
| ユーザー A（owner） | `user-a@example.com` | `ユーザーA` | ウィンドウ A |
| ユーザー B（editor / 招待の受け手） | `user-b@example.com` | `ユーザーB` | ウィンドウ B |
| ユーザー C（viewer / 非メンバー） | `user-c@example.com` | `ユーザーC` | ウィンドウ C |

## 確認項目

上から順に、同一の `pnpm dev` プロセス内で実行する。各項目は前の項目が作った状態を引き継ぐ。

作るワークスペース:

| 名前 | スラッグ | 構成 |
|---|---|---|
| `設計チーム` | `design-team` | A が owner、B が editor、C が viewer |
| `個人検証` | （未設定 → 途中で設定） | A が唯一の owner。項目 14 で削除する |

### 1. WS-01 — ワークスペースを作成して owner として参加した状態になる

- **対応する受け入れ基準:** AC-2
- **検証手段:** browser
- **目的:** 作成の基本フローが通り、作成直後の状態（自分が唯一の owner / 非公開 / 招待導線）が正しいこと
- **前提:** ウィンドウ A でユーザー A としてサインイン済み
- **手順:**
  1. 上部バーのスコープトークンを開き、「ワークスペースを作成」を選ぶ
  2. 名前に `設計チーム`、説明に `テスト用`、スラッグに `design-team` を入力する
  3. 「作成する」を押す
  4. 設定タブの「メンバー」を開く
  5. 設定タブの「公開」を開く
- **期待結果:** 手順 1 で作成画面（`/workspaces/new`）が開く。手順 3 で `/workspaces/{workspaceId}/settings/general` へ遷移し、設定タブの「メンバー」が招待への導線になっている。手順 4 で自分が owner として 1 名だけ表示される。手順 5 で「非公開」のバッジが付いている。
- **確認ポイント:** 作成直後の公開ステータスが非公開であること（WS-01 の異常系）。スコープトークンの表示が `設計チーム` に変わっていること。**スラッグの可否は入力中には判定されない**（作成時にサーバーが予約して初めて分かる）ので、手順 2 で「使用可能」の表示が出なくても失敗として記録しない — spec/pages P-30 の「スラッグ重複の即時検出」との差分は別途 Issue に上げる。

### 2. WS-01 — スラッグと名前の検証・境界値

- **対応する受け入れ基準:** AC-2
- **検証手段:** browser
- **目的:** 重複検出・予約語・文字種・正規化・文字数境界が働くこと（判定は**作成の実行時**に返る）
- **前提:** 項目 1 で `design-team` が使用済みになっている
- **手順:**
  1. 作成画面で名前に適当な値を入れ、スラッグに `design-team`（項目 1 と同じ値）を入力して作成を試みる
  2. スラッグに `new` を入れて作成を試みる
  3. スラッグに `チーム` を入れて作成を試みる
  4. スラッグを 2 文字にして作成を試み、次に 3 文字・30 文字で試す。続けて 31 文字目を打ち込もうとする
  5. 名前を空にする
  6. 名前に 80 文字を入れ、続けて 81 文字目を打ち込もうとする
  7. 名前を `大文字検証`、スラッグを `My-Team` にして作成し、遷移先の一般設定でスラッグ欄を確認する
  8. `/workspaces/new` に戻り、名前を `個人検証`、スラッグを空にして作成する
- **期待結果:** 手順 1 で使用済みである旨と代替候補（`design-team-2` など）が示され、作成されない。手順 2 で予約語である旨が示される。手順 3 でスラッグの字種と長さの制約が示される。手順 4 は 2 文字で「3〜30 文字」の制約が示され、3 / 30 文字は受け付けられる。**31 文字目は入力欄の `maxLength` が打ち切るので入らない**。手順 5 は「作成する」が押せなくなる（名前必須は操作の無効化で示される）。手順 6 も **81 文字目は入力欄が打ち切る**。手順 7 でスラッグ欄が `my-team` に正規化されている。手順 8 で `個人検証` がスラッグ未設定のまま作成される。
- **確認ポイント:** 手順 1 の代替候補ボタンを押すとスラッグ欄が置き換わること。手順 8 のようにスラッグ未設定でも作成できること（公開時に初めて必須になる）。

### 3. WS-01 — 所有数の上限（20 件）

- **対応する受け入れ基準:** AC-2
- **検証手段:** browser
- **目的:** 1 人あたり 20 件の上限が働くこと
- **前提:** ユーザー A が項目 1・2 で 2 件所有している
- **手順:**
  1. 名前だけを変えて 18 件のワークスペースを追加で作成する（計 20 件）
  2. 21 件目を作成しようとする
- **期待結果:** 手順 1 の 20 件目までは作成できる。手順 2 で所有できるのは 20 件までである旨が示され、作成されない。
- **確認ポイント:** 上限に達したときの文言が理由を示していること（WS-01「理由を示して拒否する」）。**この項目を実行すると以降のスコープトークンに 20 件が並ぶ**ので、項目 4 のページングの確認と兼ねてよい。18 件を手で作るのが現実的でなければ、件数を減らして「上限に達していない」ことだけ確認し、上限の合否は自動テスト（TC-workspace-062 / 063 / 068）に委ねた旨を記録する。

### 4. WS-02 — 文脈の切り替えと URL・再訪時の引き継ぎ

- **対応する受け入れ基準:** AC-3
- **検証手段:** browser
- **目的:** 参加中のワークスペースが一覧され、選択が URL と次回訪問に反映されること
- **手順:**
  1. 上部バーのスコープトークンを開く
  2. 一覧末尾の「さらに読み込む」を押す（項目 3 で 20 件以上ある場合）
  3. `設計チーム` を選ぶ
  4. URL を確認する
  5. スコープトークンから個人の文脈に切り替える
  6. ウィンドウ A を閉じて開き直し、`http://localhost:3000/` を開く
- **期待結果:** 手順 1 で「個人」と参加中のワークスペースが並ぶ。手順 2 で次の 20 件が追加され、既に表示したものが重複しない。手順 3 で `設計チーム` の文脈に切り替わる。手順 4 の URL が `/workspaces/{workspaceId}/settings/general` になっている。手順 5 で `/notes` に戻る。手順 6 で前回の文脈（`設計チーム` の設定）へリダイレクトされる。
- **確認ポイント:** ワークスペースを選んだときの遷移先が設定「一般」なのは、ワークスペース文脈のノート一覧が **Issue #7** だから（`components/layout/ScopeToken` と `routes/index.tsx` の JSDoc が同じ理由を書いている）。切り替え時に検索語・タグを持ち越さないこと（WS-02）は、`/notes` に検索 UI が無いため本スライスでは観測できない — 対象外として記録する。

### 5. WS-03 — メンバーを招待し、保留中の一覧と有効期限を確認する

- **対応する受け入れ基準:** AC-4
- **検証手段:** browser
- **目的:** 招待が発行され、メールにリンクが載り、保留中として一覧されること
- **前提:** ウィンドウ A で `設計チーム` の文脈。`pnpm dev` のターミナルを見られる状態
- **手順:**
  1. `設計チーム` の設定タブ「メンバー」を開く
  2. 「メンバーを招待」に `user-b@example.com` を入力し、ロールに editor を選んで「招待を送る」を押す
  3. `pnpm dev` のターミナルで `mail.sent` 行を確認する
  4. 「保留中の招待」の有効期限を確認する
  5. 続けて `user-c@example.com` を viewer で招待する
  6. 招待パネルに現れた「招待リンクをコピー」を押す
- **期待結果:** 手順 1 でメールアドレスとロールの入力欄が出る。手順 2 で「保留中の招待」に表示される。手順 3 のログ行に招待リンクを含む `actionUrl` が出る。手順 4 の有効期限が発行から 14 日後になっている。手順 6 で「招待リンクをコピーしました」と示される。
- **確認ポイント:** 送信直後に楽観的に一覧へ追加され、失敗したら巻き戻ること（`CLAUDE.md`「Frontend」の三層）。**「招待リンクをコピー」は直前に発行した 1 件にしか出ない**（一覧はトークンを持たないため、保留中の行にコピーの操作は無い）ので、手順 6 でコピーされるのは手順 5 の `user-c@example.com` 宛のリンクになる。ロールに owner を選んだときの「権限の重さを説明する確認」（WS-03）は**未実装**なので、出なくても失敗として記録せず別途 Issue に上げる。

### 6. WS-04 — 招待リンクから参加する（サインイン済み / リンクをコピーして共有）

- **対応する受け入れ基準:** AC-5
- **検証手段:** browser
- **目的:** 招待の preview が出て、受諾でメンバーになり、そのワークスペースへ遷移すること
- **手順:**
  1. 項目 5 手順 3 で得た `user-b@example.com` 宛のリンクを、ウィンドウ B（ユーザー B でサインイン済み）で開く
  2. 表示内容を確認する
  3. 「参加する」を押す
  4. 項目 5 手順 6 でコピーした `user-c@example.com` 宛のリンクをウィンドウ C（ユーザー C でサインイン済み）で開き、「参加する」を押す
  5. ウィンドウ A でメンバー管理を再読み込みする
- **期待結果:** 手順 2 でワークスペースの名前・説明・付与されるロールとその説明・招待者・招待先のメールアドレスが表示される。手順 3 で `設計チーム` の文脈（設定「一般」）に遷移する。手順 5 でユーザー B が editor、ユーザー C が viewer として一覧に表示される（計 3 名）。
- **確認ポイント:** 受諾後、ユーザー B / C のスコープトークンに `設計チーム` が現れること。**受諾後の遷移先が `/workspaces/{id}/settings/general` なのは Issue #7 待ちのため**で、ノート一覧に行かないことを失敗として記録しない。受諾した本人が同じリンクを開き直すと「すでに参加しています」になること（TC-31）。

### 7. WS-04 — 未サインインから招待リンクを開き、サインアップして招待へ戻る

- **対応する受け入れ基準:** AC-5
- **検証手段:** browser
- **目的:** 未サインインの経路で認証後に招待の確認画面へ復帰すること（PAGE-p06-004）
- **手順:**
  1. ウィンドウ A で `invitee@example.com` を editor として招待する
  2. `mail.sent` 行から `actionUrl` を取り出す
  3. **新しいシークレットウィンドウ**（未サインイン）でそのリンクを開く
  4. 表示された「アカウントを作る」から、dev IdP で `invitee@example.com` / 表示名 `招待ユーザー` / `email_verified` ON で登録する
  5. 遷移先を確認し、「参加する」を押す
- **期待結果:** 手順 3 で未サインインでも招待の preview（ワークスペース名・説明・ロール・招待者・招待先）が表示され、「サインインして参加する」/「アカウントを作る」が出る。手順 4 の完了後、**招待の確認画面に戻る**（`/notes` へ直行しない）。手順 5 で `設計チーム` の文脈（設定「一般」）へ遷移し、メンバーになる。
- **確認ポイント:** 招待メールの受信をもって到達性が確認できているため、メール確認を省いてそのままサインインされること（WS-04 基本フロー 3）。dev IdP を使う場合はこの分岐が観測しづらいので、`email_verified` を OFF にして登録し、それでも確認待ちにならないことを見る。

### 8. WS-03 — 招待の再送と取り消し

- **対応する受け入れ基準:** AC-4
- **検証手段:** browser
- **目的:** 再送で新しいリンクが発行されて旧リンクが失効し、取り消しで一覧から消えること
- **前提:** 保留中の招待を 2 件作る（未使用のメールアドレス `pending-1@example.com` / `pending-2@example.com` を editor で招待）
- **手順:**
  1. `pending-1@example.com` の招待の**旧リンク**を `mail.sent` から控える
  2. その招待の行の「再送」を押す
  3. `mail.sent` の新しい `actionUrl` を控える（行に現れる「リンクをコピー」でも取れる）
  4. 手順 1 の旧リンクをシークレットウィンドウで開く
  5. 手順 3 の新リンクを開く
  6. `pending-2@example.com` の招待の「取り消し」→「取り消す」で確定する
  7. 取り消した招待のリンクを開く
- **期待結果:** 手順 2 で有効期限が更新される。手順 3 で新しいリンクを含むメールがログに出る。手順 4 の旧リンクは「この招待は使えません」になる。手順 5 の新リンクは有効な preview が表示される。手順 6 で保留中の一覧から消え、「招待を取り消しました。」と表示される。手順 7 も「この招待は使えません」になる。

  3. ウィンドウ A で `設計チーム 2026` の一般設定からアイコンをアップロードする（項目 12 手順 4 と同じ）
  4. ウィンドウ C で `/workspaces/{workspaceId}/settings/general` を直接開く
  5. `/settings/usage` を開く（項目 18）
- **期待結果:** 手順 1 でワークスペース所有のノートが成立する（`moveNote` は移動先で `createNote` を再認可するので、以前の workspace 一律拒否が残っていればここで落ちる）。手順 2 は「このノートは見つかりません」で拒否される。手順 3 は成功する（以前は workspace subject が一律拒否）。手順 4 は「このワークスペースは開けません」になり、アイコンのアップロード操作に到達できない。手順 5 で使用量ページが例外にならずに表示される（ワークスペースの内訳は項目 18 のとおり未描画）。
- **確認ポイント:** **手順 2 と手順 4 が通ってしまったら重大な後退**（`recalculateStorageUsage` の fail-open 認可ホールと同種）。コード側で `placeholderWorkspaceAuthorization`・「is not implemented in this slice」・「until `WorkspaceAuthorization` exists」の文字列が残っていないことも併せて確認する（`grep` で 0 件）。**ワークスペース文脈の新規作成 UI は無い**（`createBlankNoteFn` は個人スコープ固定、Issue #7）ので、`createBlankNote` の workspace 所有はユニットテスト側の担保に委ね、ここでは移動経由の認可で代替する。

### 2. editor が管理操作をしようとする

- **検証手段:** browser
- **目的:** WS-03 / WS-05 / WS-07 / WS-08 / WS-10 の権限（読み取り専用への縮退）
- **手順:** ウィンドウ B（editor として再参加させた状態）で `設計チーム 2026` の設定タブ (1) メンバー (2) 一般 (3) 公開 (4) 削除 を順に開く
- **期待結果:** どのタブにも「読み取り専用です」が出る。(1) メンバー一覧と自分の「脱退」だけが読め、招待パネル・保留中の招待・ロール変更・除名は**描画されない**。(2) 入力欄が無効で保存バーが出ない。(3) 公開の切り替えボタンが出ない。(4) 確認欄と実行ボタンが無効。いずれも操作が「表示されるが押すと失敗する」形になっていないこと

### 3. 無効な招待リンク（使用済み・存在しないトークン・削除済みワークスペース）

- **検証手段:** browser
- **目的:** WS-04 の異常系。状態ごとに表示が分かれること
- **手順:** (1) 項目 6 で受諾済みのリンクを、招待された本人**以外**のブラウザー（未サインインのシークレットウィンドウ）で開く (2) そのリンクの token 末尾 1 文字を書き換えて開く (3) 削除済みワークスペース宛に発行してあった招待リンクを開く
- **期待結果:** (1)(2)(3) のいずれも「この招待は使えません」＋トップへ戻る導線になる。例外画面やスタックトレースにならないこと。期限切れ（14 日経過）は 1 プロセス内で作れないため対象外
- **注記:** spec/pages P-06 は期限切れ / 取り消し済み / 使用済み / ワークスペース削除済みを**別々の状態**として持つが、実装は 1 つの表示に畳んでいる（存在の有無を漏らさないため）。差分は別途 Issue に上げ、ここでは失敗として記録しない。受諾した本人が再訪した場合だけは「すでに参加しています」に分岐する

### 4. 招待されたのと違うアカウントで受諾する / 既にメンバーが開く / 辞退する

- **検証手段:** browser
- **目的:** WS-04 の 3 分岐（リンク自体を認可の根拠とする / 既参加 / 破棄）
- **手順:** (1) `invitee@example.com` 宛の新しい招待リンクを、`user-c@example.com` でサインイン中のウィンドウ C で開いて「参加する」を押す (2) 既にメンバーであるユーザー B 宛に `設計チーム 2026` の招待を新しく発行し、そのリンクをユーザー B のブラウザーで開く (3) 別の招待リンクを開いて「参加しない」を選ぶ
- **期待結果:** (1) 招待先のメールアドレスが preview に表示されたうえで受諾でき、ユーザー C がメンバーになる（リンク自体を認可の根拠とする） (2) 「すでに参加しています」と「{ワークスペース名} を開く」の導線が出る。**自分のロールが招待のロールに書き換わらない** (3) 招待の確認画面から離れてトップへ移り、スコープトークンにそのワークスペースは並ばない
- **注記:** (1) の「招待されたメールアドレスと異なる旨を示したうえで確認する」（WS-04）は**未実装**で、preview が招待先を表示するだけ。差分は別途 Issue に上げ、失敗として記録しない

### 5. 既にメンバー / 保留中の招待があるメールアドレスへの招待、不正なメール形式

- **検証手段:** browser
- **目的:** WS-03 の重複防止と入力バリデーション
- **手順:** (1) 既にメンバーであるユーザー B のメールアドレスで招待する (2) 保留中の招待があるアドレスで再度招待する (3) 招待欄に `not-an-email` と入力して「招待を送る」を押し、正しい形式に直して送り直す
- **期待結果:** (1) 「このメールアドレスはすでにメンバーです。招待は必要ありません。」が示され招待されない (2) 再送として扱われ、重複した招待行が増えない (3) 「メールアドレスの形式が正しくありません。」が示されて招待は作られず、直すと送信できる
- **注記:** (3) の判定は**送信して初めて返る**（クライアント側で送信前に弾いていない。フォームは `noValidate`）。WS-03「メールアドレスの形式が不正な場合は送信前に弾く」との差分は別途 Issue に上げる

### 7. 公開中のワークスペースのスラッグを外す / スラッグを変更して旧 URL が失効する
