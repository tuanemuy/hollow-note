## 確認環境

この Issue の変更を確認するために必要な手順のみ記載（`pnpm install` などプロジェクト全体のセットアップは省略）。

### 環境変数（起動前に必須）

`apps/web/.env` が無ければ `cp apps/web/.env.example apps/web/.env` で作る。`.env.example` は**サインイン手段を 2 つともコメントアウトした状態で配布される**ため、そのままでは起動が拒否される（`apps/web/.env.example` 19〜36 行）。以下の 3 行が有効になっていること。

```
APP_URL=http://localhost:3000
OAUTH_DEV_MODE=true
MEMORY_MAIL_LOG_ACTION_URL=true
```

- `OAUTH_DEV_MODE=true` — アプリ内の dev 同意画面（`/dev/oauth/authorize`）で 3 アカウントを Google 資格情報なしに作るためのスイッチ。`NODE_ENV=development` でしか受理されず、これを設定するのは `vite dev` だけなので `pnpm dev` 前提（`.env.example` 22〜29 行）。
- `MEMORY_MAIL_LOG_ACTION_URL=true` — in-memory の `MailSender` が `mail.sent` ログ行に `actionUrl` を出す。**招待リンクの取得に必須**で、既定は off。off のままだと WS-03 / WS-04 の確認が実行できない（`.env.example` 56〜62 行）。
- `DELETION_TICKET_KEY` は未設定でよい（本計画ではアカウント削除を扱わない）。

### 検証環境の起動

- 開発サーバー: リポジトリルートで `pnpm dev` を実行し、`http://localhost:3000` を開く（root `package.json` の `dev` → `@repo/web` の `dev:node` → `vite dev --config vite.config.node.ts`。`vite dev` は `APP_URL` のポートに strict bind するので、3000 が塞がっていると起動が失敗する）。
- **DB のプロビジョニング・マイグレーション・シードはすべて不要**。永続化は in-memory アダプターのみで、マイグレーションコマンドは存在しない（README「Persistence is in-memory, so there is no schema to generate and no migration command.」）。
- **データはプロセス内メモリのみ**。本計画の確認項目は **1 プロセス内で上から順に通しで実行**する。途中でサーバーを再起動すると全アカウント・全ワークスペースが消え、作り直しになる。
- **メール本文の取得**: `pnpm dev` を実行しているターミナルの `mail.sent` ログ行を読む。`actionUrl` フィールドが招待リンクの URL。
- **削除・除名の進捗**: 継続タスクランナーが dev サーバーと同一プロセスで動く。`deleteWorkspace` は受理後に非同期で manifest 構築 → cleanup と進むので、画面の表示を最大 60 秒待って判定する。
- 本番ビルドの確認（「既存機能への影響確認」で使用）: `pnpm build` → `pnpm start`。待ち受け URL は起動ログの `[listen.node] listening on http://...` 行で確認する（`apps/web/scripts/listen.node.ts`）。
- 静的検証: `pnpm typecheck` / `pnpm lint:fix` / `pnpm format` / `pnpm test:unit`（`pnpm test:node` / `pnpm test:workers` で片方ずつも実行できる。root `package.json` の scripts）。

### デプロイ方法

なし（Node ランタイム一本でローカル起動のみ。Cloudflare 側の実行環境は本 Issue の対象外）。

### ブラウザーの使い分け

3 つの独立したブラウザーコンテキストを使う（セッション Cookie を共有しないこと）。

- **ウィンドウ A** = ユーザー A（owner 役、主操作）
- **ウィンドウ B** = ユーザー B（editor / 招待の受け手役）
- **ウィンドウ C** = シークレットウィンドウ（ユーザー C 役、および未サインインの外部閲覧者役）

### 事前に作るアカウント

すべて dev IdP（`/signin` の「Google で続ける」→ 同意画面でメールアドレスと表示名を入力し `email_verified` を ON）で作る。メール確認の往復が不要になる。

| 役 | メールアドレス | 表示名 | 作る場所 |
|---|---|---|---|
| ユーザー A（owner） | `user-a@example.com` | `ユーザーA` | ウィンドウ A |
| ユーザー B（editor / 招待の受け手） | `user-b@example.com` | `ユーザーB` | ウィンドウ B |
| ユーザー C（viewer / 非メンバー） | `user-c@example.com` | `ユーザーC` | ウィンドウ C |

上から順に、同一の `pnpm dev` プロセス内で実行する。各項目は前の項目が作った状態を引き継ぐ。

|---|---|---|
| `設計チーム` | `design-team` | A が owner、B が editor、C が viewer |
| `大文字検証` | `my-team`（`My-Team` を正規化） | A が唯一の owner。項目 2 手順 7 で作り、以降は slug の重複確認に使う |

### 1. WS-01 — ワークスペースを作成して owner として参加した状態になる

- **対応する受け入れ基準:** AC-2
- **検証手段:** browser
- **目的:** 作成の基本フローが通り、作成直後の状態（自分が唯一の owner / 非公開 / 招待導線）が正しいこと
- **前提:** ウィンドウ A でユーザー A としてサインイン済み
- **手順:**
  1. 上部バーのスコープトークンを開き、「ワークスペースを作成」を選ぶ
  2. 名前に `設計チーム`、説明に `テスト用`、スラッグに `design-team` を入力する
  3. 「作成する」を押す
  4. 遷移先の画面を確認する
  5. 設定タブの「公開」を開く
- **期待結果:** 手順 1 で作成画面（`/workspaces/new`）が開く。手順 2 で入力の 0.4 秒後に「確認中...」→「このスラッグは使用できます」に変わる。手順 3 で `/workspaces/{workspaceId}/settings/members` へ遷移する（WS-01 手順 4 の「メンバー招待への導線」＝ P-32 の招待欄がそのまま出ている）。手順 4 でメンバー一覧に自分が owner として 1 名だけ表示される。手順 5 で「非公開」のバッジが付いている。
- **確認ポイント:** 作成直後の公開ステータスが非公開であること（WS-01 の異常系）。スコープトークンの表示が `設計チーム` に変わっていること。入力中の可否は**目安**（`checkWorkspaceSlugAvailability`）で、確定するのは作成時の予約なので「使用できます」が出ても作成が `SLUG_ALREADY_USED` で落ちうる（並行に取られた場合）。落ちた側でも代替候補が出れば正しい。

### 2. WS-01 — スラッグと名前の検証・境界値

- **対応する受け入れ基準:** AC-2
- **検証手段:** browser
- **目的:** 重複検出・予約語・文字種・正規化・文字数境界が働くこと（重複・予約語・字種は**入力中**にも目安として返り、確定は作成の実行時）
- **前提:** 項目 1 で `design-team` が使用済みになっている
- **手順:**
  1. 作成画面で名前に適当な値を入れ、スラッグに `design-team`（項目 1 と同じ値）を入力して作成を試みる
  2. スラッグに `new` を入れて作成を試みる
  3. スラッグに `チーム` を入れて作成を試みる
  4. スラッグを 2 文字にして作成を試み、次に 3 文字・30 文字で試す。続けて 31 文字目を打ち込もうとする
  5. 名前を空にする
  6. 名前に 80 文字を入れ、続けて 81 文字目を打ち込もうとする
  7. 名前を `大文字検証`、スラッグを `My-Team` にして作成し、**遷移後に一般設定を開いて**スラッグ欄を確認する（作成後の遷移先はメンバー設定）
  8. `/workspaces/new` に戻り、名前を `個人検証`、スラッグを空にして作成する
- **期待結果:** 手順 1 で使用済みである旨と代替候補（`design-team-2` など）が示され、作成されない。手順 2 で予約語である旨が示される。手順 3 でスラッグの字種と長さの制約が示される。手順 4 は 2 文字で「3〜30 文字」の制約が示され、3 / 30 文字は受け付けられる。**31 文字目は入力欄の `maxLength` が打ち切るので入らない**。手順 5 は「作成する」が押せなくなる（名前必須は操作の無効化で示される）。手順 6 も **81 文字目は入力欄が打ち切る**。手順 7 でスラッグ欄が `my-team` に正規化されている。手順 8 で `個人検証` がスラッグ未設定のまま作成される。
- **確認ポイント:** 手順 1〜3 は**作成を押す前**に同じ指摘（と手順 1 では代替候補）が入力欄の下に出る。代替候補ボタンを押すとスラッグ欄が置き換わり、指摘が「このスラッグは使用できます」に変わること。手順 8 のようにスラッグ未設定でも作成できること（公開時に初めて必須になる）。P-31 のスラッグ欄も同じ目安を出す（項目 12 手順 6）。

### 3. WS-01 — 所有数の上限（20 件）

- **対応する受け入れ基準:** AC-2
- **検証手段:** browser
- **目的:** 1 人あたり 20 件の上限が働くこと
- **前提:** ユーザー A が項目 1・2 で 3 件所有している（項目 1 の `設計チーム`、項目 2 手順 7 の `大文字検証`、同手順 8 の `個人検証`。手順 1〜6 は失敗させる試行なので増えない）
- **手順:**
  1. 名前だけを変えて 17 件のワークスペースを追加で作成する（計 20 件）
  2. 21 件目を作成しようとする
- **期待結果:** 手順 1 の 20 件目までは作成できる。手順 2 で所有できるのは 20 件までである旨が示され、作成されない。
- **確認ポイント:** 上限に達したときの文言が理由を示していること（WS-01「理由を示して拒否する」）。**この項目を実行すると以降のスコープトークンに 20 件が並ぶ**ので、項目 4 のページングの確認と兼ねてよい。17 件を手で作るのが現実的でなければ、件数を減らして「上限に達していない」ことだけ確認し、上限の合否は自動テスト（TC-workspace-062 / 063 / 068）に委ねた旨を記録する。

### 4. WS-02 — 文脈の切り替えと URL・再訪時の引き継ぎ

- **対応する受け入れ基準:** AC-3
- **検証手段:** browser
- **目的:** 参加中のワークスペースが一覧され、選択が URL と次回訪問に反映されること
- **手順:**
  1. 上部バーのスコープトークンを開く
  2. 一覧末尾に「さらに読み込む」が出ていれば押す（1 ページ 20 件。**所有できるのも 20 件が上限なので、A が他人のワークスペースに招待されていない限り 2 ページ目は出ない** — 出ない場合は 20 件が重複なく 1 ページに並ぶことだけを見る）
  3. `設計チーム` を選ぶ
  4. URL を確認する
  5. スコープトークンから個人の文脈に切り替える
  6. ウィンドウ A を閉じて開き直し、`http://localhost:3000/` を開く
- **期待結果:** 手順 1 で「個人」と参加中のワークスペースが並ぶ。手順 2 で（2 ページ目がある場合のみ）次の 20 件が追加され、既に表示したものが重複しない。手順 3 で `設計チーム` のノート一覧に切り替わり、見出しがワークスペース名になる。手順 4 の URL が `/workspaces/{workspaceId}/notes` になっている。手順 5 で `/notes` に戻り、個人のノートだけが並ぶ。手順 6 で前回の文脈（`設計チーム` のノート一覧）へリダイレクトされる。
- **確認ポイント:** 一覧に並ぶノートがその文脈のものだけであること（個人のノートが混ざらない）。切り替え時に検索語・タグを持ち越さないこと（WS-02）は、一覧に絞り込みの UI がまだ無い（Issue #8）ため URL に条件が残らないことまでしか観測できない — その範囲で記録する。

### 5. WS-03 — メンバーを招待し、保留中の一覧と有効期限を確認する

- **対応する受け入れ基準:** AC-4
- **検証手段:** browser
- **目的:** 招待が発行され、メールにリンクが載り、保留中として一覧されること
- **前提:** ウィンドウ A で `設計チーム` の文脈。`pnpm dev` のターミナルを見られる状態
- **手順:**
  1. `設計チーム` の設定タブ「メンバー」を開く
  2. 「メンバーを招待」に `user-b@example.com` を入力し、ロールに editor を選んで「招待を送る」を押す
  3. `pnpm dev` のターミナルで `mail.sent` 行を確認する
  4. 「保留中の招待」の有効期限を確認する
  5. 続けて `user-c@example.com` を viewer で招待する
  6. 招待パネルに現れた「招待リンクをコピー」を押す
  7. ロールに owner を選び、`owner-candidate@example.com` で「招待を送る」を押す
- **期待結果:** 手順 1 でメールアドレスとロールの入力欄が出る。手順 2 で「保留中の招待」に表示される。手順 3 のログ行に招待リンクを含む `actionUrl` が出る。手順 4 の有効期限が発行から 14 日後になっている。手順 6 で「招待リンクをコピーしました」と示される。手順 7 では**招待が作られず**、owner が行えること（メンバーの招待・ロール変更・除名、設定・公開・削除）と宛先を示す確認が出る。「owner として招待する」で確定すると発行され、「やめる」で確認が閉じて何も起きない。
- **確認ポイント:** 送信直後に楽観的に一覧へ追加され、失敗したら巻き戻ること（`CLAUDE.md`「Frontend」の三層）。owner の確認を挟んでも同じで、確定を押した瞬間に一覧へ楽観的に増え、ボタンが「送信中...」になること。**「招待リンクをコピー」は直前に発行した 1 件にしか出ない**（一覧はトークンを持たないため、保留中の行にコピーの操作は無い）ので、手順 6 でコピーされるのは手順 5 の `user-c@example.com` 宛のリンクになる。

### 6. WS-04 — 招待リンクから参加する（サインイン済み / リンクをコピーして共有）

- **対応する受け入れ基準:** AC-5
- **検証手段:** browser
- **目的:** 招待の preview が出て、受諾でメンバーになり、そのワークスペースへ遷移すること
- **手順:**
  1. 項目 5 手順 3 で得た `user-b@example.com` 宛のリンクを、ウィンドウ B（ユーザー B でサインイン済み）で開く
  2. 表示内容を確認する
  3. 「参加する」を押す
  4. 項目 5 手順 6 でコピーした `user-c@example.com` 宛のリンクをウィンドウ C（ユーザー C でサインイン済み）で開き、同じように参加する
  5. ウィンドウ A でメンバー管理を再読み込みする
- **期待結果:** 手順 2 でワークスペースの名前・説明・付与されるロールとその説明・招待者・招待先のメールアドレスが表示される。手順 3 は招待先とサインイン中のアドレスが一致するので**確認を挟まず** `設計チーム` のノート一覧（`/workspaces/{workspaceId}/notes`）へ遷移する。手順 5 でユーザー B が editor、ユーザー C が viewer として一覧に表示される（計 3 名）。
- **確認ポイント:** 受諾後、ユーザー B / C のスコープトークンに `設計チーム` が現れること。押した瞬間にボタンが「参加しました」に変わること（楽観 UI）。受諾した本人が同じリンクを開き直すと「すでに参加しています」になり、そこから開くのもノート一覧であること（TC-31）。招待先と違うアカウントで開いた場合だけ確認が 1 段入る（項目 22 と TC-30）。

### 7. WS-04 — 未サインインから招待リンクを開き、サインアップして招待へ戻る

- **対応する受け入れ基準:** AC-5
- **検証手段:** browser

### 8. WS-03 — 招待の再送と取り消し

- **対応する受け入れ基準:** AC-4
- **検証手段:** browser
- **目的:** 再送で新しいリンクが発行されて旧リンクが失効し、取り消しで一覧から消えること
- **前提:** 保留中の招待を 2 件作る（未使用のメールアドレス `pending-1@example.com` / `pending-2@example.com` を editor で招待）
- **手順:**
  1. `pending-1@example.com` の招待の**旧リンク**を `mail.sent` から控える
  2. その招待の行の「再送」を押す
  3. `mail.sent` の新しい `actionUrl` を控える（行に現れる「リンクをコピー」でも取れる）
  4. 手順 1 の旧リンクをシークレットウィンドウで開く
  5. 手順 3 の新リンクを開く
  6. `pending-2@example.com` の招待の「取り消し」→「取り消す」で確定する
  7. 取り消した招待のリンクを開く
- **期待結果:** 手順 2 で有効期限が更新される。手順 3 で新しいリンクを含むメールがログに出る。手順 4 の旧リンクは「この招待は使えません」になる。手順 5 の新リンクは有効な preview が表示される。手順 6 で保留中の一覧から消え、「招待を取り消しました。」と表示される。手順 7 は「この招待は取り消されています」になる。

- **確認ポイント:** 取り消しは**一覧メンバーシップの変更**なので、楽観的な削除が親（一覧の所有者）で行われ、失敗時に行が戻ること。

### 11. WS-06 — ワークスペースを脱退する / 最後の owner を保護する

- **対応する受け入れ基準:** AC-7
- **検証手段:** browser

- **手順:**
  1. ウィンドウ A で `設計チーム`（owner が A 1 名）の設定タブ「メンバー」を開き、自分の行を見る

  4. ユーザー B を owner に昇格させてから、もう一度自分の行とパネル下部を見る
  5. ウィンドウ B でユーザー B がパネル下部の「脱退する」→ 確認の「脱退する」を押す
  6. ウィンドウ B のスコープトークンを確認する
- **期待結果:** 手順 1 で自分の行にはロールセレクターが出ず、現在のロール（owner）だけが表示される。手順 2 で自分の除名の操作は出ない（脱退を使う）。脱退の導線は一覧の中ではなく**パネル下部の「このワークスペースから脱退」**にあり、閲覧者自身の行がページに載っているかに依らず出る。手順 3 で「脱退する」が無効になっており、「最後の owner は脱退できません。別のメンバーを owner にするか、…ワークスペースを削除してください。」が表示され、「ワークスペースを削除」が削除タブへのリンクになっている。手順 4 では owner が 2 名になるので「脱退する」が押せるようになる（自分のロールセレクターは依然として出ない）。手順 5 で脱退の説明（ノートにアクセスできなくなる / 作成したノートは残る / 再参加には招待が要る）を経て脱退が完了し、`/notes` へ遷移する。手順 6 に `設計チーム` が並ばない。

  4. 確認の内容を読み、「設計チーム 2026へ移動」を押して移動中・移動後の表示を確認する
  5. ページを再読み込みする
  6. 控えておいたノートの URL を開く
  7. アプリ内のノート URL を確認する
  8. 元ファイル / メディアを持つノートで同じ移動を行い、表示を確認する
- **期待結果:** 手順 2 で個人と editor 以上のワークスペースだけが並び、**viewer としてのみ参加している `閲覧のみ` と現在の所属先は出ない**。手順 3 では移動は走らず、「`設計チーム 2026` のメンバー全員がこのノートを読めるようになります」「タグは移動先に引き継がれません」「公開ページと共有リンクの URL は変わりません」を含む確認に変わる（「戻る」で候補一覧に戻れる）。手順 4 で「移動中...」の表示を経てメニューが閉じ、失敗表示が出ない。手順 6 で控えておいた `/notes/{noteId}` を開いても同じノートが読め、URL が `/workspaces/{workspaceId}/notes/{noteId}` へ正規化される。手順 7 のアプリ内 URL も同じ形になっている。

  - **変換処理中のノートの移動拒否**（Issue #5 / #6）— 処理中ノートを作れない

### 18. AC-14 — 使用量ページにワークスペースの内訳が出る

- **対応する受け入れ基準:** AC-14
- **検証手段:** browser + api
- **目的:** `getUsageSnapshot` が `workspaceCursor` / `workspaceLimit` を受け、`workspaces` / `nextWorkspaceCursor` を返し、P-24 がそれを描くこと
- **前提:** ユーザー A が複数のワークスペースに参加している（項目 3 を実行していれば 20 件ちょうど）
- **手順:**
  1. `pnpm test:node -- getUsageSnapshot` で `getUsageSnapshot` のユニットテストを実行し、keyset ページング・並行 RPC・部分失敗時の `unavailable` を覆うケースが緑であることを確認する
  2. ウィンドウ A で `/settings/usage` を開く
  3. ワークスペースのセクションを確認する
  4. 末尾に「ワークスペースをさらに読み込む」が出ていれば押す（1 ページ 20 件で所有上限も 20 件なので、A が他人のワークスペースに招待されていない限り出ない）
- **期待結果:** 手順 1 が失敗 0 件。手順 2 で個人の使用量・LLM 実行回数・最終更新時刻が `NaN` / `Invalid Date` / 例外画面にならずに表示される。手順 3 で owner / editor として参加しているワークスペースが個人と AI の間に並ぶ（viewer のワークスペースは並ばない）。手順 4 で（ボタンが出ている場合のみ）次のページが重複なく足され、押している間はボタンが「読み込み中...」になる。
