## 確認環境

この Issue の変更を確認するために必要な手順のみ記載（プロジェクト全体のセットアップは省略）。

### 環境変数（起動前に必須）

`apps/web/.env` に以下の 3 行が入っていること。`OAUTH_DEV_MODE` が無いと **dev サーバーが起動時に失敗する**（ADR-003 の規則 3。既存の `.env` は `APP_URL` しか持たないので 1 行足す必要がある）。

```
APP_URL=http://localhost:3000
OAUTH_DEV_MODE=true
MEMORY_MAIL_LOG_ACTION_URL=true
```

- `OAUTH_DEV_MODE=true` — OAuth を本番の Google ではなく **dev IdP** で確認するためのスイッチ（`.thread/2/adr.md` ADR-003 / ADR-021、steps.md 手順 13）。同意画面はアプリ内ルート `http://localhost:3000/dev/oauth/authorize` で、Google 資格情報は不要。
- `MEMORY_MAIL_LOG_ACTION_URL=true` — in-memory の `MailSender` が `mail.sent` ログ行に `actionUrl`（確認 URL・再設定 URL）を出す（`apps/web/.env.example`、`docs/runtime_node.md` の env 表）。**既定は off で、off のままだと確認リンク・再設定リンクを取得できず本計画の大半が実行できない。**
- `DELETION_TICKET_KEY` は未設定でよい（未設定はプロセス毎のランダム鍵 — ADR-006）。

### 検証環境の起動

- 開発サーバー: リポジトリルートで `pnpm dev` を実行し、`http://localhost:3000` を開く（root `package.json` の `dev` → `@repo/web` の `dev:node` → `vite dev --config vite.config.node.ts`。ポートは `apps/web/vite.config.node.ts` の `server.port: 3000`）。
- DB マイグレーション・シードは**不要**。永続化は in-memory アダプターのみで、DB もマイグレーションスクリプトも存在しない（`docs/runtime_node.md`「Persistence model」）。
- **データはプロセス内メモリのみ**（`docs/runtime_node.md`「Manual test scenarios must complete within one process lifetime.」）。本計画の確認項目は **1 プロセス内で上から順に通しで実行**し、テストアカウントは項目 1 から順に作る。途中でサーバーを再起動したらすべて作り直しになる。
- **メール本文の取得**: `pnpm dev` を実行しているターミナルのサーバーログの `mail.sent` 行を読む。`actionUrl` フィールドが確認リンク / パスワード再設定リンクの URL。
- **削除の進捗**: 継続タスクランナー（`ScopeTaskQueue.listDue` を 1 秒間隔で回す tick + commit 後 kick — ADR-005 / ADR-023）が dev サーバーと同一プロセスで動く。`deleteAccount` は数秒で `accepted` → `running` → `completed` まで進むので、画面のポーリング表示を最大 60 秒待って判定する。
- 本番ビルドの確認（「既存機能への影響確認」で使用）: `pnpm build` → `pnpm start`。待ち受け URL は起動ログの `[listen.node] listening on http://...` 行で確認する（`apps/web/scripts/listen.node.ts`）。
- 静的検証: `pnpm typecheck && pnpm lint:fix && pnpm format && pnpm test:unit`（root `package.json` の scripts。AC-30）。

## 確認項目

上から順に、同一の `pnpm dev` プロセス内で実行する。各項目は前の項目が作ったアカウント・状態を引き継ぐ。

作るアカウント（すべてこの計画の中で作る）:

| 用途 | メールアドレス | パスワード |
|---|---|---|
| ユーザー A（主役。最後に削除する） | `user-a@example.com` | `Passw0rd123` → `NewPassw0rd456` |
| ユーザー B（ハンドル重複の相手役） | `user-b@example.com` | `Passw0rd123` |
| 未確認ユーザー | `pending@example.com` | `Passw0rd123` |
| ロック検証用の使い捨て | `locked@example.com` | `Passw0rd123` |
| Google のみユーザー（dev IdP） | `google-a@example.com` | （なし → 途中で `Passw0rd123` を追加） |

### 1. メール確認 — 確認リンクでサインイン状態になり空状態が出る

- **対応する受け入れ基準:** AC-4、AC-5（TC-02。前提として TC-01 の手順を実行するが、合否は TC-02 の手順で判定する）
- **目的:** サインアップ → 確認リンクの e2e が通り、ノート一覧の空状態とアカウントメニューが出ること
- **手順:**
  1. ウィンドウ1 で `http://localhost:3000/signup` を開く
  2. メールアドレス `user-a@example.com`、パスワード `Passw0rd123`、表示名 `ユーザーA` を入力し、利用規約への同意にチェックを入れて送信する
  3. サーバーログの `mail.sent` 行から `actionUrl`（`/verify-email?token=...`）を取り出す
  4. **同じウィンドウ1** でその URL を開く
  5. 遷移後、上部バーのアカウントメニューを開く
- **期待結果:** 確認ページが処理中を表示した後 `/notes` へ遷移し、サインイン状態になる。ノート 0 件の空状態（新規作成への導線を含む）が表示される。アカウントメニューに表示名 `ユーザーA` が出る。
- **確認ポイント:** 空状態に**アップロード導線が無いのは正しい**（取り込みスライス #6 のため — #1 からの継続縮退）。確認 URL は必ずサインアップした同じウィンドウで開く（別ウィンドウだと ADR-038 どおり「確認しました → サインインへ」に倒れる）。

### 2. メール確認 — 使用済み・改ざんリンクの状態表示

- **対応する受け入れ基準:** AC-4、AC-5（TC-20）
- **目的:** トークンの再利用・改竄が拒否され、P-03 の各状態が出ること
- **手順:**
  1. 項目 1 で使用済みの確認 URL をウィンドウ1 でもう一度開く
  2. その URL の `token` の末尾 1 文字を書き換えて開く
- **期待結果:** 手順 1 は「このメールアドレスは確認済みです」相当の状態とサインイン画面への導線が出る。手順 2 は「このリンクは使えません」相当の無効状態と**確認メールの再送導線**が出る。どちらも `/notes` へは遷移しない。
- **確認ポイント:** トークン消費は GET のページ表示ではなくマウント後の POST（server function）で行われる（開発者ツールの Network タブで確認）。

### 3. メール確認 — 無効リンクからの再送で確認が完了する

- **対応する受け入れ基準:** AC-3、AC-5（TC-19 の代替実行。手順 1「24 時間経過したリンク」は再現不可のため、同じ再送導線を持つ**無効リンク状態**から実行する）
- **目的:** `resendVerificationEmail` が PendingUser に対して再送し、新しいリンクで確認が完了すること
- **手順:**
  1. ウィンドウ2（シークレット）で `/signup` を開き、`user-b@example.com` / `Passw0rd123` / 表示名 `ユーザーB` で登録する
  2. サーバーログから `user-b@example.com` 宛の `actionUrl` を取り出し、**`token` の末尾 1 文字を書き換えて**ウィンドウ2 で開く
  3. 表示された無効状態から「確認メールを再送」を押す
  4. サーバーログに出た**新しい** `actionUrl` をウィンドウ2 で開く
- **期待結果:** 手順 3 で送信中 → 送信済みの表示になり、サーバーログに `user-b@example.com` 宛の新しい確認メールが出る。手順 4 で確認が完了し `/notes` へ遷移してサインイン状態になる。
- **確認ポイント:** 手順 3 を続けて 2 回押すとクールダウン（60 秒以内は無送信）になり、**画面の応答は成功のまま変わらない**（ログに 2 通目が出ないのが正しい）。TC-19 を代替実行した旨を記録に残す。

### 4. メール確認 — 未確認アカウントのサインインと P-02 の再送導線

- **対応する受け入れ基準:** AC-3、AC-5（PAGE-p02-006）（TC-21）
- **目的:** 未確認は認証失敗とは別状態になり、サインイン画面から再送できること
- **手順:**
  1. ウィンドウ2 でアカウントメニューからサインアウトする
  2. `/signup` で `pending@example.com` / `Passw0rd123` / 表示名 `未確認ユーザー` を登録する（**確認リンクは開かない**）
  3. `/signin` で `pending@example.com` / `Passw0rd123` を送信する
  4. 表示された再送導線を押す
  5. `/notes` を直接開く
- **期待結果:** 手順 3 で「メールアドレスの確認が必要」である旨の専用状態と再送導線が出る（認証失敗の共通文言ではない）。手順 4 で再送が成功し、サーバーログに `pending@example.com` 宛の確認メールが出る。手順 5 はサインイン画面へリダイレクトされる（セッションが発行されていない）。
- **確認ポイント:** 手順 4 で送ったリンクは**開かない**（`pending@example.com` は項目 12 の TC-23 手順 6 で未確認のまま使う）。

### 5. OAuth — dev IdP の同意をキャンセルする

- **対応する受け入れ基準:** AC-6（ADR-021）、AC-9（P-05 キャンセル状態）（TC-40）
- **目的:** 同意画面のキャンセルが `error=access_denied` としてコールバックに届き、専用状態が出ること
- **手順:**
  1. ウィンドウ2 の `/signin` で「Google で続ける」を押す
  2. 遷移先が `http://localhost:3000/dev/oauth/authorize?...`（`client_id` / `redirect_uri` / `state` / `code_challenge` / `code_challenge_method` / `scope` 付き）であることを URL バーで確認する
  3. 「キャンセル」を押す
  4. 戻った画面からサインイン画面へ戻り、もう一度「Google で続ける」を押す
- **期待結果:** 手順 3 で `/auth/callback/google?error=access_denied&state=...` へ遷移し、P-05 の**キャンセル状態**（「キャンセルしました」相当と元の画面へ戻る導線）が表示される。サインイン状態にはならない。手順 4 で通常どおり同意画面が再表示される（state は毎回別の値）。
- **確認ポイント:** 認可 URL に `code_challenge_method=S256` と 43 文字の `code_challenge` が含まれている（ADR-010）。

### 6. OAuth — dev IdP で新規サインアップし、認証手段が Google 1 件になる

- **対応する受け入れ基準:** AC-6、AC-8、AC-9（PAGE-p01-003 / p02-003）、AC-17（TC-05 手順 1〜3。手順 4 は skip → #4）
- **目的:** OAuth 経由の新規登録が成立し、P-22 に Google 1 件が出て解除できないこと
- **手順:**
  1. ウィンドウ2 の同意画面（項目 5 手順 4 で開いたもの）で、メールアドレス `google-a@example.com`、表示名 `グーグル太郎` を入力し、`email_verified` トグルを **ON** にして「許可する」を押す
  2. 遷移後の画面を確認する
  3. アカウントメニューから「設定」→「ログイン方法」タブ（`/settings/auth`）を開く
- **期待結果:** 手順 1 で `/auth/callback/google?code=...&state=...` を経て `/notes` へ遷移し、サインイン状態になる（アカウントメニューに `グーグル太郎`）。手順 3 で有効なログイン方法が **Google 1 件だけ**表示され、その解除ボタンが無効になっている。
- **確認ポイント:** `/settings` のタブは **プロフィール / ログイン方法 / 使用量 / アカウント削除の 4 つ**（「連携」タブが無いのは正しい — P-23 が #4）。TC-05 手順 4（外部連携一覧）は skip（#4）。

### 7. パスワード再設定 — パスワード手段を持たないアカウントへの申請

- **対応する受け入れ基準:** AC-10、AC-12（TC-25）
- **目的:** Google のみのアカウントには再設定リンクではなく案内メールが出ること
- **手順:**
  1. ウィンドウ2 でサインアウトし、`/signin` の「パスワードを忘れた」から `/reset-password` を開く
  2. `google-a@example.com` を入力して送信する
  3. サーバーログを確認する
- **期待結果:** 画面には共通の完了文言（「登録しているメールアドレスに、再設定のリンクを送ります」に対する送信完了表示）が出る。サーバーログには**再設定リンクではなく**「Google でサインインしてから設定でパスワードを追加する」旨の案内メール（`passwordResetUnavailable`）が出る。
- **確認ポイント:** `/signin` の「パスワードを忘れた」が**実リンク**になっている（#1 では文言のみだった）。

### 8. パスワード再設定 — 未登録メールでの申請（存在を漏らさない）

- **対応する受け入れ基準:** AC-10（TC-24）
- **目的:** 未登録でも応答が同一で、メールが出ないこと
- **手順:**
  1. `/reset-password` で `nobody@example.com` を送信する
  2. サーバーログを確認する
- **期待結果:** 項目 7 手順 2 と**まったく同じ**完了表示になる。サーバーログに `nobody@example.com` 宛のメールは 1 通も出ない。

### 9. パスワード再設定 — 入力不一致とリンクからの再設定、他セッションの失効

- **対応する受け入れ基準:** AC-10、AC-11、AC-12、AC-16（TC-27 と TC-06）
- **目的:** 2 回入力の不一致が弾かれ、再設定が完了し、他端末のセッションが失効すること
- **手順:**
  1. ウィンドウ1（項目 1 の `user-a@example.com` でサインイン済み）で `/notes` が表示されていることを確認する
  2. ウィンドウ2 の `/reset-password` で `user-a@example.com` を送信する
  3. サーバーログの `actionUrl`（`/reset-password?token=...`）をウィンドウ2 で開く
  4. 新しいパスワードに `NewPassw0rd1`、確認に `NewPassw0rd2` を入力する
  5. 両方を `NewPassw0rd456` に揃えて確定する
  6. `/signin` で `user-a@example.com` / `NewPassw0rd456` を送信する
  7. **ウィンドウ1** を再読み込みする
- **期待結果:** 手順 4 で「2 つのパスワードが一致しません」が表示され送信できない。手順 5 で完了の案内が出てサインイン画面へ誘導される。手順 6 で `/notes` へ遷移する。手順 7 でウィンドウ1 がサインアウトされ、サインイン画面が表示される。
- **確認ポイント:** 手順 5 の画面に「設定すると、すべての端末のサインインが解除されます」相当の説明が出る。手順 7 の失効は `authEpoch` バンプによるもので、待たずに（再読み込み 1 回で）反映される。以降ユーザー A のパスワードは **`NewPassw0rd456`**。

### 10. パスワード再設定 — 使用済み・改ざんリンク

- **対応する受け入れ基準:** AC-11、AC-12（TC-26 手順 2。手順 1「1 時間経過」は再現不可）
- **目的:** 消費済み・不正なトークンが再申請へ戻されること
- **手順:**
  1. 項目 9 手順 3 で使用済みの再設定 URL をもう一度開く
  2. その URL の `token` の末尾 1 文字を書き換えて開く
- **期待結果:** どちらも「この再設定リンクは使えません／期限が切れているか、すでに使われています」相当の状態になり、**再申請への導線**が出る。新しいパスワードの入力欄は出ない。

### 11. 認証手段管理 — 認証失敗の共通文言と Google 導線

- **対応する受け入れ基準:** AC-9（P-02 の Google 導線）（TC-22）
- **目的:** 失敗の原因を区別せず、Google のみアカウントには Google 導線が添えられること
- **前提:** 項目 9 の結果としてウィンドウ1 は未サインイン、ウィンドウ2 は `user-a` でサインイン済み。本項目はウィンドウ1 で実行する
- **手順:**
  1. ウィンドウ1 の `/signin` で `user-b@example.com` / `WrongPass1` を送信する
  2. `nobody@example.com` / `Passw0rd123` を送信する
  3. `google-a@example.com` / `Passw0rd123` を送信する
- **期待結果:** 手順 1 と手順 2 が**まったく同じ**共通エラー表示になる。手順 3 も同じ共通エラーだが、あわせて「Google で続ける」への導線が出る。
- **確認ポイント:** ここで `user-b@example.com` に失敗が 2 回以上溜まらないようにする（3 回目から待機に入り、項目 17 以降で使えなくなる）。手順 1 は 1 回だけ実行する。

### 12. 認証手段管理 — 段階待機とロック

- **対応する受け入れ基準:** AC-12（LOCKED からの再設定導線が実リンク）（TC-23 手順 1〜3, 5, 6。手順 4 と 7 は実行不可 — 「実行しても再現できない手順」表を参照）
- **目的:** 失敗の累積で待機 → ロックへ遷移し、記録がメールアドレス単位で分かれること
- **手順:**
  1. ウィンドウ1 の `/signup` で `locked@example.com` / `Passw0rd123` / 表示名 `ロック検証` を登録し、サーバーログの確認リンクを**同じウィンドウ1 で**開いて確認まで済ませ、そのままサインアウトする
  2. `/signin` で `locked@example.com` / `WrongPass1` を **3 回**続けて送信する
  3. 待機表示が出ている間に、正しいパスワード `Passw0rd123` で送信する
  4. 待機秒数（1 → 2 → 4 → 8 → 16 → 32 → 60 → 60 秒。合計およそ 3 分）を待ちながら誤ったパスワードの送信を繰り返し、**通算 10 回**の失敗に到達させる。Network タブで HTTP ステータスも見る
  5. `other@example.com` / `WrongPass1` を 1 回送信する
  6. `pending@example.com` / `Passw0rd123`（正しいパスワード）を送信する
- **期待結果:** 手順 2 の 3 回目で待機が必要である旨と待機秒数が表示される。手順 3 は待機中である旨が出てサインインできない。手順 4 の 10 回目で「一時的にロックされた」旨と解除時刻、および**パスワード再設定への実リンク**が表示される（待機中・ロック中の応答は HTTP 429）。手順 5 は待機に巻き込まれず 1 回目の失敗として共通エラーになる。手順 6 は「メールアドレスの確認が必要」の表示になり、失敗回数は増えない。
- **確認ポイント:** 手順 4 のリンクを押すと `/reset-password` の申請モードへ遷移する（#1 の「文言のみ」縮退が解消されている）。`locked@example.com` はこれ以降 15 分間サインインできないが、以降の項目では使わない。

### 26. 使用量 — 個人の使用量が表示される

- **対応する受け入れ基準:** AC-21、AC-22、AC-23（TC-11 手順 1〜3。手順 4〜6 は skip → #3）
- **目的:** P-24 が個人の容量・ノート件数・当月 AI 実行回数・最終更新時刻を表示すること
- **手順:**
  1. `/settings/usage` を開く
  2. 当月の AI 実行回数の表示を確認する
  3. 最終更新時刻の表示を確認する
  4. `/settings/danger` への導線を押して遷移することを確認し、`/settings/usage` に戻る
- **期待結果:** 個人の保存容量の消費量と上限（上限 5 GB）、ノート件数、当月の AI 実行回数と上限（300 回）、集計の最終更新時刻が表示される。読み込み中はスケルトンが出る。**保存容量の消費量とノート件数は本 Issue では常に 0 を表示する**（#6 まで実値は反映されない）— アバターを保存済みでも、#1 の `createBlankNote` でノートを作成済みでも「0 B」「0 件」のままであり、**不具合として扱わない**。
- **確認ポイント:**
  - **消費容量とノート件数が 0 のままなのは実装どおり**（ADR-004 の縮退）。即時反映を担う `applyStorageDelta` / `initializeQuota` が本 Issue 外で、`recalculateStorageUsage` は spec 上の運用操作のため本番の駆動主体が無く、`storage_quotas` の行そのものが作られない。確認するのは値の正しさではなく、上限（5 GB / 300 回）と単位・書式が破綻していないこと。
  - ワークスペースのセクションと「さらに読み込む」が**出ないのは正しい**（PAGE-p24-002 見送り、workspace は常に空配列 — #3）。
  - 最終更新時刻はクォータ行が無い状態のフォールバック値（表示時点の初期化時刻）なので、再読み込みのたびに直近の時刻になる。表示が破綻していないこと（`NaN`・`Invalid Date`・例外画面でないこと）を確認する。

### 27. アカウント削除 — 確認入力が一致しないと実行できない

- **対応する受け入れ基準:** AC-26、AC-28（TC-38）
- **目的:** 削除実行前の確認入力が働くこと
- **手順:**

  2. 確認欄に `user-b@example.com`（誤ったメールアドレス）を入力する
  3. 確認欄を `user-a@example.com` に直す
- **期待結果:** 手順 1 で削除されるもの・されないものの説明が表示される。手順 2 では削除ボタンが押せないまま、または押しても入力が一致しない旨が表示される。手順 3 で削除ボタンが押せるようになる。

### 28. アカウント削除 — 受理からの完走（accepted → running → completed）

- **対応する受け入れ基準:** AC-26、AC-27、AC-28、AC-29、AC-31、AC-32（TC-14 手順 1〜3。手順 4〜7 は skip → #9 / #3 / #5 / #6）
- **目的:** 削除要求が受理され、継続タスクランナーが完了まで駆動し、進捗が画面に出ること
- **手順:**
  1. `/settings/danger` の確認欄に `user-a@example.com` を入力し、削除を実行する。Network タブを開いておく
  2. 実行直後の画面表示と応答ステータスを確認する
  3. 画面から離れずに進捗表示を最大 60 秒観察する
  4. 進捗が完了になったら、完了表示からの遷移導線を押す
  5. 遷移後に `/notes` を開く
- **期待結果:** 手順 2 で HTTP **202** が返り、セッション Cookie が破棄され（`Set-Cookie`）、**画面は `/settings/danger` に留まったまま**削除が処理中であることと進捗が表示される。手順 3 で進捗が `accepted` → `running` → `completed` と進む。手順 4 でトップページへフル遷移する。手順 5 はサインイン画面へリダイレクトされる。
- **確認ポイント:**
  - 手順 2 の時点で画面が別ページへ遷移してしまう場合は失敗（ADR-006 の「削除実行後はナビゲートしない」に反する）。
  - 進捗ポーリング中にページを再読み込みしても、`sessionStorage` の ticket から進捗表示に復帰する。
  - サーバーログに `usage` / `storage` の personal cleanup と `authResidue` / `uniquenessRelease` の処理が出ており、エラーで止まっていない。
  - 完了までに 60 秒以上かかる場合は継続タスクランナーの配線（ADR-023 の 1 秒 tick / commit kick）を疑い、観測結果を記録する。

- **目的:** `deleteAccount` の finalize で一意性予約（email / handle / providerAccount）が解放されていること（AC-26、TC-identity-093 の実機確認）
- **手順:**
  1. 項目 28 の完了後、`/signup` で `user-a@example.com` / `Passw0rd123` / 表示名 `再登録ユーザー` を登録する
  2. サーバーログの確認リンクを開く
  3. `/settings/profile` でハンドル `test-user`（項目 22 で `user-a` が使っていた値）を設定する
- **期待結果:** 手順 1 は「既に登録済み」ではなく通常のサインアップとして受理され、確認メールが出る。手順 2 で確認が完了しサインインできる。手順 3 のハンドルも取得できる。
- **注記:** 手順 3 のハンドルが「使われています」になる場合、旧ハンドル予約の解放漏れなので原因つきで記録する。

### 2. 削除実行後の旧セッションでの操作

- **目的:** 削除受理（barrier）後に書き込み入口が `ACCOUNT_DELETING` で閉じること（AC-19 / AC-22 の `assertWritable`）
- **手順:** 項目 28 を始める**前に**ウィンドウ2 でも `user-a@example.com` / `NewPassw0rd456` でサインインしておき、項目 28 の手順 1 の直後（進捗が `running` の間）にウィンドウ2 で `/settings/profile` を開いてアイコンをアップロードするか、`/notes` で新規ノート作成を試す
- **期待結果:** セッションが失効しているためサインイン画面へ倒れる。仮にセッションが残っていた場合でも、書き込みは「アカウントを削除中」である旨のエラーになり、成功しない。
- **注記:** 削除は数秒で完了するのでタイミングを取れないことがある。取れなかった場合は「タイミング上未実行」と記録する（ユニットテスト TC-identity-045 が担保する範囲）。

### 3. dev IdP のコールバックを直接改ざんする

- **目的:** `state` が消費済み / 不正のときに P-05 の失敗状態へ倒れること（AC-9）
- **手順:** 項目 6 で成功したコールバック URL（`/auth/callback/google?code=...&state=...`）をそのまま再度開く
- **期待結果:** サインイン状態にはならず、「連携を完了できませんでした」相当の失敗状態が表示される（`state` は 1 回消費 — ADR-007）。

### 4. 再設定リンク・確認リンクのオープンリダイレクト耐性

- **目的:** OAuth の `redirectTo` と再設定後の遷移先が同一オリジンに制限されていること
- **手順:** `/dev/oauth/authorize?...&redirect_uri=https://example.com/` の形に URL を書き換えて開く
- **期待結果:** 外部オリジンの `redirect_uri` は受理されず、エラー表示になる（`AppConfig.appUrl` と同一オリジンのパスのみ — ADR-021）。

### 5. `OAUTH_DEV_MODE` が偽のとき dev IdP のルートが 404 になる

- **目的:** dev IdP が production に漏れないガード（ADR-003 / ADR-021）
- **手順:**
  1. **この項目は他のすべての確認が終わってから実行する**（サーバー再起動でデータが全消去されるため）
  2. `apps/web/.env` の `OAUTH_DEV_MODE=true` を削除し、代わりに `GOOGLE_OAUTH_CLIENT_ID=dummy` と `GOOGLE_OAUTH_CLIENT_SECRET=dummy` を書いて `pnpm dev` を再起動する
  3. `http://localhost:3000/dev/oauth/authorize` を開く
  4. `.env` を元（`OAUTH_DEV_MODE=true`、Google の 2 行を削除）に戻す
- **期待結果:** 手順 2 でサーバーが起動する（Google アダプターが選択される）。手順 3 は 404 相当の「見つかりません」表示になり、同意画面は描画されない。
- **補足:** `OAUTH_DEV_MODE` も Google 資格情報も無い状態では**起動そのものが失敗する**（ADR-003 の規則 3）。起動失敗メッセージに「`.env` に `OAUTH_DEV_MODE=true` を足す」旨の案内が含まれることも確認する。

### 6. サーバー再起動でデータが消える（仕様の確認）

- **目的:** in-memory 前提の把握（不具合ではない）
- **手順:** dev サーバーを再起動し、サインイン済みだったウィンドウで `/notes` を再読み込みする
- **期待結果:** アカウント・ノート・アバターがすべて消え、セッションも無効になってサインイン画面へ整然と誘導される（エラー画面やクラッシュにならない）。
- **注記:** AC-29 の「プロセスを落として再起動しても未完の継続を拾って完走する」は、**in-memory ランタイムでは実機確認できない**（再起動で `scheduled_tasks` ごと消える）。ユニットテスト側の担保に委ねる旨を記録する。
