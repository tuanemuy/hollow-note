### 確認した主な観点（結論）

- **ミューテーションの三層規律と所有権**: 破れなし。リスト増減（追加 / 解除）は親島 `IdentityList/board.tsx` が `useOptimistic` ごと所有し、解除は必ず親で走る（`onRemove`、楽観的除去で葉がアンマウントしてもエラー表示が残る）。追加はフォームの action から dispatch し、フォームは一覧の外にある（`AddPasswordForm` は入力と pending 表示だけを持つ）。パスワード変更・他端末サインアウトはリストを変えない葉なのでそれぞれが自分の server function と pending / エラーを持つ。P-21 の保存は `useActionState`＋アイコンの `useOptimistic`＋`useTransition`、P-25 の実行は `useActionState`。`useServerFn` は `useCallback([router, serverFn])` で安定なので、`ProfileEditor` のハンドル debounce と `DeleteAccountPanel` のポーリングが effect 依存で再購読ループになることはない。
- **`router.invalidate()` での再整合**: `ProfileEditor`（保存 / アイコン差し替え / 削除）、`IdentityBoard`（追加 / 解除 / 他端末サインアウト）、`ChangePasswordForm`、`OAuthCallbackPanel`、`ResetPasswordPanel` のいずれも再整合あり。P-25 だけが意図的な例外で、理由（再基底化するとローダーが `UNAUTHENTICATED` で落ち進捗表示ごと消える）が JSDoc に残り、完了後のフル遷移（`window.location.assign`）で代替している。
- **ローディングフォールバックの 2 種**: `/settings/{profile,auth,usage}` は loader が `renderServerFragment(...)` の未解決 promise をそのまま転送し、`<Suspense fallback>` + `Deferred` で per-fragment streaming。3 つのスケルトンはいずれも実 DOM のクラス（`panelClass` / `grid-cols-[auto_1fr_auto]` / `h-11` / `h-1.5` / `border-t border-hairline py-5`）を写しており、条件付きで出る要素（ハンドル変更の警告・使用量のアラート）は意図的に置いていない旨がコメントにある。`/settings/danger` は読み出すサーバー状態が無いので loader を持たず、島を直接描く（route-level pending は親 `/settings` の `beforeLoad` が担う）。
- **状態のモデル化**: P-05 / P-04 / P-25 / P-03 / P-02 いずれも `kind` タグ付きの直和で、`DeleteAccountPanel` の `Phase`（idle / accepted / running / completed / settled）と `SaveError` の `target: "handle" | "form"`、`SubmitError` の `target: "field" | "panel"` は「どこに出すか」まで型に入っている。`sessionStorage` の復元は `readStoredTicket` で境界デコードし、`userId` 不一致では復元しない。純関数（`passwordStrength` / `devOAuth` / `oauthStateBinding` / `deletionTicket`）はフレームワーク非依存に切り出され、単体テストを持つ。
- **入力バリデーションの 2 点**: 転送境界は `validateSearch`（`reset-password` / `verify-email` / `auth/callback/$provider` / `dev/oauth/authorize`）と `.validator(validateInput(...))` のみ。`serverData` は `loadIdentities` / `loadProfile` / `loadUsageSnapshot` の 3 本で、いずれも引数はセッションから引いた `userId` だけで外部入力を通していない。業務不変条件（表示名 50 / 自己紹介 500 / ハンドル 3〜30 / 5 MB）は値オブジェクトとドメインポリシー側にあり、転送境界のスキーマは形と DoS 上限（`+1` の余裕、8 MB のアップロード上限）に留めている。
- **`__root.tsx` への副作用 import**: 新設した server function モジュール 5 本（`ResendVerificationForm/action` / `ResetPasswordPanel/action` / `routes/auth/-action` / `routes/dev/-action` / `routes/settings/-action`）がすべて追加済み。`settings/*/action.ts` の 3 本は `serverData` であって server function ではないので追加不要で、正しく除かれている。
- **見送り行の非表示**: `PAGE-p21-004`（公開プロフィール preview）・`PAGE-p24-002`（workspace 行と追加読込）・`PAGE-p25-004`（唯一 owner）のいずれも、対応要素も無効ボタンの placeholder も存在しない。P-20 のタブ列も「連携」を除く 4 タブのみで、無効タブを置いていない（`SettingsTabs`）。`AccountMenu` も設定とサインアウトだけで、未実装画面を並べていない。
- **モックとの照合**: `P21` / `P22` / `P25` の h2 構成（公開プロフィール / 公開ハンドル、有効なログイン方法 / パスワードを変更 / 他の端末からサインアウト、アカウントを削除）と `P24` の見出し無し構成が実装と一致。
- **アクセシビリティ**: 常設 live region（空でも DOM に残し余白だけ条件付き＝`errorTextClass` の `not-empty:mt-2`）、`aria-describedby` によるラベル・エラーの関連付け、`aria-invalid` を項目エラー時だけに限定する分離、アイコンの `aria-hidden`、アイコンのみボタンの `aria-label`、`<dialog>` の `showModal()` によるフォーカストラップと Esc、`aria-current="page"` のタブ、live region の入れ子回避（`ResendVerificationForm` が自前の region を持たない）、毎秒進むカウンターの `aria-hidden` — いずれも規律どおり。ハイドレーション不一致になりうる値（`Date.now()` / `new Date()` / `crypto.randomUUID` / `sessionStorage`）は初回描画に一切現れず、島で日付を描く `IdentityBoard` は `timeZone: "UTC"` 固定で理由もコメントにある。
- **デザイントークン**: 生の色は `spec/design/index.md` §8 が指定するアバターのフォールバックグラデーション（`#c9d3df` → `#8e99a8`）だけで、他はすべて `text-ink-*` / `bg-surface*` / `border-hairline*` / `bg-accent*` / `--bar-bg` / `--list-max` 経由。設定画面の recipe は `panelStyles.ts` の 1 箇所に集約されている。
- **テストによる裏づけ**: `passwordStrength.test.ts` がクライアント側のパスワードゲートをドメインの `PlainPassword` と同値であることまで固定しており（送信を止める条件が UI 独自に厳しくならない）、`oauthStateBindingWiring.test.ts` が「開始で Cookie を焼く / 照合が `state` 消費より前 / 成否によらず Cookie が残らない」の順序を、`deletionTicket.test.ts` が ticket の改竄・鍵違い・版解決・期限境界を固定している。島そのものの振る舞い（楽観的更新の所有権・`router.invalidate()` の呼び出し）は、テスト環境が `environment: "node"` 単一でコンポーネントテスト基盤を持たないため自動テストの対象外で、`spec/manual-tests/account.md` の実行に委ねられている（本 PR の方針として plan.md のテスト方針と整合）。
- **残す必要のない記述**: コード・コメントに指摘への弁明や修正の経緯は見当たらない。コメントはいずれも WHY（束縛 Cookie を置く理由、P-25 が再基底化しない理由、解除を親に置く理由、`hidden` を `sr-only` にしない理由、UTC 固定の理由、`exactOptionalPropertyTypes` 下で明示的に積み直す理由など）に限られている。旧 `ADR 0xx` 表記を `spec/adr/0xx` へ揃える整理も入っている。
