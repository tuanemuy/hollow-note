#### 検証した観点と根拠（指摘なしの裏取り）

- **ドメイン/ユースケースの責務配置**: `UploadValidationPolicy` / `QuotaEnforcement` / `IdentityPolicy` / `AccountDeletionRetryPolicy` / `SameOriginPolicy` はいずれも I/O・設定読み取りを持たない純粋な判断。`uniqueness.ts` は「2 ストアを順序づける手続き」であって業務判断を持たず、application 層に置く判断が JSDoc で明示されている。逆に `StoredFile` の `PersistentProvenance` 除外・`AvatarUrl` / `ObjectKey` / `ByteSize` の brand・`ActivePersonalCleanupComponent` の型導出など、不変条件は型で表現されている。
- **UoW 規律（ネストしない）**: 削除オーケストレーションの全経路（`admission` → `manifestBuild` → `cleanupDispatch` / `globalCleanup` → `authorRedaction` → `finalize` → `compaction` → `terminalPrune`）と `scopeTaskRunner` / `settleCleanupTurn` / `handOverPersonalCleanup` を追跡し、`run` の入れ子は 0 件。トランザクションを共有する必要のある共有手続き（`deleteStoredFiles` / `completePersonalCleanupIfDone`）はいずれも `ctx` を受け取る形で、自分では `run` を開かない。
- **Outbox / 冪等性**: `mintEventIdFor` による `continuationKey` 由来の決定的 EventId と `OutboxRepository.save` の「先着行をそのまま残す no-op」契約が噛み合っている。`finalize` 継続だけは発行元（`uniquenessRelease` / `authResidue` / `redaction`）を `cursor` で名乗り分けており、「最後に receipt を埋めた枝が必ず別 ID の finalize を撃てる」が成立する。`redaction` / `compact` は turn 番号を cursor に持つので自己の ID を再発行して停止する事故がない。`userAuthResidueCleanupContinued` だけ `continuationKey` を持たない（ADR-025）が、処理が「payload の epoch 未満の行の有界削除」で本質的に冪等なため二重チェーンでも収束する。
- **同一 UoW 要件**: `removeIdentity`（行削除 + receipt + event）、`resetPassword` / `changePassword` / `signOutOtherSessions`（identity/user/session + 継続イベント）、`deleteQuota` / `deleteFilesByOwner`（削除 + ack + 次タスク + `markApplied`）、`runAccountDeletionGlobalCleanup`（`uniquenessRelease` receipt + finalize 継続）、`compaction`（`markCompleted` + `markState`）、`terminalPrune`（header + `deleteTerminal`）をいずれも 1 トランザクションで確認。`authResidueCleanup` の receipt と finalize 継続だけは 2 段だが、早期 return を持たないため中断後の再配送が同じ terminal turn に再到達して両方を撃ち直す（JSDoc の主張どおり成立することを追跡確認）。
- **Cross-layer catch policy**: application の `try/catch` は (1) saga の補償解放（`reserveUniqueKeys` / `activateUniqueKeys` / `updateProfile` / `completeOAuthSignIn` / `linkOAuthIdentity`）、(2) `storeAvatar` のオブジェクト巻き戻し、(3) メール送信の best-effort、(4) worker の行単位隔離（`scopeTaskRunner` / `terminalPrune`）に限られており、いずれも明示的境界。`updateProfile` の catch が `OPTIMISTIC_LOCK_FAILURE` のときだけ補償しない条件は、勝者の予約行を消さないための正しい向き。
- **入力バリデーション 2 点**: 転送境界は `routes/*/-action.tsx` の zod スキーマ（`userId` は常に `requireSession()` 由来でクライアント入力を採らない）、業務不変条件は VO 構築（`UserId` / `Handle` / `AvatarUrl` / `PlainPassword` / `Email` / `ObjectKey` …）。`requireRequestId` / `readUniquenessKeys` は「利用者入力の検査」と「壊れた行の検出（`SystemError(DataIntegrityError)`）」を正しく撃ち分けている。
- **削除オーケストレーション**: 受理順（terminal 計数 → operation 決定 → user 遷移 → barrier）が「巻き戻さない」ために load-bearing であること、resume が `beginDeletion` を再実行せず epoch を二重に進めないこと、barrier がコミット後に別トランザクションで張られるため barrier 前の write が scan に拾われること（TC-identity-044/045）を確認。応答喪失からの再開は、イベント再配送（global 平面）と scope task 行（scope 平面）＋ ADR-106 の引き渡し行の 3 系統で覆われており、残る窓は progress.md 記載の 1 点のみ。
- **uniqueness 解放の順序**: `deleteAccount` は admission で payload に鍵を凍結 → cleanup wave で `beginRelease` → `release`（receipt は解放後）→ finalize、`removeIdentity` は receipt 先行 → consumer が `providerAccountKey` で解放、`updateProfile` は 新 key reserve → commit → activate → 旧 key 解放。いずれも「両方の鍵が空く窓」も「両方を持ったまま終わる」も作らない。`releaseActiveUniqueKey` の operationId が全経路で決定的なので、`beginRelease` と `release` のあいだで落ちても再実行が収束する（`updateProfile` の旧ハンドルだけ再駆動主体が無い＝記録済みの縮退）。
- **`authEpoch` バンプ 4 経路**: `resetPassword` / `changePassword` / `signOutOtherSessions` / `deleteAccount(beginDeletion)` の 4 つとも、同一 UoW で `userAuthResidueCleanup{ table: "sessions" }` を積み、掃除側は `deleteOlderEpochByUser(userId, payload.authEpoch, 100)`＋「保存済み epoch と payload epoch の一致」ガードで現世代を消さない。現セッションを残す 2 経路だけが `refreshAuthEpoch` を撃ち、残す必要のない 2 経路は撃たない。`deleting` 到達後は 4 経路すべてが `status !== "active"` で弾かれるため、削除駆動チェーンが `stale` に落ちて finalize が永久待ちになる経路は無い。
- **`DeletingUser` / `DeletedUser` での倒れ方**: `startOAuthFlow`（`UNAUTHENTICATED`）/ `linkOAuthIdentity`（deleted→`USER_NOT_FOUND` / deleting→`ACCOUNT_UNAVAILABLE`）/ `completeOAuthSignIn`（3 分岐すべて最終 UoW で再読して `ACCOUNT_UNAVAILABLE`）/ `requestPasswordReset`・`resendVerificationEmail`（無送信で同一応答）/ `resetPassword`・`changePassword`（`AUTH_TOKEN_NOT_FOUND` / `UNAUTHENTICATED`）/ `addPasswordIdentity`（`ACCOUNT_UNAVAILABLE`）/ `getProfile`・`updateProfile`（`USER_NOT_FOUND` / `ACCOUNT_UNAVAILABLE`）を確認。tombstone は email / handle を持たないので directory 経由の解決が「未登録」に収束する。
- **テストによる担保**: `deletionDriver.ts#runUntilSettled` は本物の relay（`processOutboxEvents` + `dispatchDomainEvent` の実レジストリ）と `runDueScopeTasks` を交互に回し、「動かない round があれば失敗する」形なので、チェーンが切れたら緑にならない。`subscribers.test.ts` が継続 4 種すべてに購読者があることを型と実行の両方で固定し、`scopeTaskRunner.test.ts` が引き渡し喪失からの再駆動を押さえている。上記の観点はいずれも TC ID 付きのテストか、それに相当する固定テストで守られている。
- **不要な記述**: ドメイン / ユースケース層のコメントは、いずれも「なぜこの順序か」「なぜこの分岐が無いか」「冪等性の根拠は何か」の非自明な制約を述べており、レビュー指摘への弁明や修正経緯の記録は見当たらなかった。`verifyEmail.test.ts` の「walking-skeleton glue なので〜」という経緯コメントは本 PR で削除されている。
