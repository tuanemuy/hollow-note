# レビュー 005 — Domain / Use Case

ゼロベース。過去ラウンドの指摘は前提にせず、現在のコードだけを読んで検証した。

### Domain / Use Case

#### Blockers

- **[B-001]** `completeOAuthSignIn` の既存リンク経路が directory の claim だけで判断し、UserId shard の Identity 行を確認しないため、`removeIdentity` 済みの OAuth 手段でサインインできる窓が残る / 場所: `packages/core/src/application/identity/completeOAuthSignIn.ts:107-114`, `packages/core/src/application/identity/completeOAuthSignIn.ts:154-194` / 理由:
  - `spec/usecases/identity.md#completeOAuthSignIn` 手順 3 は「providerAccount directory を解決し、**返った UserId shard で既存 Identity と User を確認する**」と定めるが、`signInLinkedUser` は `ctx.userRepository.findById` しか読まず、`identityRepository` を一切引かない。
  - `removeIdentity`（`packages/core/src/application/identity/removeIdentity.ts:95-115`）は Identity 行を削除するが directory の `active` 行はそのまま残し、解放は `identity.identity.removed` の global consumer（`identityRemovalRelease`）に委ねる非同期処理。したがって「解除は成功応答を返したのに、その Google アカウントでまだサインインできる」状態が必ず一度は発生する。
  - 窓は一時的とは限らない。outbox は失敗回数超過で quarantine される（`application/ports/outboxRepository.ts` の JSDoc / `eventRelayWorker.ts` 冒頭）ので、`identityRemovalRelease` が恒久的に失敗するか consumer が停止したままだと claim は永久に `active` のまま残る。さらに `pruneExpiredAuthState` は `identity_removal_receipts` を 30 日で掃除するので（ADR-075）、30 日経過後に再配送されても `noReceipt` で `keep` に倒れ、**解放は二度と起きない**。spec が手順 4 で「consumer 停止は一時的な過剰予約にだけなる」と書けているのは、まさに手順 3 が Identity 行を確認する前提があるからで、その確認を落としたことで前提が崩れている。
  - `linkOAuthIdentity` 側は同じ状態を `existingLinkId`（`linkOAuthIdentity.ts:183-205`）で検出しているので、実装内でも扱いが非対称。
  - テストでも守られていない。`TC-identity-184`（`application/identity/__tests__/removeIdentity.test.ts:150`）は `drainRemovalEvents` を挟んでから `completeOAuthSignIn` を呼ぶので、解放前の窓を一切踏まない。「解除直後（未 drain）にその provider account でサインインできない」ことを assert したテストは存在しない。
  / 提案: `signInLinkedUser` の最終 UoW（セッションを insert するトランザクション）で `ctx.identityRepository.listByUserId(userId)` を読み、`providerAccountKey(provider, providerAccountId)` が一致する oauth identity が無ければセッションを発行せず拒否する（`ValidationError("OAUTH_STATE_INVALID")` 相当か、`existingLinkId` と同じ「claim はあるが行が無い」扱い）。`identityRemovalRelease` が ADR-104 で `listByUserId` を 1 回追加読みしているのと同じコストで、identity は 8 件上限なので実質定数。回帰は「`removeIdentity` 後、イベントを drain せずに同じ provider account でサインインを試みると拒否される」1 ケースで固定できる。

#### Warnings

- **[W-001]** 同じ窓で本人が再連携すると `PROVIDER_ACCOUNT_ALREADY_LINKED`（画面文言は「別の利用者に紐づいています」）になる / 場所: `packages/core/src/application/identity/linkOAuthIdentity.ts:196-203` / 理由: コメントは「directory と shard の不一致は成功経路では作れない」と述べているが、B-001 と同じ `removeIdentity` → 解放 consumer 未達の窓が**正常系として**これを作る。`errorDisplay.ts:72-73` の写しは「この外部アカウントは別の利用者に紐づいています。別のアカウントでお試しください。」なので、利用者は自分が今解除したアカウントを他人のものだと告げられる。実害は一時的（再試行で解消）だが、B-001 と同根で、コメントの事実認識が誤っている点も含めて同時に直すべき。 / 提案: B-001 の修正に合わせ、この分岐を「解放待ちの claim」として別コード（例: 再試行を促す `ConflictError`）に分けるか、少なくともコメントから「no successful path can produce」の断定を外して発生経路を書く。

- **[W-002]** `authResidueCleanup` の終端ターンが `authResidue` receipt と finalize 継続を別トランザクションで書いており、ADR-069 が `uniquenessRelease` に対して確立した「receipt と finalize 継続を同一 UoW」の規律から外れている / 場所: `packages/core/src/application/identity/authResidueCleanup.ts:85-111` / 理由: `acknowledgeReceipt` はコンテナ直付けのストア経由で**どの UoW にも入らず**呼ばれ、finalize 継続はその後の別 UoW で発行される。JSDoc は「receipt が manifest 側にありこのトランザクションに入らないから」と説明しているが、`GlobalUnitOfWorkContext` は `accountDeletionManifestStore` を持っており（`application/execution/unitOfWork.ts` の差分）、`globalCleanup.ts:88-103` と `finalize.ts:41` は実際に `ctx.accountDeletionManifestStore` を使っている。つまり理由が事実に反し、同一 UoW で書ける。通常は継続イベントの再配送（relay はハンドラー復帰後にのみ processed を立てる）で回復するが、その継続行が quarantine に落ちると「receipt は入っているのに finalize 試行が一度も発行されない」＝削除が `running` のまま駆動主体を失う状態が残せる。ADR-069 が同じ形を避けた理由がそのまま当てはまる。 / 提案: 終端ターンの UoW（`outcome === "finished"` を返すトランザクション）内で `ctx.accountDeletionManifestStore.acknowledgeReceipt(deletionOperationId, "authResidue")` と `ctx.collectEvents([... finalize:authResidue])` をまとめる。`deletionOperationId === null` の経路は従来どおり何もしない。

#### 検証したが問題を認めなかった点（記録）

- **scope→global 引き渡し（`identity.personalCleanupHandoverContinued`）の再駆動**: `scopeTaskRunner.ts:47-74` は barrier を閉じたターンの直後に専用行を arm し、`acknowledgePersonalCleanup` が入ってから `complete` する。ハンドラーは同 kind で登録済み（`scopeTaskRunner.ts:100`）、`schedule` は `(kind, operationId)` upsert（memory 実装で確認）、`acknowledgeReceipt` は冪等、継続イベントは決定的 id で折り畳まれるので、例外でもプロセス断でも次の tick が同じ引き渡しだけを再実行して収束する。`runDueScopeTasks` の catch が backoff するのは元の cleanup 行（既に `complete` 済み＝no-op）なので毒行にはならない。`scopeTaskRunner.test.ts:114` が global UoW を全面的に失敗させる形でこの経路をプロセス再起動込みで固定している。残る穴（barrier commit と arm のあいだの断）は ADR-106 と plan.md の縮退に明記済み。
- **イベント駆動側の引き渡し**: `dispatchAccountDeletionCleanup` は handover 行を積まないが、`cleanup` フェーズの outbox 行が処理完了まで processed にならないため、再配送で `progress.status === "completed"` → 再 ack に収束する（`cleanupDispatch.ts:141-160`）。
- **`identityRemovalRelease` の「解除 → 再連携 → 再配送」**: ADR-104 どおり `listByUserId` で現行 identity が同じ `providerAccountKey` を名乗っていないことを確認してから解放しており（`identityRemovalRelease.ts:48-63`）、判定は直和で返して呼び出し側に再検査の余地が無い。`removeIdentity.test.ts:212` が固定している。`beginRelease` は所有者不一致・`reserved` 行を no-op にするので、他人の claim も進行中の予約も奪えない（memory 実装と port JSDoc の双方で確認）。
- **`authEpoch` バンプ 4 経路と「現世代を消さない」**: `resetPassword` / `changePassword` / `signOutOtherSessions` / `beginDeletion` のいずれも `User.advanceAuthEpoch`（または `beginDeletion`）の直後に同一 UoW で `userAuthResidueCleanup` 継続を積み、consumer は `versioned.entity.authEpoch !== authEpoch` を stale として降り、削除は `authEpoch < currentEpoch` に限定される（memory の `sessionRepository` / `authTokenRepository` 双方で strict less-than を確認）。継続イベントに `continuationKey` が無いので id は毎回採番され、outbox の同一 id 折り畳みで連鎖が止まることも無い（ADR-025 と `execution/eventId.ts` が一致）。
- **`DeletingUser` / `DeletedUser` での倒れ方**: `signInLinkedUser` / `attachToExistingUser` / `linkOAuthIdentity` / `startOAuthFlow`(linkIdentity) / `addPasswordIdentity` / `changePassword` / `signOutOtherSessions` / `resetPassword` / `requestPasswordReset` / `updateProfile` / `getProfile` はいずれも最終 UoW 内で `status !== "active"` を再確認しており、資格発行と削除開始の直列化は保たれている。`resendVerificationEmail` は `pending` 限定で対称。
- **一意性サガ 3 kind**: `reserveUniqueKeys` の部分失敗解放、`activateUniqueKeys` の `confirm` 1 回化、`updateProfile` の OCC 敗北時に補償しない条件（ADR-089）、`globalCleanup` の payload 凍結キーからの解放順序（release → receipt → finalize）はいずれも整合。`releaseActiveUniqueKey` は `expectedUserId` 一致でしか動かないので、削除後に同じメールで再登録された行を巻き込まない。
- **UoW のネスト**: 新規コードに scope UoW と global UoW を入れ子にする箇所は無い（`authorRedaction` / `scopeTaskRunner` / `cleanupDispatch` はいずれも一方が閉じてから他方を開く）。
- **入力バリデーション 2 点**: `requireRequestId` の UUID 検査、`readUniquenessKeys` の payload 整合検査（破損は `SystemError(DataIntegrityError)`）、VO 構築（`Handle` / `AvatarUrl` / `PlainPassword` / `Email`）はいずれも境界に置かれている。`SameOriginPolicy` が `//` / `\` / C0 制御文字を弾き、`redirectTo` と `AvatarUrl` の両方が同じ述語を通る。
- **Cross-layer catch policy**: 新規コードの `try/catch` は (a) 外部ポート境界（`mailSender`・`objectStorage` のロールバック）、(b) サガ補償、(c) worker の行単位耐性、(d) `resetPassword` の `AUTH_TOKEN_ALREADY_CONSUMED` → `AUTH_TOKEN_NOT_FOUND` 変換（同一 usecase 内の意図的な収斂）に限られる。`changePassword` が旧パスワードの `BusinessRuleError` を `INVALID_CREDENTIALS` に畳むのはドメインエラーの再変換にあたるが、旧値の強度をオラクルにしないための意図的な措置で JSDoc に理由がある。
- **コード内の弁明・経緯コメント**: `grep` で `TODO` / `FIXME` / 「レビュー」「指摘」「以前は」等を全走査したが、レビュー由来の経緯を残す記述は無かった。
