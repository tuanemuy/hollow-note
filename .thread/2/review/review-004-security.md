#### Warnings

- **[W-001]** OAuth の束縛 Cookie の値が `state` から誰でも導出できるので、束縛は「開始したブラウザーへの束縛」ではなく「login CSRF の一方向の防止」までしか成り立たない / 場所: `apps/web/app/presentation/oauthStateBinding.ts:24-29`（`deriveOAuthStateBinding` = `sha256(state)`）、`apps/web/app/presentation/oauthStateCookie.ts:29` / 理由: Cookie の中身が `sha256(state)` で、`state` は認可 URL とコールバック URL のクエリーに載って往復する。したがって **`state` を知る者は Cookie 値をそのまま計算できる**。攻撃者が被害者のコールバック URL（`?state=…&code=…`）を消費前に入手できた場合（同一 PC の別利用者、履歴同期、社内プロキシー・スクリーン共有・貼り付けミス等。同一オリジンなので `Referer` 経由の外部漏洩は `Referrer-Policy` が塞いでいる）、攻撃者は**自分のブラウザーに `hollow_oauth_state=sha256(state)` を自分で置くだけ**で照合を通し、被害者のアカウントとしてサインインを完了できる。単回消費・10 分・PKCE はいずれもこの経路を止めない（`code_verifier` はサーバー側の `OAuthFlowState` にあり、攻撃者は要求を出すだけでよい）。実際に成立させるには消費前の URL 入手が要るため到達性は低く Blocker にはしないが、コード側の JSDoc（「フローを開始したブラウザーに束縛する」）はこの一方向性より強い性質を主張しているので、記述と実体が食い違っている点も含めて残す / 提案: Cookie に入れる値を `state` と独立な乱数（`secureTokenGenerator.issue()`）にし、その digest を `OAuthStateStore` の `OAuthFlowState` に 1 フィールド足して保持する。照合は `sha256(cookie) === flow.stateBindingHash`。ストアは既にあるので追加コストは 1 フィールドで、これなら `state` を握った第三者では Cookie を再現できず、双方向の束縛になる。

- **[W-002]** ドメインイベントの payload 全体が production の worker で無条件に info ログへ出る / 場所: `apps/web/app/worker/node/runner.ts:99`（`container.logger.info("[queue] received …", { event })`） / 理由: `{ event }` は payload ごと出るので、`identity.user.profileUpdated` の `displayName`、`identity.user.handleChanged` の `previousHandle` / `currentHandle`、`identity.identity.removed` の `providerAccountKey`（= `google:<Google の sub>`、第三者 IdP における安定識別子）が全配送でログに残る。`server.node.ts` の worker runner は `pnpm start` でも同じ経路なので dev 限定ではなく、CLAUDE.md / `docs/runtime_node.md` の「秘密は `MEMORY_MAIL_LOG_ACTION_URL` を立てたときだけ」という整理からも外れる。トークン・パスワードは含まれないので Blocker ではないが、ログ転送先が増えるほど PII の面が広がる / 提案: `{ eventId: event.id, eventType: event.type, aggregateId: event.aggregateId }` だけにする（同ファイル群の `subscribers.ts:190` が既にこの形）。payload まで要る場面は debug レベルに落とす。

#### 確認した観点と結論（Blocker なしの根拠）

- **認証・認可**: server function で `userId` を要求本文から受ける入口は 1 つも無い（`routes/settings/-action.tsx` / `routes/auth/-action.tsx` / `components/*/action.ts` を全数確認）。主体はすべて `requireSession()` 由来。`renderIdentityList` / `renderProfileForm` / `renderUsagePanel` も `requireSession()` を通してから `serverData` に渡している。`removeIdentity` は UoW 内の `listByUserId(userId)` で所有権を確定し、他人の / 不在の ID を同じ `IDENTITY_NOT_FOUND` に畳む。`getAccountDeletionStatusFn` だけがセッション不要だが、`operationId` は**検証済み ticket からしか取らず**、要求本文の値は使わない（TC-identity-048 の性質が成立）。
- **`assertWritable` / `assertActorWritable`**: 通常 write 入口 3 本（`createBlankNote` / `storeAvatar` / `recalculateStorageUsage`）がいずれも 2 本とも呼んでいる（全数 grep 済み）。cleanup 経路（`deleteFilesByOwner` / `deleteQuota`）は代わりに `assertOwner(deletionOperationId)` を通す。`recalculateStorageUsage` は `subjectType === "user"` で actor と subject の一致を検査。
- **列挙耐性**: `resendVerificationEmail` / `requestPasswordReset` はいずれも全分岐で同一の空応答（`UNIFORM_RESPONSE`）、view 型も `Record<string, never>`。`signOut` は不在・不正トークンでも成功。`/storage/$` は形式違反も不在も同じ 404。応答時間の非等時性は plan.md の縮退（#18）どおりなので触れない。
- **トークン**: リセット / 確認トークンはハッシュで保存し、`locateUser` → `findByTokenHash` → purpose / status / `authEpoch` / user status の 4 条件をすべて `AUTH_TOKEN_NOT_FOUND` に畳む。単回消費は UoW 内の条件付き更新（`authTokenRepository.save(consumed)`）が担い、並行消費の敗者は `AUTH_TOKEN_ALREADY_CONSUMED` → `AUTH_TOKEN_NOT_FOUND`。`AuthToken.consume` の期限判定はトランザクション前で、以降の失敗では pending のまま残る。
- **セッション**: `HttpOnly` / `SameSite=Lax` / `Path=/`、`Domain` なし、`Expires` は `Session.ttlMs` 由来。`secure` は `NODE_ENV === "production"` で、**production ビルドでは vite が `isProduction = () => true` に畳み込む**ことを実際のビルド成果物（`dist/server/rsc/assets/session-CUwNhnv4.js:25`）で確認した。一括失効は `authEpoch` バンプで O(1)、現セッションだけ `refreshAuthEpoch` で追随。`signOutFn` / `deleteAccountFn` / `resetPasswordFn` はいずれも応答で Cookie を破棄する。
- **OAuth**: `state` は `secureTokenGenerator.issue()` の単回消費（`take` = atomic get+delete）、分岐根拠は `OAuthFlowState.intent` のみでクエリーもセッションも見ない。`:provider` は保存値との照合にのみ使用。intent は転送境界で入口を分けてクライアントに選ばせない（`startOAuthSignInFn` は `signIn` 固定、`startOAuthLinkFn` は `linkIdentity` 固定 + `redirectTo` もサーバー固定）。`linkIdentity` は `userAuthEpoch` を UoW 内で再照合するので世代失効後の紐づけは通らない。PKCE は両アダプター共通の `deriveCodeChallengeS256`（`base64url(sha256)`、`code_challenge_method=S256`）。`redirectTo` は `SameOriginPolicy.isSameOriginPath`（`//`・`\`・C0/DEL を排除）を通り、復帰は `router.history.push` のパス遷移。`email_verified` は `AccountLinkingPolicy.decide` の第一条件で、偽なら既存利用者の状態によらず拒否。`id_token` は `iss` / `aud` / `exp` / `sub` / `email` を検証（署名の非検証は OIDC Core §3.1.3.7 の許容範囲で、TLS 直受け + PKCE + client_secret が前提として揃っている）。束縛 Cookie の生成・照合・破棄の 3 経路は `oauthStateBindingWiring.test.ts` が実 `Set-Cookie` / `Cookie` ヘッダーで固定しており、照合が `take` より前であること・照合を通れば成否によらず破棄されること・消費されない往復では `abandonOAuthFlowFn` が破棄することまで検証されている（残る弱点は W-001）。`OAuthProvider.create` は `"google"` 固定のホワイトリスト。
- **dev IdP の production 遮断（実機確認済み）**: `pnpm build` 後に
  - `OAUTH_DEV_MODE=true pnpm start` → `ZodError: OAUTH_DEV_MODE=true cannot be combined with NODE_ENV=production` で起動失敗（`readNodeServerEnv` at `dist/server/server.node.js`）。
  - `GOOGLE_OAUTH_*` 指定で起動 → `GET /dev/oauth/authorize?...` が **404**。
  - 併せて応答ヘッダーに `X-Content-Type-Options` / `Referrer-Policy` / `Cache-Control: private, no-store` / CSP（`frame-ancestors` / `form-action` / `object-src` / `base-uri`）が乗ることを確認。
  - `scripts/listen.node.ts:20` の `process.env.NODE_ENV ??= "production"` が dotenv より前にあるので、`.env` からの降格もできない（実際に手元の `.env` の `OAUTH_DEV_MODE=true` が拒否されるところまで観測した）。`submitDevConsentFn` 自身も `container.oauthDevMode` を再確認するので、ルート 404 を迂回しても通らない。
- **削除 status ticket**: HMAC-SHA-256 / 鍵は composition root 供給（`RequestContainer.deletionTicketKeyRing`、既定は `randomBytes(32)` のプロセス毎鍵、`DELETION_TICKET_KEY` は 32 バイト検証つきで不正なら起動失敗）。版を平文前置 → 鍵解決 → `crypto.subtle.verify`（定数時間）→ **署名検証の後で**期限判定、という順序。中身は `operationId` と期限だけで権限を広げる材料が無く、`getAccountDeletionStatus` は `findByOperationId` の読み取りビュー（`Pick`）経由で列挙も走査も持たない。`sessionStorage` の退避は保存時の `userId` を併せ持ち、別利用者がサインイン中は復元しない。`deletionTicket.test.ts` が改竄・別鍵・未知版・非 ticket・期限境界を固定している。
- **アップロード / 配信**: MIME もサイズも**実バイトから**決める（`identifyContentType` のマジックバイト + `body.byteLength`）。宣言値は記録に使わない。転送境界は形と DoS 上限（8 MB）だけで、業務上限 5 MB はドメイン。プロセス全体の本文上限 12 MB は `listen.node.ts` が `Content-Length` / チャンク長で 413 に落とす。`ObjectKey.create` は `..` と先頭 `/` を拒否、`purposeOf` は 4 セグメント形以外を `null` にし、`/storage/$` は `avatar` 以外を 404。配信は `nosniff` + `Content-Security-Policy: sandbox; default-src 'none'` + `Cache-Control: private` + `Content-Disposition` のファイル名サニタイズつき。memory アダプターは Map の完全一致引きなのでトラバーサル自体が成立しない。
- **入力バリデーション / CSRF**: 検証点は転送境界（zod、形と上限のみ）と値オブジェクトの 2 点に収まっている。`start.ts` の `createCsrfMiddleware({ filter: ctx => ctx.handlerType === "serverFn" })` はビルド成果物に含まれ（`dist/server/assets/createCsrfMiddleware-*.js`）、`handlerType: "serverFn"` がフレームワーク側で実際に立つことも成果物で確認した。フレームワーク実装は `Sec-Fetch-Site` → `Origin` → `Referer` の順で、3 つとも無い要求は `allowRequestsWithoutOriginCheck` 未指定なので **403 に倒れる**（fail-closed）。
- **暗号 / 乱数**: 鍵・トークンはすべて `node:crypto` の `randomBytes` / `SecureTokenGenerator` 由来。クライアント側の `requestId` も `crypto.randomUUID`、非セキュアコンテキストでは `crypto.getRandomValues` で v4 を組む（`Math.random` の混入なし）。パスワードは scrypt ハッシャー、比較は `PasswordHasher.verify`。`changePassword` は不正形式の現行パスワードを `WeakPassword` ではなく `INVALID_CREDENTIALS` に畳む。
- **一意性ディレクトリの解放**: `beginRelease` は `expectedUserId` 不一致・`reserved` 行を no-op にするので、他人の鍵を奪う経路が無い（memory 実装で確認）。`release(operationId)` が消すのは `reserved` / `releasing` のみ。operationId はすべてサーバー側の決定的合成で、利用者入力が混じる `handle` も `[a-z0-9_-]{3,30}` に制限されており既存 ID と衝突しない。
- **ログ**: パスワード・トークン・メールアドレスをログへ出す箇所は無い（`logger.*` 全数確認）。`serverErrorLog` は `kind === "system" | "unknown"` のときだけ発火し、クライアントへは `redactForClient` 後のみ返す。`uniqueness.ts` のログは `parentOperationId` と `kind` に絞られていて `normalizedKey`（メール / ハンドル）を出さない。残る PII 面は W-002 のみ。
- **テストによる担保**: 束縛 Cookie（純関数 4 + 配線 4）、ticket（6）、dev IdP のリダイレクト（4、外部オリジン・非 URL の拒否を含む）、`deriveCodeChallenge` の S256 契約（資格情報なしで両アダプター実行）が揃っており、本レビューで確認した挙動のうち回帰しうるものはテストが押さえている。
- **弁明・経緯の残置**: コード・コメントに「レビュー指摘への対応」「R1 で〜」のような経緯記述は見つからなかった（コメントはいずれも WHY として成立している）。
