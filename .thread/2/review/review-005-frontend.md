#### Warnings

- **[W-001]** パスワード追加ダイアログで「もう一度入力」が空のままでも送信できる / 場所: `apps/web/app/components/settings/AddPasswordForm/index.tsx:66,85,142` / 理由: `mismatch = confirmation.length > 0 && confirmation !== password` なので確認欄が空のときは `mismatch === false` になり、送信ボタンの `disabled` 条件（`isPending || password.length === 0 || mismatch`）を通る。`<form noValidate>` を付けているため入力欄の `required` も効かない。結果、二重入力によるタイプミス検出が実質無効化され、打ち間違えたパスワードがそのまま `addPasswordIdentity` に渡る。P-22 は「別の方法を追加してから解除」を前提にした画面なので、使えないパスワードを追加した利用者が Google を解除して締め出される経路が生まれる。同じ画面の `ChangePasswordForm`（`confirmation !== password` で無効化）・`ResetPasswordPanel` の `ResetMode`（同じ条件）とも挙動が食い違う / 提案: 送信条件を他の 2 フォームと揃えて `confirmation !== password` を無効化条件にする。
- **[W-002]** P-21 で表示名を空にして保存すると、どの欄の問題か分からない汎用文言しか出ない / 場所: `apps/web/app/components/settings/ProfileForm/editor.tsx:321-329,498-511` / 理由: 表示名の入力欄はクライアント側の検証を持たず（`maxLength` のみ）、`save` は常に `String(formData.get("displayName") ?? "")` を送る。`DisplayName.create` は空文字を `IDENTITY_INVALID_DISPLAY_NAME` で弾く（`packages/core/src/domain/identity/valueObject.ts:123`）が、このコードは `errorDisplay` の辞書に無いため `MESSAGE_BY_KIND.business` の「入力内容を確認してもう一度お試しください。」に落ちる。さらに `saveErrorFor` は `HANDLE_ERROR_CODES` 以外を `target: "form"` に倒すので、文言は下部バーに出るだけで表示名の欄には `aria-invalid` も欄内エラーも付かない。欄を空にして保存するだけで到達する経路であり、P-21 の状態一覧が求める「どの項目の問題か」が伝わらない。同種の検証は `SignUpForm` が `displayNameError` として既に持っている / 提案: `IDENTITY_INVALID_DISPLAY_NAME` を辞書に追加し、あわせて `SignUpForm` と同じ欄内検証（または `saveErrorFor` の欄割り当て）を表示名にも付ける。
- **[W-003]** P-25 の「受理しました / サインアウトしました」がスクリーンリーダーに読み上げられない / 場所: `apps/web/app/components/settings/DeleteAccountPanel/index.tsx:268-275,396-410` / 理由: `phase !== "idle"` になった瞬間にフォーム側の常設 live region（`role="status"` の 2 つの `<p>`）ごと `<section>` が差し替わり、進捗側の `Alert role="status"` と `<p aria-live="polite">` は**新規マウント**として現れる。live region は内容が入る前から DOM に在ることが読み上げの条件で、この規律は同じ PR 内の `SignInForm`（`alertRef` の常設 `role="status"` に「Inserting a live region together with its text is not announced」というコメント付き）と `ResetPasswordPanel` の `Result`（焦点移動で補う）が明示的に守っている。P-25 だけがどちらの手当ても持たないため、アプリ中で最も後戻りできない操作の「受理された・サインアウトされた」が支援技術に伝わらない / 提案: 常設の `role="status"` ラッパーをフォームと進捗の外側に置いて中身だけ差し替えるか、`ResetPasswordPanel.Result` と同じく完了パネルへ焦点を移す。
