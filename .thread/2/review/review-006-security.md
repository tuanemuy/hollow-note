#### 確認したが問題なしと判断した点

- **主体の決定**: `/settings/*` の server function 11 本と `auth/-action.tsx` の 3 本は、すべて `requireSession()` が返す `userId` だけを使い、要求本文から `userId` / `subjectId` を取らない（`uploadAvatarFn` は `subjectId: user.userId` を固定、`storeAvatar` 側も `input.subjectId !== userId` を `InsufficientRole` で弾く）。クライアント島（`IdentityList/board.tsx`, `ProfileForm/editor.tsx`, `ChangePasswordForm`, `AddPasswordForm`）も userId を送っていない。`changePassword` / `signOutOtherSessions` はセッショントークンを Cookie から読み、クライアントに往復させない。
- **`assertWritable` / `assertActorWritable`**: `storeAvatar` は scope UoW の先頭で 2 本とも呼ぶ。削除継続側は `assertOwner(deletionOperationId)`。
- **今ラウンドの変更（解除済み OAuth 手段でのサインイン）**: `completeOAuthSignIn.signInLinkedUser` が最終 UoW 内で `identityRepository.listByUserId` を読み、`providerAccountKey` を名乗る identity が残っていなければ `PROVIDER_ACCOUNT_RELEASE_PENDING` で **セッションを作らずに** 落ちる。`removeIdentity.test.ts`「refuses to sign in with the provider account of a removed identity before the release lands」がセッション行数の不変まで検証しており、実効的に塞がっている。`linkOAuthIdentity.existingLinkId` も同じ判定で冪等経路を塞ぐ。
- **`PROVIDER_ACCOUNT_RELEASE_PENDING` の情報漏洩**: この応答に到達できるのは当該 provider account の認可を通過した本人だけで、`PROVIDER_ACCOUNT_ALREADY_LINKED`（他人所有）とは到達条件が排他。文言（`errorDisplay.ts`）も「解除処理が進行中」までで、所有者・メールアドレス・アカウント有無を出さない。
- **列挙耐性**: `resendVerificationEmail` / `requestPasswordReset` はどの分岐でも `Readonly<Record<string, never>>` を返し、view 型自体が空。`AccountLinkingPolicy` は `providerEmailUnverified` を最優先で返すので、`EXISTING_ACCOUNT_UNVERIFIED` / `ACCOUNT_UNAVAILABLE` は「そのメールアドレスの管理権をプロバイダーで証明した相手」にしか出ない。`removeIdentity` は他人の identityId を `IDENTITY_NOT_FOUND` に畳み、receipt 経路も `receipt.userId === userId` を要求する。
- **ログ**: 新規の 40 箇所すべてが `{ cause, parentOperationId, kind, operationId, userId, eventId }` の識別子止まりで、生キー（メール / ハンドル / providerAccountId）を含む `reservationOperationId` はモジュール外へ出ていない（`uniqueness.ts` の JSDoc どおり）。`runner.ts` の per-event ログも識別子のみ。`toSerialized()` は `cause` を載せないので、Google トークンエンドポイントの応答本文（`invalidCode(detail)` の cause）はクライアントに出ない。
- **トークン**: reset / verification は `hashOf` で保存、`AuthToken.consume` の条件付き更新が単回消費、purpose・`authEpoch`・`status` を全経路で照合し、失敗はすべて `AUTH_TOKEN_NOT_FOUND` に畳む。`resetPassword` はトークン検証を通ってから scrypt を回すので、未認証の計算量増幅にならない。
- **セッション**: `HttpOnly` / `SameSite=Lax` / `Path=/` / `Secure`（production ビルドではビルド時に固定）/ `Expires` = 行の期限。一括失効は `authEpoch` バンプで O(1)、現端末だけ `refreshAuthEpoch`。`deleteAccount` は同じ応答で `clearSessionCookie()`。`requireSession()` は無効 Cookie を消さない（GET を状態変更にしない）。
- **OAuth**: `state` は `oauthStateStore.take` の atomic get+delete で単回、`provider` はパスと突き合わせ、intent は state 行だけが決める（クエリーもセッションも根拠にしない）。転送境界で intent をクライアントに選ばせず、サインイン用と連携用で入口を分けている。PKCE は両アダプター共通の S256 純関数で、認可 URL に `code_challenge_method=S256`。`redirectTo` は `SameOriginPolicy.isSameOriginPath`（`//`・`\`・C0 制御文字を拒否）、dev の `redirect_uri` は `resolveDevRedirectUri` でオリジン一致必須。`id_token` は `iss` / `aud` / `exp` / `sub` / `email` を検証（署名検証の省略は OIDC Core §3.1.3.7 の直接受領ケースで、根拠が JSDoc に明記）。`email_verified` は `=== true` の厳密判定。束縛 Cookie の照合は `take` より前で、成否によらず破棄される（`oauthStateBindingWiring.test.ts` が順序ごと固定）。
- **削除 status ticket**: HMAC-SHA-256 / 鍵は composition root 供給（`DELETION_TICKET_KEY` が壊れていれば起動失敗、未設定はプロセス毎乱数）/ 版は平文先頭で鍵選択のみ / 期限は**署名検証の後**にだけ見る / `operationId` は検証済み claims からしか取らず要求本文を信じない（`getAccountDeletionStatus` も 1 件参照のみで列挙経路なし）/ `crypto.subtle.verify` なので比較は定数時間。`sessionStorage` 退避は `userId` を添えて別利用者への復元を防いでいる。
- **アップロード / 配信**: MIME もサイズもマジックバイトと `byteLength` から測り、宣言を信じない（`UploadValidationPolicy`）。転送境界 8 MB → ドメイン 5 MB、リスナー側は 12 MB で `Content-Length` と chunked の両方を 413 に落とす。`ObjectKey.create` は `..` と先頭 `/` を拒否、配信ルートは `purposeOf(key) !== "avatar"` を 404 に畳み、形式違反も 404 に統一。`Content-Disposition` の filename はサニタイズ済み、`nosniff` + `Content-Security-Policy: sandbox; default-src 'none'` + `Cache-Control: private`。`withSecurityHeaders` は既存ヘッダーを上書きしないのでこの CSP が残る。
- **CSRF**: `start.ts` が `createCsrfMiddleware` を明示的に再登録している。production ビルドに対して `Origin: https://evil.example` + `Sec-Fetch-Site: cross-site` の `application/x-www-form-urlencoded` POST を投げて **403** を確認した。`signOutFn` も POST 限定。
- **入力バリデーション 2 点 / DoS 上限**: 転送境界は形と長さだけ（`PASSWORD_MAX_LENGTH` / 2048 / 512 / 4096 / 254 …）で業務不変条件を二重化していない。`requestId` の UUID 判定は usecase 側 1 箇所。
- **`AvatarUrl`**: `javascript:` / `data:` / `//evil` / `\` / 制御文字はすべて拒否され、同一オリジンのパスか絶対 URL のみ通る。
- **経緯コメントの残存**: `grep` で「レビュー」「指摘」「R1〜R5」「previously/used to」を走査したが、修正の経緯・弁明を残す記述は実装コードに無い。
