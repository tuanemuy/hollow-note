#### 確認した主な性質

- **主体はすべて Cookie セッション**。`/settings/*` の server function は 1 本も `userId` を要求本文で受けず、`requireSession()` の戻り値だけを使う（`apps/web/app/routes/settings/-action.tsx`）。`serverData`（`loadIdentities` / `loadProfile` / `loadUsageSnapshot`）は `createServerFn` ではない素の関数なので RPC として外から呼べない。要求本文で `userId` を渡せる経路は存在しない。
- **`assertWritable` / `assertActorWritable`** は scope の通常 write 入口 3 本（`createBlankNote` / `storeAvatar` / `recalculateStorageUsage`）すべてで対になって呼ばれている。global 平面の `updateProfile` / `addPasswordIdentity` / `changePassword` / `linkOAuthIdentity` は UoW 内で `status === "active"` を再読して `deleting` を弾く。
- **失効の実効性**: `authenticateSession` が `session.authEpoch !== user.authEpoch` と `status !== "active"` の両方で `UNAUTHENTICATED` に倒すので、`resetPassword` / `changePassword` / `signOutOtherSessions` / `deleteAccount` の epoch バンプは即座に効く。`authResidueCleanup` は `deleteOlderEpochByUser` で現世代を消さない。
- **列挙耐性**: `resendVerificationEmail` / `requestPasswordReset` は全分岐で同一の空応答、view 型自体が `Record<string, never>`。確認待ち Cookie は成否によらず常に焼く。エラー文言は `errorDisplay` の code/kind 辞書からのみ引き、`SerializedError.message` を画面に出さない。`system` / `unknown` は `redactForClient` で code / message ごと落ちる。
- **ログ**: 秘密・PII の出力は見当たらない。`reservationOperationId` は生キー（メール / ハンドル）を含むが、ログには `{ parentOperationId, kind }` しか出さない規律が守られている（`uniqueness.ts`）。`finalize` が出す `receipts` は enum 名のみ。メールの action URL は `MEMORY_MAIL_LOG_ACTION_URL` を明示したときだけ。
- **トークン**: `SecureTokenGenerator` は 256bit CSPRNG + SHA-256 保存で、locator だけでは認証できない。`verifyEmail` / `resetPassword` は purpose・status・`authEpoch`・user status をすべて照合し、消費は条件付き更新（負けた側は `AUTH_TOKEN_NOT_FOUND`）。
- **セッション Cookie**: `HttpOnly` / `SameSite=Lax` / `Path=/`、dev の平文 http を除いて `Secure`、`Expires` は行の期限と同期。`clearSessionCookie` は削除受理・パスワード再設定・サインアウトの各応答で焼かれる。認証状態を変える経路はすべて POST（GET の server function は 8 本すべて読み取り専用）。
- **OAuth**: `state` は 256bit 乱数で `take` が単回消費（memory は同期 get+delete）。分岐根拠は `OAuthFlowState.intent` だけで、intent は転送境界で `signIn` / `linkIdentity` に固定され、クライアントが選べない。束縛 Cookie の照合はユースケース呼び出しより**前**（`completeOAuthCallbackFn`）で、通過後は成否によらず破棄。`redirectTo` は `SameOriginPolicy.isSameOriginPath`（`//`・`\`・C0/DEL を排除）で検査し、コールバック画面は `router.history.push` にその検査済み値しか渡さない。PKCE は両アダプター共通の S256 純関数で、認可 URL に `code_challenge_method=S256` が載る。Google の `id_token` は `iss` / `aud` / `exp` / `sub` / `email` を検証し（署名検証の省略は OIDC Core §3.1.3.7 の条件を満たす直接受領）、`email_verified` は `AccountLinkingPolicy` が自動リンクの条件として使う。プロバイダーの `picture` は保存されない（`AvatarUrl` の同一オリジン検査を迂回する経路が無い）。
- **dev IdP**: 判定は `RequestContainer.oauthDevMode` の 1 箇所で、ルート（404）と `submitDevConsentFn`（`NotFoundError`）の二重。`resolveDevRedirectUri` が `redirect_uri` を自オリジンに限定するのでオープンリダイレクトにならない。起動ガードは上表のとおり実測で allowlist として機能する。
- **削除 status ticket**: HMAC-SHA256 / 鍵は composition root 供給（`process.env` をこの層が読まない）/ 版は平文前置で鍵解決のみに使用 / 期限は**署名検証を通った後**にだけ見る / claims は `operationId` と期限だけ。`getDeletionStatusFn` は要求本文の `operationId` を一切見ず、検証済み ticket の値だけを `getAccountDeletionStatus` に渡す（TC-identity-048）。`sessionStorage` 退避は主体（`userId`）付きで、別利用者がサインインしている場合は復元しない。
- **アップロード**: MIME はマジックバイト、サイズは実バイト長で判定（宣言値を信じない）。転送境界 8MB → ドメイン 5MB の二段で、理由づけはドメイン側に残る。本文サイズ上限 12MB は `listen.node.ts` が `Content-Length` / chunked の両方で切る。配信は `purpose === "avatar"` に限定し、`nosniff` + `CSP: sandbox; default-src 'none'` + `Cache-Control: private` + サニタイズ済みファイル名。
- **CSRF**: `start.ts` が `createCsrfMiddleware` を明示再登録しており、`FormData` を受ける `uploadAvatarFn` もその後段。
- **テスト**: 上記のうち security 上の要（束縛 Cookie の配線順序 / ticket の偽造・改竄・期限・鍵版 / dev IdP の env allowlist と 404 ガード / dev redirect_uri のオリジン検査）はいずれも専用テストで固定されている（`oauthStateBindingWiring.test.ts` / `deletionTicket.test.ts` / `serverNode.test.ts` / `devOAuth.test.ts`）。
- **弁明・経緯コメント**: コード中に修正履歴・レビュー言及・TODO / FIXME の残骸は見当たらなかった。
