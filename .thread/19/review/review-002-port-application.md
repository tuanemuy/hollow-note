# Port Contract & Application

## Blockers

- **[B-001]** `claimDue` の相互排除（同時 claim が同じ行を二重に配らないこと）がポート契約のどこにも要求されていない
  - 場所: `packages/core/src/application/ports/scopeTaskScheduler.ts:59-63`（および `packages/core/src/application/ports/scopeTaskQueue.ts:16-18`）
  - 理由: 本 Issue の目的は「#11 が D1 / DO を書く前提となる契約を確定させる」であり、AC-15 は縮退記述「`claimDue` は scope オブジェクトが single writer である前提にのみ依存して…」を消すことを求めている。実際その文は消え、代わりに「Claiming takes a lease **rather than trusting a scope to have a single writer**」が入った。ところが**リースが排他を与えるための条件 — 候補の読み取りと `running` への遷移が行単位で原子的であること — は一文も書かれていない**。書かれているのは結果側（"no reader sees that row again until the deadline is reached"）だけで、これは「claim 後の読み手」に対する規定であり、`claimDue` が**同時に 2 本走ったとき**にどちらか一方しか行を得ないことを要求していない。D1 は対話型トランザクションを持たないので、`SELECT` した候補を後から `UPDATE ... SET status='running'` する素朴な実装が自然に書け、それは JSDoc のどの文にも違反しない。ADR-005 が「リース超過時に B が武装し直した行を A が settle する → アカウントが恒久的に `deleting`」という実害を積み上げているのは、そもそも「claim は 1 人しか勝たない」が成り立っている前提の上である。前提そのものが契約に無い。
    さらに `scopeTaskQueue.ts:18` は今も「the serialization rule (claim inside the scope transaction) is **unchanged**」と、その "serialization rule" を定義していた `scopeTaskScheduler.ts` の文が削除された後も参照し続けている。2 つのポート JSDoc が、どこにも書かれていない規則を指している状態。ADR 026 §1（「インターフェースと JSDoc だけを読んで実装者が必要な振る舞いに到達できること。liveness に関わる状態遷移はポート定義に書く」）に正面から反する。適合スイートは単一スレッドなのでここを拘束できないので、JSDoc が唯一の正本になる。
  - 提案: `claimDue` の段落に排他の要求を 1〜2 文で明記する。例:「`claimDue` は候補の選択と `running` への遷移を行単位で原子的に行わなければならない — 同時に走る 2 つの `claimDue` が同じ行を返してはならない。参照ランタイムは scope の unit of work がこれを与える。対話型トランザクションを持たないバックエンドは条件付き更新（`WHERE status='pending' AND due_at <= ?` / `WHERE status='running' AND lease_expires_at <= ?`）で同じ保証を作ること。」あわせて `scopeTaskQueue.ts:18` の「the serialization rule … is unchanged」を、`ScopeTaskScheduler` の当該規定への参照へ書き換える（`unchanged` は #2 時点の文への参照なので、指し先が消えた今は宙に浮いている）。

## Warnings

- **[W-001]** `backoffOrSchedule` が既存行の `payload` をどう扱うかが、遷移表にも散文にも適合スイートにも無い
  - 場所: `packages/core/src/application/ports/scopeTaskScheduler.ts:92`, `packages/core/src/adapters/conformance/scopeTaskScheduler.ts:379-408`
  - 理由: `backoffOrSchedule` は `priority` と `payload` を両方入力に取る。遷移表は priority について「mints the row with `input.priority` … An **existing** row keeps its `priority`」と非対称性まで明記したのに、`payload` については一言も無い。memory 実装（`adapters/memory/repositories/scopeTaskScheduler.ts:111-120`）は `table.get(key) ?? {…}` なので**既存行があれば `input.payload` を捨てて既存の payload を保つ**。これは観測可能な振る舞いで、別バックエンドが `input.payload` で上書きしても JSDoc にも適合スイートにも違反しない。ADR 026「契約的な振る舞いを足すならポート JSDoc とスイートの両方を触る」の基準では、priority と同格の入力である payload だけが片方も拘束されていないのは穴。現在の 1 呼び出し側（`deleteFilesByOwner`）は毎回同じ payload を渡すので今日の実害は無いが、#11 が読む契約としては未定義のまま残る。
    同じ欠落は遷移表の `claimDue` 行（"`dueAt`, `attempt` and `priority` unchanged" と列挙して `payload` を落としている）にもある。適合スイートの reclaim ケース（`:341`）は payload 保存を assert しているので、スイートのほうが契約より強い状態になっている。
  - 提案: 遷移表の `backoffOrSchedule` セルに「既存行は `priority` と `payload` を保ち、`input.payload` は mint 時のみ使う」を足し、`claimDue` セルの「unchanged」列挙に `payload` を加える。適合スイートには「既存行を別 payload で `backoffOrSchedule` しても claim が返す payload が変わらない」を 1 ケース足す（既存の `keeps the priority of an existing row …` に assert を 1 行足すだけで済む）。

- **[W-002]** `leaseMs` の選び方が、本 PR が `spec/platform` に書いた選定規則の**下限側しか**契約に入っていない。既定値 5 分は上限側の規則に反している
  - 場所: `packages/core/src/application/ports/scopeTaskScheduler.ts:43-44,122-132`, `apps/web/.env.example:78-81`
  - 理由: 本 PR は `spec/platform/index.md:186` に「リース期間は…**最悪ケースの turn 所要時間**（これを下回るとturn中に別writerが同じ行を掴む）と **priority 0 の age SLO**（これを上回るとクラッシュ1回の回収がSLO違反を含む）の**両方**を見て選ぶ」を追加した。ところがポート JSDoc は下限だけ（"must exceed the worst-case turn — the whole claimed batch, not one row"）を書き、上限側（priority 0 の最古 task age SLO = 1 分）に触れていない。`.env.example` と `docs/runtime_node.md` の説明も下限だけ。そして既定値は `SCOPE_TASK_LEASE_MS = 5 * 60 * 1000` で、その JSDoc は「matching the outbox relay's own default」— つまり **SLO ではなく outbox との対称性で選ばれており、priority 0 の SLO の 5 倍**になっている。ADR-010 が「契約文だけが配備側に責務を負わせて配線が既定値固定のままだと、実害の重さを黙って既定値に賭ける形になる」と言って env を通した以上、その配備側が読む契約に判断材料の半分しか無いのは同じ穴の別形。ポート JSDoc だけを読んだ #11 は下限だけ見て 5 分以上を選ぶ。
  - 提案: `leaseMs` の段落に上限側を 1 文足す（「長くするほどクラッシュした writer の行が戻るまでの遅延が伸びる。priority 0 の最古 task age SLO を上回る値は、1 回のクラッシュ回収がそれだけで SLO 違反になることを意味する」）。`SCOPE_TASK_LEASE_MS` 定数の JSDoc の「matching the outbox relay's own default」は、なぜ scope task にとってもその値でよいのかを 1 句で補うか、参照ランタイムには SLO 監視が無いので既定は対称性で置いた旨に改める。

- **[W-003]** 適合スイートが `leaseMs` を一度も既定値以外で呼んでいないので、「バックエンドが `leaseMs` を実際に使うこと」が拘束されていない
  - 場所: `packages/core/src/adapters/conformance/scopeTaskScheduler.ts:54-55`
  - 理由: ヘルパが `const claim = (limit, leaseMs = SCOPE_TASK_LEASE_MS) => …` で、スイート内の全呼び出しが既定値を使っている。`leaseExpiresAt` を assert しているケース（`:44-56` と `:341-350`）も `now + SCOPE_TASK_LEASE_MS` を期待するだけなので、**`leaseMs` 引数を無視して自前の定数 5 分を使うバックエンドがスイート全緑で通る**。`leaseMs` は本 Issue が新設したポート入力であり、ADR-005 が「配備側が選ぶ」を契約の柱に据え、ADR-010 がそのために env 経路まで通した値そのもの。その値が backend に効くかどうかが executable contract に落ちていないのは、ADR 026「スイート自体が契約の実行形」に照らして穴。参照ランタイムの配線（`server.node.ts:109` → `runner.ts:137` → `runDueScopeTasks`）は型では繋がっているが、memory 側が leaseMs を尊重することは backend-local にも確認されていない。
  - 提案: 既存の reclaim ケースか lease ケースのどちらかを非既定値（例 `claim(10, 2 * MINUTE_MS)`）で行い、(a) `leaseExpiresAt` がその値で返ること、(b) `advance(2 * MINUTE_MS - 1)` では再 claim されず `advance(1)` で戻ること、を assert する。ケースを増やさずに既存ケースの引数を変えるだけで足りる。

## 確認した点（指摘に至らなかったもの）

- **runner の budget 会計とリースの相互作用**: `runDueScopeTasks`（`workers/scopeTaskRunner.ts:147-188`）は `claimDue({limit: budget})` の直後に同じ `budget` を 1 件ずつ減らしながら claimed を回すので、`claimed.length <= budget` が算術的に保たれ、内側の `if (budget <= 0) break` は claimed を回り切った後にしか成立しない。「その round で settle しきる件数までしか claim しない」は成立している。唯一の例外はハンドラ未登録 kind（settle されずリース満了まで `running` に残る）だが、これは ADR-004 の意図した帰結で、`scopeTaskHandlers` の JSDoc がリース周期と最古 task age の話へ正しく書き直されている。
- **未 settle 経路の網羅**: 登録済み 4 kind（`deleteFilesByOwner` / `deleteQuota` / handover / barrier prune）は全分岐で `complete` / `schedule` / `backoffOrSchedule` のいずれかを撃つ。`alreadyApplied` だけが無 settle だが、これは `commandKey` が渡る初回コマンド（イベント駆動）でしか到達せず runner 経路には現れない。ハンドラが throw した場合は runner の `backOff` がリースを解放する。よってリースが 5 分ロックする既知経路は未登録 kind のみ。
- **指数バックオフの計算**: `backoffDelayMs` は変更されておらず、claim がリースを取ることで「負けた側が backoff を撃つ」経路自体が消えている。`workers/__tests__/scopeTaskRunner.test.ts:264-282` が「同じ clock で 2 回 `runDueScopeTasks` → ハンドラ 1 回 / `processed: 0` / 行が claim 直後から不変 → リース満了後に 2 回目」を実効的に拘束しており、Issue の影響②に対応している。`toEqual(claimed)` が同一参照との比較になっている点は、行が `Readonly<…>` の判別共用体で in-place 変異が型で塞がれているため実質的な穴にならない。
- **選択規則の実装**: `adapters/memory/scopeTaskSelection.ts` の予約パスは `ordered` が priority 昇順に並ぶことで各 priority グループが連続する性質に依存しており、`reservedPriority` を直前の値だけ保持する実装で正しく「各 priority の先頭 1 件」になる。返却は `ordered.filter(has)` なので順序も契約どおり。`limit <= 0` が 1 か所（純粋関数の入口）で処理され、`claimDue` / `listDue` が同じ関数を通る（AC-10）。
- **priority の割り当て**: `storage.ownerDeleteContinued` / `usage.userCleanupContinued` / `identity.personalCleanupHandoverContinued` = `securityCleanup`、`identity.personalBarrierPruneContinued` = `expiryCollection`。全 6 呼び出し箇所（`personalCleanup.ts:62,104` / `deleteQuota.ts:75` / `deleteFilesByOwner.ts:95,110` / `scopeTaskRunner.ts:60`）で同一 kind に同一 priority が渡っており、ADR-006 のトレードオフ（同一 kind の priority 分裂）は現時点で発生していない。
- **UoW の 2 プレーン分離**: `claimDue` が書き込みになったが scope プレーンの中で閉じており、ハンドラは claim の UoW が閉じた後に自分の UoW を開く。`acknowledgePersonalCleanup`（global プレーン）も scope UoW の外。ネストは導入されていない。commit kick は `schedule` だけを観測するので claim が runner を自分で叩き起こす経路も無い（`adapters/memory/__tests__/unitOfWork.test.ts:103-119` が拘束）。
- **保存表現の漏れ**: 遷移表が `pending` / `running` / `failed` を使うのは ADR 026 §1 が「liveness に関わる状態遷移はポート定義に書く」と明示している範囲。`lease_expires_at` 列や索引の話はポート JSDoc に入らず `spec/database` 側に留まっており、ADR-002 の切り分けどおり。適合スイートは `state` を一切 assert せず、`ScopeTask` のフィールドだけを見ている。
- **コメント方針**: 新規コメント（`scopeTaskRunner.ts:158-160`、`memory/repositories/scopeTaskScheduler.ts:125-128`、`di/env.ts:18-22`、`di/serverNode.ts:118-124`、テスト内の各注釈）はいずれも WHY で、修正の経緯や指摘への弁明は混じっていない。
- **スコープ逸脱**: application / ports / adapters 側に「含まれないもの」（`last_error`、attempt 上限の運用イベント、未実装 kind の追加、D1/DO 実装）の混入は無い。`di/serverNode.ts` の `nonEmpty` 化は outbox 4 変数の挙動も変える（`""` が boot 拒否 → unset 扱い）が、JSDoc に理由が書かれており AC-17 の配線に必要な範囲。
