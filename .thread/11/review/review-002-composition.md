- **[B-002]** `AuthTokenRepository.findPendingByUserAndPurpose` — spec を改訂した一方でポート JSDoc が旧い制約を主張し続けており、新設した「いちばん新しい発行を返す」規則が適合スイートにも memory にも無い（memory と Cloudflare で観測結果が割れる）

  - 理由: 三者が食い違っている。(a) spec は本 PR で「pending の (`user_id`, `purpose`) ごと最大 1 件は usecase 側が保つ。**DB 制約としては置かない**。部分 UNIQUE を張るとポート契約に反する（適合スイート ADP-identity-024）」へ改訂された — これ自体は正しい（`conformance/authTokenRepository.ts:113-119` が同じ組の pending を 2 件 insert する）。(b) しかしポート JSDoc は今も `The at-most-one live token of the pair, **per the partial unique index on (user_id, purpose) over status = 'pending'** (spec/database/index.md#auth_tokens)` と書いており、**自分が指している spec の節が「置くな」と言っている索引を根拠に不変条件を主張している**。ADR 026 決定 1 の「JSDoc だけを読んだ実装者が到達する振る舞い」は、この JSDoc からは「部分 UNIQUE を張る」であり、張れば ADP-identity-024 で落ちる。(c) spec が新設した「複数 pending が在るときは `ORDER BY created_at DESC, id DESC` で最新を返す」は、ポート JSDoc にも共有適合スイートにも無い。実際 Cloudflare は最新を返し（`ORDER BY created_at DESC, id DESC LIMIT 1`）、memory は `table.values().find(...)` で**挿入順の最初**を返す。pending が 2 件ある状態（契約が許し、スイートが実際に作る状態）で両バックエンドの答えが割れ、しかも再送間隔の判定材料であるにもかかわらず**両方とも緑のまま**通る。ADR 046 / AC-8 が塞ごうとしている穴そのもの
