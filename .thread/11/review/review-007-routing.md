#### 検証したことの要点（記録用）

- **`NoteRouteStore` の 5 状態**: 各分岐が読んだ行から固有符号（`STALE_SCOPE_ROUTE` / 状態機械 `ConflictError` / `NOTE_NOT_FOUND`）を決め、`unchangedGuard`（`note_id, state, route_version, operation_id, migration_id`）／`absentGuard` を write の直前に staged する形は、DDL の 5 本の `CHECK`（`0001_global_schema.sql:206-210`）と矛盾なく閉じている。`switchMove` の lost-response 再試行は `route_version + 1` と `last_migration_id` の 2 条件で識別しており、`last_migration_id` が `switchMove` 以外で書かれない点も確認した。`isReadable` は memory 実装（`adapters/memory/repositories/noteRouteStore.ts:52-58`）と同型で、適合スイート `conformance/noteRouteStore.ts:253` の tombstone 期待とも一致する

- **`OutboxRepository`**: `save` の `ON CONFLICT DO NOTHING`（ADR 042 の「先着行をそのまま残す」）、`claimPending` の単一文 + `RETURNING` + JS 側での `(created_at, id)` 再整列、`finalize` の成功 / 失敗 1 原子ステップ、`failed_at` による quarantine、`refuseStaged` による staged 拒否、`MAX_SAVE_BINDING_BYTES` の事前拒否、`writeCounted` 経由の件数取得 — いずれも契約どおり。`idempotency.test.ts` / `routeGuard.test.ts` が id 衝突・二重 claim・staged 拒否・サイズ上限を実バインディングで観測している
- **`claimDue` の per-row 排他**: `claimGuardStatement` → `claimStatement` の順序、`ScopeTaskScheduler` JSDoc に足された `OPTIMISTIC_LOCK_FAILURE`、`runDueScopeTasks` がその 1 符号だけを skip し他の `ConflictError` は投げ直す形、いずれも `lease.test.ts`（autocommit / staged の 2 形）と `scopeTaskRunner.test.ts` の新規 2 ケースで守られている
