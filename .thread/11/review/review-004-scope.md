#### Warnings

- **[W-001]** OCC guard を持つ 2 つの投影経路 — `redactAuthor` と `NoteProjectionRevisionStore.bump` — に、割り込みを観測するテストが 1 件も無い
  - 場所: `packages/core/src/adapters/cloudflare/projection/snapshotWriter.ts:249`, `packages/core/src/adapters/cloudflare/do/repositories/noteProjection.ts:105`, `packages/core/src/adapters/cloudflare/__tests__/projectionConcurrency.test.ts:70`
  - 理由: どちらも JSDoc が「なぜ条件付き UPDATE ではなく guard なのか」を具体的な失敗像で主張している。`redactAuthor` は「条件付き UPDATE が 0 行でも `true` を返し、overlay が storage の取らなかった値を配る」、`bump` は「lost update が 2 つの event に同じ revision を渡し、順序づけ不能にする」。どちらもこの PR が意図して入れた規律だが、`projectionConcurrency.test.ts` が pin しているのは `replaceSnapshotIfNewer` / `removeIfNewer` / 初回 insert の 3 経路だけで、`redactAuthor` と `bump` は共有適合スイート（`ADP-note-055/056` / `ADP-note-034`）の単一スレッド観測しか無い。memory は単一スレッドなので適合スイートはこの割り込みを原理的に観測できず（同ファイルの冒頭コメント自身がそう書いている）、guard を外しても全テストが緑のままになる。`bump` は scope DO の 2 RPC（read → applyWriteSet）にまたがるので、同一 scope への並行呼び出しで実際に割り込みうる。
  - 提案: `projectionConcurrency.test.ts` の `interposeOnce` をそのまま使い、(a) `redactAuthor` の読みと write の間に rival の `replaceSnapshotIfNewer`（より新しい `authorVersion`）を差し込んで `ConflictError` と「旧表示名が復活しないこと」を観測する、(b) `deleteFilesByOwner.test.ts` と同型の scope セッションで `bump` の read と write の間に別の `bump` を差し込み、2 つの呼び出しが同じ revision を返さない（敗者が `ConflictError`）ことを観測する、の 2 ケースを足す。どちらも適合スイート本体には触れないので AC-8 の手続きは不要。

- **[W-002]** AC-5 のテスト冒頭コメントが「実測値は予算文書ではなくアダプターに属する」と書いているが、`spec/platform/index.md` は今まさにその実測値を載せており、引いている ADR 056 の決定番号も違う

  - 理由: ADR 056 決定 2 は「バックエンド依存の数値は実行基盤の予算文書に置く（表の直後の段落として、設計目標と明記して）」であり、決定 3 は「**どのバックエンドがその数に届かないか**は予算文書ではなく ADR のコンテキストに残す」である。`spec/platform/index.md:155` はこの区別どおりに直っていて、`4n + 3` を本文に持ち（決定 2）、届かないバックエンドの話だけを ADR へ送っている（決定 3）。テスト側のコメントだけが「The measured figures themselves belong to the adapter rather than to the budget document (ADR 056 決定 3)」と、決定 2 が定めた配置と正反対のことを、決定 3 を根拠に主張している。canon と実装コメントが同じ論点で食い違って残るのは、次に触る人がどちらを正とするか判断できない。

- **[W-003]** `PublicNoteProjectionWriter.removeForPurge` のポート JSDoc が「acknowledged under the operation」と約束しているが、どちらのバックエンドも観測される acknowledgement を持たない
  - 場所: `packages/core/src/domain/note/ports/publicNoteProjectionWriter.ts:44`, `packages/core/src/adapters/cloudflare/d1/repositories/publicNoteProjection.ts:89`
  - 理由: D1 実装は `operationId` / `routeVersion` / `projectionRevision` の 3 引数をどれも使わず、行を読んで消すだけである。実装側の JSDoc は「operation は既に route を閉じているので比較対象が無く、冪等性は『消えているものを消す』の形を取る」と理由を述べており、判断としては妥当だと考える。問題は正本側で、ポート JSDoc の「acknowledged under the operation」という語が残っている。memory 側は `publicPurgeAcks` に受領行を書くが、この表は**リポジトリ全体でどこからも読まれない**（`store.ts:422` の宣言と `noteProjection.ts:219` の書き込みだけ）。適合スイート `ADP-note-032` も「2 回呼んでも失敗しない」しか見ないので、契約語・memory の死んだ表・D1 の非実装という三者不整合が、新バックエンドの追加で表面化したまま残る。ADR 046 が扱う類の食い違いである。

- **[W-004]** 本文ハイライトの位置写像を書記素クラスタ 1 つずつ `normalize("NFKC").toLowerCase()` で作るため、未認証の公開検索 1 ページで最大 8 万回規模の文字列正規化が走る
  - 場所: `packages/core/src/adapters/cloudflare/search/highlight.ts:72`, `packages/core/src/adapters/cloudflare/projection/searchClauses.ts:95`
  - 理由: `excerpt` は 200 文字上限（ADR 017 の `content_excerpt` 800 バイト）なので `highlightExcerpt` は安い。効くのは `bodyHighlights` の方で、excerpt に一致が無かった行だけとはいえ**ページの全行がそうなりうる**。1 行あたり `substr(text, 1, 4000)` の 4,000 クラスタ × `normalize` と `toLowerCase` の 2 呼び出し、`limit` が 20 なら 1 リクエストで 16 万回。`spec/database/index.md:966` が 4,000 文字の上限を置いた理由は「1 ページが 800,000 バイトの本文を limit 件ぶん運ばない」ための**転送量**であって、CPU の見積もりはどこにも無い。`searchPublic` はサインイン不要の経路（ADR 063 が「誰でも位置を動かせる」と明記している）なので、ここが 1 ページあたりの CPU の主項になるのは避けたい。
  - 提案: `mapPositions` に ASCII の速路を足すのが安全かつ最小。書記素クラスタが 1 コードユニットで `< 0x80` のとき、NFKC は恒等で `toLowerCase` は長さを変えないので、`piece = segment.toLowerCase()`（`normalize` を呼ばない）に落として構わない。英語本文ではこれで正規化呼び出しが消える。日本語本文も残るのは `toLowerCase` 側だけになる。全文正規化での事前フィルタは、全文 NFKC がクラスタ境界を跨いで合成しうるためクラスタ単位の一致を取りこぼす方向にずれる可能性があり、負のフィルタとしても安全とは言い切れないので勧めない。
