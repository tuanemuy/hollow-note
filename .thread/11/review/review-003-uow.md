### UoW / 実行機構・SQL 土台

#### Blockers

- **[B-001]** commit 後の `publishDueIndex` 失敗に、**この PR が配線している配備では回復経路が無い**（ADR-060 の「両者が互いの保険」と canon の「Alarm が治す」が、レジストリ空の配備では成り立たない）
  - 場所: `packages/core/src/adapters/cloudflare/do/scopeObject.ts:150-163` / `packages/core/src/adapters/cloudflare/do/alarm.ts:254-263` / `spec/database/index.md:1088`
  - 理由:
    `armAndPublish` は `rescheduleAlarm` と `publishDueIndex` を独立に warn へ倒し、その根拠を「両者が互いの保険」に置いている（`scopeObject.ts:143-149`、adr.md ADR-060）。canon も同じことを言う — `spec/database/index.md:1088`「commit と索引更新のあいだで落ちた場合の drift は、当該 scope の Alarm が自分の `scheduled_tasks` を正として書き直して治す」。
    ところがこの保険は、**本 PR が実際に配線している配備では存在しない**。`rescheduleAlarm` は `scopeAlarmDrivesTasks()`（＝ハンドラレジストリが非空か）が偽なら常に `deleteAlarm()` へ落ちる（`alarm.ts:257-262`、ADR-045）。`registerScopeTaskHandler` の呼び出しは `__tests__/alarm.test.ts` にしか無く、production コードのどこからも登録されない（plan.md「含まれないもの」が Queue consumer / Cron ハンドラをスコープ外に置いているため当然）。したがって既定配備では **どの scope object も alarm を持たず、turn は一度も走らない**。
    その結果、`applyWriteSet` が `scheduled_tasks` を名指した commit の直後に `publishDueIndex` が D1 の一時障害で落ちると:
    - 索引に行が**載らない**（欠落方向）
    - object は武装されない（レジストリ空なので `rescheduleAlarm` は `deleteAlarm`）
    - 中央 runner は `listDue` が索引しか読まない（`scopeTaskQueue.ts:41-88`）ので、その scope へ二度と到達しない
    - constructor の再武装（`scopeObject.ts:92`）も `rescheduleAlarm` だけで publish はしないので治らない
    - 治るのは「同じ scope に対して別の write-set が再び `scheduled_tasks` を触ったとき」だけ。それが最後の task だった場合は永久に来ない

    `dueIndex.ts:26-27` の弁明「a stale row costs at most one failed claim」は**余分な行**の方向にしか掛からず、欠落方向を覆っていない。plan.md「リスクと注意点」最終行が名指している害（personal cleanup の継続が止まり `accountDeletionBarrier` が開いたまま User が `deleting` で残る／自動復旧経路が無い）が、そのまま実現する経路になっている。
    `__tests__/alarm.test.ts:448-490`（"keeps a committed write-set when the due index publish fails"）は `register("due.later", noop)` を先に呼んでレジストリを非空にしているため、**既定配備そのものを観測していない**。武装されたケースだけが緑になっている。
  - 提案:
    (a) `publishDueIndex` が失敗したときだけ、レジストリの有無に関わらず再試行用の alarm を張る。`alarm()` はレジストリ空なら `runScopeAlarmTurn` が `EMPTY_TURN` を返して即座に `finally` の `armAndPublish` に入るので、既存の機構をそのまま publish のリトライに使える。ADR-060 が選んだ arm 先行の順序は保ったまま、publish の catch 側で `setAlarm(now + backoff)` を足すだけで閉じる（`rescheduleAlarm` の `deleteAlarm` を後から上書きする形になる点は明示が要る）。
    (b) あるいは publish をアダプタ内で有界リトライする（CLAUDE.md「Retry strategy」の driver-level transient は adapter で吸収する、に沿う。現状 Cloudflare アダプタ群には再試行が 1 つも無い）。
    いずれにせよ `spec/database/index.md:1088` と `dueIndex.ts` の JSDoc・adr.md ADR-060 の「互いの保険」は、レジストリ空の配備で片側が存在しないことを書き足して正す必要がある（AC-9）。既定配備を観測するテスト（`register` せずに publish を落とし、後で索引に行が現れること）も併せて欲しい。

#### Warnings

- **[W-001]** `readRows` の LIMIT ガードは「述語から外れた／消えた」しか見ないので、`compare` が並べ替えでページ外へ押し出した行を取りこぼす
  - 場所: `packages/core/src/adapters/cloudflare/sql/session.ts:147-179`
  - 理由:
    今回の変更（`staged.includes(null)` → `dropsAStoredRow()`）はガードを**広げた**もので、退行は無い。良い変更。
    ただし残った穴が 1 つある。`stored` が LIMIT ぶん埋まった状態で、同じ unit が stored 行を **`matches` を満たしたまま** 更新し、その更新が `compare` の順序上その行をページ境界の外へ動かすと、ガードは発火せず、storage 側の n+1 番目の行を引き当てられないまま**中身の違うページ**が返る。例: `ORDER BY x LIMIT 2`、storage が x=1,2,3、unit が x=1 の行を x=10 に更新 → 正解は [2,3] だが overlay は [2,10] を返す。
    `RowsRead` の JSDoc は落ち方を「deleted, or updated out of the predicate」の 2 つに限定して数え上げており、`compare` は「repeats the statement's ORDER BY」としか書いていないので、この形は契約上「安全」に読める。
    現行の呼び出し地点は全て安全だと確認した — `compare` + `limit` の組は `noteRevisionRepository:113`（append-only）、`noteRepository.listPurgeable:430`（新規 trash は `purge_after` が未来なので `matches` に入らない）、`llmUsageRepository.deleteByUser:227`（削除のみ）、`accountDeletionManifestStore:783`（PK での順序なので更新で動かない）、`authTokenRepository:152`（消費は state を変えるので `matches` から外れる）、`noteRouteFanOutReader:107`（autocommit）。到達不能なので Blocker にはしない。
  - 提案: `stored.length >= limit && spec.compare !== undefined` のとき、overlay で書き換わった stored 行が 1 つでもあれば拒否する（`matches` を満たしていても）。あるいは `RowsRead` の JSDoc に「`compare` の順序を動かす更新も同じ理由で合成できない」と明記し、ガードの守備範囲を契約として狭く宣言する。今の JSDoc は前者を約束しているように読める。

- **[W-002]** テストコメントが「以前の実装がこうだった」という修正の経緯を残している
  - 場所: `packages/core/src/adapters/cloudflare/__tests__/sessionOverlay.test.ts:112-114`
  - 理由: 「The row is still there, so **the delete-only guard let this through** and the overlay returned a page one short of what it promised.」は、round 002 時点のガード（`staged.includes(null)`）を指した過去形の記述で、現在のコードには存在しない状態を説明している。CLAUDE.md の「Default to no comments. Add one only when the WHY is non-obvious」に照らすと、残すべきは「なぜ述語から外れた更新も拒否されねばならないか」であって、以前どう漏れていたかではない。
  - 提案: 「行は残っているが述語から外れているので、このページは overlay では埋め直せない」といった現在形の理由に書き換える。

#### 確認したこと（Blocker/Warning に至らなかった点）

以下は穴を探した結果「閉じている」と判断した項目。記録として残す。

- **二平面 UoW の契約** — 失敗時の全ロールバック（`durability.test.ts:81-192` が D1 batch 中断・`transactionSync` 巻き戻し・索引未 publish を実バインディングで観測）、並行 run の半端な観測（`unitOfWork.test.ts:352-371`）、入れ子禁止の 4 方向（同上 400-414）、UoW 外の原子操作が巻き込まれないこと（autocommit session が別の executor パスを取る）はいずれも実効的なテストがある。
- **`run` の `async` 化と ALS の外での kick** — `openUnit.run(plane, fn)` は `fn` が promise を返した時点で同期的に抜けるため、provider の `await` 継続は呼び出し元の文脈で走り、store は未設定になる。`unitOfWork.test.ts:416-473` が「kick の中で別の `run` を開いて解決すること」を両平面で観測しており、これが正しい観測方法。例外経路では `committed` に到達しないので kick は飛ばない（`durability.test.ts:158` が `relayKicks === 0` を固定）。`flushedEvents` / `armedTasks` は ALS ブロック内で確定して戻り値に載せる形になっており、受け渡しに穴は無い。kick が throw した場合に commit 済みの `run` が reject する点は、`RelayTrigger` / `ScopeTaskTrigger` の JSDoc が「MUST NOT throw」を契約にしているので実装側の守備範囲外。memory バックエンド（`adapters/memory/store.ts:69-76`）も同じく素の `Error` を `Promise.reject` する形で、入れ子エラーの形も揃っている。
- **文数上限の executor 入口への移動** — `createD1Executor.apply` が唯一のゲートになったので、UoW commit と autocommit `write` が同じ 250 に掛かる。`sessionOverlay.test.ts:169-222` が cap ちょうど / cap+1 / autocommit の 3 面を固定している。scope 平面に cap が無いことは `statement.ts:47-51` で理由付きで宣言されており、DO 側は `spec/platform/index.md` の行数予算が効く。250 = 設計上限 500 の半分という根拠も `spec/platform/index.md:134` と一致。
- **`writeCounted` / `applyCounted`** — `applyCounted` は `SqlExecutor` の optional で、答えられない backend（scope stub / DO storage）では `writeCounted` が明示的に落ちる。呼び出し地点は `d1/repositories/outboxRepository.ts:256`（prune）の 1 か所のみで、`WorkerContainer.outboxRepository` は autocommit の global session 上に建つので到達可能。staged session 側の `writeCounted` も「そもそも走っていない」と言い切るメッセージになっている。
- **`readRows` LIMIT ガードの正当な使い方への誤爆** — 変更はガードを広げる方向なので誤爆は増えない。唯一気になった `llmUsageRepository.deleteByUser` の反復呼び出しは、`application/usage/deleteQuota.ts:70-83` が 1 UoW につき 1 ページしか読まない（続きは継続 task）ので発火しない。
- **claim した chunk の最低 1 行訪問** — `alarm.ts:189` の `index > 0 &&` は、claim 自体が予算を食い切ったときの「claim → 全 release → 過去の `due_at` で即再武装」という進捗ゼロのループを構造的に閉じている。`alarm.test.ts:393-440` が `elapsedMs` を差し込んで claimed=3 / handled=1 / released=2 を固定しており、`released` は `due_at`・`attempts` を据え置く（同 324-385）ことも別ケースで固定済み。
- **`_occ_guard`** — DDL は両平面にあり（`d1/migrations/0001_global_schema.sql:20-23`、`do/schema.ts:53`）、制約名は `errors.ts:25` の単一定数から DDL と分類器の双方が引く。guard は必ず保護対象の直前に積まれる（`scopeTaskScheduler.ts:204-220` の `flatMap`、`unitOfWork.test.ts:116-134`）。発火経路は global（`unitOfWork.test.ts:373-391`）、scope の RPC 越え（同 516-561）、`claimDue` の 2 経路（`lease.test.ts:170-292`）で観測済み。guard 表が発火後も空であること（`unitOfWork.test.ts:393-398`）まで見ている。積み忘れは探した範囲では見つからなかった。
- **write-set と overlay** — `opaque` の read-your-writes 非参加と `table` 宣言による `touchedTables()` 参加は `sessionOverlay.test.ts:149-167` が両方向を固定。`scopeTaskScheduler` の `backedOffImage` は `backoffStatement` の SQL 算術と一致する（pre-increment `attempts` に対し `BASE * 2^a`、上限 `MAX_BACKOFF`、ceiling 超えで `failed` かつ `due_at` 据え置き）ことを手で突き合わせて確認した。`claimDue` の候補読みが意図的に overlay を通さない（`scopeTaskScheduler.ts:146-149`）のも正しい — 候補は他 writer から見えている行でなければならない。
- **bound parameter 上限・`json_each`・エラー翻訳** — `assertBindable` が D1 / DO storage / scope stub の 3 経路すべてに掛かる。`support.test.ts:35-103` が 250 件の insert / select / delete を 1 文ずつで通し、上限超過のメッセージをアンカー付きで固定。`resolveMany` は入力上限（500 / 100）を満たして実測している（同 113-153）。`throwTranslated` は occGuard を `ConflictError` に、それ以外を `SystemError(DatabaseError)` に倒し、独自の意味を持つ制約は `classifySqlError` で各リポジトリが自分で判断する形になっている。
- **alarm / due index の再入・再スケジュール・lease・有界化** — 再入は `alarm.test.ts:597-671` がリース中の再配送で行が一切動かないこと・失効後の再 claim が attempt を消費しないことまで固定。lease 回収は `lease.test.ts:85-162` が `due_at` / `attempts` / `priority` / `payload` の据え置きを実測。有界化は `dueIndexRowsStatement` が優先度ごとに 25 行（合計 100 行）で切り、`dueCandidatesStatement` / `scopeTaskQueue` の候補読みが `ROW_NUMBER() OVER (PARTITION BY priority)` で `4 × limit` に抑えている — 素の `LIMIT` だと予約枠が届かない、という理由付けも正しい。
- **`AsyncLocalStorage` の文脈** — `nodejs_compat` 下で使えることを `harness.test.ts:124-129` が実バインディングで確認。DO は別 isolate なので worker 側の store が RPC を越えて漏れることはなく、`ScopeObject.alarm()` は UoW の外から始まる。
- **scope 検証とセキュリティ** — object は自分の `ScopeKey` を `_scope_identity` に pin し、以降の全 RPC で一致を検査（`scopeObject.ts:183-216`、`harness.test.ts:100-122`）。`scopeObjectName` の名前空間接頭辞は due index の行には載らない（`dueIndex.ts:35-42` に理由と制約が明記）。cursor は capability ではない（`cursor.ts:16-20`、ADR 063）。
- **`ScopeTaskScheduler` 契約の追記と runner 側の隔離** — `claimDue` が `ConflictError("OPTIMISTIC_LOCK_FAILURE")` を投げうることをポート JSDoc に足し、`runDueScopeTasks` が当該 scope だけを飛ばして round を続ける形（`scopeTaskRunner.ts:161-178`）。memory では起きない事象なので、`application/workers/__tests__/scopeTaskRunner.test.ts` が UoW を包んで注入する形でテストしている。適合スイートへケースを足していない点は triage-keys の `conformance/scopeTaskScheduler.ts:並行claimケース`（#48・wont-fix）で決着済みなので蒸し返さない。
