  - 提案: 打ち切りが働いたことを直接観測するケースへ差し替える。(a) 予算超過を NFKC 展開で作る（`"㍿".repeat(...)` を本文に置き、`bigramIndexText` の出力が `1_800_000` 以下に収まることと、打ち切りを外せば 2,000,000 を超えることが分かる形にする）、または (b) spec の「既知の限界」が約束している観測を書く — **本文の頭にあるキーワードは引けるが、予算を越えた末尾にしか無いキーワードは引けず、`replaceSnapshotIfNewer` は `"written"` を返す**。(b) のほうが契約文言と 1 対 1 に対応するので望ましい。あわせて 167-171 行のコメントを `bigram.ts` の JSDoc と同じ根拠（NFKC 展開）に直す。

- **[W-003]** 索引テキストの予算がトークン粒度で、非 CJK の「トークン」は run 全体なので、長い非 CJK run では「頭からは引ける」が成り立たず索引が丸ごと空になる
  - 場所: `packages/core/src/adapters/cloudflare/search/bigram.ts:119-133`（`splitRuns` は `bigram.ts:54-71`）
  - 理由: `bigramIndexText` は CJK run を 2 文字トークンへ割るので、CJK 側では予算超過が「前方から入り、末尾が落ちる」細かい打ち切りになる。ところが非 CJK 側は `run.cjk ? bigramsOf(run.text) : [run.text]` で **run 全体が 1 トークン**であり、空白も非 CJK なので「本文中の連続する非 CJK 部分（英文なら本文まるごと）」が 1 トークンになる。この 1 トークンが単独で予算を越えると `if (bytes + size > MAX_INDEX_TEXT_BYTES) return tokens.join(" ")` が最初の反復で返り、**その列の索引テキストは空文字列**になる。
    到達しうる入力はある。`PlainTextContent` の上限は 800,000 バイトだが NFKC は展開しうる — 例えば U+FDFA（`ﷺ`、3 バイト）は NFKC で 18 文字（33 バイト）に展開する。約 164KB ぶん（上限の 2 割）でも展開後 1 run が 1.8MB を越え、その本文は `text_fts` に 1 トークンも入らない。`spec/database/index.md`「既知の限界」は「本文の前方から入るので頭からは引ける」と約束しているので、この経路だけ約束が成り立たない（`title` / `tag_names` 由来のヒットは残るので、投影は成功し検索だけが静かに欠ける）。
  - 提案: 非 CJK run を索引テキストへ出すときに空白で分割して 1 語 1 トークンとして積む。`unicode61` はどのみち空白で切るので**索引の内容は 1 バイトも変わらず**（＝既存の索引行の取り消し互換性も保たれ、`bigram.ts` 冒頭の「変更すれば全索引を作り直し」に抵触しない）、予算超過時の挙動だけが「run 丸ごと落ちる」から「前方から入る」へ戻る。`bigramMatchExpression` 側は run をフレーズにまとめる現行のままでよい（フレーズは隣接トークン列に一致するため）。

  - 場所: `packages/core/src/adapters/cloudflare/d1/repositories/publicNoteQueryService.ts:133-140`（`ORDER BY ns.note_id ASC` 固定）。canon 側は `spec/domains/note.md:485` 付近と `spec/platform/index.md` の `### Global D1` 段落
