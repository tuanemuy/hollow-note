### Identity / directory / operation（D1 control plane）

全体としては水準が高い。`_occ_guard` の二段構え（ステージ時の読みで固有符号を決め、適用時の guard を最後の砦にする）は Identity 束・directory 束のほぼ全域で一貫して適用されており、`reserve` の 3 分岐・`beginRelease` の CAS・`AuthTokenRepository.save` の単回消費・`OAuthStateStore.take` の条件付き `DELETE … RETURNING` はいずれもポート契約どおりに読める。`json_each` 展開と bound parameter 上限のガードも徹底されている。

以下は、その一貫性から**外れている 1 か所**と、spec との突き合わせで残った差分である。

#### Blockers

- **[B-001]** `GlobalMaintenanceRunStore` だけが `_occ_guard` を 1 つも積んでおらず、lease と lane の条件付き更新が全部「読んで判定 → 無条件 UPDATE」になっている
  - 場所: `packages/core/src/adapters/cloudflare/d1/repositories/globalMaintenanceRunStore.ts:235`（`laneUpdate`）、`:311`（`beginOrResumeKind` の lease 奪取）、`:280`（`reclaimLapsedLanes`）、`:581`（`recoverLease`）
  - 理由:
    - ポート JSDoc は「Only the holder of the 10-minute lease may advance progress」と明言している。ところが実装がこれを保証する手段は `requireLeasedRun` の**読み**だけで、その後の `UPDATE ... WHERE run_id = ? AND generation = ? AND shard_id = ?` には lane の status も lease owner も条件に入っていない。読みと適用のあいだに別 writer が `recoverLease` / `beginOrResumeKind` で lease を奪っても、先行 writer の `checkpointLane` / `advanceOrAck` はそのまま着地する。結果は「回収済み lane の cursor が旧 owner に巻き戻される / table_index が二重に進む」で、authStatePrune ならその表のその keyset が**その run では掃かれない**（期限切れ session / auth token が残る）。
    - `beginOrResumeKind` の lease 奪取も無条件 `UPDATE ... WHERE run_id = ?` なので、lapsed を同時に観測した 2 人が両方「resumed」を受け取り、両方が `reclaimLapsedLanes` を撃つ。相互排他が成立しない。
    - これは本 PR 自身の [ADR-008](../adr.md) が定めた規律（「実装は『ステージ時に読んだ値で先に判定して固有のエラーを投げ、guard は同時実行に対する最後の砦にする』という二段構えを取る」）に、この 1 ファイルだけが従っていないという不整合でもある。`identityUniqueDirectory` / `distributedOperationStore` / `authTokenRepository` / `userRepository` / `identityRepository` は全部 guard を積んでいる。
    - しかも呼び出し側の `PRUNE_WORKER_ID`（`application/identity/pruneExpiredAuthState.ts`）は**プロセス定数**である。Node 参照ランタイムでは 1 プロセスなのでこれで足りていたが、Cloudflare では全 Worker が同じ `leaseOwner` 文字列を名乗るので `requireLeasedRun` は誰も弾かない。「memory では成立していた前提が、2 つ目のバックエンドで初めて崩れる」という、まさにこの Issue が実バインディングで証明するはずの性質にあたる。
    - 適合スイートは memory の直列化のせいでこれを観測できず、バックエンド固有テストにも `GlobalMaintenanceRunStore` の競合ケースが無い（`__tests__/lease.test.ts` が見ているのは `scheduled_tasks` の claim だけ）。緑であることは根拠にならない。
  - 提案: 他の store と同じ形にそろえる。
    - run 行を書く 3 か所（`beginOrResumeKind` の resume 分岐 / `recoverLease` / `advanceOrAck` の run 完了）に `occGuard(SELECT 1 FROM runs WHERE run_id = ? AND lease_owner = ? AND lease_until = ?)`（読んだ値そのもの）を前置し、外れたら `foreignLease` へ翻訳する。
    - `laneUpdate` に `occGuard(SELECT 1 FROM lanes WHERE run_id = ? AND generation = ? AND shard_id = ? AND status = ? AND table_index = ? AND cursor IS ?)`（読んだ lane の同一性）を前置する。`NoteRouteStore` が [ADR-015](../adr.md) で採った「行同一性 guard」と同じ形にできる。
    - あわせて `__tests__/lease.test.ts` に「lapsed lease を 2 人が同時に奪いに行くと 1 人だけが勝つ」「奪われた旧 owner の `checkpointLane` は着地しない」を足す（AC-4 の lease 回収の分）。
    - 併走 writer を前提にしないなら、少なくとも `spec/platform/index.md` に追記された `ScopeTaskScheduler` の fencing 注記（本 PR で追加したもの）と同じ強さの注記を `GlobalMaintenanceRunStore` 側にも置き、`PRUNE_WORKER_ID` がプロセス定数であることを配備前提として明記すること。

#### Warnings

- **[W-001]** `auth_tokens` に spec が要求する部分 UNIQUE が無く、その省略がどこにも記録されていない
  - 場所: `packages/core/src/adapters/cloudflare/d1/migrations/0001_global_schema.sql:110`（`auth_tokens_user_purpose_idx` は非 UNIQUE）
  - 理由: `spec/database/index.md#auth_tokens` は「pending tokenは(`user_id`, `purpose`)で部分UNIQUEとし最大1件」と定めている。一方、適合スイート `conformance/authTokenRepository.ts` の ADP-identity-024 は同一 `(userId, 'email_verification')` の pending token を 2 件 insert するので、この索引を張るとスイートが落ちる。つまり spec とポート契約が真正面から食い違っており、実装はポート側に倒した（[ADR 046](../../../spec/adr/046-port-contract-divergence.md) の手続きとしては正しい向き）。ところがその判断が `spec/database/index.md` にも `.thread/11/adr.md` にも残っていない — AC-8（乖離の解決が ADR 046 に従っていること）と AC-9（反映しない差分は adr.md に理由とともに残す）の両方に触れる。実害としては、`findPendingByUserAndPurpose` が `LIMIT 1` を `ORDER BY` 無しで撃つため、pending が複数ある状態では「どの 1 件が返るか」が SQLite の走査順まかせになる。これは `resendVerificationEmail` / `requestPasswordReset` の再送間隔の判定材料（ポート JSDoc: 「the only reading of when a token was last issued」）なので、非決定になってよい値ではない。
  - 提案: (a) `spec/database/index.md#auth_tokens` の当該記述を「最大 1 件は usecase 側が `deleteByUserAndPurpose` で保つ。DB 制約としては置かない（適合スイート ADP-identity-024 が複数 pending を許すため）」へ改め、adr.md に判断を 1 本足す。(b) 併せて `findPendingByUserAndPurpose` に `ORDER BY created_at DESC, id DESC` を入れて、複数 pending 時の戻り値を決定的にする（memory は挿入順の `find` なので、どちらにせよ両者の観測は今すでに揃っていない）。

- **[W-002]** 新設した物理表 2 つが `spec/database/index.md` の物理配置表にも列定義にも現れない（AC-9）
  - 場所: `packages/core/src/adapters/cloudflare/d1/migrations/0001_global_schema.sql:229`（`account_deletion_manifest_items`）、`:275`（`global_maintenance_run_lanes`）
  - 理由: 同じ PR が `scope_task_due_index` と `_scope_identity` はきちんと物理配置表に足し、専用の節まで書いている（spec/database/index.md の「両 plane 共通の infrastructure table」「`_scope_identity`」）。ところが header/items の 2 表分割と run/lanes の 2 表分割は、spec 側では依然として「1 表がまとめて持つ」書き方のままである（`### account_deletion_manifests` の「itemsは(`operation_id`, `kind`, `target_key`) PK」、`### global_maintenance_runs` の「generation/shardごとの…position…を持つ」）。実装は `(operation_id, key)` の 2 列 PK（`kind` を `key` の接頭辞へ畳んでいる）と、独立した `global_maintenance_run_lanes` 表である。[ADR 061](../../../spec/adr/061-maintenance-sweep-order-authority.md) の「影響」は run 行の表集合と lane の position を **database/index.md が対で定める**と明示しているので、ここは spec の持ち分としてはっきり要求されている箇所でもある。
  - 提案: 物理配置表（`global D1: directory / operation`）に 2 表を足し、`### account_deletion_manifests` / `### global_maintenance_runs` の節を「header 表 + items/lanes 表」の 2 表構成として列表付きで書き直す。畳んだ PK（`kind` を `key` に含める）はポート側の `AccountDeletionManifestItem.key` がそもそも合成キーなので、その旨も 1 行で足せば足りる。

- **[W-003]** 上記 2 表以外にも、Identity / directory 4 表の列が spec の列表と細かくずれたまま
  - 場所: `packages/core/src/adapters/cloudflare/d1/migrations/0001_global_schema.sql:142`（`identity_unique_reservations`）、`:71`（`identity_removal_receipts`）
  - 理由: 洗い出すと 3 点。(1) `identity_unique_reservations.user_version` は spec の列表に無い列で、しかも**書かれるだけで一度も読まれない**（`reserve` で NULL、`activate` で `expectedUserVersion`、参照ゼロ）。memory の `DirectoryRow.userVersion` と同型なので実装間では揃っているが、spec には現れない。(2) `identity_removal_receipts` は spec が挙げる `created_at` を持たず、代わりにポートが要求する `kind` を持つ（`kind` の追加は正しい — `IdentityRemovalReceipt.kind` があるため）。(3) `identity_unique_reservations_user_idx (user_id, kind)` も spec に無い索引で、かつ現状どのクエリも `user_id` で引いていない（`readByOperation` は `operation_id`、`readOne` は PK）。AC-9 は「新規に決めた物理スキーマ（列名・索引）が spec に反映されている」ことを求めている。
  - 提案: `created_at` は足すか spec から落とす。`user_version` と `(user_id, kind)` 索引は、読み手が無い以上どちらかに倒す — spec に足して「将来 X が読む」と書くか、列と索引を落とすか。使われない索引は D1 の write コストにそのまま乗る。

- **[W-004]** `identities` の 8 件上限を守る `BEFORE INSERT` トリガーが無く、省略の記録も無い
  - 場所: `packages/core/src/adapters/cloudflare/d1/migrations/0001_global_schema.sql:51`
  - 理由: `spec/database/index.md#identities` は「Password/OAuth合計8件。UserId shardの最終UoWでcurrent件数を検査し、**`BEFORE INSERT` triggerも同じ`user_id`が既に8件ならabortする**」と、アプリ側検査に加えた多層防御として明示している。実装はアプリ側検査（`IdentityPolicy`）だけに依存している。`identities_user_password_uq` は spec どおり張っているので、同じ節の指示のうち一方だけを落としたことになる。
  - 提案: トリガーを足すか、`.thread/11/adr.md` に「ポート契約が要求しておらず適合スイートも観測しないので置かない」と理由を残す（[ADR 054](../../../spec/adr/054-provider-account-uniqueness-owner.md) が provider account について同種の判断を明文化しているので、それに倣える）。

- **[W-005]** `beginOrResumeKind` が、同じ hour bucket で完了済み run が残っているときに `SystemError(DatabaseError)` を投げる
  - 場所: `packages/core/src/adapters/cloudflare/d1/repositories/globalMaintenanceRunStore.ts:363`
  - 理由: `candidateRunId` は `authStatePrune:${hourBucketOf(now)}:${generations}` と決定的で、completed run は 30 日保持される。同じ hour bucket 内で run が完走したあとにもう一度 cron / 手動再駆動が入ると、`readRunningRun` は null（completed なので）を返し、そのまま `INSERT INTO global_maintenance_runs` に進んで `run_id` の PRIMARY KEY 違反になる。catch は `databaseError` へ落とすので、呼び出し側には DB 障害と区別できない `SystemError` が出る。memory は `table.set(candidateRunId, …)` で completed 行を上書きして `started` を返すので、両バックエンドの観測が割れる（ポート JSDoc は「only after completion does a candidate run start fresh (`started`)」なので memory 側が契約に合っている）。適合スイートは run ごとに別 ID を使うので、この分岐を踏まない。
  - 提案: `INSERT … ON CONFLICT (run_id) DO UPDATE SET status='running', tables=…, as_of=…, lease_owner=…, lease_until=…, completed_at=NULL, expires_at=NULL` にして memory と同じ「作り直し」に揃える（lane 側も `conflict: ["status","table_index","cursor","command_key"]` へ）。あるいは completed 行が残る場合の振る舞いを契約として決め、両バックエンド・適合スイートに 1 ケース足す。

- **[W-006]** `DEFAULT_MAINTENANCE_TABLES` の実体が 3 つに増えた
  - 場所: `packages/core/src/application/di/cloudflareRuntime.ts:131`、`packages/core/src/adapters/cloudflare/__tests__/conformanceBackend.ts:294`、既存の `packages/core/src/adapters/memory/store.ts:376`
  - 理由: [ADR 062](../../../spec/adr/062-unknown-sweep-table-skip.md) の「残存条件（原因 2 は解消しない）」がまさにこれ — run の表集合の供給元と sweep レジストリの供給元がずれると、その表は**恒久的に、静かに、掃かれない**（未知表は error ログを残して ack で飛ばされるだけ）。今回それが 3 コピーに増え、うち 1 つ（`cloudflareRuntime.ts`）は `authStateSweeps` の登録キー集合とも独立に手で並べられている。今は 5 表が一致しているが、表を 1 つ足すときに 3 か所を同時に直す義務が生まれた。
  - 提案: 既定の表集合を 1 か所（`application/cleanup/participants.ts` の隣あたり、`REQUIRED_FINALIZE_RECEIPTS` と同じ位置づけ）へ引き上げ、memory / cloudflare / 適合ハーネスの 3 者がそこを読む。少なくとも `cloudflareRuntime.ts` の `authStateSweeps` のキー集合と `DEFAULT_MAINTENANCE_TABLES.authStatePrune` が同一であることを型で結ぶ（`Record<AuthStateTable, ExpirySweep>` のキーから配列を導く）だけでも、ADR 062 が挙げた「綴りを誤る」経路は塞げる。

- **[W-007]** `DO NOTHING` の文に `upsert` の行像を添えているので、行が既にあると read-your-writes が嘘をつく
  - 場所: `packages/core/src/adapters/cloudflare/d1/repositories/accountDeletionManifestStore.ts:257`（`begin`）、`packages/core/src/adapters/cloudflare/d1/repositories/identityRemovalReceiptStore.ts:62`（`record`）
  - 理由: どちらも「先に読んで在れば早期 return、無ければ `INSERT … ON CONFLICT DO NOTHING`」という形だが、write-set には `upsert({ row })` として**新しい行像**を積んでいる。読みと適用は原子的ではないので、あいだに別 UoW が同じ鍵で commit すると、SQL は正しく何もしない一方でオーバーレイには自分の行像が残る。同一 UoW 内で `describe(operationId)` / `findByIdentityId(id)` を続けて呼ぶと、実際には他人が書いた行なのに自分の `user_id` / `operation_id` が返る。`begin` は「A replayed begin must preserve everything already recorded」というコメントが付いているだけに、オーバーレイ側だけがその不変条件を破っている。
  - 提案: 2 つとも `opaque(…)` にして、オーバーレイに寄与させない（[ADR-029](../adr.md) が manifest の item 側で採った判断と同じ）。読み返しが要るなら、逆に `readRow` を `query` へ寄せて素通しにする。どちらでもよいが、「SQL は何もしないのに行像だけ残る」形は避ける。

- **[W-008]** 本束の `_occ_guard` が実際に発火することを観測するバックエンド固有テストが無い（AC-4）
  - 場所: `packages/core/src/adapters/cloudflare/__tests__/`（`durability.test.ts` / `idempotency.test.ts` / `lease.test.ts`）
  - 理由: AC-4 は「適合スイートが観測できない driver 固有の性質 — SQL 制約違反、bound parameter 上限、D1 batch の原子性 …」を統合テストで確認せよと言う。実際 `durability.test.ts` は batch 原子性を、`support.test.ts` は binding 上限を、`idempotency.test.ts` は outbox claim の競合を観測している。ところが**一意性予約と distributed operation の競合**、すなわち本束で `_occ_guard` と部分ユニーク索引が守っている当の性質には、実バインディングのテストが 1 つも無い。memory は UoW を直列化するので適合スイートからは原理的に観測できない領域であり、AC-4 の言う「memory が証明できない性質」の中心にあたる。
  - 提案: 2 ケース足す。(a) 同一 `(kind, normalizedKey)` への `reserve` を `Promise.all` で 2 本撃ち、ちょうど 1 本が成功、もう 1 本が `EMAIL_ALREADY_USED`（`occGuard` でも `unique` でも同じ符号へ翻訳されること）になる。(b) 同一 `(kind, partitionKey)` への `beginOrResume` を 2 本撃ち、running が 1 件だけになる。どちらも `lease.test.ts` の「gives a contested row to exactly one of two writers」と同じ形で書ける。

- **[W-009]** 作業経緯を語るコメントと、役目を終えた足場が残っている
  - 場所: `packages/core/src/adapters/cloudflare/__tests__/pendingPorts.ts:1`（`PENDING_PORTS` は空配列＋ステップ見出しコメントだけ）、`packages/core/src/adapters/cloudflare/__tests__/conformance/identity.test.ts:12`（「Red until they are: a failure reading "not implemented: X.y" means the adapter is missing…」）、同 `directory.test.ts:1` ほか各束の「Step N — …。Ports wired in …」
  - 理由: CLAUDE.md の既定は「コメントは WHY が自明でないときだけ」。`pendingPorts.ts` は 78 行のうちほぼ全部が「並列委譲中に未実装ポートをどう埋めるか」という**完了した作業手順**の説明で、`PENDING_PORTS` は空、`port(name, build)` は今や `build()` を呼ぶだけの恒等関数になっている。`identity.test.ts` の「Red until they are」は過去の状態を説明する文で、現在の読者には意味を持たない。`ports/{束}.ts` の「Owner of this file wires each port by (1) deleting its name from `PENDING_PORTS` …」も同種。
  - 提案: `pendingPorts.ts` を削り、`ports/{束}.ts` は factory を直接返す形に戻す（`port("UserRepository", () => …)` → `createD1UserRepository(deps)`）。束の見出しコメントは「どの適合スイートがこの束を見るか」だけを残す。次のスライスが同じ足場を欲しがったら、その時に git 履歴から戻せばよい。

- **[W-010]** `activate` の「複数行を全部か無かで publish する」ループは、`operation_id UNIQUE` のせいで 1 行しか回らない
  - 場所: `packages/core/src/adapters/cloudflare/d1/repositories/identityUniqueDirectory.ts:278`（`// Every row is checked before any is written: the durable claims of one operation publish together or not at all.`）
  - 理由: `identity_unique_reservations.operation_id` は `NOT NULL UNIQUE`（spec の列表どおり）なので、`readByOperation` は定義上 0 件か 1 件しか返さない。したがってこのコメントが説明する性質は成立しようがない。ポート JSDoc の `activate(operationId)` / `release(operationId)` は複数行に対する操作として書かれており（"Drops the operation's `reserved` and `releasing` rows"）、memory 実装も `rowsByOperation` が配列を返す形で複数行を許すので、契約・memory・D1 スキーマの三者で「1 operation = 何行か」の理解が割れている。今日の呼び出し側は `reservationOperationId(parent, key)` で鍵ごとに別 ID を導出するので実害は無いが、将来 1 つの operation ID で 2 鍵を予約する呼び出しが現れると、2 件目の `reserve` が `operation_id` の UNIQUE 違反を起こし、`translateReserve` がそれを**その鍵が使われている**（`HANDLE_ALREADY_USED` など）と誤訳する。空いている鍵に対して「使われています」と返す形になる。
  - 提案: どちらかへ倒して 3 者をそろえる。(a) 1 operation = 1 行を契約として確定し、ポート JSDoc の複数形と memory の `rowsByOperation` を単数へ寄せ、このコメントを削る。(b) 複数行を認めるなら spec の `operation_id UNIQUE` を落とし、`(operation_id)` の非 UNIQUE 索引にする。少なくとも `translateReserve` は `unique` を無条件に「鍵が取られている」と読まないこと（PK 衝突と `operation_id` 衝突を区別する）。

#### その他の観察（対応不要と判断したもの）

- `sessions.token_hash` / `auth_tokens.token_hash` の `UNIQUE` はポート契約が要求しないが、[ADR 054](../../../spec/adr/054-provider-account-uniqueness-owner.md) が「契約として要求されない DB 側制約を置いてよい」と明示しており、spec の列表とも一致するので問題なし。
- `LoginAttemptStore.recordFailure` の `CASE WHEN expires_at <= ?` は memory と適合スイート（ADP-identity-036/038）に一致しており、[ADR-012](../adr.md) と spec 改訂も対で入っている。単一文のままなので 10 並列 = 10 の原子性も保たれる。アカウント列挙耐性（[ADR 028](../../../spec/adr/028-account-enumeration-resistance.md)）に関しては、この store は判定材料を返すだけで応答の形を決めないので影響なし。
- `OAuthStateStore.take` は `WHERE state = ? AND state_binding_hash = ?` の `DELETE … RETURNING` 1 文で、期限は返った行で判定している。spec の記述（`### oauth_flow_states` 末尾）と [ADR 034](../../../spec/adr/034-oauth-callback-browser-binding.md) の「照合が消費と同一の原子操作」に厳密に一致する。束縛不一致で行が残ることも確認した。
- `deleteExpiredPage` / `deleteBoundedByKey` が 1 ページを件数ぶんの `DELETE` 文にしている点は、[ADR-014](../adr.md) がトレードオフとして明示的に記録済み。ただし 5 表 × 100 件を 1 invocation で回すと D1 の query 予算（500）に接するので、`spec/platform/index.md` の予算節に 1 行実測を足すか、`deleteRowsFromJson` + `markTouched` へ寄せる価値はある（今回は指摘に数えない）。
- `_occ_guard` の節、`scope_task_due_index` の節、`_scope_identity` の節、`login_attempts` の SQL 断片、`distributed_operations` の kind 込み一意索引 — いずれも spec 改訂が実装と一致しており、`distributed_operations` の kind スコープ化は memory 実装（`inPartition` が `kind` で絞る）に spec を合わせた向きなので契約は弱まっていない。
- `membership_directory` の `membership_id` NULL 可と `(user_id, operation_id)` 索引は [ADR-027](../adr.md) に理由付きで記録済み、migration ファイル冒頭にも書かれている。`CHECK (state NOT IN ('active','removing') OR membership_id IS NOT NULL)` が settled edge の不変条件を保っているので、契約は弱まっていない。
- `UserBatchReader` の 100 件上限・`SystemError(DatabaseError)`・`json_each` 展開は契約どおりで、`support.test.ts` が実データ 100 行で展開の完全性まで観測している。
- staged session（UoW 内）で `reserve` / `beginOrResume` が競り負けた場合、commit 時の翻訳が既定の `OPTIMISTIC_LOCK_FAILURE` になり固有符号を失う点は [ADR-013](../adr.md) が一般則として記録済み。現在の呼び出し側はこの 2 ポートを常に autocommit 経路（container 直下）から呼ぶので実害なし。
