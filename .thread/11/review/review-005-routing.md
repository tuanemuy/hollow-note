以下は「問題なし」と確認した主要点（再検証の記録として残す）。

- **`NoteRouteStore` の 5 状態と CAS** — 9 遷移すべてが「読んだ行像の全列書き戻し + 行同一性 guard」で閉じている。guard の同定タプル `(note_id, state, route_version, operation_id, migration_id)` は網羅的で、9 遷移のいずれもこの 5 列の少なくとも 1 つを動かすため「別 writer が動かしたのに guard が通る」経路は無い。`switchMove` の lost-response 再試行は `state = active ∧ route_version = expected + 1 ∧ last_migration_id = migrationId` の 3 条件で、stale 要求（`expectedRouteVersion` 違い）とは別分岐へ落ちる。`reserveCreate` は `operation_id` 一致で冪等、期限切れ予約だけを奪う。物理 schema の 5 本の `CHECK` はどの遷移でも破れない（`beginMove` が `operation_id` を触らない点も、`active` へ至る全経路が `operation_id` を保持するので問題にならない）。
- **`readableRow` の安全側フィルタ** — `reserved` / `purging` を落とし、`tombstone` は期限まで返す。memory 実装（`adapters/memory/repositories/noteRouteStore.ts:47-58`）と同型で、適合スイート `ADP-note-043/044/045` が `resolve` の `tombstone` を固定している。
- **keyset の正しさ** — `noteRouteFanOutReader` は `OFFSET` を使わず `note_id > ?` の 1 本、`state <> 'reserved'` は残余述語、索引 `note_routes_created_by_idx` / `note_routes_scope_idx` が `(key, note_id)` なので keyset 順が索引から出る。`probe = limit + 1` で次カーソルの有無を追加クエリ無しに決めており、cursor には query fingerprint が乗るので走査をまたいだ再生は `INVALID_PAGINATION` になる。NoteId は ASCII なので JS の `>` と SQLite BINARY 照合が一致する。
- **`OutboxRepository`** — lease は `claimed_at IS NULL OR claimed_at <= now - leaseMs` を `UPDATE … RETURNING` の 1 文に閉じ込めており、2 relay の同時 claim は SQLite の書き直列化で 1 人に決まる（`__tests__/idempotency.test.ts:128`）。id 衝突 no-op は `ON CONFLICT (id) DO NOTHING`（ADR 042）、quarantine は `failed_at IS NOT NULL` の候補除外、staged 拒否は `refuseStaged` が `claimPending` / `pruneProcessed` に掛かる（`__tests__/routeGuard.test.ts:208`）。`finalize` の `UPDATE … FROM json_each` は SET 句の `?` が FROM の `?` より前にあり、位置束縛の順序も合っている。サイズ上限は 1 binding 単位で見ており（`__tests__/routeGuard.test.ts:231`）、`assertBindable` の件数上限とは軸が違うので二重にならない。
- **`claimDue` の per-row 排他** — `claimGuardStatement` を `claimStatement` の直前に `opaque` で積む形で、staged / autocommit の両方で敗者が中断する。**両経路とも実バインディングで観測されている**（`__tests__/lease.test.ts:170` と `:231`）。
- **ポート JSDoc に足した「1 unit of work につき 1 回」** — バックエンド非依存の呼び出し側前提として妥当。理由（ステージする backend は commit 済み行から候補を選ぶ）は memory 側の振る舞いを狭めず、memory は自明に満たす。唯一の呼び出し側 `runDueScopeTasks` は `scopeUnitOfWorkProvider.run` の中で `claimDue` を 1 回だけ呼び、settle（`backoff` / `schedule` / `complete`）は別の `run` に分けているので前提を守っている（`application/workers/scopeTaskRunner.ts:169-171, 219-221`）。適合スイートは `forScope(...)` の autocommit セッション越しに呼ぶので、そもそも unit of work の中に入らない。
- **`OPTIMISTIC_LOCK_FAILURE` を耐える側を runner に置いた判断** — 契約行に「投げうる失敗」として明記され、runner は**そのコード 1 つだけ**を skip して他の `ConflictError` は投げ返す。肯定・否定の両ケースがテストで固定されている（`application/workers/__tests__/scopeTaskRunner.test.ts` の 2 ケース）。
- **constructor が alarm を張るだけになった変更** — `armForStoredRows` は `scopeAlarmDrivesTasks()` が偽なら何もせず、真でも `armNoLaterThan` しか呼ばない。したがって「publish 失敗が張った再試行 alarm を、evict 後の最初の読みが消す」経路が塞がっている（`__tests__/alarm.test.ts:587`）。alarm を消す地点は `rescheduleAlarm` の 1 か所（turn の出口）だけで、`spec/platform/index.md` の書き直された記述と一致する。cold start のコストは DDL（`IF NOT EXISTS` 22 文）＋ `_scope_identity` の 1 読み＋ `getAlarm` / `setAlarm` で、外部 I/O を `blockConcurrencyWhile` の中で待たない要件も守られている。
- **publish の直列化が継続を止めないか** — `armAndPublish` は例外を外へ出さない（`tolerate` と `catch` で二重に封じられ、`upkeep` 鎖も `catch(() => {})` で汚染されない）ので、`alarm()` の `finally` が turn の例外を差し替えることも、`applyWriteSet` が commit 済みの書きを失敗として返すこともない。alarm が張られっぱなしになる経路は「駆動しない配備に残った古い alarm」だけで、配送された turn が `EMPTY_TURN` → `rescheduleAlarm` で自分で落とす（`__tests__/alarm.test.ts:555` が実バインディングで観測）。
- **`listDue` と due index の同期・有界化** — index の候補述語（`lease_expires_at IS NULL` ↔ `status = 'pending'`）は scope 側 schema の `CHECK ((status = 'running') = (lease_expires_at IS NOT NULL))` に支えられて厳密に対応する。有界化（優先度ごと 25 行）で溢れた行は「全置換 publish」により settle のたびに繰り上がるので、恒久的に取りこぼす経路は無い。`failed` 行は index に載らず、`backoff` が `failed` へ落とす経路も write-set が `scheduled_tasks` を名指すので publish が追随する。
- **`ScopeCleanupAdmissionStore`** — 書き込みバリアは `assertWritable` / `assertActorWritable` が「receipt が 1 件でもあれば拒否」で、completed でも閉じたまま（`abort` だけが開ける）というポート記述どおり。所有権検査は `requireOwner` が `operation_id` 一致 ∧ `state = running` の 2 条件、component ack は `json_set` で可換、既定は `ALL_COMPONENTS`（宣言なし＝ stall 側）。**「1 personal scope の barrier receipt は 1 件」は実装・canon・スイートの三者で一致している** — 実装は `kind` で 1 件として読み `beginPersonalAccountDeletion` が `NOT EXISTS(kind)` guard で 2 件目を原子的に弾き、`spec/database/index.md` の `applied_operations` 節に同文が入り、`application/cleanup/personalCleanup.ts` の「full-page branch は全 backend で到達しない」という JSDoc もその前提を明示している。
- **AC-6 の fencing 決着** — 「`leaseMs` の運用下限＋単一 writer」で決着し、`spec/platform/index.md`「Scope Alarm」が driver ごとに場合分けして書き直されている。実装側の裏づけ（レジストリが空なら object は claim も武装もしない）は `do/alarm.ts:83-85, 254-263, 277-287` にあり、production ソースに `registerScopeTaskHandler` の呼び出しは 0 件なので既定の合成は「中央 runner 単独」に落ちる。`__tests__/alarm.test.ts:284` がそれを観測している。
- **セキュリティ** — cursor は非認証だが「どこから始まるか」しか決めず、`page()` は cursor とは独立に `condition` と `state <> 'reserved'` を必ず掛ける。`ScopeObject.bind` / `assertAddressed` が scope の取り違えを `DataIntegrityError` で拒む。`json_set` のパス連結に入るのは型付きリテラル union のみで注入面は無い。SQL はすべて位置束縛。

#### Warnings

- **[W-001]** `scope_task_due_index` の canon が、autocommit publish 経路の利用者を「中央 runner の claim / settle」と書いているが、実装の中央 runner はその経路を通らない

- **[W-002]** autocommit 経路の due index publish だけが直列化の外にあり、「索引に載らなかった行は誰も探しに来ない」非対称ドリフトを再び開きうる
  - 場所: `packages/core/src/adapters/cloudflare/do/repositories/scopeTaskScheduler.ts:101-124`
  - 理由: 設計は「publish は全置換なので順序さえ保てばよい。だから object は自分の publish を読みごと直列化する」と繰り返し述べる（`do/dueIndex.ts:50-56`、`do/scopeObject.ts:163-171`、`spec/database/index.md:1111`）。ところが autocommit 分岐の publish は object の `upkeep` 鎖の外で走るので、同じ scope へ並行に settle する 2 人がいれば古いスライスが後に着地しうる。落ちた行は `listDue` から消え、`spec/database/index.md:1113` が「唯一の回復経路」と書く再試行 alarm は **publish が失敗したときにしか張られない** — 成功したが古いスライス、では張られない。したがってその scope は次に誰かがその scope へ書き込むまで永久に見えなくなる。今日は production の呼び出し側が無い（W-001）ので実害は無いが、配備スライスが Queue consumer から UoW を開かずに settle させた瞬間に開く穴で、その時に気づける仕掛けが無い。
  - 提案: publish をリポジトリから外し、object 側の 1 本に寄せる。`RowMutation` は既に `table` を持っているので、`createAutocommitSession.write` が touched tables を集めて、executor が `ScopeSqlExecutor` なら `apply` ではなく `applyWriteSet(statements, tables)` を呼ぶ形にすれば足りる（`sql/session.ts:118-120` と `do/scopeStub.ts:44-46`）。そうすれば autocommit の書きも object の `armAndPublish` 鎖を通り、`publishDueIndex` / `logger` / `db` 依存を scheduler から落とせ、W-001 の canon 記述もそのまま真になる。武装しない要件（ADR-020）は `rescheduleAlarm` がレジストリ空なら何もしない既存の分岐で保たれる。

- **[W-003]** constructor の再武装（`armForStoredRows` が実際に alarm を張る側）を観測するテストが無い
  - 場所: `packages/core/src/adapters/cloudflare/do/scopeObject.ts:86-101` / `packages/core/src/adapters/cloudflare/__tests__/alarm.test.ts:587-608`
  - 理由: `rebuild()` を使う唯一のケース（`:587`）はハンドラを登録しないまま走るので、`armForStoredRows` は `scopeAlarmDrivesTasks()` の偽分岐で即 return する。つまりこのテストが固定しているのは「constructor が alarm を**消さない**」ことだけで、`spec/platform/index.md` が新しく約束した「切り替え時に既に積まれている行は、その object が次に起きたときに武装され直す」ほうは 1 行も観測されていない。`armForStoredRows` を丸ごと no-op にしても全テストが緑になる。
  - 提案: `register(...)` してから、alarm を持たない状態の object に `scheduled_tasks` の行を（`arm = false` の `seed` で）置き、`rebuild(scope)` → 任意の読み、で `armedAt(scope)` が `nextWakeAt` になることを見る 1 ケースを足す。既存のヘルパー（`seed` / `rebuild` / `armedAt`）だけで書ける。

- **[W-004]** due index スライスの並び順が canon の記述と食い違う
  - 場所: `packages/core/src/adapters/cloudflare/do/scheduledTasks.ts:89-104` / `spec/database/index.md:1112`
  - 理由: canon は「優先度ごとに `due_at` の早い 25 行」と書くが、実装は `ORDER BY COALESCE(lease_expires_at, due_at), kind, operation_id` で並べる。実装のほうが正しい（`running` 行が次に取れるのはリース失効時なので、`due_at` で並べると遠い将来にリースが切れる行が、いま due な `pending` 行をスライスから押し出しうる）。canon の文言だけが古い。AC-9 の対象。
  - 提案: 当該行を「優先度ごとに、次に取れる時刻（`pending` は `due_at`、`running` はリース失効時刻）の早い 25 行」へ直す。

- **[W-005]** `armAndPublish` の直列化に合流（coalescing）が無く、同一 scope への並行 commit が publish 回数ぶんの待ちを積む
  - 場所: `packages/core/src/adapters/cloudflare/do/scopeObject.ts:172-177`
  - 理由: `applyWriteSet` は自分の publish だけでなく、先に鎖へ並んだ publish すべての完了を待つ。publish は「storage の読み 1 回＋ global D1 への batch 1 回」で、D1 往復は 10ms 台。1 つの scope に N 件の `scheduled_tasks` 更新が並ぶと、N 番目の呼び出し元の応答は N 回ぶんの往復だけ遅れる。スライスは全置換なので、正しさに必要なのは「自分の書き込みより後に読み始めた publish が 1 回ある」ことだけで、N 回すべてを直列に流す必要は無い。
  - 提案: 「まだ `scheduled_tasks` を読み始めていない publish が鎖の末尾にあるなら、それに合流して新しく積まない」形にする（`armAndPublishNow` の入口で読み開始フラグを立て、`armAndPublish` はフラグが未立ての末尾 promise をそのまま返す）。順序の保証は変わらず、待ちは最大 2 回ぶんに収まる。急がないなら現状のままでも正しさは保たれるので、性能上の指摘に留める。
