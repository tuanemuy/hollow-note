  - 提案: 「**適合スイートが叩くポートは**一切 stub しない。バックエンド固有テストが、対象外のポートを触ったら落とすために throw する stand-in を使うことはある」程度に条件を付ける。

- **[W-010]** `spec/platform/index.md` の改訂が「往復」という同じ語で、隣の契約文と逆のことを言っている
  - 場所: `spec/platform/index.md:152-156`（改訂後）、`spec/testcases/storage/deleteFilesByOwner.md`（「件数に比例した追加の往復を要求しない」— AC-5 により不変）
  - 理由: 改訂文は「書き込みをバッチ件数によらず 1 回の原子適用にまとめる（scope DO なら `transactionSync` 1 回 = **RPC 1 往復**）」と書き、続けて「1 turn の SQL 文の総数は件数に比例する … 1 件あたり読み 2（`findById` + 削除前の版確認）」と書く。ところが `__tests__/deleteFilesByOwner.test.ts:86` の計数器は `query` を「one SQL statement and **one round trip** each」と定義しており、実測 `reads = 2n + 2` は **2n 回の DO への RPC 往復**そのものである。つまり同じ節の中に「往復は件数に比例しない（契約）」と「往復は 2n（実測）」が、どちらも「往復」の語で並んでいる。AC-5 が testcases 側を動かすなと言ったのは正しいが、その結果として platform 側に軸の説明を足す義務が生じている。実測と判断（ADR-025）そのものは妥当で、テストも実効的である。
  - 提案: platform 側の一文を「**1 回の原子適用**にまとめる（書き込み側の RPC 往復は 1 回）。読み側は 1 件あたり 2 回の RPC を要する」と書き分け、testcases の「往復」が**ポート呼び出しの追加往復**（`listByOwner` を件数ぶん呼ばない、の意）を指すことを 1 行で明示する。

#### 判断（Blocker にしなかったもの）

- **`application/di/cloudflareRuntime.ts` が `D1Database` / `R2Bucket` / DO を名指すこと自体はレイヤー規約違反ではない。** CLAUDE.md は「Application ... **the DI wiring**」を application 層の持ち分と明記しており、`memoryRuntime.ts` も既に `adapters/memory/*` を 30 本以上 import している。合成根はバックエンドを名指してよい唯一の場所であり、内側（domain / usecase / ports）に Cloudflare の名前は 1 つも漏れていない（`grep` で確認）。ADR-030 が代替案「`adapters/cloudflare/runtime.ts` へ置く」を検討して棄却した理由（`memoryRuntime.ts` と並べて読めること）も筋が通る。ただし代償として `tsconfig.json` の `exclude` / `tsconfig.cloudflare.json` の `include` に**ファイル 1 つを名指しで両方書く**例外ができた（`packages/core/tsconfig.json:8-11`）。2 つ目のランタイムを足すときに片方だけ更新すると、そのファイルはどちらのプログラムからも消えて**型検査から静かに落ちる**。`src/application/di/cloudflare*.ts` のような規約パターンにしておけば、名指しの二重管理を避けられる。
- **`cloudflareRuntime.ts:47-52` が `adapters/memory/` から暗号アダプターを import している点は、スコープ外として起票に回した判断で妥当。** ADR-030 と plan.md「含まれないもの」が根拠を述べており、scrypt が `nodejs_compat` 下で動くことは `harness.test.ts:104-109` が実測で固定している。ただし読み手には「Cloudflare ランタイムが in-memory バックエンドに依存している」と読める。`ephemeralKeyRing` を `crypto.getRandomValues` に差し替えた（`:143-146`）ように、これらは既に backend-neutral な実装である。分離 Issue を起票する際は `adapters/crypto/` への移動を提案に含めること。
- **`AppRuntime` の抽出は妥当だが、`MemoryRuntime` の適合が `runtimeComposition.test.ts:116-123` の 1 ケース（`asAppRuntime(null as unknown as MemoryRuntime)`）だけで固定されている点は残る弱さ。** progress.md も「後続に引き継ぐ観測」として自己申告している。AC-7 を理由に `memoryRuntime.ts` を触らなかった判断は理解できるが、`export type MemoryRuntime = AppRuntime & Readonly<{ backend; mailSender }>` への書き換えは振る舞いを 1 バイトも変えない型注釈であり、AC-7 の「memory バックエンドと Node entry の振る舞いを変更していない」には当たらないと思う。次スライスで最初に片付ける対象として妥当。
- **`wrangler.test.jsonc` はテスト専用であることが十分に明確で、本番へ漏れる経路は無い。** 名前が `core-cloudflare-adapters-test`、`main` が `__tests__/worker.ts`、`database_name` / `bucket_name` に `-test` 接尾辞、`account_id` も secret も無し。`wrangler` は既定で `wrangler.jsonc` / `wrangler.toml` を探すのでこのファイルは `-c` 明示でしか読まれず、`package.json` に `deploy` 系スクリプトも無い。`compatibility_flags: ["nodejs_compat"]` と `new_sqlite_classes` の理由もコメントで述べられている。**問題なし。**
- **適合ハーネスの 3 面分離（ADR-004）は実効的に効いている。** DO は factory 呼び出しごとの新しい `namespace` が object 名の一部になるので新しい object、R2 は `${namespace}/` の key prefix、D1 は共有 1 本を factory 冒頭で全消し。`harness.test.ts:118-149` が 3 面すべてを 1 ケースで観測している（後発 backend から先発の user / note / object が見えず、かつ先発の DO / R2 側は残っている）。適合スイート 30 本が `makeBackend(` を 1 ファイル 1 箇所でしか呼ばないことも確認したので、「D1 の wipe が同一テスト内の先発 backend を壊す」経路は今日存在しない。ただし将来 1 テストで 2 backend を作る適合ケースを書くと D1 面だけ破綻するので、その制約は `conformance/backend.ts` の JSDoc 側にも 1 行あるとよい。
- **`.thread/11/adr.md` の ADR-026 が欠番**（ADR-025 → ADR-027）。migration の `0002` 欠番と同じく、読み手が「削られた判断があるのか」を確認する手間になる。W-003 に含めるほどではないが、番号を詰めるか欠番の旨を書いておくとよい。
