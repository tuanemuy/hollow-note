以下は「問題なし」と確認した主要点（再検証の記録として残す）。

- **`NoteRouteStore` の 5 状態と `routeVersion` の CAS** — 9 遷移すべてが「読んだ行像の全列書き戻し（`writeStatement`）＋ 行同一性 guard」で閉じている。`unchangedGuard` の同定タプル `(note_id, state, route_version, operation_id, migration_id)` は `IS` 比較で NULL も含めて厳密で、9 遷移のいずれもこの 5 列の少なくとも 1 つを動かすため「別 writer が動かしたのに guard が通る」経路は無い。新規行だけが `absentGuard`（`NOT EXISTS`）を使う。`switchMove` の lost-response 再試行は `state = active ∧ route_version = expected + 1 ∧ last_migration_id = migrationId` の 3 条件で、stale 要求（`expectedRouteVersion` 違い）とは別分岐へ落ちる。`reserveCreate` は `operation_id` 一致で冪等、期限切れ予約だけを奪い、奪う場合も `route_version` は 1 のまま（`reserved` 行は定義上 1 しか取り得ない）。`lastMigrationId` は `switchMove` だけが書き、以後どの遷移も消さないので再試行判定の材料として生き続ける。
- **物理 schema の 5 本の `CHECK`** — `moving` ↔ `target_scope_*`、`reserved` ↔ `reservation_expires_at`、`tombstone` ↔ `tombstone_expires_at`、`reserved/moving/purging ⇒ operation_id NOT NULL` のいずれも、上記 9 遷移が書く行像で破れない（`activateCreate` が `reservation_expires_at` を、`abortMove` / `switchMove` が `target_scope_*` を明示的に NULL へ戻す）。
- **`readableRow` の安全側フィルタ** — `isReadable` が `reserved` / `purging` を落とし、`tombstone` は `tombstone_expires_at` を clock と突き合わせて期限まで返す。`resolve` / `resolveMany` の両方が同じ関数を通る。`ScopeRouter.resolveNote` はその結果が null なら `NOTE_NOT_FOUND` へ倒すので、進行中の作成・purge が「書き込める scope」として外へ漏れる経路が無い。
- **keyset の正しさ** — `noteRouteFanOutReader` は `OFFSET` を使わず `note_id > ?` の 1 本。`state <> 'reserved'` を残余述語に留める判断は索引 `note_routes_created_by_idx` / `note_routes_scope_idx` が `(key, note_id)` である以上正しく、コメントと DDL のコメントが一致している。`probe = limit + 1` で次カーソルの有無を追加クエリ無しに決め、`limit` は 200 で頭打ち（ポート JSDoc の「max 200 across all shards」と一致）。cursor は fingerprint を持つので走査をまたいだ再生は `INVALID_PAGINATION`。staged セッションで `LIMIT` と自 UoW の書きが交差した場合は `readRows` が修復不能として落ちるが、`noteRouteFanOutReader` は worker container の autocommit session にしか組まれていないので到達しない。
- **`OutboxRepository`** — lease は `claimed_at IS NULL OR claimed_at <= now - leaseMs` を `UPDATE … RETURNING` の 1 文に閉じ込め、`RETURNING` の順序を信用せず `(created_at, id)` で並べ直す。id 衝突 no-op は `ON CONFLICT (id) DO NOTHING`（ADR 042、ポート JSDoc の「stored row を一切触らない」と一致）。quarantine は `failed_at IS NOT NULL` の候補除外で、`finalize` は `next_attempt_at IS NULL` のときだけ `failed_at` を立てる。`finalize` の `UPDATE … FROM json_each` は SET 句の `?` が FROM の `?` より前にあり、SQLite の位置束縛順とも合う。成功と失敗を 1 mutation 群＝ 1 batch にまとめているので「配送済みなのに再 claim 可能」な中間状態が無い。staged 拒否は `refuseStaged` が `claimPending` / `pruneProcessed` に掛かる（`finalize` は staged でも原子性が保たれるので掛けない判断も筋が通る）。サイズ上限は `save` の JSON 1 binding に対して 1,000,000 bytes で見ており、`assertBindable` の件数軸とは別。
- **`claimDue` の per-row 排他とエラー契約** — `claimGuardStatement` を `claimStatement` の直前に `opaque` で積む形で、SQLite が 0 行 UPDATE をエラーにしないことを `_occ_guard` で補っている。staged / autocommit の両経路が実バインディングで観測済み（`__tests__/lease.test.ts:170` と `:231`）。ポート JSDoc は「staged backend は commit で `OPTIMISTIC_LOCK_FAILURE` を投げる」と明記し、`runDueScopeTasks` は**そのコードだけ**を skip して他の `ConflictError` は投げ返す（両ケースが `application/workers/__tests__/scopeTaskRunner.test.ts` で固定）。
- **`runDueScopeTasks` の耐性と前提遵守** — scope 重複排除、budget 内でしか claim しない（claim して訪問しない行はリース満了まで不可視になるため）、1 タスクの例外を `backOff` で隔離し backoff 自体の失敗も飲む。ポートが新たに明記した「1 unit of work につき `claimDue` は 1 回」も守れている（claim と settle は別の `run`）。
- **`armAndPublish` の `Upkeep` 分岐が継続を止めないか** — `commit` は `armForStoredRows`（`armNoLaterThan` しか呼ばず絶対に消さない）、`turnExit` だけが `rescheduleAlarm`（唯一の削除地点）。これにより「publish 失敗が張った再試行 alarm を、後続の commit や evict 後の再構築が消す」経路が構造的に消え、`spec/platform/index.md`「Alarm を消す地点は turn の出口 1 か所に限る」と実装が 1 対 1 になった。`armAndPublishNow` は arm→publish の順で、publish 失敗時は `DUE_INDEX_REPUBLISH_DELAY_MS` へ引き寄せ直す。副作用は「最後の行が消えた commit の直後に空 turn が 1 回走る」だけで、その turn が `EMPTY_TURN` → `rescheduleAlarm` で自分を落とす。例外は `tolerate` と `catch` で二重に封じられ、`upkeep` 鎖も `catch(() => {})` で汚染されない（commit 済みの書きを失敗として返さない）。この 5 つの性質はすべて `__tests__/alarm.test.ts:518 / 557 / 589 / 619 / 650 / 715 / 765` が実バインディングで観測している。
- **object 駆動配備で autocommit scheduler を拒む変更** — 判定は `!session.staged && scopeAlarmDrivesTasks()` の 2 条件で、`session.write` の**前**に落ちるので行が半端に残らない（`alarm.test.ts:678` が「拒否後も行数 1 のまま」を観測）。production では `registerScopeTaskHandler` の呼び出しが 0 件、適合ハーネスの `forScope` は handler を登録しないので発火しない。workers pool の分離は**ファイル単位**なので、`alarm.test.ts` の登録が `conformance/scopeInfra.test.ts` へ漏れることも無い（加えて `afterEach` で undo）。将来 object 駆動を選ぶ配備は UoW を開く経路（＝ `createCloudflareScopeTaskScheduler` を `buildRepositories` から取る経路）だけが残るので、壊れるのは「UoW を開かずに settle する」という、そもそも武装されない使い方だけ。
- **`ScopeTaskQueue.listDue` と due index の同期・有界化・並び順** — index の候補述語（`lease_expires_at IS NULL` ↔ `status = 'pending'`）は scope 側 schema の `CHECK ((status = 'running') = (lease_expires_at IS NOT NULL))` に支えられて厳密に対応する。スライスの有界化は `PARTITION BY priority ORDER BY COALESCE(lease_expires_at, due_at)` で優先度ごと 25 行 ＝ 全体 100 行、`status <> 'failed'` を除外。前ラウンドで指摘した canon 側の文言（`spec/database/index.md:1112`）が「次に取れる時刻（`pending` は `due_at`、`running` はリース失効時刻）の早い 25 行」へ直っており、実装と一致した。`listDue` 側の候補順（`priority, due_at, kind, operation_id`）はポート JSDoc の選択規則そのままで、scope 同点は SQL の `scope_type, scope_id` と `Array.prototype.sort` の安定性で決まる。溢れた行は全置換 publish により settle のたびに繰り上がる。commit RPC 内で publish が終わってから応答するので `run` 解決時点で索引が新しいことも `runtimeComposition.test.ts:238` が実バインディングで観測している。
- **`ScopeCleanupAdmissionStore`** — 書き込みバリアは `assertWritable` / `assertActorWritable` が「receipt が 1 件でもあれば拒否」で、completed でも閉じたまま（`abort` だけが開ける）。所有権検査は `requireOwner` が `operation_id` 一致 ∧ `state = 'running'` の 2 条件で、全 mutation が `runningReceiptStatement` の guard を伴う。component ack は `json_set` のパス連結で可換、連結に入るのは型付きリテラル union のみで注入面は無い。既定は `ALL_COMPONENTS`（宣言なし＝ stall 側、ADR 039）で、`cloudflareRuntime` は `REQUIRED_PERSONAL_CLEANUP_COMPONENTS` を渡す。`pruneCompleted` は `expires_at` を持つ completed 行だけを対象にし、running receipt は `expires_at` が NULL なので時計をどれだけ進めても拾われない。
- **AC-6 の fencing 決着** — 「`leaseMs` の運用下限＋単一 writer」で決着し、`spec/platform/index.md`「Scope Alarm」が driver ごと（object 駆動 / 中央 runner 駆動）に場合分けして書き直されている。「どちらが writer かはハンドラのレジストリが決める」という実装側の裏づけは `do/alarm.ts:83-85, 127-129, 262, 287-289` にあり、`alarm.test.ts:286` が「レジストリが空なら claim も武装もしない」を実バインディングで観測している。
- **AC-1 / AC-2 / AC-4（本観点の持ち分）** — `NoteRouteStore` / `NoteRouteFanOutReader` / `OutboxRepository` / `IdempotencyStore` / `ScopeRouter` / `ScopeTaskScheduler` / `ScopeCleanupAdmissionStore` はすべて共有適合スイートを実バインディングで通す配線になっており（`conformance/route.test.ts` / `conformance/scopeInfra.test.ts`）、`ScopeTaskQueue.listDue` はスイート本体を変えずに `scopeTaskScheduler` スイートの中で観測されている。AC-4 の driver 固有性質（lease 回収・id 衝突 no-op・claim の per-row 排他・alarm の再入）は `lease.test.ts` / `idempotency.test.ts` / `alarm.test.ts:847` が個別に固定している。
- **セキュリティ** — cursor は非認証（ADR 063）だが `page()` は cursor と独立に `condition` と `state <> 'reserved'` を必ず掛けるので、cursor は「どこから始まるか」しか決めない。`ScopeObject.bind` / `assertAddressed` が scope の取り違えを `DataIntegrityError` で拒み、`scopeColumnsFromName` は不正な key を弾く。due index の行は名前空間接頭辞を持たない生の `ScopeKey` で、その制約はテスト側の注意として `dueIndex.ts` に明記されている。SQL はすべて位置束縛で、テーブル名以外の文字列連結は無い。

#### Warnings

- **[W-001]** scope 平面の `pruneProcessed` は実行できないのに、canon はその平面で撃たれる前提で部分索引を正当化している
  - 場所: `packages/core/src/adapters/cloudflare/d1/repositories/outboxRepository.ts:250-264` / `packages/core/src/adapters/cloudflare/sql/executor.ts:98-129` / `spec/database/index.md:1076`
  - 理由: `pruneProcessed` は `session.writeCounted` を通り、`createAutocommitSession.writeCounted` は `executor.applyCounted` が無ければ `databaseError` を投げる。`applyCounted` を持つのは `createD1Executor` だけで、scope 平面の 2 つの executor（`createScopeStubExecutor` / `createStorageExecutor`）はどちらも持たない。つまり **`OutboxRepository` を scope セッションで組んだ瞬間、`pruneProcessed` だけがポート契約を満たさない実装になる**（`__tests__/ports/route.ts:18-20` と `outboxRepository.ts:56-60` はどちらも「1 実装が両平面に当たる」と書いている）。一方 `spec/database/index.md` の `outbox_events` 節は「**部分索引はどちらも両 plane に置く** — `pruneProcessed` は plane を問わず `processed_at IS NOT NULL AND processed_at < ?` を撃つので」と、現在形でその平面での実行を根拠に scope 側 DDL（`do/schema.ts:253-254`）を正当化している。今日は `pruneOutbox` が `WorkerContainer.outboxRepository`（global 平面）しか触らないので実害は無いが、適合スイートも global 平面の合成しか回さないため、**壊れていることを誰も観測できない**。`.thread/11/adr.md` ADR-063 のトレードオフ欄は「`refuseStaged` により global 平面の autocommit session からしか呼べない」と書くが、`refuseStaged` が保証するのは autocommit であることだけで平面は弁別しないので、この一文は根拠として成立していない。
  - 提案: どちらか一方に倒す。(a) `createStorageExecutor` に `applyCounted`（`storage.sql.exec(...).rowsWritten`）を足し、`ScopeObject` に 1 本 RPC を生やして `createScopeStubExecutor` からも答えられるようにする。(b) 本 PR のスコープ（scope outbox の relay / prune は配線しない）に合わせ、ADR-063 の当該行を「scope 平面では `pruneProcessed` は未実装で、relay を配線するスライスが `applyCounted` ごと足す」へ改め、`spec/database/index.md` の索引正当化も「その平面へ prune を配線した時点で効く」と将来形に直す。(b) なら差分は 2 行で、AC-9 の「反映しない差分は adr.md に理由とともに残っている」も満たせる。

- **[W-002]** object 駆動 turn の `leaseMs` がコンパイル時定数で、AC-6 の決着が配備へ委ねた唯一のつまみが CF 側だけ回せない
  - 場所: `packages/core/src/adapters/cloudflare/do/scopeObject.ts:3, 142`
  - 理由: AC-6 は「fencing token を足さず、`leaseMs` を十分に取る運用で足りる」で決着し、ポート JSDoc は「`leaseMs` は配備が選ぶ値で、最悪ケースの turn を超え、かつ age SLO を下回らねばならない」、`spec/platform/index.md`「Scope Alarm」は上下 2 つの境界が作る帯を定義している。つまり**この決着の安全性は配備が値を選べることに完全に依存している**。中央 runner 側はそれが可能で（`runDueScopeTasks` の `options.leaseMs`、Node 側は `SCOPE_TASK_LEASE_MS` 環境変数まで通っている）、`ScopeObject.alarm()` だけがポート定数を直接読んでいる。`ScopeObjectEnv` は `GLOBAL_DB` しか持たないので、object を driver に選んだ配備は帯の中の別の値を選べず、コードを書き換えるしかない。今日 production に object 駆動配備が無いのは事実だが、`spec/platform` の「駆動する配備は帯から選ぶ」は object 駆動を明示的に含んでいる。
  - 提案: `ScopeObjectEnv` に `SCOPE_TASK_LEASE_MS?: string` を足し、`alarm()` が「読めなければ `SCOPE_TASK_LEASE_MS` 定数」へフォールバックする 3 行にする（`di/env.ts` の `leaseMsField` と同じ形）。採らないなら、`spec/platform/index.md`「Scope Alarm」に「object 駆動配備は既定値に固定され、帯の中の別の値を選ぶには配備スライスの追加が要る」と一行書き、AC-9 の対象として閉じる。
