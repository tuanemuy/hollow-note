### Routing / outbox / scope インフラ

#### Blockers

- **[B-001]** ADR-070 で入れた「publish 失敗 → 10 秒後の再試行 alarm」を、`ScopeObject` の constructor が**同じ理由で**消す — 既定配備（レジストリ空）で欠落方向の drift の唯一の回復経路が cold start で失われる
  - 場所: `packages/core/src/adapters/cloudflare/do/scopeObject.ts:80-94`（constructor の `blockConcurrencyWhile` → `rescheduleAlarm`）、`packages/core/src/adapters/cloudflare/do/alarm.ts:254-263`（`rescheduleAlarm`）、`packages/core/src/adapters/cloudflare/do/dueIndex.ts:38-43`（JSDoc の主張）、`spec/platform/index.md:201`、`.thread/11/adr.md` ADR-070
  - 理由: ADR-070 は「武装は `rescheduleAlarm` の**あと**に置く — 先に置くと `deleteAlarm` が再試行を消す」と正しく認識しているが、その手当ては `armAndPublish` の中の 1 か所にしか効いていない。`rescheduleAlarm` を呼ぶ箇所はもう 1 つあり、それが constructor である。`scopeAlarmDrivesTasks()` が false（＝ `registerScopeTaskHandler` の呼び出しが production に 0 件なので既定）だと `rescheduleAlarm` は無条件に `storage.deleteAlarm()` するので、**object が活性化されるたびに、張ってあった再試行 alarm が消える**。
    確実に壊れる経路: publish 失敗で T+10 秒に武装 → object が evict される（この 10 秒間、当該 scope は定義上アイドル。継続が止まっているので誰も触らない）→ 無関係な read / write が来て cold start → constructor が `deleteAlarm` → 再試行は永久に来ない。回復は「同じ scope の `scheduled_tasks` を名指す別の write-set の commit」だけで、ADR-070 自身が「継続要求はその 1 本で駆動されるので実質『次が無い』」と書いた状態に戻る（plan.md の最悪ケース: personal cleanup の継続が止まり `accountDeletionBarrier` が開いたまま User が `deleting` で残る）。
    さらに悪い可能性: 再試行 alarm の**配送そのもの**が cold start になる場合（10 秒アイドルは DO の evict 閾値そのものなので、これが通常経路になりうる）、constructor が `alarm()` の手前で alarm を消す。workerd が「`alarm()` 内の `deleteAlarm` は当該起動を取り消さない」と保証しているのはハンドラ内であって constructor ではないため、既定配備では再試行機構が一度も動かない可能性がある。
    `spec/platform/index.md:201`（「レジストリが空のあいだはこの張り直しが Alarm の削除になるので、既定の配備では何も起きない」）と `dueIndex.ts:38-43`（「That retry does not depend on the deployment driving tasks from the object」）は、この点で真っ向から食い違っている。canon の 2 文が両立していない。
    テストも塞げていない。`__tests__/alarm.test.ts:515`「republishes a slice whose publish failed on its own next alarm」は「これは既定配備で成り立たねばならない」と明言しているが、同じ live インスタンスに対して `runDurableObjectAlarm` を撃つだけなので constructor は 1 度も再入しない。観測しているのは「alarm ハンドラが再 publish する」ことだけで、「再試行 alarm が生き残る」ことではない。
  - 提案: 再試行を alarm 1 本という揮発的な表現から外し、**scope storage 側の状態にする**。たとえば `_scope_identity`（または専用の 1 行表）へ `due_index_dirty` を立て、`publishDueIndex` 成功で落とす。`rescheduleAlarm` はレジストリが空でもこのフラグが立っていれば `deleteAlarm` せず `now + DUE_INDEX_REPUBLISH_DELAY_MS` を返す、という 1 分岐で constructor / `armAndPublish` の両方が同じ規律になる。安価な代案として、constructor の `rescheduleAlarm` を `armAndPublish(stored)` に替える手もある（cold start ごとに slice を書き直すので drift 一般が治る代わりに、活性化ごとに D1 2 文のコストが乗る）。どちらを採るにせよ、テストは「constructor を通したあとに再試行 alarm が残っていること」を観測すること（別インスタンスからの `runInDurableObject` ではなく、`getAlarm()` を cold start 後に読む形）。ADR-070 の Consequences にもこの経路を書き足す。

#### Warnings

- **[W-001]** 同一 scope への 2 つの commit が並ぶと、due index の publish が**古い slice で新しい slice を上書き**しうる（しかも失敗していないので再試行 alarm も張られない）
  - 場所: `packages/core/src/adapters/cloudflare/do/scopeObject.ts:105-115`（`applyWriteSet`）、`:156-177`（`armAndPublish` / `publishDueIndex`）
  - 理由: `applyWriteSet` は `this.sql.apply()`（storage 操作 = input gate が閉じる）のあと、`armAndPublish` で **D1 への `await`** に入る。D1 binding 呼び出しは当該 object の storage 操作ではないので input gate は開き、その隙に次の `applyWriteSet` が配送される。結果、A の「slice 読み → D1 書き」と B のそれが交差でき、**D1 に最後に着地するのが A の slice**という順序が起こりうる。slice は全置換なので、A の slice は B が commit した行を含まない。
    落ちるのは drift の**非対称な悪い側**（索引に載らなかった行）で、しかも publish は成功しているので ADR-070 の再試行 alarm は張られない。B の write-set が「継続を 1 本積んで終わる」commit だった場合、次に同じ scope の `scheduled_tasks` を触る commit は来ないので、そこで鎖が止まる。中央 runner の claim（`scheduled_tasks` を触る write-set）と利用者要求由来の `schedule` が同じ scope で重なれば起きる、という頻度である。
  - 提案: object インスタンス内で `armAndPublish` を直列化する（`private publishing: Promise<void>` にチェーンする 1 行で足りる。slice が全置換なので、順序さえ保てれば最後の publish が正しい）。あるいは publish 直前に `scheduled_tasks` を読み直したうえで、object 側で「自分が読んだ世代より新しい commit が入っていたら publish を後段へ譲る」形にする。前者を推す。`do/dueIndex.ts` の「Replacing the whole slice … converge on the same result」という記述も、順序保証が前提であることを明記すること。

- **[W-002]** AC-6 の決着文（`spec/platform/index.md:197`）の「引き金は『1 scope に複数 writer』であって『複数 worker プロセス』ではない — scope が分かれていれば writer も分かれる」が、既定配備（中央 runner）では成り立たない
  - 場所: `spec/platform/index.md:197`、`packages/core/src/application/workers/scopeTaskRunner.ts:146-210`
  - 理由: 中央 runner は `scopeTaskQueue.listDue`（global D1 の due index）で scope を選ぶ。同じ runner の起動が 2 本並走すれば（Cloudflare の Cron / Queue consumer は前の起動の完了を待たない）、**両方が同じ scope を選びうる**。`runDueScopeTasks` の `claimedScopes` は 1 ラウンド内の重複排除にすぎず、起動をまたいでは効かない。すなわち「scope が分かれていれば writer も分かれる」は Alarm driver の場合にしか言えず、中央 runner の場合は「起動が分かれても writer は分かれない」。
    実害は fencing 節が挙げた通りのもの: 起動 1 が row X を claim してリースを超過 → 起動 2 が X を再 claim して turn を進め、決定的 `operationId` で次の継続を `schedule` → 起動 1 が遅れて `complete(kind, operationId)` を撃ち、**起動 2 が積んだ継続行を消す**。鎖が止まる。ポート JSDoc（`application/ports/scopeTaskScheduler.ts:132-147`）はこの筋書きをすでに書いているのに、platform 側の文が「複数プロセスは引き金ではない」と打ち消してしまっている。
  - 提案: 197 行目の最後の一文を、driver の種類で場合分けして書き直す。「object Alarm が driver の配備では scope ごとに writer が分かれるので、worker プロセスの多重度は引き金にならない。中央 runner が driver の配備では due index が全 scope 共有なので、**runner の起動が重ならないこと**（1 配備あたり同時 1 起動）が単一 writer 前提そのものである」。実配備（Queue consumer / Cron ハンドラ）は本 PR のスコープ外なので、記述の訂正だけで閉じられる。

- **[W-003]** `claimDue` の候補読みに付いたコメントが、コードが持っていない性質を主張している（同一 unit で 2 度呼ぶと同じ行を 2 回配る）
  - 場所: `packages/core/src/adapters/cloudflare/do/repositories/scopeTaskScheduler.ts:146-159`
  - 理由: コメントは「a row this very unit of work scheduled is not one, **and one it has already staged a claim for must not be selected twice**」と書くが、`queryCandidates` は `session.query`（＝ commit 済み storage 直読み、オーバーレイ非参照）なので、後半は成り立たない。同じ unit で `claimDue` を 2 度呼ぶと、1 度目に staged した claim は storage に見えないため同じ行が再選択され、同じ `ScopeTask` が 2 度返る（claim 文自体は冪等なので storage は壊れないが、呼び出し元はハンドラを 2 度回す）。memory 実装は transaction 内の table を直接書き換えるので 2 度目は候補にならず、**バックエンド間の振る舞いが割れる**。今日の唯一の呼び出し元（`runDueScopeTasks`）は 1 unit 1 回なので実害は無い。
  - 提案: 最小はコメントを実態に合わせる（前半の理由 —「候補は他の writer から見えている commit 済み行でなければならない」— だけ残す）。契約として片付けるなら、選択後にローカルの除外集合を持つか、ポート JSDoc に「1 つの unit of work で `claimDue` を複数回呼ばない」と書く。
