### Identity / directory / operation（D1 control plane）

ゼロベースで再読した。Identity 束 8 ファイル・directory / operation 束 4 ファイル・`0001_global_schema.sql`・`sql/` 支持層・`cursor.ts`、および `spec/database/index.md` / `spec/domains/identity.md` の該当節とポート JSDoc の改訂を対象にした。

本ラウンドで注目した 3 変更の判定:

- **`acknowledgeReceipt` の 1 文化** — 正しい。`json_each` の EXISTS は更新前の値を読み、`json_insert(receipts, '$[#]', ?)` は常に末尾追加なので、冪等・原子的・重複無し。`receipts` は閉じた列挙の部分集合で重複が潰れるため上限も有界。`begin` が `'[]'` を入れ `writeHeader` が当該列に触れないので、`json_each` に非配列が渡る経路も無い。早期 return は round trip 節約に留まり正しさを担っていない。順序は commit 順だが `allRequiredAcknowledged` は `includes` なので契約に影響しない。
- **`identityUniqueDirectory.activate` の CAS 化** — guard は「予約行の同一性（kind / normalized_key / operation_id / `state <> 'active'`）× `users.version`」の 1 文 JOIN で、UPDATE 側にも `operation_id = ?` が入り、`readByOperation` が返した行像に対する CAS になっている。失効予約を別 operation が奪った場合を `globalConcurrency.test.ts:162` が実バインディングで観測している。`activate` が `expires_at` を見ないこと・`releasing` 行も活性化しうることは memory と同一なので契約上の乖離ではない。翻訳先だけ W-002。
- **`writeHeader` の状態 guard 追加と `acknowledgeReceipt` の経路分離** — 判断は妥当。可換な集合への追加に敗者を作らない一方、状態遷移は読んだ `status` に対する CAS にする、という切り分けは `identityUniqueDirectory` の 4 メソッドとも一貫している。ただし追加した guard に観測が無い（W-005）。

`sessions_user_token_idx` の削除は性能を落としていない — `sessions.token_hash` は `UNIQUE`（自動索引）で `WHERE user_id = ? AND token_hash = ?` は 1 行に絞れる。`auth_tokens` と判断もそろった。NUL のエスケープ表記化も正しい。`compositeKey` に渡る部品（`kind` 閉列挙 / `normalized_key` / `run_id` / `generation` / `shard_id` / `consumer` / `event_id`）と `pruneCompleted` の keyset（`String(expires_at)` + `run_id`）はいずれも NUL を含みえないので、区切りの一意性は保たれている。`LoginAttemptStore.recordFailure` の `CASE` 付き 1 文 upsert、`OAuthStateStore.take` の束縛のみを条件にした `DELETE … RETURNING`（期限は返り行で判定）、`UserBatchReader` の `json_each` 展開と 100 件上限、`IdempotencyStore` の staged / autocommit 二経路はいずれも契約どおり。ADR 028 の列挙耐性はユースケース層の責務であり、本束の実装がそこに漏れを作っている箇所は無い。コメントに弁明・修正経緯の残骸は 0 件。

#### Blockers

- **[B-001]** account deletion manifest header の状態語彙が canon 内で自己矛盾している（AC-9 未達）
  - 場所: `spec/usecases/identity.md:809`, `spec/usecases/identity.md:815`, `spec/usecases/identity.md:821`, `spec/usecases/identity.md:827`, `spec/domains/index.md:147`, `spec/testcases/identity/deleteAccount.md:26`
  - 理由: 本 PR は ADR-055 に従って `spec/database/index.md#account_deletion_manifests` を書き直し、header の `status` を **5 値**（`building` / `built` / `rollingBack` / `completed` / `rejected`）に確定させ、さらに「[usecases/identity.md] が `compacting` / `compactingRejected` と呼ぶ段階は header の列ではなく item 行の残数が持つ状態であり、header に専用の値を足さない」と明示した。ところが同じ canon の他 3 ファイルは、`preparing` / `committing` / `compactingRejected` を **header の state として実在する**と断定したまま残っている。とくに `spec/usecases/identity.md:809` は「同じUserId shardのmanifest headerを`preparing`で開く」と書き、その根拠として `database/index.md` の `account_deletion_manifests` を参照している — 参照先はいま `preparing` を否定している。`spec/domains/index.md:147` も「`preparing` / `committing` は account deletion manifest header 側の state であって」と事実として述べている。実装（`application/ports/accountDeletionManifestStore.ts` の `AccountDeletionManifestStatus`、`createD1AccountDeletionManifestStore.begin` が `'building'` を入れる）とも食い違う。PR 前は両側とも 9 値だったので canon は自己整合していた。この矛盾は本 PR が片側だけを直したことで生じている。CLAUDE.md は「`spec/` は在force の設計の正本であり、そこに書かれていることはコードについて真であることを意図している」と定め、AC-9 は「反映しない差分は adr.md に理由とともに残っている」ことを要求するが、adr.md ADR-055 の記述は「本 Issue では確認していない」であって、反映しない**理由**ではない。
  - 提案: 3 ファイルを 5 値へそろえる。`spec/usecases/identity.md:809` は「manifest header を `building` で開く」、`:821` の「manifest headerを`committing`へ進め」は「author route 固定完了で `markBuilt`（`built`）」、`:815` / `:827` / `deleteAccount.md:26` の `compactingRejected` は「`rollingBack` のまま item を 100 件ずつ縮約する」へ、`spec/domains/index.md:147` の括弧書きは「`preparing` / `committing` という語は使わない。manifest header の status は `building` / `built` / `rollingBack` / `completed` / `rejected` の 5 値」へ。あわせて `:827` / `deleteAccount.md:69` の `expiresAt` は header の列名 `retain_until` に合わせる（`expires_at` は `distributed_operations` 側の列）。3 ファイルを直す代わりに `spec/database/index.md` 側へ戻すのは、ポート契約が正本であること（ADR 026 / ADR-055）に反するので採らない。

#### Warnings

- **[W-001]** `beginRelease` の guard 敗北が `OPTIMISTIC_LOCK_FAILURE` になる。ポート JSDoc は「一致しない行は no-op」と明示している
  - 場所: `packages/core/src/adapters/cloudflare/d1/repositories/identityUniqueDirectory.ts:417`
  - 理由: `IdentityUniqueDirectory.beginRelease` の JSDoc は「An absent row, a `reserved` row, a `releasing` row, another user's row, and a token that no longer matches are all no-ops, so a decision made about one claim can never take the key away from the claim that replaced it」と、no-op になる条件を列挙で契約している。実装は読み経路ではこれを正しく実装している（`existing === null || state !== 'active' || userId !== ... || claimToken !== ...` で早期 return）が、読みと適用のあいだに相手が行を動かした場合は guard が外れ、`throwTranslated` が `ConflictError("OPTIMISTIC_LOCK_FAILURE")` を投げる。相手が先に着地していれば同じ呼び出しは**静かに成功**していたので、敗者の答えが直列実行時の答えと一致しない。これは adr.md ADR-057 が本ラウンドで掲げた規律（「guard 敗北時の翻訳は、読み経路をもう一度撃ってその答えへ倒す」）そのものからも外れており、同ファイルの `activate` だけがその規律を適用されている点で非対称でもある。呼び出し側 `identityRemovalRelease`（outbox consumer）はこれを捕まえないので、負け続ければ event が `maxAttempts` に達して quarantine されうる。`releaseObservedUniqueKey` は `beginRelease` の後に必ず `release` を撃つが、例外はその手前で抜けるので同じ turn では回収されない。
  - 提案: `activate` と同じ形にする。`catch` で `classifySqlError(cause) === "occGuard"` なら `readOne(kind, normalizedKey)` を撃ち直し、観測した claim（`active` かつ `expectedUserId` かつ `expectedClaimToken`）がもう存在しないなら **return**（契約どおりの no-op）、それ以外は `throwTranslated` に落とす。
- **[W-002]** `activateLoss` が「同じ operation の並行リプレイに負けた」場合も `OPTIMISTIC_LOCK_FAILURE` を返す
  - 場所: `packages/core/src/adapters/cloudflare/d1/repositories/identityUniqueDirectory.ts:147-158`
  - 理由: guard は `r.state <> 'active'` を条件に含むので、**同じ operationId・同じ expectedUserVersion の並行リプレイ**が先に着地しただけでも外れる（継続配送は at-least-once なので二重配送は実在する経路）。このとき `readByOperation` は行を 1 件返すため `activateLoss` は `OPTIMISTIC_LOCK_FAILURE` に倒れるが、読み経路の答えは `reservations.filter(state !== 'active')` が空 → `mutations.length === 0` → **成功（no-op）**である。関数の JSDoc は「The answer the read path would have given had the winning writer landed first」と書いているので、この分岐では自身の宣言と食い違っている。実害は `activateUniqueKeys` が `logger.error` を出したうえで `confirm()` + 再 `activate` で自己回復する（round trip 2 本と誤検知ログ）ところまでで、恒久的な破綻はしない。
  - 提案: `activateLoss` を 3 分岐にする。再読が空なら `UNIQUE_RESERVATION_NOT_FOUND`、**`state === 'active'` かつ `user_version === expectedUserVersion` なら成功として扱い（`null` を返して呼び出し側で `return`）**、それ以外は `OPTIMISTIC_LOCK_FAILURE`。
- **[W-003]** `beginOrResume` が `unique` 違反を一律 `DISTRIBUTED_OPERATION_ALREADY_RUNNING` に倒しており、同一 request key のリプレイが `resumed: true` を受け取れない
  - 場所: `packages/core/src/adapters/cloudflare/d1/repositories/distributedOperationStore.ts:180`
  - 理由: この表は 2 本の一意索引を持つ — `distributed_operations_request_uq (kind, partition_key, request_key)` と `distributed_operations_active_uq (kind, partition_key) WHERE state NOT IN (...)`。相手が**同じ request key** で先に running を作った場合、直列実行なら `siblings.find(row => row.requestKey === input.requestKey)` が当たって `{ operation, resumed: true }` を返す（`spec/database/index.md#distributed_operations` が「`UNIQUE(kind, partition_key, request_key)` が同じ送信の再生を担う」と定めている振る舞い）。ところが敗者は `ConflictError` を受け取る。これは adr.md ADR-040 が `identityUniqueDirectory.reserve` について「どの索引が外れたかで翻訳を分ける」と決めたのと同じ論点であり、こちらには適用されていない。`globalConcurrency.test.ts:226` は request key が**異なる**ケースだけを固定しているので、この差は観測されていない。
  - 提案: 敗北時に読み経路へ倒す。`catch` で `occGuard` / `unique` を受けたら `inPartition(kind, partitionKey)` を撃ち直し、同じ request key の行があれば `{ operation, resumed: true }`、無ければ現行どおり `DISTRIBUTED_OPERATION_ALREADY_RUNNING`。あわせて同一 request key の並行ケースを `globalConcurrency.test.ts` に 1 本足す。
- **[W-004]** `sessionRepository` の JSDoc が、削除済みの `(user_id, token_hash)` 索引を今も存在するものとして名指している
  - 場所: `packages/core/src/adapters/cloudflare/d1/repositories/sessionRepository.ts:55-59`
  - 理由: 「Lookup by wire token goes through the `(user_id, token_hash)` index」とあるが、`0001_global_schema.sql` の `sessions` が持つ索引は `token_hash` の `UNIQUE`（自動索引）、`sessions_user_epoch_idx`、`sessions_expires_idx` の 3 本だけで、複合索引 `(user_id, token_hash)` は本 PR の中で落とされている（adr.md ADR-069）。実際の走査路は `token_hash` の UNIQUE 1 本であり、性能上は等価なので実害は無いが、この JSDoc を根拠に「複合索引があるはず」と読んだ次の改修が索引を足し直しかねない。`spec/database/index.md#sessions` の索引一覧とも一致しない。
  - 提案: 「`token_hash` の UNIQUE で 1 行に絞り、`user_id` は所有者の照合として掛ける（`auth_tokens.findByTokenHash` と同じ形）」へ書き換える。
- **[W-005]** `writeHeader` に足した状態 guard に観測が無く、adr.md ADR-057 の「観測は `globalConcurrency.test.ts` に置いた」が当該変更については成立していない
  - 場所: `packages/core/src/adapters/cloudflare/d1/repositories/accountDeletionManifestStore.ts:238-246`
  - 理由: `globalConcurrency.test.ts` が固定しているのは `reserve` / `activate` / `acknowledgeReceipt` / `beginOrResume` / maintenance lease の 5 系統で、header の status 遷移が guard に負けるケースは 1 本も無い（`grep -rn "markBuilt\|markCompleted\|beginRollback" adapters/cloudflare/__tests__/` は 0 件）。共有適合スイートは memory が UoW を直列化するため、この分岐に構造的に到達できない。つまり ADR-057 の 3 変更のうち `writeHeader` だけが実行されるテストで守られていない状態で、guard を落とす回帰も、翻訳先（`stateViolation`）を取り違える回帰も検出されない。
  - 提案: `interposeOnce` を使って 1 ケース足す。`begin` → `markBuilt` の読みと適用のあいだに対抗 writer の `markBuilt` を割り込ませ、敗者が `ConflictError`（`stateViolation` の符号）を受け、`status` が二重に進まないことを固定する。あわせて ADR-057 の Consequences のうち観測に関する記述を実態に合わせる。
