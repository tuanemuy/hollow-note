#### Warnings

- **[W-001]** `MEDIA_SVG_MAX_DEPTH` の根拠「サニタイザーは素の再帰で歩くので 1,000 段で `RangeError`」が現在の実装と食い違い、ラウンド 010 の書き換えがそれを現在形の断定にした。あわせて TC-storage-266 の 3 本目のアサーションは depth gate に対する検出力がゼロ
  - 場所: `packages/core/src/domain/storage/services/uploadValidationPolicy.ts:55-65`（`MEDIA_SVG_MAX_DEPTH` の JSDoc「`HtmlProcessor` walks the parsed tree with plain recursion … 1,000 levels — 6 KB of `<b><i>…` — is enough for a `RangeError` that carries no `kind`」）、`packages/core/src/application/storage/__tests__/storeMedia.test.ts:889-891`（ラウンド 010 の書き換え「Without the depth gate 6 KB of this reaches `sanitizeNodes` and answers a bare `RangeError`」）と `:870`（`it` 名「past the depth the sanitizer's recursion can walk」）、`spec/inventory/test.md:2052` / `spec/testcases/storage/storeMedia.md:23`（「サニタイザーは木を素の再帰で歩くので、深さがそのままスタックの深さになる」）
  - 理由: ラウンド 006 以降 `HtmlProcessor` は `maxNestingDepth: 256` を持ち、`onItemPush`（open elements が 256 + 8 を超えた時点）と `enforceNestingLimit`（明示スタック）で `BusinessRuleError(HTML_PROCESSOR_TOO_COMPLEX)` を投げる（`adapters/html/htmlProcessor.ts`、`spec/adr/013` の上限表「走査の深さ 256 段」）。実測: `createHtmlProcessor().process` に `<svg><desc>` + `<b><i>` × 1,024（6,190 バイト）、`<g>` × 1,024、`<g>` × 5,000 を渡すといずれも `NOTE_HTML_TOO_COMPLEX`、`<g>` × 200 は正常に通る。したがって「depth gate が無ければ素の `RangeError` になる」は偽で、無ければ `HTML_PROCESSOR_TOO_COMPLEX` → `processSvg` の翻訳で `FileTooLarge` になる。さらに `repeatedInsideDesc("<b><i>", 8 * 1024)` は `<b>` が `HTML_BREAKOUT_ELEMENTS` にあるため、**深さに関係なく要素名の門で拒まれる**（実測: `<svg><desc><b><i>x</i></b></desc></svg>` の 4 段でも `readSvgDocument` は `null`、`ensureAcceptable` は `UnsupportedMimeType`）。depth gate を丸ごと外してもこのアサーションは緑のままなので、検証と数えられない。64 段の境界値（`nestedSvg(64)` / `nestedSvg(65)`）のペアだけが depth gate を守っている
  - 提案: (1) `MEDIA_SVG_MAX_DEPTH` の JSDoc を方針値として言い切る — 「実在の図版は数段。64 を超える文書は受理判定が 1 パスで断り、サニタイザーを走らせない。サニタイザー自身の上限は `HtmlProcessorLimit.maxNestingDepth`（256）で、こちらが先に効く」（breakout tag の門と同じ「前段の安価な防御」の位置づけ）。(2) `storeMedia.test.ts:889-891` のコメントを削るか、「この門が無ければ `HtmlProcessor` の `maxNestingDepth` が `HTML_PROCESSOR_TOO_COMPLEX` で答え、`FileTooLarge` へ翻訳される — 同じ拒否が別の語彙になる」に置き換え、fixture を breakout 要素を含まない形（`<g>` × 1,024 など）にして depth gate だけに掛かるようにするか、64 / 65 のペアで足りるとして 3 本目を落とす。(3) `spec/testcases/storage/storeMedia.md:23` と `spec/inventory/test.md:2052` の括弧書きを「境界値。64 は方針値で、サニタイザー側の上限 256 より先に効く」に揃える。`spec/domains/storage.md:205` は既に 256 に言及しており、「素の再帰」の一句だけ落とせばよい

- **[W-002]** `subscribers.ts` の JSDoc が「同じ型の継続購読者は unordered」と書くが、同じ JSDoc の冒頭と既存テストは登録順の実行を契約にしている
  - 場所: `packages/core/src/application/workers/subscribers.ts:246-247`（ラウンド 010 の書き換え「the continuation subscribers of one type are unordered too」）、同 `:228`（「They run in registration order, and **each one runs even when an earlier sibling threw**」）、`packages/core/src/application/workers/__tests__/subscribers.test.ts:77`（`runs every subscriber registered for the event type, in order`）
  - 理由: `dispatchDomainEvent` は `matched` を登録順に `for … await` で回すので、順序そのものは決まっている。緩められたのは「先行する兄弟が**完了している**ことを後続が前提にできる」性質であって、順序ではない。「unordered」は `:228` および `:77` のテスト名と矛盾し、読み手が「順序に依存する購読者は登録順でも守られない」と読む
  - 提案: 「the continuation subscribers of one type get no completion guarantee from that order either: a sibling runs whether or not the one registered before it succeeded」のように、失われているのが完了の保証であることを言う

- **[W-003]** `spec/usecases/usage.md` の `ensureUploadAllowed` 概要が呼び出し元を `storeUpload` だけと書くが、本 PR で `storeMedia` も呼ぶ

  - 提案: 括弧書きを「`storeUpload` / `storeMedia` から呼ばれる。`storeAvatar` は差し替えで累積しないため呼ばない」にする

- **[W-004]** `docs/frontend_implementation_example.md` の「`NoteList` / `NoteDetail` render read-only markup」が本 PR で偽になった
  - 場所: `docs/frontend_implementation_example.md:213`（「Every screen so far is complete with a loader + a server component + an ordinary `"use client"` island — `NoteList` / `NoteDetail` render read-only markup, and the interactive parts (`IdentityBoard`, `ProfileEditor`, `CreateNoteButton`) are whole client components …」）、`apps/web/app/components/note/NoteDetail/index.tsx:73`（`<NoteDetailIsland …>` を描く）、`apps/web/app/components/note/NoteDetail/detail.tsx:78-81`（`renameNoteFn` / `changeNoteStyleModeFn` / `trashNoteFn` / `restoreNoteFn`）、`apps/web/app/components/note/NoteList/board.tsx:97-98`（`trashNoteFn` / `restoreNoteFn`）
