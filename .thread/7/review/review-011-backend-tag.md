#### Warnings
- **[W-001]** 継続要求の `operation_id` 導出規則が列挙する例外が、表の全行に対して不足している（表・usecases・実装の 3 者突き合わせ）
  - 場所: `spec/domains/index.md:298`（規約 4 つの直前の段落）、`spec/database/index.md:39`
  - 理由: 規則本文は「`operation_id` は生成元 operation/event/command ID と対象 ID・version・cursor から導出する」「continuation は生成元 ID と cursor を材料にする」とし、例外として「周期の掃引（`note.trashExpiry` / `storage.orphanMediaSweep`）と `workspace.deletion*Continued`」だけを挙げる。実装を全行当たると、この 2 分類に収まらない鍵が 3 家族ある。(1) **本ラウンドで表に足した `workspace.membershipRemovalEdgeContinued`** は `removalEdgeTaskId = "${workspaceId}:${userId}"`（`application/workspace/membershipMutation.ts:261`）で、生成元 command ID を含まず対象の組だけを鍵にする（`spec/usecases/workspace.md:739` が意図として明記）。(2) `job.terminationContinued` は `trashNote.ts:164` で `operationId: noteId`（対象だけ）。(3) `note.ownerPurgeContinued` は固定の `deletionOperationId` を鍵に、再開状態（`stuckPurges`）を payload で運ぶ — 例外文が「同じ行を次の phase へ進める継続」として名指す `workspace.deletion*` と同じ形だが、括弧内に無い。cursor を鍵に混ぜる scope task は現在のツリーに 1 件も無いので、「continuation は生成元 ID と cursor を材料にする」は global outbox の `continuationKey` にしか当てはまらない。表に行を足すたびに例外文が漏れる構造で、4 ラウンド続いた指摘の根がここにある
  - 提案: 例外の列挙をやめ、鍵の形を行の多重度で分類して書く — (a) 1 operation が対象ごとに積む行: 生成元 ID + 対象 ID(+ revision)、(b) 1 operation に 1 本の継続（owner cleanup 3 種・`note.purged` 追随者 3 種・personal barrier prune / handover・`workspace.deletion*`）: operation ID だけ、再開状態は payload、(c) scope に 1 本の周期掃引: 定数、(d) 対象に 1 本の義務（`membershipRemovalEdge`・`job.terminationContinued`）: 対象の識別子だけ。`database/index.md:39` の「continuation は生成元 ID と cursor を材料にする」は global outbox の `continuationKey` に限定する

- **[W-002]** 継続 payload の reader 4 本で「読めない payload」の方針が 3 通りに割れており、`readOwnerPurgeTurn` の黙殺だけは安全側でない
  - 場所: `packages/core/src/application/note/deleteNotesForOwner.ts:76-106`（`readOwnerPurgeTurn`）、`packages/core/src/application/cleanup/personalCleanup.ts:93-103`（`readPersonalBarrierPruneTurn`）、`packages/core/src/application/cleanup/notePurgeFanOut.ts:47-66`（`readNotePurgeTurn`）、`packages/core/src/application/storage/collectOrphanMedia.ts`（`readOrphanMediaSweepTurn`）
  - 理由: `readNotePurgeTurn` は `SystemError(DataIntegrityError)` で fault（行は backoff で残り、`logger.error` に出る）。`readOrphanMediaSweepTurn` は先頭へ戻す（周期掃引なので安全、表にも明記）。`readPersonalBarrierPruneTurn` は `clock.now()` へ戻す — `now >= dueAt = asOf` なので選ぶ receipt は「保持期限が実際に過ぎた集合」の上位集合に留まり安全だが、ログを 1 行も残さない。問題は `readOwnerPurgeTurn`: 壊れた `stuckPurges` の要素を黙って捨てる。捨てた結果 `carried = []` で列挙が空なら `settle` は `remaining(0) > purgedFromPage(0)` を偽と読み、`note` 成分を ack して行を `complete` する（`deleteNotesForOwner.ts:474-489`）— これは `StuckPurge` の JSDoc と `spec/usecases/note.md` 手順 6・7 が「取り消せない誤 ack」として最も避けている結果そのものである。JSDoc の「faulting the turn would park the row and strand the very notes」は逆で、park された行は `[scope-tasks] task threw` のログと `dueAt` 付きの可視な停滞になり、黙殺は同じ note を回収不能にしたうえで退会を完了させる。書き手が自分だから壊れない、という前提は `readNotePurgeTurn` にも等しく成り立つのに、そちらは fault を選んでいる
  - 提案: `readOwnerPurgeTurn` を `readNotePurgeTurn` と同じ `DataIntegrityError` に揃える（要素単位の skip をやめ、1 件でも読めなければ fault）。あわせて方針を canon に 1 文置く — 「仕事そのものを名指す payload（対象 ID・持ち回り集合）は読めなければ fault し、再開位置だけを運ぶ payload（keyset・`asOf`）は先頭 / 現在時刻へ戻す」— を `spec/domains/index.md` の継続要求の規約に足し、`readPersonalBarrierPruneTurn` の fallback には呼び手（`scopeTaskRunner.ts:240-246`）で `logger.warn` を 1 行足す。ファイルの持ち分は note だが、共通原因は横断の方針不在なのでここに集約する

- **[W-003]** `spec/database/index.md` の scope 検証規則を「削除経路でも検査する」へ広げたが、同じバックエンドの `notes` の削除経路は検査していない
  - 場所: `spec/database/index.md:21`（「復元でも保存でもない削除（`deleteByNote` のような有界削除）— でも検査する」）、`packages/core/src/adapters/cloudflare/do/repositories/noteRepository.ts:302-310`（`readForUpdate`）・`:369-384`（`delete`）
  - 理由: 規則は「scope 鍵として使っている列 — 今日は `notes.owner_type / owner_id`、`tag_assignments.scope_type / scope_id`」の両方を主語にし、削除を外すと「いちばん破壊的な経路が唯一の無検査になる」と根拠まで書く。`tag_assignments` 側は `deleteByNote` がページ全体を検査してから消す（`scopeGuards.test.ts` ADP-tag-019 で担保）。一方 `notes` の `delete(id, expectedVersion)` は `readForUpdate` が `session.readRow` で version だけを見て `restore`（owner 検査）を通らず、そのまま `DELETE` する。`purgeNote` の local delete がこの経路なので、規則の言う「鍵を取り違えた配線が他 object の行を黙って消す」経路が `notes` に残ったまま、規則だけが「全経路で検査する」と断定している。既存コードだが、規則文はこの PR で書かれた
  - 提案: どちらかに揃える。(a) `readForUpdate` で読んだ行の `owner_type / owner_id` を `bound` と突き合わせる（`restore` と同じ 2 比較で、`save` / `delete` の両方が同時に閉じる）。(b) 規則の主語を「述語で行を選ぶ有界削除（`deleteByNote`）」に限定し、鍵と版で 1 行を指す `delete(id, expectedVersion)` は OCC が読んだ行に閉じるため対象外だと書く。`spec/inventory/adapter.md` の ADP-note-011 も選んだ側に合わせる

- **[W-004]** `identity.personalBarrierPruneContinued` の入力 DTO が usecases 側だけ古い（既存の問題 — 本 PR の変更起因ではないが、本 PR の表の書き換えで 3 者が不一致になった）
  - 場所: `spec/usecases/identity.md:801`（`{ type: "identity.personalBarrierPruneContinued"; scope: ScopeKey; asOf: Date }`）・`:811`（「固定 scope/asOf だけで」）
