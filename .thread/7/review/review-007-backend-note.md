### backend-note

#### Blockers

**[B-001]** bad-string の書き戻しが「文字列を終わらせた改行」を落とすため、1 つの壊れた宣言が `<style>` の残り全体を飲む（報告は空のまま）

- 場所: `packages/core/src/adapters/html/css.ts:129-155`（`skipString` の改行分岐 `:143-151`）と、その結果を書き戻す `filterBlock` の `:532` / `:540`（どちらも `input.slice(...).trim()`）＋ `pushStatement`（`:450-476`、`emitted = terminated ? \`${text};\` : text`）。契約側は同ファイルのモジュール JSDoc `:15-16`「Carried through means written back as they were found — the filter never supplies a `;` or a `}` the source did not have」と、`spec/adr/013-html-sanitization-policy.md:142`（決定「違反した宣言だけを落とす。要素ごと捨てると、1 つの違反で本文全体の装飾が消える」）
- 理由: 改行を bad-string の終端として読むようになったのは正しい（ラウンド 006 [B-001] の安全側は閉じた。実測で `position:fixed` は LF / CR / FF いずれでも除去される）。壊れているのは**書き戻し**のほうで、文字列を終わらせていた当の改行が `trim()`（と `filterBlock:513-516` の空白読み飛ばし）で消え、そこに `;` だけが付く。結果、出力の文字列は閉じ引用符も改行も持たないまま `;` を飲み込み、ブラウザではスタイルシートの末尾まで走る（CSS Syntax: EOF-in-string は bad-string ではなく string-token を返す）。実測（`createHtmlProcessor().process`）:

  | 入力 | 出力 | `removed` | ブラウザに残る規則 |
  | --- | --- | --- | --- |
  | `<style>.o{content:"a⏎;position:fixed}\n.p{color:red}\n.q{font-weight:bold}</style>` | `<style>.o{content:"a;}.p{color:red}.q{font-weight:bold}</style>` | `position` 1 件 | `.o` のみ。`.p` / `.q` は `content` の値の中 |
  | `<style>.o{content:"a⏎;color:blue}\n.p{color:red}</style>` | `<style>.o{content:"a;color:blue}.p{color:red}</style>` | **空** | `.o` のみ。`.p` は消える |
  | `<p style='content:"a⏎;color:blue'>` | `<p style="content:&quot;a;color:blue">` | 空 | `color` が消える |

  入力のほうはブラウザが改行で bad-string を回復するので `.p` / `.q` は当たっていた。つまりサニタイズが**装飾を新たに壊している**。2 行目・3 行目は `removed` が空なので、ADR 013 の「除去した内容は利用者に提示する」も同時に空振りする — 利用者から見て「何も除去されていないのに装飾が消えた」になる。壊れた CSS 限定の話ではあるが、この走査が相手にしているのは「取り込んだ任意の CSS」であり、モジュール JSDoc `:12-16` 自身が「losing it is worse than keeping something inert」を方針として書いている。
- 到達経路: `updateNoteBody`（HTML モード）→ `htmlProcessor.process` → `filterCss`。保存後は `applyTextNodeEdits` / `restoreNoteRevision` / `listNoteRevisions` の再サニタイズを通っても不動点なので、以後ずっとこの形で残る（不動点であること自体は確認済み）。
- テスト側にも焼き付いている: `packages/core/src/adapters/html/__tests__/htmlProcessor.test.ts:549-557`（TC-note-705）は `present: ['content:"a;', "top:0"]` を期待値として書いている。`top:0` は**文字列の中にある**ので描画には効かない。文字列としての存在を「保たれた」と読んでいるため、この欠陥は現行スイートでは検出されない。
- 提案: 書き戻しから文字列の終端を落とさない。どちらでも不動点は保たれる（2 巡目が同じ位置で同じ分割をする）:
  - **(a) 改行をそのまま残す** — 統計上いちばん保守的で、JSDoc の「written back as they were found」に一致する。`pushStatement` に渡すのを `input.slice(i, stop)` の**前方だけ** trim した文字列にし、末尾の空白（＝ bad-string を終わらせた改行）は保持する。整形式な CSS では末尾に空白が無いか、あっても宣言の意味を変えないので、上限以下の通常入力の出力は変わらない（`legit flat/media/media2` 300〜780 KB で入出力長が完全一致することは実測済み）
  - **(b) 閉じ引用符を補う** — `skipString` を `kind: "bad-string"` として返し、その字句で終わる statement には `"` を足してから `;` を書く（`content:"a";`）。ブラウザが 1 つ目の宣言について計算する値そのものになる
  - どちらを採るにせよ、`htmlProcessor.test.ts` の当該行の `present` を「後続の規則がブラウザに届く形で残る」ことを主張する形（`present: ['.p{color:red}']` かつ `content` の文字列が閉じている）に直し、**除去が 0 件の入力**（上表 2 行目）を新しいケースとして足すこと — 現状 `sanitizeCases` に「何も除去しないのに壊れた文字列がある CSS」の行が 1 件も無く、そこが B-001 の抜け道になっている

**[W-003]** 計量の主張が実装より強い — `spend` は「走査が見た 1 文字につき 1 歩」ではないし、8,000,000 歩は「1 バイトあたり 4 回」ではない

- 場所: `packages/core/src/adapters/html/css.ts:88-100`（`spend` の JSDoc「Called once per character a scan examines, which is what makes the meter independent of which scan is running and of how the input nests」）と `spec/adr/013-html-sanitization-policy.md:188`（「転送境界が通す 1 バイトあたり 4 回の走査」）
- 理由: 2 点とも実装とずれる。(a) コメント・文字列・url-token は `readLexeme` が 1 歩で丸ごと飛ばすので、1.8 MB のコメント 1 個は 1 歩で 1.8 MB を読む。ネストの各段で `scanTo` と `findBlockEnd` が読み直すため、歩数 O(深さ) に対して仕事は O(深さ × 字句長)になる。(b) 1 バイトあたりの走査回数はネストの段数に比例する（`findBlockEnd` + `scanTo` が段ごと、最内で `canonicalize` + `disallowedPositionProperty`）。TC-note-821 が「32 段 × 300 KB」で上限に当たるのはこの比例のためで、「1 バイトあたり 4 回」なら当たらない
- ただし**上限そのものは効いている**（ここが指摘の限界）。最悪形を実測した: `<style>` の 32 段の内側に 1.8 MB の単一コメント／文字列／url-token を置く形で 145 / 332 / 263 ms、`@media a{` 12,000 段は 136 ms で `NOTE_HTML_TOO_COMPLEX`、300〜780 KB の正当なスタイルシート（平坦 / `@media` / `@media`+`@supports`）は 62〜220 ms で入出力が 1 バイトも変わらずに通る。つまり穴ではなく**根拠の記述の不正確さ**である。次に走査を足す人がこの 2 行を読んで「1 文字 1 歩だから安全」と結論する
- 提案: `spend` の JSDoc を「走査が進める 1 位置につき 1 歩。字句 1 個は長さによらず 1 歩なので、歩数は仕事の**上界ではなく代理**であり、字句の長さは入力長で、読み直しの回数は `maxCssNestingDepth` で別に縛られている」と書き直す。ADR `:188` の根拠欄も「1 バイトあたり 4 回」ではなく「ネストの段数に比例する読み直しを含めた総量」に直す（値を変える必要は無い）

**[W-004]** 4 上限のどれにも掛からない平坦な 1.95 MB の本文が、800,000 バイトの出力上限で拒まれるまでに秒オーダーの CPU を焼く。その定数が ADR の表に無い

- 場所: `packages/core/src/adapters/html/htmlProcessor.ts:901-907`（`parse`）／ `:923-966`（`process`）と、転送境界 `apps/web/app/components/note/schema.ts:46`（`NOTE_HTML_TRANSPORT_MAX = 2_000_000`）対 出力上限 `packages/core/src/domain/note/valueObject.ts:77`（`CONTENT_MAX_BYTES = 800_000`）。契約側は `spec/adr/013-html-sanitization-policy.md:177-190` と `packages/core/src/domain/note/ports/htmlProcessor.ts:17-23`（「sanitization costs a bounded amount of CPU and memory *whatever shape the input has*」）
- 理由: `<p>xxxxxxxx</p>` を 130,000 回（1,950,000 バイト、転送境界の内側）は、木が 1.95 MB で 4 倍の膨張枠に収まり、深さは 3、CSS は 0 なので**どの上限にも掛からない**。素の Node で parse5 単体の `parseFragment` が 1,375 ms、`process` 全体は同オーダー（vitest 内の実測は環境の分だけ 3〜5 倍に膨らむので数字はそちらを採らない）。そのあと `NoteHtml.create` が 800,000 バイト超で `ContentTooLarge` にするので、**必ず失敗すると分かっている 1 リクエストに 1.5 秒級の CPU を丸ごと払う**。参照ランタイムは HTTP と worker を兼ねる単一 Node プロセス（CLAUDE.md「Reference runtime」）、目標プラットフォームでは scope が単一スレッドの DO である
- 上限の設計は正しく、これは「上限が効いていない」という指摘ではない（1.95 MB を弾く安全な事前判定は無い — サニタイズは内容を大きく削りうるので、入力長から出力長は決められない）。問題は **ADR の表が「1 回の `process` が最悪どれだけ掛かるか」を読者に渡していない**ことで、この節はまさにそれを渡すために書かれている。`applyTextNodeEdits` の JSDoc（`:51-64`）は同じ性質を自分の側でだけ正直に書いている
- 提案: ADR 013「サニタイズは資源で有界である」に、4 上限の表の下に 1 行足す — 「4 上限をすべて満たす最悪の入力（転送境界いっぱいの平坦な markup）で 1 回の `process` は約 X 秒。転送境界 2,000,000 と本文上限 800,000 の差はサニタイズが削る分の余地であり、その差の分だけ『必ず `ContentTooLarge` になる入力』にも同じ費用が掛かる」。数値を canon に置けば、次に転送境界を触る人がこの取引を見られる
