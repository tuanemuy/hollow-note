#### Warnings
- **[W-001]** 「読めない payload」規約の fault 側の記述が、`ScopeTaskScheduler` の契約と runner の実装に反している（本ラウンドで canon に置いた文そのものが偽）
  - 場所: `spec/domains/index.md:333`（「fault した行は `dueAt` を保ったまま backoff で残り、runner の報告に出る」）、`packages/core/src/application/note/deleteNotesForOwner.ts:91-92`（`readOwnerPurgeTurn` JSDoc「A parked row is instead visible in the runner's report and keeps its `dueAt`」）
  - 理由: handler が throw した行は `runDueScopeTasks` が `backoff(kind, operationId, now)` に落とす（`scopeTaskRunner.ts:344-350, 356-368`）。`backoff` の契約は `dueAt = now + BASE × 2^(attempt-1)`・`attempt + 1`・上限で `failed`（`ports/scopeTaskScheduler.ts:106-108`）であり、`dueAt` を保つのは**lease 再claim**だけ（同 `:111-114`）。したがって「`dueAt` を保ったまま」は偽で、破損 payload のような**恒久的な**fault は `SCOPE_TASK_MAX_ATTEMPTS` 回の backoff の後に `failed` へ駐車され、以後 claim されない（`schedule` だけが戻す道）。さらに `[scope-tasks] task threw` のログ行は `dueAt` を載せない（載せるのは handler 不在の warn だけ、`:330-339`）ので「報告に出る」が指す観測面も違う。運用上の意味が逆になる — 最古 task age の SLO は `due_at` から測る（`spec/database/index.md` の `scheduled_tasks`）ため、backoff で `dueAt` が前へ動く fault は SLO に**現れず**、可視性は error ログと `failed` 行だけに依る。`readOwnerPurgeTurn` 側のテスト（`deleteNotesForOwner.test.ts:787-822`）は「行が残り ack が出ない」までは固定するが、`dueAt` / `attempt` / `failed` 遷移は見ていない
  - 提案: 両方を実装どおりに言い直す — 「fault した turn は行を残し、runner が `backoff` する（`dueAt` は次回時刻へ進み、上限で `failed` に駐車されて以後 claim されない）。空の列挙を根拠にした ack は出ないので、退会は `running` のまま error ログ（`[scope-tasks] task threw`）と `failed` 行として可視化される」。`readOwnerPurgeTurn` の JSDoc も同じ内容へ。ラウンド011 [W-002] の提案文（「`dueAt` 付きの可視な停滞」）が不正確だったのが根で、canon に写す前に port 契約で裏を取ること

- **[W-002]** 「再開位置だけを運ぶ payload は先頭へ戻し、`logger.warn` を 1 行残す」規約に対し、orphan sweep の reader は warn を残さず、barrier prune の warn は検出力ゼロのまま
  - 場所: `packages/core/src/application/storage/collectOrphanMedia.ts:163-180`（`readOrphanMediaSweepTurn`）、`packages/core/src/application/workers/scopeTaskRunner.ts:173-178`（`ORPHAN_MEDIA_TASK_KIND` handler）、`packages/core/src/application/workers/__tests__/subscribers.test.ts:511-531`
  - 理由: `spec/domains/index.md:333` は「後者を選んだ実装は `logger.warn` を 1 行残す」と断定し、表の `storage.orphanMediaContinued` 行も「読めなければ先頭から」を明記する。実装は `readOrphanMediaSweepTurn` が `null` を黙って返し、runner の handler も warn を出さない（`PERSONAL_BARRIER_PRUNE_TASK_KIND` handler だけが `fromPayload` を見て warn する）。一方 barrier prune 側の fallback テスト（`:511`）は receipt が消えたことだけを見て `h.logger.byLevel("warn")` を確認しないので、warn を消しても緑のまま通る。注意点として orphan の通常 payload は `sweepPayload(null) = {}` なので、「鍵が無い」を warn すると毎日のパスが警告になる — warn すべきは「鍵があるのに読めない」場合だけで、`{}` と区別する必要がある
  - 提案: `readOrphanMediaSweepTurn` を `readPersonalBarrierPruneTurn` と同じ `{ cursor, fromPayload }` 形にし、鍵が存在するのに解釈できないときだけ `fromPayload: false` を返して runner が warn する（`{}` は `fromPayload: true` 相当の正常）。barrier prune のテストに `h.logger.byLevel("warn")` の 1 行を足し、orphan にも同型のテストを足す。canon を緩める（warn を任意にする）なら `:333` の文を直す

- **[W-003]** 継続要求で駆動される usecase の入力 DTO が、表・実装と食い違ったまま 4 件残っている（ラウンド011 [W-004] と同じ欠陥、identity 以外）

- **[W-004]** 「対象ごとに 1 本」の具体式の参照先が、参照した節に無い（記述の衛生）
