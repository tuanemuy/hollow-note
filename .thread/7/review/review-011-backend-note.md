#### Blockers

`inlineStylesheets` のエスケープ（`filtered.replace(/<\/(?=style)/gi, "<\\/")`）は最重点で検証した。論証と実試行の両方で穴は見つからなかった。

- **トークナイザー上の論証**: HTML の RAWTEXT 状態が `<style>` を閉じる条件は「`<` の直後に `/`、続けて ASCII 字母で `style` と一致し、その次が空白 / `/` / `>`」の 1 通りだけで、実体参照・コメント・NUL の特例はない（NUL は U+FFFD に置換されるだけ）。置換は `</` と `style` の間に `\` を 1 文字挿入するだけで、出力に現れる `</style` は原文で連続していた 7 文字でしかありえず、その位置は必ず置換されている（`</` のマッチは 2 文字で重ならない）。したがって出力に `</style` は残らず、`<\/` は `</` を含まないので 2 回目の適用も無変化 — 不動点の主張は正しい
- **CSS としての妥当性**: `\/` は CSS の識別子・文字列・引用符なし `url()` のいずれでも `/` のエスケープなので意味は変わらない。`css.ts` は出力を必ずソースのまま書き戻し（`canonicalize` は分類専用）、再 `process` で `\/` が `/` に戻ることはない
- **実試行（現在のツリーで 30 入力）**: `</st</styleyle` / 3 重の入れ子 / `</STYLE` / `</style\n` `\f` `\r` / `</style/` / 事前エスケープ済み `<\/style` / `<` の直後に NUL / 名前の中に NUL / `\3c /style` / 長い s（`ſ`）/ ケルビン記号 / `</styles` / 文字列の中 / `position:fixed` 除去による接合（`</st;position:fixed;yle`）/ `}` `@import` の除去による接合 / コメントで分断 / `</script>` / `<plaintext>` / `<!--` / `<!</style` / CRLF / 二重バックスラッシュ — すべて再パース後の要素列が `p, style, p` のまま（突き破りなし）で、`removed` は空。不動点でなかったのは `\r` と NUL を含む 3 件だけで、これは HTML の入力ストリーム正規化（CR→LF、NUL→U+FFFD）によるもので境界には無関係
