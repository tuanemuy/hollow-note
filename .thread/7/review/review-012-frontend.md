### frontend

#### Blockers

- **[B-001]** `takeSnapshot` は `title`（と `mode`）を**描画が捕まえた閉包**から読むので、往復の最中に打ったタイトルが `reseedIfUnchanged` の門をすり抜け、載せ直しの `setTitle` に黙って捨てられる。門の JSDoc（「本文だけを見ると、往復のあいだに打ったタイトルが載せ直しの `setTitle` に黙って捨てられ」）はまさにこの穴を避けるために `sameSnapshot` を置いたと書いているが、比較の左辺 `takeSnapshot().title` は往復を始めた描画の `title`（＝ `sent.title`）のままなので、タイトル側の比較は**恒真**である。`visualCurrent` は ref なので本文側だけが生きた値で比べられている
  - 場所: `apps/web/app/components/note/NoteEditor/editor.tsx:581-602`（`takeSnapshot` が state の `title` / `mode` / `baseline` を読む）、`editor.tsx:915-919`（`sameSnapshot(takeSnapshot(), sent)`）、`editor.tsx:1300-1303`（`loadSurface` の無条件 `setTitle`）、`editor.tsx:903-905`（JSDoc の主張）、`editor.tsx:1004-1029`（自動保存 effect の依存に `mode` が無い）
  - 理由: 到達経路は 2 つで、どちらも「非同期の往復の中で描画時の値を読む」という同じ原因である。(1) **ビジュアルモードで `needsReseed` になる保存**（丸ごと送る枝 — 退避の復元・競合の上書き・`dropPathwise` 後 — と、`skipped` が 1 件以上あった経路単位の保存）の往復中にタイトルを打つと、`confirm` の関数型 `setTitle` は打鍵を残すのに、直後の `reseedIfUnchanged` が古い `title` で「動いていない」と判定して `reseedFromServer` → `loadSurface(latest.title, …)` が入力欄を正本で上書きし、`confirmed.title` も正本になるので `dirty` が下りて自動保存も走らない — 打鍵が痕跡なく消える。TC-04 手順 5 は経路単位で `skipped` 0 件の往復（`needsReseed` 偽）しか踏まないので通ってしまい、この経路を検出しない。(2) `acknowledgeWysiwyg` の未保存枝（退避の復元 → 「了解して進む」、または「保存して切り替える」の往復中に打鍵 → 警告 → 了解）は `switchMode` と `loadSurface(kept)` を呼ぶが、`title` / `body` / `status.kind` / `visualDirty` / `visualEditSeq` のどれも動かさないので自動保存 effect は張り直されず、1.5 秒以内に発火するタイマーは**前のモード**の `commit` を走らせる。HTML → WYSIWYG なら `takeSnapshot` は `body`（`<style>` 込みの切替前の本文）を返し、`wysiwygConversion` 理由で `<style>` を落とさないまま保存する。面はすでに `<style>` を落としているので、次の打鍵の `manualEdit` で初めて装飾が消える — ED-04 の「保存の直前に版が保持される」の版理由と実際の喪失点が 1 保存ずれる
  - 提案: 描画のたびに `title` / `mode` / `baseline` を書く 1 つの ref（`leaveConfirmRef` と同じ形）を置き、`takeSnapshot` と `commit`（`importing` / `needsReseed` の `mode` 判定）はそこから読む。`visualCurrent` が既にそうであるように、「面の内容を読む唯一の手段」が読む値をすべて生きた値に揃える。それで (1) と (2) が同時に閉じる（(2) だけなら自動保存 effect の依存に `mode` を足すことでも張り直せるが、閉包の問題を依存の列挙で追い続ける形になる）。手順書は TC-04 に「退避を復元したあとの自動保存の往復中にタイトルを打つ」を、TC-06 に「退避の復元 → 1.5 秒以内に了解して進む」を足す

#### Warnings

- **[W-001]** `reload` に集約された 2 つの経路は**「確定値がサーバーと一致しているか」が違う**。破棄の失敗では `confirmed` はまだ正本だが、版の復元が確定したあとの載せ直しの失敗では `confirmed` は**復元前の本文**のまま `failed { kind: "reload" }` になる。この状態で `commit` が到達可能（「保存」ボタンは `!editable || busy || creationFailed` でしか閉じない）で、押すと (a) 面の直列化が確定値と同じなら往復なしで `confirm` → `saved` になり、復元前の内容を見せたまま「保存済み」と告げる（`失敗` の Alert も消える。`dirty` 偽なので「破棄」で正本へ戻す手段は無い）、(b) 違えば / 1 文字打ってから押せば復元前の本文 + 打鍵が `expectedVersion: 復元後の版` で通り、**確定した復元を版 1 つで黙って取り消す**。ビジュアルでは (a) のあとの打鍵が復元前のテキストを `expected` に送って全件 `contentChanged` → 「反映できなかった編集があります」→ 載せ直しで打鍵が消える。加えて再試行の `reloadFromServer` は成功で `idle` に落とし、`restore` 本体の後半（`saved` / `savedAt` / `setRevisions(null)` / `reconcile()`）を持たないので、復元の再試行だけが `router.invalidate()` を経ない。`spec/pages/index.md:319` の「正本の引き直し（破棄と、版を復元したあとの載せ直し）は「破棄」と同じである」は入口が同じという意味では真だが、この 2 点で扱いは同じにならない
  - 場所: `apps/web/app/components/note/NoteEditor/editor.tsx:1440-1478`（`restore` の 2 段目の `catch`）、`editor.tsx:1326-1346`（`reloadFromServer`）、`editor.tsx:620-624, 724`（`commit` が `confirmedRef.current.body` を正本と見なす）、`editor.tsx:2331-2333`（保存ボタンの活性）、`apps/web/app/components/note/NoteEditor/saveStatus.ts:32-36`、`packages/core/src/application/note/restoreNoteRevision.ts:134-145`（`processed.html` を持っているのに `{ noteId, version }` しか返さない）
  - 理由: `commit` は「`confirmed` はサーバーが持っている姿」を前提に組まれている（`EditorSnapshot` の JSDoc）。復元の 2 段目の `try` を分けたこと自体は正しいが、分けた結果「確定は済んだが手元の確定値は古い」という状態が生まれ、その状態を `SaveStatus` は表せない（`failed` は「往復そのものが成立しなかった」の意味）。ラウンド 011 以前も同じ穴はあった（`failed { revision }` でも保存は押せた）が、`reload` へ集約した今回、破棄の失敗（安全）と同じ `kind` に相乗りしたことで、この違いが型からも JSDoc からも見えなくなった
  - 提案: `RestoredNoteRevisionView` に `title` / `html`（`processed.html`）を載せ、`restore` の 2 段目を `seedMode(surfaceModeFor(mode, restored.html, false), restored.title, restored.html)` の同期処理にする。往復が 1 つになるので 2 段目の失敗そのものが無くなり、`reload` は破棄だけの 1 対 1 に戻る（`restoreNote` が `version` を返すのと同じ理由で、復元の応答が次の状態を全部運ぶ）。`saveStatus.ts` の表・JSDoc と `spec/pages/index.md:319` の「版を復元したあとの載せ直し」の 2 文を落とし、`describeFailure` の `reload` の案内も破棄だけの文言に戻す。手順書 TC-11 手順 7 は「オフラインで復元」のままでよい（往復が 1 つなので「版が 1 つだけ増える」の判定はそのまま成り立つ）

- **[W-002]** `SaveIndicator` は `failed` を `retry.kind` によらず「保存に失敗しました」と出す。`describeFailure` が Alert の見出しを 5 種に分けた（「版を復元できませんでした」「最新の内容を読み込めませんでした」…）のに、同じ画面の上部バーは破棄・モード切替・復元・競合解決の失敗にも「保存に失敗しました」を出し、`spec/pages/index.md:319` の「見出しと案内は落ちた往復ごとに分ける — 版の復元が落ちた画面で「保存できませんでした」と告げると、利用者は保存されていない打鍵を探しに行く」がバーの側では成り立たない
  - 場所: `apps/web/app/components/note/NoteEditor/editor.tsx:2428-2429`、`apps/web/app/components/note/NoteEditor/saveStatus.ts:124-130`
  - 提案: `FAILED_TITLE` と同じ `Record<RetryTarget["kind"], string>` で短いラベルを `saveStatus.ts` に置き（`save: "保存に失敗しました"`、他は「切り替えに失敗」「読み込みに失敗」「復元に失敗」「解決に失敗」など）、`SaveIndicator` はそれを引く。閉じた `Record` なので種類が増えればここも型で落ちる

#### 検証メモ（指摘にしなかったもの）

- `RetryTarget` 5 種の入口: `save` → `commit(true)`（明示保存と同一。`catch` の `appliedTitle` 確定により再送で rename が重複しない）、`conflict` → `resolveConflict(keepLocal)`（`takeSnapshot` は再試行時に取り直す。一次経路と同一）、`revision` → `restore(revisionId)`（`identityRef` の版で送る。門なしは TC-11 手順 5 と一致）、`reload` → `reloadFromServer()`（破棄と同一。`clearDraft` / `setDraftOffer(null)` は初回で済んでいる）。`mode` → `requestMode(mode, acknowledged)` は一次経路と同一だが、`failed { mode, acknowledged: true }` のあとに打鍵して `dirty` になった状態からの再試行だけは `acknowledgeWysiwyg` の未保存枝（面だけ差し替え）ではなく「未保存の変更があります → 保存して切り替える → 警告をもう一度」へ落ちる。到達は「了解して進む」が通信で落ちたあとに打鍵する経路に限られ、結果は警告が 1 回余分に出るだけなので指摘にしない
- `retryFailed` に固有の門・分岐が無いことをコードで確認した（`switch` 5 分岐が各入口を引数そのままで呼ぶだけ）。`dirty` の門は `requestMode` の中にしか無く、破棄・復元の再試行には掛からない（ラウンド 011 [B-002] の回帰は無い）
- `seed`: `baselineSeed` を進めるのは `loadSurface` だけで、呼び出し元は `reseed`（`seedMode` / `resolveConflict` の上書き）・退避の復元・`acknowledgeWysiwyg` の未保存枝の 4 つ。いずれも利用者の操作か `runExclusive` の内側で、`commit` の保存後は `reseedIfUnchanged` の門を通る（門のタイトル側が恒真である点は [B-001]）。`WysiwygSurface` は `seededRef !== seed` のときだけ短絡を外し、同じ世代の再実行（StrictMode の二重実行）では `innerHTML` 比較に戻る。マウント直後は `seededRef === null` なので必ず載る。打鍵で `baseline` / `seed` が動く経路は無い
- `visualEditSeq`: `onChange` ごとに 1 進めて依存に置くだけで、保存回数は増えない（タイマーの張り直しにしか効かない）。`onReady` は進めないので載せ直し直後に余分な保存は走らない。連続入力中の保存はラウンド 011 [W-002] のとおり静止後 1 回になった
- `key={noteId}` は `NoteEditorIsland`（`NoteEditor/index.tsx:93-94`）・`NewNoteEditor`（文脈で `key`）・`NoteDetailIsland`（`NoteDetail/index.tsx:77-78`）の 3 か所に入っている
- ビジュアルの丸ごと保存は `importing = mode === "visual" ? false : importReferences` で固定（`editor.tsx:632`。`mode` が閉包の値である点は [B-001] の (2) に含めた）
- `errorDisplay.ts:97` の ADR 参照はフルパスに直り、`adrReference.test.ts` の `PATH_REFERENCE` は末尾のハイフンを要求しなくなった。frontend 6 か所の `ADR 007` / `ADR 013` は `spec/adr/` に実在する
- `discard` を新規ノート（`identity.kind === "new"`）で押すと `status` が `dirty` のまま残り、`SaveIndicator` は空文字になる（`new` の「未保存」に戻らない）。次の打鍵で `dirty` に戻るだけなので指摘にしない
- `spec/pages/index.md` P-10「操作実行中」「削除直後」、P-11「操作実行中」「削除直後」「メニュー」、P-12「保存できません」「構文の補正」「WYSIWYG 警告」「ビジュアル不可」、P-14「削除を予約」の各行を実装と突き合わせ、前ラウンドの書き換えが偽の主張を作っていないことを確認した（P-14 の「処理履歴（P-15）への導線」は他スライスの未実装を残す ADR-039 の扱いで、手順書 TC-13 の確認ポイントがその読み替えを持つ）。`spec/presentation/index.md` の差分は「ストレージの配信元」行の削除 1 件のみで、`StorageUrlPolicy` が `ObjectStorage.publicUrl` から取る形と整合
- 手順書: TC-10 手順 8〜10、TC-11 手順 5〜7、TC-06 手順 7、TC-08 手順 6、TC-21 手順 8、TC-24 手順 4、TC-32 手順 3 をコードの活性条件・遷移と突き合わせ、いずれも現在の実装で PASS する形になっている。TC-11 手順 7 の「増えた版は 1 つだけ」はオフライン（要求が届かない）が前提で、応答だけが失われる形は対象外
- 記述の衛生: 担当範囲のソース・spec・手順書に経緯を語る記述（「以前は」「〜するようになった」）は無い
