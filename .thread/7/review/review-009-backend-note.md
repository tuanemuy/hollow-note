- **[W-001]** `restoreNoteRevision` だけが「実行中の変換・再生成ジョブは本文の書き込みを拒む」門を持たない
  - 場所: `packages/core/src/application/note/restoreNoteRevision.ts:63-64`（`ensureNotTrashed` の直後に `bodyLockingJob` の判定が無い）、`:121`（`jobs.listActiveForNote` は取り込み登録のためだけに、保存**後**に読んでいる）、`spec/usecases/note.md:1036-1043`（処理フローに `NoteLockedByJob` の行が無い）
  - 理由: 本文を書き換える 3 経路のうち `updateNoteBody`（`spec/usecases/note.md:471` 手順 2、`updateNoteBody.ts:74`）と `applyTextNodeEdits`（`:522` 手順 2、`applyTextNodeEdits.ts`）は `JobRepository.listActiveByTarget` を引いて `conversion` / `regeneration` があれば `BusinessRuleError(NoteLockedByJob)` で拒む。`restoreNoteRevision` は同じ `Note.updateBody` を当てるのに、この判定を持たずに保存へ進む。`regeneration` は本文を `ready` のまま書き換えるジョブなので、版の復元が着地した直後に再生成の結果で上書きされる（あるいはその逆）競合が、この 1 経路だけ許される。`domains/note.md` の「再生成中は編集拒否」は編集の経路を選ばない規則である。コードは spec の処理フローに忠実なので、抜けているのは spec 側（本 PR 以前からの記述）と、それを写した本 PR の実装の両方。`jobs.listActiveForNote` は既に呼んでいるので、Job seam を足さずに閉じられる
  - 提案: `spec/usecases/note.md#restoreNoteRevision` の処理フローに `updateNoteBody` 手順 2 と同じ行（`listActiveByTarget` → `conversion` / `regeneration` があれば `NoteLockedByJob`）とエラー表の行を足し、`restoreNoteRevision.ts` は `ensureNotTrashed` の直後で `bodyLockingJob(await jobs.listActiveForNote(container, noteId))` を判定して、その結果を保存後の `requestReferenceImportIfNeeded` の `activeJobs` にも渡す（`updateNoteBody` と同じ 1 回読み）。`spec/testcases/note/restoreNoteRevision.md` と `restoreNoteRevision.test.ts` に「実行中の再生成ジョブがある — 戻す — `NoteLockedByJob`」を 1 行足す

- **[W-002]** `spec/domains/note.md` の「資源で有界」が ADR 013 と食い違ったまま残っている
  - 場所: `spec/domains/note.md:374`
  - 理由: ラウンド 008 で `HtmlProcessorLimit` に節点数（`maxNodes: 50_000`）が加わり、`spec/adr/013-html-sanitization-policy.md`「サニタイズは資源で有界である」は「**5 つの上限のうち 4 つは**…届かない高さに置く。**節点数だけは違い、正当な本文が到達しうる高さにある**」と書き換えられた。`domains/note.md:374` は「解析後の木の大きさ・走査の深さ・CSS のブロックの入れ子・CSS の走査の総量の **4 つ**に上限があり」「上限は本文の長さの上限から到達しうる**どの文書よりも高い**ところにある」のままで、上限の数も「正当な本文が届きうる」という ADR の取引も反映していない。ポートの JSDoc（`domain/note/ports/htmlProcessor.ts:41-70`）は 5 つで正しく、`domains/note.md` だけが古い。CLAUDE.md は `spec/` を「what is written there is meant to be true of the code」と定める
  - 提案: `domains/note.md:374` を「解析後の木の大きさ・節点数・走査の深さ・CSS のブロックの入れ子・CSS の走査の総量の 5 つ」に直し、「どの文書よりも高い」の断言を「節点数を除く 4 つは…。節点数は正当な本文が届きうる高さで、その取引は ADR 013 が持つ」に改める（値と根拠の正典を ADR に置く現在の形は維持する）

- **[W-003]** `trashNote` 手順 5 の「同じ transaction で `findNextPurgeDeadline` を引き直す」が、`spec/database/index.md` の同一 UoW 読みの規則 (3) と正面から矛盾している。実装が安全である理由は正典のどこにも書かれていない

  - 理由: `findNextPurgeDeadline` はまさに (3) が禁じる「順序付きで `LIMIT` が埋まる読み」であり、trashNote はそれを書き込みの後に呼ぶ。staged session の実装を読むと、`LIMIT` が埋まった保存済みページに**この UoW が触れた行が載っている**ときだけ `DatabaseError` を投げ、載っていなければ staged 行を `matches` で足して `compare` で並べ直す。`trashNote` の場合、触れた行（active → trashed に反転させたノート）は `WHERE lifecycle = 'trashed'` の**保存済み**ページには決して現れない（commit 前は active）ので、投げられずに正しく答える — つまり実装は安全だが、その安全性は「触れた行が保存済み述語の外にある」という条件に依存しており、規則 (3) はこの条件を認めていない。cloudflare 側でこの読みを実際に通すテストも無い（`trashNote` の usecase テストは memory backend のみ。conformance の ADP-note-057 は書き込み無しの読みだけ）。規則を読んだ次の実装者が手順 5 を「(3) 違反」として保存の前へ動かすと、いま保存したノートが答えに入らなくなる（手順 5 自身が「引き直すことが…条件」と書いている理由が失われる）
  - 提案: どちらか一方を正典に書く。(a) `spec/database/index.md` の (3) に「自 UoW が書き換えた行が**保存済みの述語に入りえない**場合（述語の外から中へ反転させる書き込み）は staged 行を重ねて答えてよく、`trashNote` 手順 5 がこの形」と例外を足す、または (b) `NoteRepository.findNextPurgeDeadline` の JSDoc（`domain/note/ports/noteRepository.ts`）と `domains/note.md` の箇条書きに「同じ UoW で active → trashed に反転させた直後に呼ぶ契約であり、staged 行を含めて答える」を書く。あわせて `adapters/cloudflare/__tests__/ports/scopeBusiness.ts` 側に「同じ UoW で 1 件を trash して `findNextPurgeDeadline` を引くと、その期限が返る」を 1 ケース足して staged session でも成立することを固定する

- **[W-004]** ADR 013 は「許可リストにない要素は剥がして中身を残す」「これらは内容ごと落とす」という 2 段の規則を持っていないのに、`allowList.ts` は自分を ADR の「転記であってそれ以外ではない」と宣言している
