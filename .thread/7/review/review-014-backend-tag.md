#### Warnings
- **[W-001]** `AssignmentId` / `BackupRecordId` 再利用の fault は、ポート JSDoc と ADP-tag-010 / ADP-integration-008 が `SystemError(DatabaseError)` と名指しているのに、conformance スイートは `isSystemError` しか見ていない
  - 場所: `packages/core/src/adapters/conformance/tagAssignmentRepository.ts:70`、`packages/core/src/adapters/conformance/backupRecordRepository.ts:93`
  - 理由: [ADR 026](../../../spec/adr/026-port-contract-and-conformance.md) はポート JSDoc の契約をスイートが実行形として担うと定める。JSDoc は「`ASSIGNMENT_ALREADY_EXISTS` と `SystemError(DatabaseError)` の 2 種へ写し分ける」ことを契約にしており（`domain/tag/ports/tagAssignmentRepository.ts` の `insert`、`spec/domains/tag.md:175`）、両バックエンドは実際に `DatabaseError` を返す（memory は `support.ts:duplicateKey`、cloudflare は `databaseError(...)` と `throwTranslated`）。しかしスイートの述語は `isSystemError` で、`DataIntegrityError` や `ScopeMismatch` など別 code の `SystemError` を返す実装も緑で通る。「id 再利用は再試行ではなく修正すべき事故」という区別を守るのがこの case の目的なので、code を pin しないと検出力が落ちる。両スイートが同じ形なので共通原因として 1 件にまとめる
  - 提案: `rejects.toSatisfy((e) => isSystemError(e) && e.code === SystemErrorCode.DatabaseError)` に揃える（`scopeGuards.test.ts` が `DataIntegrityError` を pin しているのと同じ形）
