#### Warnings
- **[W-001]** 属性値に `&lt;` を持つ整形式な SVG が、サニタイズ後の再判定で `UnsupportedMimeType` として拒まれる
  - 場所: `packages/core/src/application/storage/storeMedia.ts:148-162`（`asStandaloneSvg`）、`packages/core/src/domain/storage/services/uploadValidationPolicy.ts:402-439`（`readAttributes` の `value.includes("<")`）
  - 理由: 実測（`createHtmlProcessor().process`）: `<svg xmlns=…><rect data-note="a&lt;b" …/></svg>` → `<svg><rect data-note="a<b" …></rect></svg>`、`<svg … aria-label="x &lt; y">` → `aria-label="x < y"`。HTML の直列化は属性値の `<` をエスケープしない（`&` と `"` だけ）ので、XML では正しく `&lt;` と書かれていた入力が、`process` の出力では属性値に生の `<` を持つ。受理判定（intake）は通り、`asStandaloneSvg` → `readSvgDocument` が `value.includes("<")` で `null` を返して `UnsupportedMimeType`（"does not sanitize into a single standalone document"）になる。`&nbsp;` と同じ種類の「HTML 直列化と XML の差」であり、`aria-label` / `title` / `data-*` に `<` を書く SVG はブラウザで開けるのに拒まれ、しかも「形式が扱えない」という偽の説明が返る。spec/usecases/storage.md 手順 3 は「直列化が出しうる非定義の参照はこれ 1 つ（`&nbsp;`）」と断言しているが、参照ではなく**生の `<`** がもう 1 つの差分として残っている
  - 提案: `asStandaloneSvg` で `&nbsp;` と同じ扱いにする — タグ走査（`readSvgDocument` の `readAttributes` は既に属性値の区間を切り出している）から属性値の位置を返させ、属性値内の `<` を `&lt;` に書き戻してから `readSvgDocument` に掛ける（許可リストには要素も属性も足さないので ADR 013 の適用点は増えない）。`storeMedia.test.ts` に `aria-label="x &lt; y"` の受理ケースを足し、`spec/testcases/storage/storeMedia.md` / `spec/usecases/storage.md` 手順 3 の「これ 1 つ」を「`&nbsp;` と属性値の `<`」に直す

- **[W-002]** `collectOrphanMedia` の 1 turn が保持する本文の総量に上限が無い（ノート数の予算は解析回数を縛るが常駐メモリは縛らない）
  - 場所: `packages/core/src/application/storage/collectOrphanMedia.ts:297-317`（`readNoteBodies`）、`:526-598`（`sweepOnce` の scan transaction）、JSDoc `:290-295`
  - 理由: scan transaction は 1 ページの全ノート（最大 `ORPHAN_MEDIA_NOTE_BUDGET = 5`）について現在の本文＋`NoteRevision.RETENTION = 20` 版の本文を `htmls` に集めてから transaction を閉じ、その後 `decideOrphans` が全部を解析する。上限は 5 × 21 = 105 本 × `NoteHtml` 800,000 バイトで、JS 文字列は UTF-16 なので ASCII 本文でも 1 本 1.6 MB、**最悪 168 MB が transaction を閉じた時点で同時に常駐**する。JSDoc は「that cap is what bounds the bodies this turn holds in memory as well」と書くが、縛った先が Cloudflare Workers の isolate 上限（128 MB）を超えており、上限として機能していない。通常の本文はこれより桁で小さいので実害は最悪ケースに限られるが、「設計上の上限が platform の上限の内側にある」ことを主張する箇所なので数字が合っていないのは問題
  - 提案: ノート数の予算と並べて**バイト予算**を置く（例: `ORPHAN_MEDIA_BODY_BUDGET_BYTES = 8 MB`。`readNoteBodies` の結果を積むたびに `htmls` の長さの合計を足し、超えたらノート予算と同じ経路 `outOfBudget` で打ち切る — cursor は判定し終えた行まで前進するので取りこぼさない）。代替として、参照抽出をノート単位で transaction の外に出す形（ノート 1 件ごとに読み → 閉じ → `extractExternalReferences` → URL 列だけ保持）も同じ効果を持つが transaction 数が増える。どちらを採っても `spec/usecases/storage.md#collectOrphanMedia` 手順 2 と `ORPHAN_MEDIA_NOTE_BUDGET` の JSDoc の「メモリも縛る」を実態に合わせる

- **[W-003]** `StoredFileRepository` の JSDoc が「未実装は artifact 系だけ」と述べるが、spec が move に割り当てる `listByNote`（ADP-storage-006）は実装も先送りの宣言も無い
  - 場所: `packages/core/src/domain/storage/ports/storedFileRepository.ts:44-48`（"the artifact listings (`findArtifactByNoteAndVersion`, `listExpired`) arrive with the slice that generates artifacts"）、`packages/core/src/application/storage/relocateFilesForNote.ts:135-146`（`listNoteFiles` の JSDoc）、`spec/domains/storage.md:285,297`、`spec/inventory/adapter.md` ADP-storage-006
  - 理由: 既存の問題（本 PR の変更起因ではない — 旧 JSDoc は "the import slice adds the note / artifact / expiry listings" と `listByNote` を先送りに含めていた）。本 PR がこの文を「artifact 系だけが未着」に書き換えたため、`listByNote` が「無いのに先送りでもない」状態になった。`relocateFilesForNote` の新しい JSDoc も `listByOwner` を選ぶ理由を `listDeletableByNote` との比較だけで述べ、spec が名指しする `listByNote` に触れない。ポート JSDoc は契約の正典（ADR 026）なので、spec との差分は JSDoc 側に明記されているべき
  - 提案: JSDoc の先送りリストに `listByNote`（move の全 purpose 列挙）を足し、`relocateFilesForNote.listNoteFiles` の JSDoc に「spec の `listByNote` が着くまで `listByOwner` + `noteId` filter」と 1 文残す。または `listByNote` を 3 点セット（port / memory / cloudflare / conformance）で実装して move をそれに乗せる

- **[W-004]** `spec/usecases/storage.md#collectOrphanMedia` の「30 日境界を跨いだ行はそのパスでは拾わず翌日」は実装と逆
  - 場所: `spec/usecases/storage.md:428`（「走査中に 30 日境界を跨いだ行はカーソルの後ろに現れうるので、そのパスでは拾わず翌日の先頭からの走査で拾う」）、`packages/core/src/application/storage/collectOrphanMedia.ts:515-534`（`createdBefore = now - 30d` を turn ごとに再計算）
  - 理由: 継続 turn は自分の `now` から `createdBefore` を引き直すため、直前の turn 以降に境界を跨いだ行は候補になる。その行の `createdAt` は既に読んだ全行より新しいので順序上は必ずカーソルの**先**（未読側）に並び、同じパスの継続 turn がそれを読んで判定する。「そのパスでは拾わない」は成立しない（拾っても害は無いので実装は正しい。文が違う）
  - 提案: 該当文を「継続 turn は自分の `now` で境界を引き直すので、パスの途中で 30 日を越えた行はカーソルの先に現れ、同じパスで判定される」に直す（fix-editorial）

- **[W-005]** TC-storage-060 のテストが `ConflictError` の種別だけを見ており、spec が定める `CLEANUP_OPERATION_MISMATCH` を固定していない
  - 場所: `packages/core/src/application/storage/__tests__/deleteFilesForNote.test.ts:383-396`（`expect(isConflictError(error)).toBe(true)` のみ）
  - 理由: `spec/testcases/storage/deleteFilesForNote.md` と inventory の TC-storage-060 は「`ConflictError("CLEANUP_OPERATION_MISMATCH")` として拒否する」を期待結果にしている。`assertWritable` 由来の `ACCOUNT_DELETING` など別コードの `ConflictError` でも通るので、受理判定が `describePersonalCleanup` から別の述語（例: `assertOwner`）に戻っても検出できない。同じ purge fan-out の integration 側テスト（`deleteBackupRecordsForNote.test.ts` TC-integration-022）はコードまで固定しており、3 追随者で検出力が揃っていない
  - 提案: `expect(isConflictError(error) && error.code).toBe("CLEANUP_OPERATION_MISMATCH")` に倒す（tag 側の同型テストも同じ確認を推奨）
