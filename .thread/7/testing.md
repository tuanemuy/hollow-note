### 検証環境の起動

```bash
cp apps/web/.env.example apps/web/.env
```

`apps/web/.env` を次のように設定する（いずれも `.env.example` に項目がある）。

- `APP_URL` — 必須。既定値は `http://localhost:3000`（`pnpm dev` はこの URL のポートで待ち受ける）
- `OAUTH_DEV_MODE=true` — コメントアウトを外す。ループバック dev IdP（同意画面は `/dev/oauth/authorize`）が使えるようになり、Google 資格情報なしでサインインできる。**`NODE_ENV=development` のときだけ受理される**ので `pnpm dev` 専用（`pnpm start` では使えない）
- `MEMORY_MAIL_LOG_ACTION_URL=true` — コメントアウトを外す。メール確認リンクの実 URL が `pnpm dev` のターミナルログの `mail.sent` 行に `actionUrl` として出る。本計画はユーザー 2 名をメール確認込みで作るので有効にしておく

```bash
pnpm dev
```

`http://localhost:3000`（= `APP_URL`）を開く。永続化は in-memory なので、**サーバーを再起動するとデータが全て消える**。以下の確認は 1 回の起動の中で通しで行う。

### 素朴ノート / 空ノート / 処理中ノートの用意

- **素朴ノート** — WYSIWYG モードで新規作成し、見出しと段落だけを入力する（取り込みが無いのでファイル由来では作れない）
- **空ノート** — 新規作成して本文を空のまま保存する（TC-16）
- **処理中ノート** — 本スライスでは作れない（変換ジョブは Issue #5 / #6）。後述「本スライス単独では確認できない手順」を参照

## 確認項目

以下の browser 項目の全体が、そのまま **AC-13**（`spec/manual-tests/editing.md` の TC-04〜TC-34 のうち本スライスの対象シナリオ ED-02〜ED-11 に属する手順が実機で PASS する）の確認になる。各項目の手順・期待結果は同ファイルの該当 TC を実体とする。

### 1. ビジュアルモードでテキストだけを書き換える（TC-04）

- **対応する受け入れ基準:** AC-2
- **検証手段:** browser
- **目的:** ビジュアルモードの編集が、元の構造・`class` / `style` / `data-*` を壊さずにテキストノードだけを更新することを確認する
- **手順:**
  1. HTML モードに `decorated.html` の内容を貼り付けて保存し、装飾ノートを作る
  2. そのノートの詳細から編集を開始する（`/notes/:noteId/edit` が開く）
  3. ビジュアルモードに切り替える
  4. 見出しの文字を `新しい見出し` に書き換える
  5. 保存する
  6. ノート詳細で表示を確認する
  7. 編集画面の HTML モードでソースを確認する
- **期待結果:** 手順 3 で本文が通常どおりレンダリングされテキスト部分だけが編集可能になる。手順 4 で表示が即座に変わる。手順 6 で見出しの文字だけが変わり装飾・レイアウトは元のまま。手順 7 で `class` / `style` / `data-kind` 属性が保持されている
- **確認ポイント:** `<style>` の中身が編集対象になっていないこと。経路（`path`）の解決がずれていると保存が全件無効になるので、書き換えが 1 文字も反映されない場合はここを疑う。あわせて手順 2 の遷移直後（本文の骨組みだけが並ぶ読み込み中）にも上部バーと「ノートへ戻る」が出ていること — 読み込みのあいだだけ戻る導線が消えないこと
- **確認ポイント（往復中の打鍵）:** 開発者ツールで回線を絞り（Slow 3G など）、手順 4 の自動保存が**走っている最中に**もう 1 文字打つ。保存表示が「保存済み」で止まらず、続けてもう一度自動保存が走って**その 1 文字も届く**こと（ページを読み直して確認する）。「反映できなかった編集があります」が出たら誤り — 送っていない打鍵を「保存済み」に取り込んでいる印である
- **確認ポイント（丸ごと送る保存でも打鍵が消えない）:** ビジュアルモードで**退避の「復元する」または競合の「自分の内容で上書きする」を経た直後**（この 2 経路のあとは本文が丸ごと送られる）に、回線を絞ったまま自動保存を走らせ、その最中に 1 文字打つ。往復が終わったときに面から**その 1 文字が消えていない**こと、続けてもう一度自動保存が走って届くこと（面ごと載せ直す枝が往復中の打鍵を捨てていたら誤り）
- **確認ポイント（反映できなかった編集の後始末）:** 「反映できなかった編集があります」が出たときは、通知が出たあとに同じ箇所をもう一度書き換えて保存し、**今度は通る**ことを見る（読み直さずに同じ書き換えを抱えたままだと、その箇所は何度打っても保存されない）。打鍵が止まっていれば面は最新の本文で読み直され、打鍵が続いているあいだは読み直さず打鍵を保つ — 通知の文言は読み直しを約束していない
- **確認ポイント（往復中に打ったタイトルが消えない）:** ビジュアルモードで回線を絞り、本文を書き換えて自動保存を走らせ、**その最中にタイトル欄へ 1 文字打つ**。往復が終わったときにタイトル欄からその 1 文字が消えていないこと、保存表示が「保存済み」で止まらずもう一度自動保存が走ってタイトルも届くこと（面を載せ直す枝がタイトルを正本で上書きしていたら誤り。上書きされると「未保存」の表示すら出ないまま消える）

### 2. HTML モードでソースを編集する（TC-05 / TC-17e）

- **対応する受け入れ基準:** AC-3
- **検証手段:** browser
- **目的:** HTML モードの編集がサニタイズを経て保存され、許可リストの内側の表現は落とされないことを確認する
- **手順:**
  1. 編集画面で HTML モードに切り替える
  2. `<p>追記した段落</p>` を末尾に加える
  3. 保存し、ノート詳細で表示を確認する
  4. 別のノートの HTML モードに `safe-rich.html` の内容を貼り付けて保存する
  5. ノート詳細を開く
  6. 保存後のソースを確認する
- **期待結果:** 手順 1 でシンタックスハイライト付きのソースエディタが出る。手順 2 でプレビューに段落が追加される。手順 3 で追記した段落が表示される。手順 4 は保存が成功し、**除去された内容の通知は表示されない**。手順 5 で入れ子の表・`<details>` の開閉・`<figure>` とキャプション・ルビがそのまま表示される。手順 6 で `class` / `data-*` / `aria-*` が残っている
- **確認ポイント:** 手順 4 で「何も除去していない」ときに空の通知枠が出ないこと。サニタイズ通知は**直近の保存結果**を指すので、除去が出た保存のあとに**タイトルだけを変えて保存**したら通知が消えること（前回の「N 件を取り除きました」が、何も除去していない保存の結果として残らない）

### 3. WYSIWYG モードで編集し、版から戻す（TC-06）

- **対応する受け入れ基準:** AC-4
- **検証手段:** browser
- **目的:** HTML 由来のノートで WYSIWYG に入るときの警告と、保存前の版の保持・復元を確認する
- **手順:**
  1. 装飾ノート（手順 1 の項目で作ったもの）の編集画面を開く
  2. WYSIWYG モードに切り替える
  3. 警告を了解して進む
  4. 見出しとリストを追加する
  5. 保存する
  6. ノート詳細のメニューから版の一覧を開く
  7. 保存前の版に戻す
- **期待結果:** 手順 1 で**このノートは WYSIWYG ではなく HTML モードで開く**（装飾を持つノートを警告なしに WYSIWYG へ入れないため）。手順 2 で装飾が失われる可能性を伝える警告が出る。手順 3 でリッチテキストエディタが表示される。手順 6 で保存前の内容が版として記録され、その理由が「WYSIWYG への変換」になっている。手順 7 で元の装飾を持つ内容に戻る
- **確認ポイント:** 警告を出さずに WYSIWYG へ入れてしまうと装飾の喪失が不可逆になる。手順 1〜2 が最重要。警告に「今後表示しない」は**無い**（再表示に戻す設定画面が本スライスの外にあるため。adr.md ADR-070）
- **確認ポイント（警告の「了解して進む」）:** 警告が出ている状態で別の往復（自動保存・破棄）が走っているあいだは「了解して進む」が無効であること。押せてしまい、**警告だけ消えてモードが変わらない**なら誤り
- **確認ポイント（本文の `<style>` が編集画面に効かない）:** HTML モードで本文の先頭に `<style>header, button { display: none !important; }</style>` を書いて保存し、ページを読み直す。(1) このノートは **HTML モードで開く**（`<style>` を持つ本文も ED-04 の門の後ろにある）。(2) 上部バーの戻る導線・モードの切替・保存ボタンが**消えていない**。(3) WYSIWYG へ切り替えると警告が出て、了解して進むと `<style>` が面から落ちている（本文が素の見た目になる）。(4) そのまま保存すると `<style>` が本文から消え、版の一覧に「WYSIWYG への変換」の版が残っていて手順 7 と同じ手順で戻せる。ビジュアル / HTML モードでは `<style>` は残る（面が shadow root の中にあるため）
- **確認ポイント（門は「これから載る本文」で判定する）:** `<style>` を持たない素朴ノートを開き（WYSIWYG で開く）、**HTML モードへ切り替えてから** `<style>p { color: red }</style>` を本文の先頭に足して自動保存を待つ（画面は再読み込みしない）。そのまま WYSIWYG へ切り替えると **ED-04 の警告が出る**こと。警告なしに入れて `<style>` が落ちたら誤り（断片を描いた時点の本文で門を判定している印。自動保存は断片を描き直さない）。了解して進んだあとの保存は版の理由が「WYSIWYG への変換」になり、手順 7 と同じ手順で戻せること
- **確認ポイント（モードを変えない載せ直しでも門が掛かる）:** 手順 3 で WYSIWYG に**居るまま**、編集画面の下端の「版を復元」から手順 5 より前の版（`<style>` を持つ版）を復元する。(1) 面が **HTML モードへ移り**、ED-04 の警告が出ること。(2) 復元された本文に `<style>` が**残っている**こと。WYSIWYG に居たまま装飾だけが消えたら誤り — 面は載せ直しのたびに無条件で `<style>` を落とすので、門が「モードを変える瞬間」にしか掛かっていない印である（そのまま 1 文字打つと、次の保存で本文からも消える）。同じことを競合の「自分の変更を破棄する」（他の利用者が `<style>` を足した場合）と、退避の「復元する」（HTML モードで書いた `<style>` 入りの退避を WYSIWYG に居るときに戻す場合）でも見る
- **確認ポイント（了解して進んでも未保存の内容が消えない）:** HTML モードで本文の先頭に `<style>p { color: red }</style>` を足し、自動保存が走る前に通信を遮断して自動保存を失敗させる。ページを再読み込みし（`<style>` を持たない保存済み本文なので WYSIWYG で開く）、通信を回復してから「復元する」を押す。(1) 面が **HTML モードへ移り** ED-04 の警告が出ること。(2) そのまま「了解して進む」を押すと WYSIWYG へ入り、**復元した未保存の内容がそのまま面に残っている**こと（サーバーの正本で置き換わり、直後にまた復元の提案が出たら誤り — 正本を引き直す載せ直しが未保存の内容を踏んでいる印）。(3) 未保存の表示が続き、そのまま自動保存が通ること。未保存が無い状態（版の復元・競合の解決から立った門）で「了解して進む」を押した場合は、従来どおり正本を引き直して載せ直すこと
- **確認ポイント（門が同じ面で繰り返し出ない）:** 装飾ノートで警告を了解して WYSIWYG に入ったあと、本文を打って自動保存を数回走らせる。**警告が再び出ない**こと（出るなら、載せ直しの門が「取り込み由来か」まで材料にしている印。入ったあとの面には落とすものがもう無い）
- **確認ポイント（貼り付け・リンク）:** WYSIWYG の面で、別のタブから `<img src="x" onerror="alert(1)">` を含む HTML をコピーして貼り付けても `alert` が出ないこと。書式バーの「リンク」で `javascript:alert(1)` を入れると受け付けずに案内が出て、`https://example.com` と `#anchor` は通ること。貼り付けた内容が caret の位置に入り、caret がその直後へ移ること（貼り付けはブラウザーの取り消し履歴に載らないので、Ctrl+Z で戻らないのは仕様である）
- **確認ポイント（`<form>` の中の散文が面で消えない）:** 別のタブから `<form action="/x"><p>これは本文です</p></form>` を含む HTML をコピーして WYSIWYG の面へ貼り付ける。`<form>` そのものは面から外れるが、**中の「これは本文です」は残る**こと（消えたら誤り — 保存側は未許可要素を unwrap して散文を残すので、面だけが散文ごと捨てていることになる）。そのまま保存し、詳細でもその段落が残っていることを見る

### 4. 編集モードを切り替え、既定を引き継ぐ（TC-07）

- **対応する受け入れ基準:** AC-5
- **検証手段:** browser
- **目的:** 未保存の変更があるときの切り替え確認と、選んだモードが端末に保持されて次の編集の既定になることを確認する
- **手順:**
  1. HTML モードで本文を変更し、保存前にビジュアルモードへ切り替えようとする
  2. 確定する
  3. ノート一覧に戻り、別の既存ノートの編集を開く
  4. WYSIWYG モードへ切り替え、装飾ノート（確認項目 3 のもの）の編集を開き直す
- **期待結果:** 手順 1 で切り替えの前に保存されることを伝える確認が出る。手順 2 で保存されてからビジュアルモードで開かれ、同じ本文が表示される。手順 3 で前回選んだモードが既定として開かれる。手順 4 で既定が WYSIWYG でも、装飾ノートは WYSIWYG に入る前に ED-04 の警告を挟む（既定の復元が警告を素通りしない）
- **確認ポイント:** モードの既定は端末側の保持で、サーバーへ永続化しない。**新規作成（`/notes/new`）は常に WYSIWYG** で開くこと（既定の引き継ぎ対象外）。手順 2 で面に載るのは**サーバーから引き直した本文**なので、切り替えた直後に本文が編集前へ巻き戻らないこと、そのまま 2 秒ほど待っても自動保存が走らない（「保存済み」のまま）ことを併せて見る。ビジュアルモードで書き換えて保存したあと HTML モードへ切り替えたときも、その書き換えが残っていること。手順 4 の警告で「取りやめ」を選んだら WYSIWYG へ入らないこと
- **確認ポイント（門の逃げ先は既定にならない）:** WYSIWYG モードで作業しているノートで、下端の「版を復元」から `<style>` を持つ版を復元する（面は HTML へ移り警告が出る）。そこで「取りやめ」を選び、**別の既存ノートの編集を開く**。そのノートが **WYSIWYG で開く**こと。HTML で開いたら誤り — 門の逃げ先として強制されたモードを端末の既定として書いている印で、一度装飾を持つ版に触れただけで以後どのノートも HTML で開くことになる（ED-05 が端末に持つと定めているのは「**選んだ**モード」）。開発者ツールの Application → Local Storage の `hollow.noteEditor.mode` が復元の前後で変わっていないことも見る。同じことを競合の解決・退避の復元で門が立った場合にも見る。逆に、モードのラジオで選んだ切替と警告の「了解して進む」は**書かれる**こと（手順 3〜4 が変わらず通ること）

### 5. 画像を本文に挿入する（TC-08）

- **対応する受け入れ基準:** AC-6
- **検証手段:** browser
- **目的:** ツールバーからのメディアアップロードが完了し、保存先 URL を参照する要素が本文に挿入されることを確認する
- **手順:**
  1. WYSIWYG モードのツールバーから画像の挿入を開始する
  2. `/tmp/hollow-manual-7/media.png` を選ぶ
  3. 書式ツールバーの「代替テキスト」を押し、`図 1` と入力する
  4. 保存してノート詳細を開く
  5. HTML モードでソースを確認する
- **期待結果:** 手順 2 でその場に進捗が表示され、完了後に画像が挿入される。手順 3 の入力値が `alt` として保存される。手順 4 で画像が表示される。手順 5 で画像の参照先がサービス内のストレージ（`/storage/...`）を指す URL になり、`alt="図 1"` が残っている
- **確認ポイント:** 参照先が `blob:` や `data:` のままになっていないこと（保存後に別セッションで開いても表示されるか）。「代替テキスト」は**本文で選んでいる画像**に効く。挿入直後はその画像が選ばれているので押すだけでよいが、あとから変えるときは本文の画像をクリックしてから押す（画像を選んでいなければ押せない）。進捗の行が同じファイルで 2 本並ばないことも見る
- **確認ポイント（自動保存と並行してよい操作）:** 本文を打って自動保存が走っている最中に、書式ツールバーの「太字」「見出し」と「画像・動画を挿入」「版を復元」が**押せる**こと（これらは版を進める往復を持たない）。逆に「保存」「破棄」とモードのラジオは往復のあいだ無効のままであること
- **確認ポイント（ファイル名の `$` が本文を壊さない）:** `media.png` を `a$'b.png`（および `a$&b.png`）という名前でコピーし、**HTML モードで**本文の途中に挿入する。挿入後のソースで `<img … alt="a$'b.png">` が 1 つだけ入り、**本文の後半がその `alt` の中へ複製されていない**こと（`$'` / `$&` は置換値として展開される記法なので、文字列のまま渡すと要素の境界が壊れる）
- **確認ポイント（失敗行の後始末）:** アップロードを失敗させて「再試行」の行を出したままモードを切り替えると、その行が消えること（面を載せ直した以上、行が指していた仮の要素はもう無い。とくにビジュアルモードには挿入そのものが無いので、行が残ると押せる「再試行」だけが残る）

### 6. タイトルをインラインで変更する（TC-09）

- **対応する受け入れ基準:** AC-7
- **検証手段:** browser
- **目的:** ノート詳細でのタイトル自動保存と、一覧・詳細への反映を確認する
- **手順:**
  1. ノート詳細でタイトルを選んで `改題したノート` に書き換える
  2. ノート一覧に戻る
  3. タイトルを空にする
- **期待結果:** 手順 1 で入力が終わると自動保存され、保存完了が表示される。手順 2 で新しいタイトルで表示される。手順 3 で「無題」を示す既定のタイトルに戻る
- **確認ポイント:** 編集画面側のタイトル欄でも同じ挙動になること（PAGE-p11-002 と P-12 の両方に入口がある）
- **確認ポイント（詳細の 4 往復の排他）:** 開発者ツールで回線を絞り（Slow 3G など）、ノート詳細でタイトルを 1 文字打ってから **800ms 以内に**メニューから表示スタイルを切り替える（同じ手で「ゴミ箱へ移動」も試す）。競合の文言が出ずタイトルが巻き戻らないこと、切替が終わったあとにタイトルの自動保存が改めて走って**その打鍵も届く**こと（ページを読み直して確認する）。両者が同じ版を同時に送っていると後着が必ず競合する
- **確認ポイント（新規作成の初回保存）:** `/notes/new` をタイトル空のまま（本文だけ書いて）自動保存させると、保存後に編集画面のタイトル欄が**「無題」になる**こと。空のまま残り「未保存」が下りないなら誤り（サーバーが正規化したタイトルではなく送った生値を確定済みにしている）。前後に空白を入れたタイトルでも同じく、保存後の欄から空白が落ちていること

### 7. 編集内容を破棄する（TC-10）

- **対応する受け入れ基準:** AC-8
- **検証手段:** browser
- **目的:** 「未保存」の状態表示と明示的な破棄を確認する
- **手順:**
  1. 編集画面で本文を変更する
  2. 編集内容を破棄する
  3. 本文を確認する
  4. ビジュアルモードへ切り替え、テキストを 1 か所書き換えて保存する
  5. 続けて別の箇所を書き換え、保存される前に破棄する
  6. 本文を確認し、そのまま 3 秒ほど待つ
- **期待結果:** 手順 1 で未保存の変更があることが表示される。手順 2 で確認のうえ最後に保存した状態に戻る。手順 3 で変更前の内容になっている。手順 6 で**手順 5 の書き換えだけが消え、手順 4 の書き換えは残っている**。待っても自動保存は走らない（「保存済み」のまま）
- **確認ポイント:** 「保存中 / 保存済み / 未保存」の 3 状態が区別して見えること。ビジュアルモードの破棄は面の見た目が戻るだけでは足りない — 手順 6 のあとに 1 文字打って自動保存させ、手順 5 で捨てたはずの書き換えが送られないことまで見る（送られると本文に復活する）。**破棄は開発者ツールで回線を絞って（Slow 3G など）押す** — 破棄は正本を引き直す 1 往復なので、その最中に自動保存が走ると破棄対象がそのまま保存され、画面上も破棄が起きない。往復のあいだは「破棄」「保存」とモードのラジオが無効になり、戻ってきたときに本文が手順 5 の前へ戻っていること

### 8. 版が記録され、過去の版から復元できる（TC-11）

- **対応する受け入れ基準:** AC-8
- **検証手段:** browser
- **目的:** 保存のたびの版の記録と、復元自体も版になることを確認する
- **手順:**
  1. 本文を 3 回変更して保存する
  2. 版の一覧を開く
  3. 最も古い版を選んで戻す
  4. 版の一覧を再度開く
- **期待結果:** 手順 2 で 3 件が新しい順に、作成者・日時・理由・抜粋つきで並ぶ。手順 3 で本文がその内容になる。手順 4 で戻す直前の内容が新しい版として記録されている
- **確認ポイント:** 未保存の変更を残したまま手順 3 の復元を押しても、**復元前の内容が復元後の版の上に書き戻らない**こと（復元は 2 往復あり、そのあいだ自動保存が走ってはならない）。直近 20 版の保持。21 回以上保存したときに古い版から落ちること。理由の列は保存経路ごとに分かれる — WYSIWYG へ**切り替えた直後の 1 回目**だけが「WYSIWYG への変換」で、同じ面での 2 回目以降は「編集」になること（全行が「WYSIWYG への変換」になっていたら誤り）
- **確認ポイント（性能）:** 抜粋は保存されておらず、一覧を開くたびに 20 版すべてを `HtmlProcessor.process` に通して作り直す。大きな本文（数百 KB の保存済み Web ページなど）で 20 版まで貯めた状態で一覧を開き、体感で待たされないかを見る。重ければ実装側の持ち分（`listNoteRevisions` の JSDoc に選択肢を残してある）で、手順の誤りではない

### 9. ゴミ箱に入れて復元する（TC-12）

- **対応する受け入れ基準:** AC-9, AC-10
- **検証手段:** browser
- **目的:** 削除 → ゴミ箱表示 → 復元の往復と、復元後の属性の保存を確認する
- **手順:**
  1. ノート詳細のメニューからノートを削除する
  2. 確定する
  3. スコープトークンのメニューからゴミ箱を開く
  4. そのノートを復元する
  5. 復元したノートのタグと公開ステータスを確認する
- **期待結果:** 手順 1 で確認が表示される。手順 2 で一覧から消え、削除を取り消す導線が画面上に出る。手順 3 でそのノートが削除日時順に並び、残り 30 日であることが示される。手順 4 でノートが一覧に戻る。手順 5 で削除前と同じ
- **確認ポイント:** 手順 3 の入口がスコープトークンのメニューにあること（L-01 の「使えない行き先は並べずに消す」）
- **確認ポイント（追加）:** 手順 2 のあと、そのノートの詳細 URL（`/notes/:noteId`）と編集 URL（`/notes/:noteId/edit`）を**直接開き直す**と、どちらも「見つかりません」になること（`spec/pages/index.md#P-11` の「削除済み」）。以前はゴミ箱のノートが通常どおり描かれ、編集画面では書けたうえで最初の保存だけが落ちていた。手順 4 の復元後は同じ URL が通常どおり開くこと
- **確認ポイント（追加）:** 手順 2 で出る「元に戻す」を押すと、追加の読み取りなしに 1 往復で戻ること（`trashNote` の応答が復元に要る版を運ぶ）。戻したあとに続けてタイトルを書き換えて自動保存し、競合にならないこと（`restoreNote` の応答の版を握り直しているかがここに出る）

### 10. 削除直後に取り消す（TC-33）

### 12. 表示スタイルを切り替える（TC-14 手順 1〜3）

- **確認ポイント（競合したあとに再試行が成立する）:** ユーザー A が `設計チーム` のノートの詳細を開いたまま、ユーザー B が同じノートの本文を編集して保存する（版が 1 つ進む）。ユーザー A が表示スタイルを切り替えると失敗し、「もう一度お試しください」が出る。**そのままもう一度切り替えると今度は成功する**こと。何度押しても同じ失敗が続くなら誤り（失敗のあとに版を引き直していない印で、画面を離れるまで永久に失敗する）。同じことを、詳細のタイトルの書き換え・詳細のメニューからの削除、ノート一覧の行メニューからの削除、ゴミ箱の「復元」「完全に削除」でも見る。詳細では引き直しても**入力中のタイトルが消えない**ことを併せて確認する（打鍵しながら別のブラウザで保存させて再現する）

## エッジケース・異常系

### 1. ビジュアルモードで要素を追加・削除しようとする（TC-15）

- **対応する受け入れ基準:** AC-2
- **検証手段:** browser
- **目的:** ビジュアルモードがテキストの書き換えに限られることを確認する
- **手順:**
  1. ビジュアルモードで本文の末尾に改行して新しい段落を作ろうとする
  2. 要素をまるごと選択して削除しようとする
  3. 画像の挿入操作を探す
- **期待結果:** 手順 1 で追加されず、面の上に出ている案内（「テキストの書き換えだけを行えます。段落や画像の追加・削除・並べ替えはできません」）がその旨を説明している。手順 2 で構造は削除されない。手順 3 でビジュアルモードには画像挿入が提供されていない

### 2. ビジュアルモードが選べない状態（TC-16）

- **対応する受け入れ基準:** AC-5
- **検証手段:** browser
- **目的:** 編集可能なテキストノードがない本文でモードが選べないことを確認する
- **手順:**
  1. 本文が空のノートの編集画面を開く
  2. 本文を入力して保存する
  3. 再度モード切り替えを確認する
- **期待結果:** 手順 1 でビジュアルモードが選べない状態になっている。手順 3 で選べるようになる
- **確認ポイント:** 端末の既定が「ビジュアル」になっている状態（別のノートで一度選んでおく）で手順 1 を行い、**既定の復元がこの判定を迂回しない**ことを見る。編集欄が 1 つも無いビジュアル面が開いたら誤りで、開いた直後のモードのまま開くのが正しい
- **確認ポイント（逃げ先が警告を立てない）:** 端末の既定を「ビジュアル」にしたまま、装飾ノート（確認項目 3 のもの。テキストノードを持たない `<style>` だけの本文でよい）の編集を開く。**何も操作していないのに ED-04 の警告が立たない**こと。立つなら逃げ先が WYSIWYG に固定されている印で、利用者は「取りやめ」を押して初めて HTML の面で作業を始められる

### 3. 許可リストにない要素・属性が除去される（TC-17 / TC-17b）

- **対応する受け入れ基準:** AC-3
- **検証手段:** browser
- **目的:** 要素単位の除去と、属性値の中の HTML というすり抜け経路の両方が塞がれていることを確認する
- **手順:**
  1. HTML モードで `<script>alert(1)</script>` を加えて保存する
  2. `<a href="javascript:alert(1)">link</a>` を加えて保存する
  3. `<div onclick="alert(1)">x</div>` を加えて保存する
  4. `unsafe-elements.html` の内容を貼り付けて保存し、詳細のソースを確認する
  5. `unsafe-srcdoc.html` の内容を貼り付けて保存し、詳細のソースを確認する
- **期待結果:** 手順 1〜3 は保存自体は成功し、除去された内容（`script` 要素 / 危険な URL / イベントハンドラー属性）が保存後に一覧される。手順 4 で `iframe` / `object` / `embed` / `form` と入力欄 / `base` / `meta` / `link` と未知の `foo` 要素がすべて除去された旨が一覧され、詳細に 1 つも残らず入力欄も表示されない。手順 5 で `iframe` 要素と `srcdoc` 属性の両方の除去が示され、`srcdoc` の中の `script` も残らず、許可される `div` は残って `srcdoc` 属性だけが落ちる
- **確認ポイント:** どの手順でもスクリプトが実行されないこと。除去の一覧は**保存後に**表示される（保存を拒否するのではない）

### 4. 本文の CSS から危険な宣言が除去される（TC-17c）

- **対応する受け入れ基準:** AC-3
- **検証手段:** browser
- **目的:** サニタイズが CSS の宣言単位で働き、装飾全体を落とさないことを確認する
- **手順:**
  1. HTML モードに `unsafe-css.html` の内容を貼り付けて保存する
  2. ノート詳細を開く
  3. 保存後の `<style>` と `style` 属性の内容を確認する
  4. `decorated.html` から作った装飾ノートを保存し直す
  5. `<style>.a{content:"</style>` だけを本文にして保存し、詳細のソースを控えてから、同じノートをもう一度保存する
- **期待結果:** 手順 1 で `position` と `@import` の除去が示される（一覧は種類ごとに 1 行にまとまるので、綴りの数だけ行が増えるわけではない）。手順 2 で本文が画面全体を覆うオーバーレイにならない。手順 3 で `position: fixed` / `position: sticky` だけが落ち、`color` などの他の宣言と `<style>` 要素そのものは残る。`position: absolute` は残り、基準は本文の内側に収まる。手順 4 で非許可の宣言がない装飾はそのまま保たれ、見た目が変わらない。手順 5 は 2 回目の保存のあともソースが 1 回目と一致する
- **確認ポイント:** ベンダー接頭辞付きの同義指定も落ちること。`position/**/:fixed` / `position:/**/fixed` / `position:\66 ixed` / `@\69 mport` のように CSS コメント・識別子エスケープで綴った指定も同じく落ち、`#906` / `#960` / `#603` の色だけが残ること（ブラウザはコメントとエスケープを解決してから読むので、これらは実効的に素の綴りと同じ）。`position:var(--x)` も `--x:fixed` の有無にかかわらず落ちること（値の判定は許可リストなので、ブラウザ側でしか解決できない間接は綴りを列挙せずに落ちる）— `.indirect` の `#c39` と属性側の `#39c` は残るが配置は効かず、画面全体を覆う面にならないこと。`position:inherit` は残ること。**引用符そのもの・括弧そのものをエスケープした綴り**（`content:\";position:fixed` / `background:url\(x;position:fixed` と `.escaped` / `@import url\(…` の行）も落ち、`#690` / `#c60` / `#c09` の面が画面を覆わないこと — ブラウザはエスケープを識別子の一部として読むので `;` はそこで宣言を終端する。あわせて `@import url\(…` の**後ろの `.after` 規則が消えていない**こと（`#069` が残る）: 走査だけが括弧を開くと、除去は 1 件しか報告されないまま続く装飾ごと飲み込まれる。**引用符なしの `url(` の内側にコメント記法を混ぜた綴り**（`.urlcomment` / `.urlclosed` と属性側の `background:url(x/*);position:fixed`）も落ち、`#9c0` / `#0c9` / `#c90` の面が画面を覆わないこと — ブラウザは `url(` の内側をコード点のまま `)` まで読むので `/*` はコメントにならず、`)` の次の `;` が宣言を終端する。`background` の宣言そのもの（`url(x/*)` / `url(/*)*/`）は残ること（除去の単位は宣言であり、字句の読み方が変わっただけで装飾を余分に落としてはならない）。手順 5 は**保存を繰り返しても本文が 1 バイトも変わらない**こと — サニタイズは不動点でなければならず（同じ本文を 2 回通しても結果が変わらない）、閉じていない CSS 文字列に `;` を補うと保存のたびに本文が伸びる（自動保存のたびに起きるので、伸びた分は除去の一覧にも画面にも出ない） **改行で終わる CSS 文字列**（`.badstring` と属性側の `content:'a⏎;position:fixed`）も落ち、`#963` / `#639` の面が画面を覆わないこと — ブラウザは素の改行で文字列を bad-string として終わらせ、続く `;` が宣言を終端する。`content` の宣言そのものは残り、**その改行も残る**こと — `.badstring` の後ろに書かれた `.fnurl` / `.ok` の装飾（`#369` / `#036`）が効いていること。改行を落として `;` を書くと出力では文字列が開き直し、後続の規則がまるごと値に飲まれる（除去の一覧は空か `position` 1 件のままなので、画面からは「何も除去されていないのに装飾が消えた」ようにしか見えない）。**`url(` でない関数トークン**（`.fnurl` の `myurl(a(b);position:fixed)`）は規則ごとそのまま残り、`#369` の装飾が失われないこと — ここで url-token として過剰に一致させると、除去した側が閉じ括弧を持ち去って同じ規則の残りまで飲まれる。

### 4b. サニタイズが資源で有界である（TC-17f）

- **対応する受け入れ基準:** AC-3 / AC-6
- **検証手段:** browser
- **目的:** 入力の形によらず、サニタイズが有界な費用で終わるか明示的なエラーで打ち切られることを確認する
- **手順:**
  1. HTML モードに `<div>` を 2,000 回並べただけの本文（22 KB）を貼り付けて保存する
  2. HTML モードに `<style>` の中で `@media a{` を 12,000 回並べた本文（108 KB）を貼り付けて保存する
  3. HTML モードに `<table><tr>` の下へ `<font a="0">`〜`<font a="59">` と `<tr>X</tr>` 3,000 行を並べた本文を貼り付けて保存する
  4. HTML モードに `<p>xxxxxxxx</p>` を 130,000 回並べただけの本文（1.95 MB）を貼り付けて保存する
  5. 手順 4 の本文の先頭に `<form></form>` を足して保存する。`</template>` を足した版でも同じことをする
  6. HTML モードに `<h1>a</h1>` を 16,000 回並べた本文（160 KB）を貼り付けて保存する
  7. HTML モードに `<foo>` の下へ `<br>` を 130,000 個並べた本文（520 KB）を貼り付けて保存する
  8. 手順 1〜7 のあいだ、画面が応答し続けるか確認する
- **期待結果:** 手順 1〜3 はどれも数秒以内に保存が拒否され、「本文が複雑すぎる」旨のエラーが表示される（画面が固まったまま数十秒待たされることも、原因不明のエラーになることもない）。手順 3 の本文はタグがすべて閉じた整形式な HTML であり、許可リストにも掛からない。手順 4・5・7 も同じく数秒以内に「本文が複雑すぎる」で拒否される — 節点数の上限（50,000）に掛かるためで、**先頭の 13 バイトの有無で待ち時間が変わらない**こと（`<form>` や `</template>` を含む本文は解析の経路が変わるが、上限は同じ）。手順 6 は保存が成功し、見出しの目次が 16,000 件並ぶ（`a` / `a-2` / … / `a-16000`）— これも待たされないこと
- **確認ポイント:** 拒否は保存の前に起きるので、ノートの本文も版も増えないこと。上限より小さい本文（通常の装飾ノート）の保存は従来どおり成功し、結果が変わらないこと。手順 7 の失敗が「本文が複雑すぎる」であって「予期しないエラー」でないこと（節点数の上限が無いと素の `RangeError` になり、業務の語彙を持たない 500 として出る）

### 5. URL のスキームが選別される（TC-17d）

- **対応する受け入れ基準:** AC-3
- **検証手段:** browser
- **目的:** 許可する URL スキームの選別と、`target="_blank"` の正規化を確認する
- **手順:**
  1. HTML モードに `unsafe-url.html` の内容を貼り付けて保存する
  2. ノート詳細を開き、ソースを確認する
- **期待結果:** `javascript:` / `vbscript:` / `data:text/html` / `data:image/svg+xml` の URL が除去された旨が示される。`data:image/png` の画像だけが表示される。ナビゲーションの `data:`（`<a href="data:image/png...">`）は除去される。`https://example.com` へのリンクは残り、`rel="noopener noreferrer"` が付与されている
- **確認ポイント:** リソース参照の `data:` はラスタ画像に限って許可される。`img` と `a` で判定が分かれること
- **確認ポイント（保存前の面も同じ表で判定する）:** HTML モードに `<a href="java&#9;script:alert(1)">x</a><a href="data:text/html,<script>alert(1)</script>">y</a><img srcset="javascript:alert(1) 1x, https://example.com/a.png 2x">` を貼り、**保存せずに**プレビューのリンクをクリックする。ダイアログが出ないこと（出たら自己 XSS が成立している。ブラウザーは URL のスキームを読む前にタブ・改行・先頭の C0 制御文字を捨てるので、素朴な前置き比較では止まらない）。同じ本文をビジュアル / WYSIWYG の面へ載せても同じであること。併せて `srcset` は `https://example.com/a.png 2x` の候補が**残る**こと — 1 つ落ちただけで属性ごと消えるなら、面が保存より多く落としている印である
- **確認ポイント（ツールバーのリンク挿入）:** WYSIWYG モードで書式バーの「リンク」に `java\tscript:alert(1)`（タブを含む値）と `data:text/html,x` を入れると、どちらも断られること。`https://` / `mailto:` / `tel:` と `/notes` のような相対パスは通ること

### 6. 壊れた HTML が補正される（TC-18）

- **対応する受け入れ基準:** AC-3
- **検証手段:** browser
- **目的:** 構文補正の警告とプレビューを確認する
- **手順:**
  1. HTML モードで `<p>閉じていない段落` と入力する
  2. 保存する
- **期待結果:** 手順 1 で保存前に構文を補正したことを伝える警告と補正後のプレビューが表示される。警告は「プレビューは補正した構文で描いており、保存時にはさらに許可されていない要素・属性・CSS 宣言が取り除かれる」と読める文言になっている（「下のプレビューの内容で保存されます」という断言ではない）。手順 2 で補正された内容が保存される
- **確認ポイント:** プレビューは live DOM なので、保存前でも `on*` 属性・`<script>` / `<iframe>` を落としてから描く。`<img src="x" onerror="alert(1)">` を入力してもダイアログが出ないこと（出たら自己 XSS が成立している）。落とすのは保存時のサニタイズが落とすものの部分集合なので、プレビューが「保存される形」から外れる向きには動かない。`<div style="position:fixed;inset:0;background:red">x</div>` を入力しても、プレビューの枠の外へは広がらないこと（枠に `contain` が掛かっている。adr.md ADR-072）
- **確認ポイント（正しいソースには出ない）:** HTML モードに `<P CLASS='a'>x</P><br/><img src=y>&#x27;` を貼り、打鍵が止まって 1 秒ほど待っても**警告が出ない**こと。どれも HTML5 として正しい書き方で、ブラウザーの読み戻しが表記を正規化するだけである（大文字のタグ名・単引用符・自己終了記法・引用符の省略・エンティティ表記）。ここで警告が出るなら、判定が構造ではなく文字列の一致になっている印で、本当に壊れているときの警告が常時警告に埋もれる。逆に `<p><div>x</div></p>`（入れ子の違反）と `<table><tr><td>x</td></tr></table>`（`tbody` の補完）では**警告が出る**こと
- **確認ポイント（`:host` で面の外へ出られない）:** HTML モードで `<style>:host { transform: scale(40) !important; }</style><p>x</p>` を入力して保存する。(1) HTML モードのプレビュー枠、(2) ビジュアルモードの面、(3) ノート詳細の本文 — の 3 か所すべてで、拡大された本文が**それぞれの枠の外へ出ない**こと。上部バー・保存ボタン・詳細のメニューが覆われたら誤り（`:host` は shadow root では閉じず、`!important` が付くと内側の木が勝つので、閉じ込めはホストの**親**に要る）

### 7. 本文サイズの上限（TC-19）

- **対応する受け入れ基準:** AC-3
- **検証手段:** browser
- **目的:** 800,000 バイトの境界を確認する
- **手順:**
  1. `just-under-800kb.html`（799,876 バイト）の内容を HTML モードに貼り付けて保存する
  2. `over-800kb.html`（801,416 バイト）の内容を貼り付けて保存する
  3. 内容を減らして再保存する
- **期待結果:** 手順 1 は保存できる。手順 2 は本文が大きすぎることと分割すればよいことが伝えられ、保存されない。手順 3 は保存でき、**手順 2 の入力内容が保持されている**
- **確認ポイント:** 上限判定は**サニタイズ後**のバイト数で、ドメインが出す。転送境界の上限はサニタイズ**前**の生 HTML に掛かる別物（2 MB）なので、手順 2 は「形が不正」ではなく「本文が大きすぎる」として返ること。手順 2 で入力が消えると書きかけを失うので、保持が最重要
- **確認ポイント（成功しない再試行を勧めない）:** 手順 2 の表示は「保存できませんでした（再試行 / 端末に退避した）」ではなく、**「この内容は保存できません」＋「内容を直すと自動保存を再開します」**であること。「再試行」ボタンが出ていたら誤り（同じ本文を送るかぎり必ず同じ拒否が返る）。開発者ツールの Application → Local Storage に `hollow.noteEditor.draft.{noteId}` が**書かれていない**ことも見る（上限超えの本文を毎回退避すると quota を無駄に押す）。手順 3 のように内容を減らすと、打鍵だけで自動保存が再開して保存が通ること。タイトルの上限超え（項目 8 の手順 2 をサーバーまで到達させた場合）も同じ扱いになる
- **確認ポイント（拒否の集合が閉じている）:** 同じ扱いになるのは列挙した数コードだけではない。エッジケース項目 4b（TC-17f）の資源上限に掛かる本文（深い入れ子）を HTML モードに貼って保存したときも、**「この内容は保存できません」＋「本文の構造が複雑すぎて処理できません…」**であること。「保存できませんでした」＋「再試行」＋ローカル退避が出たら誤り（答えの変わらない拒否を通信エラーとして扱っている）。同じことを、保持から溢れた版の復元（Local Storage を使わず、版の一覧を開いたまま 20 版を超える保存を重ねてから古い版の「復元」を押す）でも見る — こちらも「この版は見つかりません…」が拒否として出て、退避も再試行も出ないこと。一般に、サーバーが業務判断として返した拒否はすべてこちら側に落ち、「保存できませんでした」に落ちるのは通信断・サーバー障害・セッション切れだけである

### 9. 自動保存が失敗したときの退避と復元（TC-21）

- **対応する受け入れ基準:** AC-8
- **検証手段:** browser
- **目的:** 通信エラー時の状態表示と、再読み込み後の復元提案を確認する
- **手順:**
  1. 編集画面で本文を変更する
  2. 開発者ツールで通信を遮断する
  3. 自動保存の実行を待つ
  4. ページを再読み込みする
  5. 通信を回復して復元を選ぶ
  6. 手順 1〜5 をビジュアルモードで繰り返す（手順 1 はテキストノードの書き換え、手順 5 のあとは自動保存を待つ）
- **期待結果:** 手順 1 で未保存の変更があることが表示される。手順 3 で保存に失敗したことと再試行中であることが表示される。手順 4 で未保存の内容を復元するかどうかの提案が出る。手順 5 で変更内容が復元され、保存できる。手順 6 でも同じで、**ビジュアルモードでの書き換えが退避され、復元した内容がサーバーへ届く**
- **確認ポイント（退避の保持期限）:** 退避は 7 日で切れる。開発者ツールの Application → Local Storage で `hollow.noteEditor.draft.{noteId}` の `savedAt` を 8 日前のミリ秒に書き換えてから編集画面を開き直すと、復元の提案が出ず**その鍵ごと消えている**こと。同じ前置きの別の鍵（存在しないノートのものでよい）を古い `savedAt` で置いておくと、それも同時に消えていること。一括の掃除が走るのは**編集画面を開いた 1 回だけ**なので、画面を開いたまま古い鍵を書き足しても、その場では消えない（次に開いたときに消える）
- **確認ポイント:** 通信エラーは競合・権限喪失と**別の状態**として提示されること。手順 4 の提案が出たまま通信を回復して「再試行」で保存を通したら、**提案の表示も消える**こと（残ったまま「復元する」を押せると、いま保存した内容を古い退避で上書きできてしまう）。手順 3 のあと通信を遮断したまま本文を打ち続けても、**「保存に失敗しました」が消えず自動保存が勝手に再開しない**こと（打鍵で状態が消えると 1.5 秒ごとにサーバーを叩き続ける）。手順 6 は復元したあとページを読み直して、**書き換えが本当に保存されている**ことまで見る（画面が「保存済み」と言うだけで送られていない、が起こりうる箇所）
- **確認ポイント（保存以外の往復が落ちたとき）:** 既存ノートの編集画面で通信を遮断してから、モードの切替（または「破棄」・版の「復元」）を押す。「保存できませんでした」に**「再試行」が出る**こと、文言が「ノートがまだ作られていないため…」に**ならない**こと（そこは正本を引き直す往復で、ノートは確実に存在している。退避が書かれるのは保存の失敗だけなので、退避の有無で案内を分けると既存ノートで事実に反する説明が出る）。通信を回復して「再試行」を押すと、**押す前に落ちた往復そのもの**がもう一度走ること — 版の「復元」で落ちたなら復元が走って本文がその版に戻り、モード切替で落ちたならモードが切り替わり、競合の解決で落ちたなら選んだ枝が進む。どれを押しても本文の保存だけが走るなら誤り（落ちた操作と再試行が指す操作が食い違っている）
- **確認ポイント（保存が通ったあとの載せ直しが落ちたとき）:** ビジュアルモードでテキストノードを 1 つ書き換え、自動保存が走った**直後**（保存の往復が終わり、面の載せ直しが始まる瞬間）に通信を遮断する。「保存できませんでした」が出たら「再試行」を押し、走るのが**面の載せ直し**であること — 本文の保存がもう一度走ったら誤りで、版と版履歴が 1 つ無駄になり、適用済みの編集が再送されて「反映できなかった編集があります」の誤報が全経路に出る。遮断したまま本文をもう 1 か所書き換えて自動保存を待つと、経路単位ではなく**本文が丸ごと送られ**て通ること（載せ直しが落ちたままでも次の保存が自力で噛み合いを戻す）
- **確認ポイント（新規作成の初回保存が落ちたとき）:** `/notes/new` を開いて本文を打ち、自動保存が走る前に通信を遮断してから自動保存を待つ。「保存できませんでした」に**「再試行」は出ず**、代わりに「内容をダウンロード」が出て、文言も「退避できていません」になっていること（ノートがまだ無く退避の鍵が作れないため。「退避した」と告げたら誤り）。下端の「保存」も無効になっていること（押せると、押した回数だけ白紙のノートが増える）。通信を回復してノート一覧を見て、**白紙のノートが 1 件を超えて増えていない**ことも見る

### 10. 未保存のまま編集画面を離れようとする（TC-22）

- **対応する受け入れ基準:** AC-8
- **検証手段:** browser
- **目的:** 離脱確認がアプリ内遷移とブラウザ戻るの両方で働くことを確認する
- **手順:**
  1. 本文を変更し、保存される前に一覧へ戻ろうとする
  2. 離脱を取りやめる
  3. ブラウザの戻るボタンを押す
- **期待結果:** 手順 1 で未保存の変更があることを伝える確認が出る。手順 2 で編集画面に留まり変更内容が保持される。手順 3 で同じ確認が出る
- **確認ポイント（初回保存の URL 置き換えで確認が出ない）:** `/notes/new` を開き、回線を絞った状態で**打ち続けたまま**初回の自動保存を走らせる。(1) 離脱の確認が**出ない**こと（自分が起こした遷移で自分の確認を出すと、利用者には選べることが何も無い）。(2) 打ち続けているあいだは URL が `/notes/new` のままで、打鍵が止まって「保存済み」になってから `/notes/:noteId/edit` へ置き換わること。(3) 置き換わったあとの本文に、往復のあいだに打った分が**残っている**こと（移った先の画面はサーバーの本文で開くので、打鍵を抱えたまま移ると消える）

### 11. 編集中に他の利用者が同じノートを更新する（TC-23）

- **対応する受け入れ基準:** AC-2, AC-8
- **検証手段:** browser
- **目的:** 楽観ロックの競合が専用の状態として提示され、上書き / 破棄を選べることを確認する
- **手順:**
  1. ユーザー A が `設計チーム` のノートの編集画面を開く
  2. ユーザー B が同じノートを別のブラウザで編集して保存する
  3. ユーザー A が本文を変更して保存する
  4. 破棄を選ぶ
  5. 手順 1〜3 を繰り返し、上書きを選ぶ
- **期待結果:** 手順 3 で他の利用者が更新したことが伝えられ、上書きするか自分の変更を破棄するかを選べる。手順 4 で最新の内容が読み込まれる。手順 5 でユーザー A の内容で保存される
- **確認ポイント:** `ConflictError("OPTIMISTIC_LOCK_FAILURE")` を握り潰して黙って上書きしないこと。`version` は編集画面の所有者側が握るので、自動保存のたびにずれて毎回競合になる実装になっていないかも見る。競合の表示が出たあとに 1 文字打っても、**「競合しました」と上書き / 破棄の 2 ボタンが消えない**こと（消えると解決に手が届かないうえ、古い版のまま再送が始まる）。ビジュアルモードで手順 5（上書き）を行ったときは、経路単位ではなく**本文が丸ごと送られ**、ページを読み直すと自分の書き換えが残っていること（`skipped` の警告だけが出て内容が消えるのは誤り）

### 12. 保存時に編集権限を失っている（TC-24）

- **対応する受け入れ基準:** AC-8
- **検証手段:** browser
- **目的:** 保存時の権限喪失が専用の状態として提示され、書きかけを失わない導線があることを確認する
- **手順:**
  1. ユーザー A が `設計チーム` のノートの編集画面を開き、本文を変更する
  2. owner（ユーザー A 以外を owner にしたワークスペースを使うか、B を owner に昇格させておく）がユーザー A を `設計チーム` から除名する
  3. ユーザー A が保存する
  4. 画面上の導線を確認する
- **期待結果:** 手順 3 で権限がないことが伝えられる。手順 4 で編集中の内容をダウンロードできる。あわせて本文の面が**編集を受け付けなくなる**（WYSIWYG は打鍵できず、HTML モードの `textarea` は読み取り専用。選択とコピーはできる）
- **確認ポイント:** 除名の反映は `workspace.membership` の投影を経るので、手順 2 の直後に保存すると間に合わないことがある。数秒おいて再試行する
- **確認ポイント（ダウンロードが実際に落ちる）:** 手順 4 の「内容をダウンロード」で、ブラウザーのダウンロード一覧に `.html` が**実体として**残ること（0 バイト・失敗・無反応はいずれも誤り）。落としたファイルを開いてタイトルと本文が入っていることまで見る
- **確認ポイント（権限喪失後に版を進める操作が残らない）:** 手順 3 のあと、上部バーの「破棄」とモードの切替、下端の「保存」と**「版を復元」**が**すべて無効**であること。版の一覧を開いたまま権限を失った場合は各行の「復元」も無効になること。版の復元は破棄よりさらに強い「版を進める往復」なので、押せると権限を失ったノートで唯一操作できるボタンとして残り、サーバーの拒否で「保存できません」に戻るだけの空振りになる。また手順 3 の代わりに**モードを切り替える**（正本を引き直す往復）だけでも権限喪失が検出され、面が編集を受け付けなくなること（切り替えたあとふつうに書けてしまい、次の保存でだけ落ちるなら誤り）

## 既存機能への影響確認

- **ノート詳細の操作メニュー（`NoteDetail/menu.tsx`）** — 本スライスが編集・表示スタイル・削除を足す先に、#3 が入れた「移動」がある。移動が引き続き動き、移動後に `NoteUrlNormalizer` が正規 URL へ送ることを確認する（確認項目 14 の手順 6 と同じ経路）
- **ノート一覧（`NoteList` / `NoteListBoard`）** — 削除・復元で行が増減するようになる。個人・ワークスペース両文脈で、削除後の件数表示と空状態が正しく切り替わることを確認する
- **`/settings/usage`** — 完全削除で保存容量とノート件数が減る（確認項目 11 手順 3）。メディアを持つノートを消したときにだけ容量が動くこと
- **`storage.fileDeleted` の購読者（`deleteStoredObjects`）** — `note.purged` の fan-out が新しく同じ経路に流れ込む。アカウント削除（`/settings/danger`）とワークスペース削除（`/workspaces/:workspaceId/settings/danger`）が引き続き完了することを 1 度確認する
- **アカウント削除の障壁と `note.purged` の追随（adr.md ADR-056）** — 削除の障壁は `note` の ack で完了するので、追随者（保管ファイル・タグ付与・バックアップ記録）は**障壁が完了した後**に配送される。ノートを 1 件以上持つアカウントを削除し、完了後にサーバーログへ購読者の失敗（`[subscribers] … failed for note.purged`）が出ていないことを確認する。ここが落ちると tag 付与・バックアップ記録が恒久的に残る
- **ゴミ箱のノートへのメディアのアップロード（adr.md ADR-081）** — `storeMedia` がゴミ箱のノートを本文側と同じ `NoteIsTrashed` で拒むようになった。画面からはゴミ箱のノートを開いて編集する導線が無いので新しい手順は起こせないが、確認項目 9（ゴミ箱に入れて復元する）のあと**復元したノートに画像を挿入できる**ことを 1 度見る。ここが拒否されたら判定が復元後まで残っている
- **アカウント削除の `note` 成分の完了条件（adr.md ADR-084）** — 障壁の ack が「列挙が尽きた」から「止まった purge が 1 件も残っていない」に変わった。正常系の見え方は変わらない（ノートを持つアカウントの削除は従来どおり完了する）が、確認項目 11 のあと `/settings/danger` からノートを 1 件以上持つアカウントを削除し、**削除が `deleting` のまま止まらずに完了すること**を 1 度見る。止まったままなら purge がどこかで中断していて、サーバーログに `[deleteNotesForOwner] a note was left behind` が出ている。持ち回る ID は**中断を検知したその場で** `scheduled_tasks` に書かれるようになった（adr.md ADR-087）ので、`[deleteNotesForOwner] a stuck purge could not be armed for the next turn` が出ていたら、その ID はどこにも残っていない — 削除が完了していても公開行が残る可能性があるため、その回だけは公開 URL（確認項目 11 手順 5）も併せて見る
- **保持期限回収の 1 turn の件数（adr.md ADR-114）** — `purgeExpiredTrash` の既定・上限が 100 件から 40 件に下がった。ゴミ箱に 41 件以上の期限切れが同時に溜まった scope でだけ turn 数が増える差で、回収そのものは直後に再予定されるため見え方は変わらない（参照ランタイムには D1 予算が無いので所要時間の差も出ない）。確認項目 11 / 13 の見え方は変わらない
- **完全削除の追随の優先度（adr.md ADR-068）** — 削除由来でない purge（ゴミ箱を空にする・retention sweep）の継続 task は priority 3（期限回収）で積まれるようになった。1 ノートの付与・記録・ファイルが 1 ページに収まらない規模でだけ観測できる差で、同じ scope に投影や outbox の仕事があると回収が 1 turn ぶん後ろへ回る。確認項目 11（完全削除）の見え方は変わらない。アカウント削除由来の追随は従来どおり priority 0 のまま
- **SVG のアップロードが返す語彙（adr.md ADR-123）** — サニタイズが本文の 800,000 バイト上限に触れる SVG も、`storeMedia` が `FileTooLarge` へ翻訳するようになった。確認は TC-25 手順 16・17 に足してある。正常な SVG（手順 5・6・8・11）の見え方は変わらない。**エスケープで膨らむだけの SVG（手順 16）と、隠した `<table>` の再構成でそれが掛け算される SVG（手順 17）で、ノート本文向けの文言が出たら FAIL**
- **アカウント削除の 1 turn が触るノート数（adr.md ADR-124）** — 持ち回っている purge がある turn は、その件数だけページを狭く読むようになった。持ち回りは global（Cloudflare の D1 / 公開投影）が壊れているときにしか生じないので、参照ランタイムでは観測できる差が出ない。確認項目 11 の見え方は変わらず、ノートを持つアカウントの削除は従来どおり完了する
