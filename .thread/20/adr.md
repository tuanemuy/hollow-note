# ADR — Issue #20: OAuth 束縛 Cookie を state から独立した乱数にする

## ADR-001: 束縛の値を `state` と独立した乱数にし、その digest をフロー行に持たせる

### Context

現状の束縛 Cookie は `sha256(state)` で、`state` は認可 URL とコールバック URL に載って往復する。したがって「Cookie を再現できるのは `state` を知っている者すべて」であり、成立しているのは login CSRF（攻撃者は被害者のブラウザーに `HttpOnly` Cookie を置けない）の一方向だけになる。ADR 034 が掲げた「認可の完了は開始したブラウザーに束縛する」は成立していない。

双方向の束縛にするには「`state` から計算できない値」が要る。取りうる形は 3 つある。

1. 独立した乱数を Cookie に置き、その digest をサーバー側（フロー行）に持つ
2. Cookie の値を `state` の**鍵付き MAC**（`HMAC(serverKey, state)`）にする。サーバー側の記憶は不要で、照合は転送境界の純関数のまま
3. `state` を Cookie 値の digest にする（`state = sha256(nonce)`、Cookie には nonce）。これもサーバー側の記憶は不要

2 は配備に新しい鍵が要る（あるいは既存鍵の用途分離）。鍵が漏れれば束縛は即座に元の弱さへ戻り、`state` から決定的に導出される点も変わらない。3 は Cookie の値が `state` の原像になるため、Cookie 単体が `state` を含む「より強い資格情報」になり、ADR 034 が「`Path=/` の Cookie を全要求に相乗りさせるから単回消費の資格情報そのものは載せない」と決めた向きに逆行する。1 だけが「往復する値」と「ブラウザーにしか無い値」を独立した 2 本に保つ。

ADR 034 は代替案「フロー状態の行にブラウザー識別子を持たせる」を却下していた。理由は「ポートと全バックエンドに transport 由来の概念が入り、束縛の実現手段（Cookie）を差し替えられなくなる」。この理由は、行に持たせるのが**ブラウザー識別子**ではなく**不透明な一回限りの秘密の digest** であれば当たらない — 運搬手段が Cookie かヘッダーかを行は知らない。却下の根拠にあった「守りたい性質は攻撃者が被害者のブラウザーへ持ち込めない値があること**だけ**」という前提自体が、この Issue で誤りだと判明した。

### Decision

案 1 を採る。`OAuthFlowState` に `stateBindingHash: TokenHash` を 1 つ足し、`startOAuthFlow` が `secureTokenGenerator.issue()` でもう 1 本の秘密を発行して `token` を転送境界へ、`hash` を行へ置く。照合は `hashOf(cookie) === flow.stateBindingHash`。

Session / AuthToken / share token がすべて取っている「`token` は渡す値、`hash` は持つ値」の形に一致させ、新しい鍵も新しい暗号プリミティブも導入しない。

### Consequences

- 良い点: `state` を握った第三者は Cookie を再現できず、束縛が双方向になる。Cookie 単体・`state` 単体のどちらも完了に不足で、独立した 2 本が揃わないと通らない
- 良い点: 配備が管理する鍵が増えない。バックエンドを差し替えても、足したのは不透明な文字列 1 列だけ
- トレードオフ: ADR 034 が「転送境界に閉じる」と書いた分担が崩れ、照合の一部が内側へ移る（→ ADR-002）。ポート契約・適合スイート・全バックエンドが追随対象になる
- トレードオフ: 未実装の Integration スライスも同じポートを共有するので、新フィールドを intent 問わず必須にする。実装時に束縛を用意する義務が生じる

## ADR-002: 照合は `take` を「束縛が一致したときだけ消費する」条件付き原子操作にして行う

### Context

ADR 034 決定 2 は「照合は**ユースケースを呼ぶ前**に通す」ことを要求している。理由は、通っていない `state` を消費させないため — 第三者に URL を踏ませるだけで消費が走ると、正規のブラウザーのフローが壊れる。

digest をフロー行に置くと、照合材料は「原子的な単回消費（`take`）でしか読めない場所」に入る。3 つの置き方がある。

1. `take(state, stateBindingHash)` に変える。束縛が一致したときだけ行を消費し、不一致は消費せず `null` を返す
2. 非消費の読み取り（`peek` / `readBindingHash`）をポートに足し、転送境界が読み出して比較してから `take` する
3. `take` の後に比較する（照合をユースケースの中の消費後に置く）

3 は ADR 034 決定 2 をそのまま失う。この Issue の脅威モデル（未消費 URL を握った第三者）がそのまま「他人のフローを焼き切れる」経路になる。

2 は ADR 034 の分担（照合は転送境界）を保てるが、往復が 2 回になり、`peek` の唯一の存在理由が転送境界の束縛になる — ADR 034 が却下理由に挙げた「ポートに transport 由来の概念が入る」の、より露骨な形。加えて「束縛なしで `take` を呼べる」余地が型の上に残る。

### Decision

案 1 を採る。`OAuthStateStore.take(state, stateBindingHash)` とし、契約に「**行を削除するのは束縛が一致したときだけ**」を足す。不一致は行を残したまま `null`。

「照合を通らないものは消費されない」が 1 回の原子操作の中の性質になるため、呼び出し側の順序に依存しなくなる。束縛を**引数として渡さずに** `take` を呼ぶことは型として書けなくなる（CLAUDE.md「Make illegal states unrepresentable」）。ただし `TokenHash` は空文字列だけを弾く brand で、`hashOf("")` も通る。型が保証するのは引数の存在までであり、「Cookie が無い要求を弾く」のは転送境界の `requireOAuthStateCookie()` の役目として残る。

### Consequences

- 良い点: 往復 1 回で「照合前に消費しない」が保たれ、性質の正本がポート契約に載る。適合スイートで全バックエンドに強制できる
- 良い点: 未実装の Integration スライスも同じ保護を強制される
- トレードオフ: 「照合は転送境界に閉じる」という ADR 034 の分担が、「Cookie の運搬と不在判定は転送境界、値の照合は原子操作の中」に変わる。ADR 034 の本文改訂が必要
- トレードオフ: 「不一致では消費されない」は転送境界の型からは見えない。契約としての検証は適合スイートが担い、配線テストは実アダプターを差して観測する（→ ADR-007）
- トレードオフ: 全バックエンドが条件付き削除を実装する必要がある。D1 なら `DELETE … WHERE state = ? AND binding_hash = ? RETURNING *` の 1 文で、原子性の要求は現行と同じ

## ADR-003: `StartOAuthFlowView` は `state` を返さず、束縛の秘密だけを返す

### Context

`StartOAuthFlowView.state` は「転送境界がプロバイダーの URL を再パースせずに束縛できるように」だけ存在する（JSDoc・spec の両方に明記）。Cookie 値が `state` から導出されなくなると、この理由は消える。転送境界が Cookie に載せるのは新しい秘密であり、`state` は使わない。

残す案もある（将来の用途、テストの読み取りやすさ）。しかし残せば、単回消費の資格情報がユースケースの外へ出続けることになり、`authorizationUrl` と二重に運ぶ。

削除の増分コストは小さい。`view.state` を実際に読んでいるのは `startOAuthFlow.test.ts:35` の 1 アサーション（TC-identity-264）だけで、残りは spec の文言追随に収まる（ステップ 7 のテスト追随は `take` の署名変更で発生する分であり、`state` を残しても消えない）。逆に残すと、`setOAuthStateCookie(view.state)` のままでも型が通る経路が 2 本（サインイン開始・連携開始）残り、Cookie に単回消費の資格情報が載る退行を型で防げなくなる。

### Decision

`state` を落とし、`stateBinding: string`（束縛の平文秘密）に置き換える。`state` はアプリケーション層の内側に留まる。

### Consequences

- 良い点: 転送境界が受け取るのは「Cookie に載せるべき値」だけになり、DTO の意味が 1 つに絞れる
- 良い点: `state` が DTO 経由で漏れる面が 1 つ減り、旧実装への差し戻しが型エラーになる（実装量の最大部分を占める作業なので、受け入れ基準 AC-8 に持ち上げて契約側で決着させる）
- トレードオフ: spec の出力 DTO 表・UC 台帳・TC 行の文言が追随する。テストヘルパー（`beginOAuthFlow`）は元々 `authorizationUrl` から `state` を読み戻しているので影響しない

## ADR-004: 破棄経路の「一致した Cookie だけ捨てる」ガードは新規ユースケースで受ける

### Context

`abandonOAuthFlowFn`（消費 POST が起きずに終わる往復の後始末）は現在 `sha256(state)` との一致で「自分が焼いた Cookie か」を判定している。この判定が転送境界だけでは成立しなくなる。

- 無条件に捨てる: `/auth/callback/:provider?error=x&state=S` へのトップレベル遷移を踏ませるだけで、被害者の進行中フローの束縛を落とせる。ADR 034 決定 3/4 が明示的に閉じた経路なので採れない
- 破棄経路そのものを廃止して TTL に委ねる: 既存機能の後退で、取り残された Cookie が最大 10 分残る
- 内側に受け皿を作る: 判定材料（行の digest）がある側で判定する

### Decision

`abandonOAuthFlow`（新規ユースケース、`{ state, stateBinding }` → `{ abandoned: boolean }`）を置き、ADR-002 の条件付き `take` をそのまま使う。一致すれば行を消費し、転送境界はその結果を見て Cookie を捨てる。

`abandoned` はサーバー内で完結させ、`abandonOAuthFlowFn` の応答は現行どおり `null` に固定する。外へ返すと「この `state` と自分の Cookie が対だったか」を答える口が増えるだけで、呼び出し元（`callback.$provider.tsx` の loader）は結果を使っていない。

### Consequences

- 良い点: 「照合できた Cookie だけ捨てる」が保たれる。判定は 1 つの原子操作に統一され、比較のロジックが 2 か所に増えない
- 良い点: 放棄された `state` 行が TTL を待たず解放される（現行実装には無い新しい振る舞いなので、受け入れ基準 AC-5 に持ち上げて検証する）
- 良い点: 応答を `null` に固定するので、転送境界の DTO の意味が「Cookie を捨ててよいかはサーバーが決める」に絞れる
- トレードオフ: ユースケースが 1 つ増える。spec/usecases・testcases・UC / TC 台帳に行が増える
- トレードオフ: 破棄が「行を消す」操作になるため、ページの loader から POST server function 経由で状態が変わる。踏ませられるのは束縛 Cookie を持つ本人のブラウザーだけなので、壊せるのは自分の未完了フローに限られる

## ADR-005: 消費経路の Cookie 破棄は「`OAUTH_STATE_INVALID` 以外なら捨てる」に倒す

### Context

現在は「照合を通ったら成否によらず捨てる／通らなければ捨てない」（ADR 034 決定 3/4）を、転送境界での照合の直後に破棄することで実現している。照合が消費と同じ操作に移ると、転送境界は結果（例外）からしか判断できない。`OAUTH_STATE_INVALID` は「束縛不一致（未消費）」「行が無い（未消費）」「provider 不一致・`integration` intent（消費済み）」のすべてに使われており、消費の有無と 1 対 1 ではない。

### Decision

`OAUTH_STATE_INVALID` のときだけ捨てず、それ以外（成功・交換失敗・その他）は捨てる。

守るべき非対称は「他人の Cookie を落とさせない」側であり、この規則は安全側に倒れる（消費済みでも捨てないケースが残るだけ）。取り残された Cookie は行が消えている以上もう何も通せず、寿命は `state` 行と同じで、次のフロー開始が上書きする。

### Consequences

- 良い点: ADR 034 決定 4（照合に失敗した Cookie は触らない）が厳密に保たれる
- トレードオフ: 消費済みなのに Cookie が残るケース（provider 不一致・`integration` intent）が生まれる。無害だが「照合を通ったら残らない」という現行の言い切りは弱まるので、ADR 034 の本文を実態に合わせる
- トレードオフ: server function ハンドラーに境界の `try / catch` が 1 つ増える（CLAUDE.md が許す「明示的な境界」に該当）

## ADR-006: 新しい ADR 番号は起こさず、ADR 034 を改訂する

### Context

守りたい性質（認可の完了を開始したブラウザーに束縛する）と適用範囲は ADR 034 のままで、変わるのは束縛値の作り方と照合の置き場所。`spec/adr/` は現在有効な判断だけを載せ、廃止した判断も変更履歴も残さない方針。

### Decision

ADR 034 を改訂する（決定セクションの前文、決定 1 / 2 / 5、決定リスト後の理由段落、検討した代替案の 1 つ目、影響、前提）。番号付きリストの外にある前文と理由段落も改訂対象に含める — 前文の「転送境界に閉じる」と理由段落の「束縛の強さは変わらない」は改訂後の決定と正面から矛盾するので、リストだけ直すと正典が自己矛盾する。新規 ADR は起こさない。`spec/adr/index.md` の前提依存マップの 034 の行は、依存している前提を足したうえで、設計上の境界の不変条件（「認可の完了は開始したブラウザーに束縛する」）を残して層の分担を併記する。本 Issue はその不変条件を初めて成立させる変更なので、分担で置き換えると索引から性質が消える。

### Consequences

- 良い点: OAuth 束縛の判断が 1 ファイルに留まり、索引の番号体系が増えない
- トレードオフ: 「なぜ却下案を採ったか」の経緯は ADR 034 本文には残らない（改訂後の本文は現在の判断だけを述べる）。経緯はこの作業ログが持つ

## ADR-007: 配線テストの `oauthStateStore` は手書きモックではなく memory の参照アダプターを差す

### Context

AC-1（`state` だけを知る第三者の Cookie では消費されない）の中心は「束縛が一致しないと行が消費されない」ことだが、これは転送境界からは観測できない。現行の配線テストは `take` を `vi.fn()` で置いており、そのまま新設計へ移すと「条件付き消費を再現しているのはテスト内のモック」になる。つまり AC-1 を満たしているのがモックであって実装ではない、という状態を作りうる。

`adapters/memory/` はテスト fake ではなく正規のバックエンドなので（docs/test.md、ADR 024）、配線テストがこれを使うことは fake 方針に反しない。

### Decision

配線テストのコンテナには `new MemoryBackend({ clock })` ＋ `createMemoryOAuthStateStore(backend)` ＋ `createNodeSecureTokenGenerator()` を差す。準備はテスト側の `put` で行い、「消費されなかった」は `backend.oauthStates` を直接見て確かめる。`startOAuthFlow` は外部 IdP へ出るのでモックのまま残す。

### Consequences

- 良い点: AC-1 の検証が実装の性質そのものに乗る。適合スイートと配線テストが同じ実装を見る
- 良い点: 「不一致なら行が残る」「一致なら行が消える」を転送境界のテストからも観測でき、破棄経路（ADR-004）の新しい振る舞いも同じ場所で固定できる
- トレードオフ: 配線テストのセットアップが増える（backend の生成と `put` の準備）。代わりに `take` の呼び出し引数を検証する assertion は不要になる

## ADR-008: 転送境界の `OAUTH_STATE_INVALID` 判定は `serializeError` の構造判定で行う

### Context

ADR-005 で消費経路の Cookie 破棄が「`OAUTH_STATE_INVALID` 以外なら捨てる」になり、転送境界が例外の種別を判定する必要が生じた。素直に書けば `application/errors` の `isValidationError` だが、その実体は `error instanceof ValidationError` である。`-action.tsx` はユースケースを動的 `import` で読むためモジュールグラフが分かれうる — `errorResponseMiddleware` が `instanceof` を捨てて構造判定を採っているのと同じ条件下にある。

ここでの誤判定は安全でない向きへ倒れる。`OAUTH_STATE_INVALID` を取りこぼすと Cookie を**捨てる**分岐に入り、ADR 034 決定 4（照合に失敗した Cookie は触らない）が崩れる。

### Decision

`serializeError(error)`（`apps/web/app/presentation/errorResponse.ts`）で `kind === "validation" && code === "OAUTH_STATE_INVALID"` を見る。`components/note/NoteDetail/index.tsx` が既に取っている形で、CLAUDE.md の「presentation は構造で判定する」にも合う。

### Consequences

- 良い点: モジュールグラフの分割に影響されず、誤判定が安全でない向きへ倒れる経路を閉じる
- 良い点: 判定方法が手順として固定されるので、配線テストが「判定方法を誤っても通る」書き方にならない
- トレードオフ: 転送境界が `code` の文字列リテラルを 1 つ知ることになる。ただし `OAUTH_STATE_INVALID` はこの経路の分岐根拠そのものなので、隠す先がない

## ADR-009: `take` の 4 象限（一致／不一致 × 期限内／期限切れ）をすべて契約に含める

### Context

条件付き `take` の契約は「一致／不一致」と「期限内／期限切れ」の 2 軸 4 象限を持つ。書き方は 2 通りある。

1. 削除条件を 1 本のルールとして書き、4 象限すべてを決定する
2. 判定の順序（束縛の一致判定が先、期限判定は取り出した後）だけを書き、一部の象限をバックエンドの裁量に残す

2 を採ろうとすると、どの象限を残すのかが決まらない。「不一致 × 期限切れ」は「不一致は行を残す」で**既に決まっている**（残す方が浮かないのはこちら）。裁量の余地が実際にあるのは「一致 × 期限切れ」だけで、D1 が `DELETE` の `WHERE` に `AND expires_at > ?` を混ぜるかどうかが分岐点になる。しかも 2 の「判定の順序」を書いた時点で、その唯一の象限も「取り出した（＝削除した）後に期限で `null`」と決まってしまう。曖昧さを残す書き方が、結局は同じ結論を遠回りに述べるだけになる。

「行が消えたか」は `deleteExpired` の件数として同じポートから観測できるので、ADR 026 の「契約化するのは観測可能な結果だけ」を留保の根拠には使えない。

### Decision

案 1 を採る。契約は削除条件の 1 本のルールに畳み、4 象限すべてを決定する。

> 削除するのは束縛が一致したときだけ。一致すれば期限切れでも削除して `null` を返す。不一致は常に行を残して `null` を返す。

判定の順序は契約から実装ノートへ降格する（このルールから導けるもので、規範ではない）。

### Consequences

- 良い点: どのバックエンドも自然に満たす。memory は「引く → 束縛比較 → 削除 → 期限判定」、D1 は `DELETE … WHERE state = ? AND binding_hash = ? RETURNING *` の 1 文（`WHERE` に期限を混ぜない、という 1 行の実装制約になるだけ）
- 良い点: バックエンド間で「一致 × 期限切れ」の行の残り方がぶれる余地が消える。期限切れ行の掃除は引き続き `deleteExpired` が担うが、その入力集合が実装ごとに変わらない
- トレードオフ: 契約が 1 象限ぶん強くなる。ただし適合スイートの追加ケースは要らない — 4 象限のうち観測差として現れるのは「不一致では消費されない」だけで、それはステップ 4 で足すケースが既に覆う
- 訂正（レビュー 001 B-001 / W-001）: この「観測差が出ない」という前提は誤りだった。memory の `take` を「期限切れなら削除しない」に書き換えても適合スイートは全緑のままで、`deleteExpired` の件数として実際に観測差が出る。適合スイートに期限切れ側の 2 象限を足し、4 象限とケースを 1 対 1 に対応させる

## ADR-010: 配線テストの「ユースケースを呼ばない」は実アダプターを包んだ `vi.fn` で観測する

### Context

ADR-007 で配線テストの `oauthStateStore` は memory の参照アダプターを差すことにした。一方 AC-1 の後半（Cookie が無い `abandon` は**ユースケースを呼ばず**、行も残る）は「呼ばれなかった」ことの観測を要求する。

素直な代替は「例外が出ていない・`Set-Cookie` が出ていない・行が残っている」の 3 点で間接的に示す形だが、この harness では `abandonOAuthFlowFn` の応答 `null` が `createServerFn` のクライアント側チェーン（`next(await extractedFn(payload))` → `userCtx.context`）で `TypeError` になるため、`expect(outcome.error).toBeUndefined()` が原理的に通らない。これは harness の制約で、コンパイラーが呼び出し側を書き換える本番経路には無い（変更前の実装も `null` を返しており、旧テストはこの assertion を持っていなかった）。「行が残っている」だけでは、束縛不一致で呼ばれた場合と区別できない。

### Decision

参照アダプターの `take` を `vi.fn(store.take)` で包み、コンテナにはその包みを差す。条件付き消費の実体は実装のままで、テストが増やすのは呼び出し回数の観測だけ。`expect(take).not.toHaveBeenCalled()` を Cookie 不在の 2 経路（消費・破棄）に置く。

### Consequences

- 良い点: ADR-007 の趣旨（AC-1 を満たすのは実装であってモックではない）を保ったまま、「呼ぶ前に畳む」を直接観測できる
- 良い点: 転送境界のガードを消すと `take` が呼ばれてテストが落ちる。間接的な 3 点観測では気づけない退行を捕まえる
- トレードオフ: `abandonOAuthFlowFn` の応答 `null` は harness では常に `TypeError` として観測されるため、この 3 ケースは「例外が出ないこと」を主張しない

## ADR-011: `abandonOAuthFlow` の後始末の失敗は転送境界で best-effort に畳む

### Context

ADR-004 で破棄が「Cookie を捨てる」からユースケース呼び出し（`OAuthStateStore.take`）に変わった。変更前の実体は Cookie 値の比較だけで、I/O が無く原理的に throw しなかった。いまはポート契約どおり `SystemError(DatabaseError)` を投げうる。

唯一の呼び出し元は `callback.$provider.tsx` の loader で、`await abandonOAuthFlowFn(...)` を裸で呼んでいる。ここを例外が抜けると、P-05 は状態表が挙げる「キャンセル」を描く代わりにルートのエラー境界（SSR では 500）へ落ちる。取り残した Cookie の掃除に失敗しただけで、往復が失敗した理由の画面すら出せなくなる。参照ランタイム（memory）では顕在化しないが、D1 バックエンドでは普通に起きる。

畳む場所は 3 つある。

1. `abandonOAuthFlowFn` のハンドラーで catch し、`container.logger` に記録して `null` を返す
2. loader 側で `.catch(() => null)` する
3. 伝播させたままにする（現状維持）

2 は route ファイルに logger が無く、原因不明の無音失敗になる。転送境界の catch がルートファイルへ散る点でも、消費経路の catch（`OAUTH_STATE_INVALID` 判定）と非対称になる。3 は上記の回帰をそのまま残す。

### Decision

案 1 を採る。ユースケース呼び出しを server function のハンドラー内で `try / catch` し、失敗は `container.logger.error(message, { cause })` に落として応答は `null` のままにする。loader 側の呼び出しは裸の `await` のまま変えない。

CLAUDE.md の cross-layer catch policy が認める server-function 境界の catch であり、同じファイルの消費経路が既に持つ境界 catch と対称になる。掃除できなかった Cookie と `state` 行は TTL が引き取るので、失敗しても不変条件は壊れない（無条件破棄と違い、他人のフローを落とす向きへは倒れない）。

### Consequences

- 良い点: 後始末の失敗がコールバック画面の描画失敗に化けなくなる。破棄は best-effort な掃除という位置づけがコードにも現れる
- 良い点: 失敗の事実と原因が logger に残る。載せるのは例外だけで、Cookie の値や `state` は載せない
- トレードオフ: 破棄が黙って失敗するので、Cookie は TTL（最大 10 分）まで残りうる。取り残された Cookie は行が残っていても次のフロー開始が上書きする
- トレードオフ: harness の制約（応答 `null` が常に `TypeError` になる）から、配線テストの主張は「例外が出ない」ではなく「境界がエラー応答へ変えていない」＋「logger に記録された」の 2 点になる
