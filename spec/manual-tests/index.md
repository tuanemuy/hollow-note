## 記述規約 — UI 文言に依存しない

テスト手順書は UI に表示される文字列を逐語引用しない。文言の正典は `spec/design/` にあり、手順書が検証するのは挙動と伝わるべき情報である。これにより UI 文言の変更は手順書に波及しない。

- 操作は意図で書く。「〜というボタンを押す」ではなく「本文の再生成を実行する」のように何を達成する操作かを書く
- 状態は意味で書く。画面ラベルの引用ではなく「AI 連携が必要な状態」のように書く。繰り返し使う状態は前提条件のテストデータ表で別名を定義して呼ぶ
- 表示の確認は伝わるべき情報の要求として書く。文字列一致ではなく「連携を解除しても生成済みの本文が残ることが明記されている」のように書く。破壊的操作の確認では何が起きるか・期限・件数が具体的に示されることを要求する
- 逐語で書いてよいもの: ファイル名・ユーザー名・ワークスペース名・URL・パス・ロール名（editor / viewer）・ドメイン状態コード（`processing` など）・具体値（30 日・100 件など）・テストデータが持つユーザー作成コンテンツ
- 語彙は UI 表記の対訳表（`spec/design/index.md` §10）に従う。LLM は AI と書く。OpenRouter などの固有名詞はそのまま

## 実行の前に

1. `spec/scenario/` と `spec/pages/` を一読し、用語と画面名を把握する
2. 各テストドキュメントの「前提条件」に従って環境とテストデータを用意する
3. 複数の利用者を使うテストがあるため、ブラウザのプロファイルまたはシークレットウィンドウを 3 つ用意する
4. 「対象外」と注記された TC は、環境の制約で実行できない場合にのみ飛ばす。実行結果は `spec/` の外で管理する

## 推奨する実行順序

前のカテゴリーで作ったデータを後のカテゴリーで使うため、次の順で実行すると準備の手間が少ない。

1. アカウント — 利用者を用意する
2. ワークスペース — 共同作業の場とメンバーを用意する
3. 外部連携 — OpenRouter と Google Drive をつなぐ
4. 取り込み — ノートを作る
5. 編集 — ノートの内容を整える
6. 整理 — タグと一覧の操作を確認する
7. 共有 — 公開範囲を設定する
8. 発見 — 公開されたものを外から確認する
9. 書き出し — ダウンロードを確認する
10. 処理 — ここまでで溜まったジョブの履歴を使って確認する
