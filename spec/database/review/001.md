# DB レビュー 001

対象: `spec/database/index.md`

## 1. `invitations` のインデックスが重複している

`invitations_workspace_idx` (`workspace_id`, `created_at`) と `invitations_workspace_created_idx` (`workspace_id`, `created_at`) が同じ列の組で二重に定義されている。

**対応**: 1 つにまとめ、用途（一覧と発行数のレート制限の両方）を注記する。

## 2. `jobs.target_id` の NOT NULL 条件が CHECK として書かれていない

カラム表には「`target_type != 'batch'` のとき NOT NULL」とあるが、CHECK 制約の一覧にこの条件がない。他の判別ユニオン（`notes` の本文、`workspaces` の公開状態）は CHECK として明記されているため、ここだけ担保が抜ける。

**対応**: CHECK 制約に加える。

## 3. `share_pass_secrets` テーブルは不要

共有パスワードの通過証は「署名付きの値としてクライアントに持たせる。改ざん検知は presentation 層の責務」とドメインで定めている。署名鍵は要求ごとに設定から読めばよく、テーブルに置くと鍵の取り回しがアプリケーション層に漏れる。他の秘密（`SecretCipher` の鍵）も設定から供給する方針と揃わない。

**対応**: テーブルを削除し、署名鍵は `AppConfig` から供給する旨を注記する。

## 4. `oauth_flow_states.intent` の `'integration'` がドメインに存在しない

テーブルの `intent` は `'signIn' | 'linkIdentity' | 'integration'` の 3 値を許すが、Identity ドメインの `OAuthFlowState.intent` は `'signIn' | 'linkIdentity'` の 2 値しかない。Integration の `startIntegrationOAuth` も同じ `OAuthStateStore` を使うため、ドメイン側の型が実際の用途を表していない。

**対応**: `OAuthFlowState` を 2 つのドメインが共有する形に整理する。Identity の `OAuthStateStore` を横断的ポートとして扱い、`intent` に `'integration'` を加える。
