# クロスフェーズ検証 003

対象: `spec/` 配下すべて

## 結果

対応が必要な問題は見つからなかった。

## トレーサビリティ

### 上流成果物 → ユースケース

- シナリオ 78 件がすべて、1 つ以上のユースケース（またはその組み合わせ）で実現される
- 画面 32（+ レイアウト 2 / 公開エンドポイント 1）の機能が、いずれもユースケースに対応づく
- 画面のみで完結する操作（編集モードの切り替え、表示形式の切り替え）は、対応するユースケースを持たないことが妥当と確認済み

### ユースケース → ドメインモデル

123 のユースケースが呼び出すドメインの振る舞いをすべて洗い出し、定義済みであることを確認した。逆方向も確認し、呼ばれない振る舞いが残っていないことを確かめた。

| 検証 | 結果 |
| --- | --- |
| ユースケースが呼ぶエンティティの振る舞い | すべて定義済み |
| ユースケースが呼ぶドメインサービス | すべて定義済み（12 種） |
| 定義されているが呼ばれない振る舞い | `StorageQuota.changeLimit` のみ（運用時の上限変更用であり、ユースケース化しないことを意図している） |

### ドメインエンティティ → DB テーブル

すべてのエンティティと、ポートが必要とする保持先にテーブルが対応する。判別ユニオンは CHECK 制約で不正な組み合わせを禁じている。永続状態を持たない Conversion にはテーブルがない。

### ポート → ユースケース

定義した 30 のポートすべてに、少なくとも 1 つの呼び出し元がある。使われないメソッド（`ObjectStorage.createUploadUrl`）は検証 001 の対応で削除済み。

### ユースケース → テストケース

123 のユースケースすべてにテストケースのファイルがあり、名前が 1 対 1 で対応する。各表は正常系・異常系・境界値・エッジケースを含み、ユースケースのエラーケース表の項目を覆っている。

## アーキテクチャ適合性

| ルール | 確認結果 |
| --- | --- |
| ドメインモデルの独立性 | ドメイン層に DB / HTTP / フレームワークの型は現れない。時刻と ID は引数とポートで受け取る |
| ビジネスロジックの配置 | 判定と状態遷移はエンティティとドメインサービスにある。ユースケースは順序づけ・ポートの呼び出し・DTO への射影のみ |
| 集約境界 | 集約をまたぐ参照はすべて ID。DB でも集約をまたぐ外部キーを張らず、イベント駆動で後始末する |
| ポートによる抽象化 | 外部依存は 30 のポートに閉じ、すべてメソッドシグネチャとエラーケースを持つ |
| ドメイン間の非循環 | `Identity → Workspace → Storage → Conversion → Note → {Tag, Integration, Job, Usage}` の一方向。循環なし |

## 実装可能性

各ドメインについて、実装に必要な情報が揃っていることを確認した。

- 型・シグネチャ・制約・不変条件・エラーコードがすべて定義されている
- 非同期処理の境界（何がジョブになるか、冪等性をどう担保するか）が明示されている
- 結果整合を許す箇所（読み取りモデルの投影、使用量の集計、タグとファイルの付け替え）と、同期的に読む箇所（権限判定、共有リンクの解決、ノート詳細）が区別されている
- 非自明な判断は 9 件の ADR に記録され、各ドキュメントから参照されている

### 数え直しの根拠

- **シナリオ**: `spec/scenario/*.md`（index.md を除く）の `## <カテゴリー略号>-<番号>` 見出し。AC 10 / IN 9 / IM 6 / ED 11 / OR 12 / SH 8 / WS 10 / DS 6 / EX 4 / JB 3 = 79。カテゴリーの前置き節（「形式ごとの変換方針」「ジョブの種類」等）は除外。
- **ドメインサービス**: `spec/domains/*.md`（index.md を除く）の `## ドメインサービス` 節直下の `###` 見出し。Identity 3 / Workspace 2 / Storage 2 / Conversion 2 / Note 2 / Tag 2 / Integration 2 / Job 2 / Usage 1 = 18。
- **ポート**: 同じく `## ポート` 節直下の `###` 見出し。Identity 9 / Workspace 3 / Storage 4 / Conversion 6 / Note 7 / Tag 3 / Integration 8 / Job 2 / Usage 2 = 44。`spec/domains/index.md` の「新設する横断的ポート」には `####` 見出しが **4 件**（`MailSender` / `TimeZoneResolver` / `OAuthStateStore` / `IdempotencyStore`）あるが、`OAuthStateStore` は `domains/identity.md` の `## ポート` 節にも `### OAuthStateStore（横断的ポート）` として挙がっており上の 44 の内数であるため、44 に足して数えるのは残る 3 件（`MailSender` / `TimeZoneResolver` / `IdempotencyStore`）に限る。既存の横断的ポート（clock / idGenerator / logger / outboxRepository）は本設計での新規定義ではないため数に含めない。
- **ユースケース**: `spec/usecases/*.md`（index.md なし）の `##` 見出し **151 件**から、ユースケースではない共通節 **12 件**を除いた 139 件。`publishWorkspace` と `unpublishWorkspace` はそれぞれ独立した `##` 見出しであり、合同見出しの補正は要らない。除外した共通節の内訳は `identity.md` 1 件（「共通の約束」）、`job.md` 6 件（「共通: 登録時の scope の決定」「共通: リース期間と回収の間隔」「共通: run 系ワーカーの冪等規則」「共通: 強制終端の後始末」「共通: 実行体の振り分け」「共通: batch 親の組み立て規則」）、`note.md` 3 件（「共通: 閲覧者コンテキストの解決」「共通: ExportTicket」「共通: ユースケースを合成するときの副作用の範囲」）、`tag.md` 1 件（「共通: スコープの解決」）、`usage.md` 1 件（「共通: UoW の境界」）。ファイル別では Identity 22−1=21 / Workspace 21−0=21 / Note 39−3=36 / Tag 13−1=12 / Storage 13−0=13 / Conversion 4−0=4 / Integration 15−0=15 / Job 16−6=10 / Usage 8−1=7 = 139。
- **テストケース**: `spec/testcases/**/*.md` の実ファイル数 139（Identity 21 / Workspace 21 / Note 36 / Tag 12 / Storage 13 / Conversion 4 / Integration 15 / Job 10 / Usage 7）。ユースケースとの 1 対 1 対応は維持されている。

なお「ポートによる抽象化」「ポート → ユースケース」の検証結論そのもの（すべてのポートに呼び出し元があり、シグネチャとエラーケースを持つ）は、数の訂正によって変わらない。
