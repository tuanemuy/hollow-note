# クロスフェーズ検証 003

対象: `spec/` 配下すべて

## 結果

対応が必要な問題は見つからなかった。

## トレーサビリティ

### 上流成果物 → ユースケース

- シナリオ 78 件がすべて、1 つ以上のユースケース（またはその組み合わせ）で実現される
- 画面 32 件（＋レイアウト 2、公開エンドポイント 1）の機能が、いずれもユースケースに対応づく
- 画面のみで完結する操作（編集モードの切り替え、表示形式の切り替え）は、対応するユースケースを持たないことが妥当と確認済み

### ユースケース → ドメインモデル

123 のユースケースが呼び出すドメインの振る舞いをすべて洗い出し、定義済みであることを確認した。逆方向も確認し、呼ばれない振る舞いが残っていないことを確かめた。

| 検証 | 結果 |
| --- | --- |
| ユースケースが呼ぶエンティティの振る舞い | すべて定義済み |
| ユースケースが呼ぶドメインサービス | すべて定義済み（12 種） |
| 定義されているが呼ばれない振る舞い | `StorageQuota.changeLimit` のみ（運用時の上限変更用であり、ユースケース化しないことを意図している） |

### ドメインエンティティ → DB テーブル

すべてのエンティティと、ポートが必要とする保持先にテーブルが対応する。判別ユニオンは CHECK 制約で不正な組み合わせを禁じている。永続状態を持たない Conversion にはテーブルがない。

### ポート → ユースケース

定義した 30 のポートすべてに、少なくとも 1 つの呼び出し元がある。使われないメソッド（`ObjectStorage.createUploadUrl`）は検証 001 の対応で削除済み。

### ユースケース → テストケース

123 のユースケースすべてにテストケースのファイルがあり、名前が 1 対 1 で対応する。各表は正常系・異常系・境界値・エッジケースを含み、ユースケースのエラーケース表の項目を覆っている。

## アーキテクチャ適合性

| ルール | 確認結果 |
| --- | --- |
| ドメインモデルの独立性 | ドメイン層に DB / HTTP / フレームワークの型は現れない。時刻と ID は引数とポートで受け取る |
| ビジネスロジックの配置 | 判定と状態遷移はエンティティとドメインサービスにある。ユースケースは順序づけ・ポートの呼び出し・DTO への射影のみ |
| 集約境界 | 集約をまたぐ参照はすべて ID。DB でも集約をまたぐ外部キーを張らず、イベント駆動で後始末する |
| ポートによる抽象化 | 外部依存は 30 のポートに閉じ、すべてメソッドシグネチャとエラーケースを持つ |
| ドメイン間の非循環 | `Identity → Workspace → Storage → Conversion → Note → {Tag, Integration, Job, Usage}` の一方向。循環なし |

## 実装可能性

各ドメインについて、実装に必要な情報が揃っていることを確認した。

- 型・シグネチャ・制約・不変条件・エラーコードがすべて定義されている
- 非同期処理の境界（何がジョブになるか、冪等性をどう担保するか）が明示されている
- 結果整合を許す箇所（読み取りモデルの投影、使用量の集計、タグとファイルの付け替え）と、同期的に読む箇所（権限判定、共有リンクの解決、ノート詳細）が区別されている
- 非自明な判断は 9 件の ADR に記録され、各ドキュメントから参照されている
