# クロスフェーズ検証 004

対象: `spec/` 配下すべて

## 実施の概要

2026-07-30 に `spec/` 全体をレビューし、6 つの独立した検証で各指摘を反証にかけた。指摘は「**実行基盤の選択に依存しないもの**」と「**依存するもの**」に仕分け、前者のみを本改訂で修正した。

仕分けを設けた理由は、[idea.md](../../idea.md) の「前提」がプラットフォームを断定形で書いていたためである。実際にはこれは確定した決定ではなく一例であり、本改訂で「未確定の技術選択（候補）」に格下げした。基盤に依存する指摘を今の候補に合わせて直すと、候補が動いたときに直し直しになるうえ、依存の事実そのものが記録から消える。したがってそれらは修正せず、**確認された事実と根拠を本記録に残して保留**する。

どの ADR がどの前提に乗っているかは [adr/index.md](../../adr/index.md) の前提依存マップを正とする。

**この記録は 2 回の改訂を含む**。2026-07-30 の改訂（下の「今回修正した指摘」）と、その作業中に判明した課題 N-01〜N-05 を扱った 2026-07-31 の改訂（末尾の「2026-07-31 の改訂」）である。基盤依存として保留した H-01〜H-05 はどちらでも修正しておらず、前提の確定を待っている。

### 3. サニタイズを許可リスト方式に改めた

否認リスト方式では 2 つの経路が残っていた。1 つは `<iframe srcdoc>` によるスクリプト実行、もう 1 つはシャドウツリー内の `position: fixed` による自オリジン上のフィッシング画面の構築である。どちらも「危険なものを列挙して落とす」設計の構造的な帰結であり、列挙を足しても次の経路が出る。許可する要素・属性・CSS プロパティを列挙し、それ以外を落とす方式に反転させた。

### 4. presentation 層の文書を新設した

セッショントークンをどう運ぶか（Cookie の属性）と CSRF をどう防ぐかは、ドメインにもユースケースにも属さず、これまでどの文書にも書かれていなかった。ユースケースは「セッションを発行する」までを担い、それを安全に運ぶのは transport の責務である。HTTP ステータス対応・CSP・レート制限の要件も同じ層に属するため、まとめて [presentation/index.md](../../presentation/index.md) に置いた。

### 5. 公開ノートの 410 / 404

確定した方針は次のとおり。

| 状態 | 応答 |
| --- | --- |
| 非公開・限定公開に戻された（公開だったものを含む） | 404（見つかりません） |
| ゴミ箱在籍中で、かつ公開状態を保持している | 410（インデックス削除を促す） |
| 完全削除後 | 404（行が存在せず判定できないため） |

**404 に寄せた理由**。この設計は共有リンクの解決で「トークン不在・再発行済み・非公開化・削除を区別しない」という**存在を漏らさない**原則を既に置いている。410 は「その ID のノートが存在したが今は取得できない」ことを ID を知る相手に伝えるため、公開を取り下げた事実の秘匿と両立しない。410 が残るのは、所有者がまだ公開を取り下げていない状態（公開のままゴミ箱にある）に限る。

**既知の限界**。完全削除されたノートの URL には 410 を返せず、検索エンジンからの削除は 404 の応答とサイトマップからの除去に依存する。公開されたことのある `noteId` の削除記録を残せば 410 を返せるが、専用の表と保持期間・掃除の設計が要る割に得られるのはインデックス削除がわずかに早まることだけなので採らない。

## 前提の確定まで保留する指摘（基盤依存）

次の 5 件は**確認済みの実在する問題**である。直し方が実行基盤の選択に依存するため保留する。前提が確定したら再検討すること。

### H-01: 読み取りモデルの投影に並行実行のレースがある

**確認された事実**。`projectNoteChanges`（[usecases/note.md](../../usecases/note.md)）は `NoteRepository.findById` で現在値を読み直して読み取りモデルへ上書きする方式である。この形は重複配送と順序入れ替わりには耐えるが、**並行配送には耐えない**。読み取りと書き込みの間に他の消費者が割り込むとロストアップデートが起き、恒久的に古い投影が残る。アウトボックス経由の配送は少なくとも 1 回・順序保証なしであり（[ADR 009](../../adr/009-read-models.md)）、消費者の並行実行を禁じる仕組みは設計のどこにもない。

**影響は表示の遅れに留まらない**。`visibility` / `lifecycle` は公開検索とサイトマップの絞り込み条件そのものであるため（ADR 009 の「読み取りモデルにはアクセス制御に使える情報を含める」）、非公開化した本文の題と抜粋が公開検索結果に残りうる。

さらに `remove`（`note.purged` の購読）と実行中の `upsert` が競合すると、削除済みノートの行が復活する。`rebuildNoteProjection`（[usecases/note.md](../../usecases/note.md)）は既存ノートを走査して `upsert` するだけで孤児行を掃除しないため、手動の再構築でも消えない。

**なぜ保留か**。解決手段が基盤に依存する — キー単位の順序保証、単一ライター、条件付き書き込み、同期投影のいずれを採るかで設計が変わる。ADR 012 の前提（ステートレスな実行環境と順序保証なしのキュー）が動けば、選べる手段そのものが変わる。

### H-02: 読み取りモデルの行が保存先の行サイズ上限に接近する

**確認された事実**。`NoteHtml` の上限は 1 MB（[domains/note.md](../../domains/note.md)）。`note_search`（[database/index.md](../../database/index.md)）は生の平文と bigram 前処理済みのテキストを**同一行**に持つ。bigram 化は日本語で約 2.2 倍に膨らむため（[ADR 011](../../adr/011-bigram-search.md) の重なりビグラム）、平文が約 623 KB を超えると行の合計が 2 MB を超える。書き込みモデルの `notes` も `content_html` と `content_text` を同一行に持つため、同じ根で接近する。

**なぜ保留か**。行サイズの上限値そのものが保存先の選択に依存する。上限が実質存在しない保存先なら問題は消え、厳しい保存先なら本文を別表へ切り出すか `NoteHtml` の上限を下げることになる。どちらを採るかは上限値が決まってからでないと選べない。

### H-03: 1 回の実行あたりのクエリ数の予算が設計に存在しない

**確認された事実**。`emptyTrash`（[usecases/note.md](../../usecases/note.md)）は 500 件以下を同期削除し、`purgeNote` を 1 件ずつ呼ぶ。`purgeNote` は 1 件ごとに独立した Unit of Work を開くため、1 回の実行で 1,500〜2,000 クエリに達する。`deleteNotesForOwner` の既定 `batchSize` も 500 で、同じく 1 件ずつ UoW を開く。設計のどこにも「1 回の実行で発行してよいクエリ数」の上限が書かれていない。

**なぜ保留か**。予算の上限は実行環境に依存する。上限が存在する環境なら分割単位（500）を上限から逆算して決める必要があり、存在しない環境なら現状のままでよい。数を決められないまま「分割する」とだけ書いても実装の指針にならない。

### H-04: 退会・ワークスペース削除の後始末でイベントのコピーが増える

**確認された事実**。`deleteNotesForOwner` は 1 バッチごとに、受け取ったのと同じ `identity.user.deleted` / `workspace.deleted` を outbox へ再投入して継続する（[usecases/note.md](../../usecases/note.md) の「既知の課題」）。`deleteFilesByOwner`（[usecases/storage.md](../../usecases/storage.md)）も消し切れなかった場合に同じイベントを再登録する。両者に残作業がある間は、購読者 8 つを持つ同じイベントのコピーが増えていく。購読者はすべて冪等で、残作業が 0 になった系列から再投入をやめるため**正確性と停止性は保たれる**が、outbox とキューを水増しする。

**なぜ保留か**。本来は継続専用のイベント（購読者 1 件・カーソル付き）に分けるべきだが、継続の媒体として何が適切か（イベントの再投入か、遅延キューか、カーソルを持つ定期ワーカーか）は実行基盤の選択に依存する。

### H-05: 失敗回数の加算がロストアップデートを起こす

**確認された事実**。サインイン（`signInWithPassword`。[usecases/identity.md](../../usecases/identity.md)）と共有リンクのパスワード照合（`verifySharePassword`。[usecases/note.md](../../usecases/note.md)）の施錠は、どちらも `LoginAttemptStore.get` → `LoginThrottlePolicy.recordFailure` → `LoginAttemptStore.put` という**読んでから書く**形で実装される（[domains/identity.md](../../domains/identity.md) の「読み書きの分担」）。`login_attempts` テーブル（[database/index.md](../../database/index.md)）に楽観ロックの列はない。攻撃者が要求を並列化すると、同じ値を読んだ複数の要求が同じ値 + 1 を書き戻すため失敗回数がほとんど増えず、施錠を回避できる。

要件そのもの（失敗回数の加算は原子的でなければならない）は [presentation/index.md](../../presentation/index.md) に記録した。

**なぜ保留か**。実現手段が基盤に依存する。主データベースの条件付き更新で解くか、原子的な加算を持つ低遅延ストアに調整状態を移すかは、[adr/index.md](../../adr/index.md) の「未決の技術選択」にある**調整状態の置き場**が決まってからでないと選べない。同じ置き場の判断が、OAuth の一時状態とイベントの重複排除にもかかる。

## 改訂の過程で新たに判明した課題

本改訂（2026-07-30）の作業中に見つかったもので、いずれも**実行基盤の選択には依存しない**。当時は範囲外としたが、**翌 2026-07-31 の改訂ですべて修正した**。以下は指摘そのものの記録であり、対応と採らなかった案は下記「2026-07-31 の改訂」にある。

### N-01: 成功したジョブの利用者向け結果を載せる器がない

[ADR 006](../../adr/006-html-content-model.md) は「除去した内容を利用者に提示する」ことを決定に含めており、[ADR 013](../../adr/013-html-sanitization-policy.md) の許可リスト化でその対象は増えた（`removed` の `kind: "css"` など）。同期の経路（[usecases/note.md](../../usecases/note.md) の `updateNoteBody`）は出力 DTO に `removed` を持つため成立する。

しかし非同期の経路（`runConversion` / `runRegeneration` / `importExternalReferences`）は結果をジョブとして返す。`Job` が利用者向けの結果として持てるのは `JobFailure` の `reason` だけで、`detail` は [domains/job.md](../../domains/job.md) が「運用者向けの文字列。利用者には `reason` から導いた文言を出す」と明記している。しかも `failure` を持つのは `failed` のジョブだけで、**取り込みは失敗した参照があっても成功として終端する**。したがって「取り込めなかった参照の一覧」「装飾が失われた外部スタイルシート」「サニタイズで除去された CSS 宣言」を利用者に見せる供給元が存在しない。

[pages/index.md](../../pages/index.md) の P-11 には本改訂でこれらの表示要件を書いたが、供給元は未定義のままである。

### N-02: セッションの有効期間が定義されていない

`Session.create` は `ttlMs` を引数で受け取る（[domains/identity.md](../../domains/identity.md)）が、その値が `spec/` のどこにも書かれていない。[presentation/index.md](../../presentation/index.md) は Cookie の寿命を `Session.expiresAt` に一致させるとだけ定め、値は決めていない。

### N-03: レート制限のエラーコードが 3 種に分かれている

`LOGIN_THROTTLED` / `LOGIN_LOCKED` / `RATE_LIMITED` はいずれも同じ状態（要求の抑止）を表し、[presentation/index.md](../../presentation/index.md) でも同じステータスに対応づく。`signInWithPassword` は待機とロックを区別するが、`verifySharePassword`（[usecases/note.md](../../usecases/note.md)）は同じ `LoginThrottlePolicy` を使いながら両者を `RATE_LIMITED` に畳んでいる。揃えるかどうかの判断が要る。

### N-04: `AppConfig` の記述の置き場

`SharePass` / `ExportTicket` の署名鍵と `SecretCipher` の鍵の供給元は [database/index.md](../../database/index.md) の末尾に書かれているが、これは DB 設計の関心事ではない。署名と検証の責務は [presentation/index.md](../../presentation/index.md) にあるため、移設が筋である。

### N-05: 外部参照の取り込みの選択がスタイルシートを含むか

[usecases/note.md](../../usecases/note.md) の `updateNoteBody` は `importReferences` を任意の入力として持ち、P-12 に対応する選択肢がある。本改訂で外部スタイルシートの取り込み経路が変わったため、この選択がスタイルシートも対象にするのかを明記する必要がある。含めない場合、外部 CSS で装飾された HTML をエディタから保存すると装飾が失われる。

### N-01 の決め手は寿命ではなく帰属だった

当初は「`JobResult` 相当を `Job` に足す」か「Note 側に保持する」の二択として整理していたが、検討の結果**どちらも単独では成立しない**ことが分かった。

決定的だったのは [usecases/job.md](../../usecases/job.md) の明文規則である — 「ジョブは実行者本人にのみ見える。**ワークスペースのノートに対するジョブでも他のメンバーには表示しない**」。P-11 はノートを読める者すべてに開かれた画面なので、ジョブに載せた情報は他のメンバーに出ない。しかも経緯を知らない他メンバーにこそ必要な情報である。加えて `deleteJobsForRequester` は退会時に状態を問わずジョブを全削除するため、寿命は「保持期間以内、要求者の退会で即時失効」になる。**表示はノートに帰属するのに、ジョブは要求者に帰属していた**。

Note の集約に持たせる案も成立しなかった。`Note.updateBody` が受け取る `ProcessedHtml` は外部参照の一覧を含まず、集約に参照集合を維持させるとドメインが HTML を解釈することになる。`importExternalReferences` 自身も `updateBody` を通るため、「本文の書き換えをまたいで解決状態を引き継ぐ」規則がその唯一の書き込み経路を壊す。版からの復元では `NoteRevision` が本文しか持たないため集合と本文が両方向に食い違う。

### 採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| Note の集約に未解決参照・取り込みレポートを持たせる | 上記のとおり `ProcessedHtml` が参照を持たず、`updateBody` の引き継ぎ規則が唯一の書き込み経路を壊し、版の復元で不変条件が両方向に破れる。派生情報を本文と別に持つこと自体が ADR 006 の「正データはサニタイズ済み HTML 1 つ」と逆を向く |
| 取り込み結果もすべて `SucceededJob.notices` に載せる | 帰属が合わない（他メンバーに出ない・退会で消える）。`JobNotice` が Conversion / Storage / Note の 3 ドメインの語彙を吸収する |
| CSS 宣言の除去記録を永続化しない | [scenario/import.md](../../scenario/import.md) の IM-05 が「取り除いた内容は取り込み結果に示す」と要求し、マニュアルテストの受け入れ条件にもなっている。同期経路の `removed` では満たせない（利用者が書いた CSS ではなく第三者の CSS が落ちる話であるため） |
| `styleMode: "preserve"` と本文の齟齬から装飾喪失を推定する | ADR 007 の `hasDecoration` は `style` 属性の多用も `preserve` の根拠に数えるため `<style>` の有無で判定できない。[scenario/editing.md](../../scenario/editing.md) が正常と認めた操作を誤検出し、2 件のうち 1 件だけ失敗した場合は検出できず、推奨している回復手順（ED-11）を踏むと条件が崩れて案内が消える |
| 未解決の参照を本文から再計算するだけで済ませる | `HtmlProcessor.extractExternalReferences` は「外部」参照だけを返す契約ではない（`collectOrphanMedia` がサービス内の URL を探すのに使っている）。加えて、取得に失敗した参照・未試行の参照・予算超過で打ち切られた参照は本文上で同じ姿になり区別できない |
| N-05 でスタイルシートを選択の対象外にして常に取り込む | 利用者の同意なく外部へ要求が出る、`maxCount: 200` の予算を選択で下げられない、P-12 / ED-03 / IM-05 の説明を全部書き換えることになる。既定を `true` にすれば、問題視した非対称（ファイルなら装飾が残りエディタでは消える）は消える |
| N-03 で `RATE_LIMITED` 1 本に統一する | 待機とロックは示す次の一手が違う（後者はパスワード再設定の案内を伴う）。1 本に畳んで待機秒数で区別すると、画面が `LoginThrottlePolicy` の待機上限 60 秒を暗黙に写すことになり、[presentation/index.md](../../presentation/index.md) が避けようとした「同じ決定が複数の文書に散る」形になる。またステータス表の側の整理は既に 1 行に畳まれて完了していた |
| N-04 で `SecretCipher` の鍵を domains に置く | 鍵の供給元はアダプターの関心事であり、ポート契約ではない。domains に書くと鍵管理基盤を移すたびにドメイン文書を書き換えることになる |
| N-04 で `AppConfig` の専用文書を作る | 項目が少なく、「値の正典」をもう 1 か所増やすことになる。既に正典を宣言している [presentation/index.md](../../presentation/index.md) に節を置いた |

### 併せて直した既存の穴

N-01〜N-05 の検討中に見つかったもので、いずれも指摘そのものとは独立に実在していた。

| No. | 内容 | 対応 |
| --- | --- | --- |
| 1 | 参照取り込みジョブの登録に重複防止がなく、自動保存の間隔ごとに 1 本ずつ増えて互いに本文を書き換え版競合していた | 登録の 4 経路（`updateNoteBody` / `runConversion` / `runRegeneration` / `restoreNoteRevision`）に未終端ジョブの検査を入れた。`ensureNoDuplicate` は使わない（例外を投げる振る舞いであり、保存自体は成功させたいため）。`domains/job.md` に「誰が呼び、誰が呼ばないか」の規則を書いた |
| 2 | 登録条件が取り込み済みの内部 URL も数えていたため、取り込むものがなくても保存のたびにジョブが登録されていた | 条件を「抽出結果のうち内部を指さないもの」に改めた |
| 3 | 「サービス内のストレージを指す URL か」の判定が `ExternalFetchPolicy.ensureFetchable` の複合条件と `importExternalReferences` の `skipped` 判定に埋まっていた | `StorageUrlPolicy.isInternal` として切り出した（`ensureFetchable` は `DnsResolver` に依存するため読み取り経路で呼べない） |
| 4 | `applyTextNodeEdits` が `HtmlProcessor.process` を通していないのに `Note.updateBody` は `ProcessedHtml` を要求していた。加えて `<style>` の中身はテキストノードなのでサニタイズを迂回できた | `process` を通す手順を明記し、`editTextNodes` の契約に「`<style>` の子テキストノードには経路を割り当てない」を加えた |
| 5 | `restoreNoteRevision` も `ProcessedHtml` の供給元が未記述で、復元後の参照取り込みも登録されていなかった | どちらも手順に加えた。取り込みは版を作らないため、直近の版は取り込み前の本文であり、復元は参照の状態を巻き戻す |
| 6 | batch 親の失敗の内訳を `detail` に書く記述が、`detail` は運用者向けという原則と食い違っていた | `childSummary` に寄せて削除した（子の行から数え直すため再試行後もずれない） |
| 7 | 予算超過で打ち切られたリソース参照の扱いが未記述だった | 再試行の主体を持たないことを明記し、`ReferenceAttempt` の `notAttempted` として記録するようにした |

### 横断

[presentation/index.md](../../presentation/index.md) の「決めること → 正典」の役割表に**値（有効期間・しきい値・上限・秘密）の正典**の行を足した。N-02（有効期間）・N-03（しきい値）・N-04（秘密）は同じ 1 つの穴の別の顔だったためである。あわせて「値の正典はその値が意味を持つ層に置く」という原則を書き、この文書がすべての値を集める台帳にならないことを明示した。
