# クロスフェーズ検証 001

対象: `spec/scenario/`, `spec/pages/`, `spec/domains/`, `spec/usecases/`, `spec/database/`, `spec/testcases/`

## トレーサビリティで見つかった不整合

### 1. ノートの移動で保管ファイルの所有者が移らない

`StoredFile` は `changeOwner` を持ち、`storage.fileOwnerChanged` を発行して Usage の付け替えを促す設計になっている。しかし、このメソッドを呼ぶユースケースが存在しない。`moveNote` はノートの所有者だけを変え、元ファイル・メディア・取り込んだ参照リソースの所有者はそのまま残る。

結果として、個人のノートをワークスペースへ移しても保存容量は個人から減らず、ワークスペースにも加算されない。`note.moved` を購読して Usage のノート件数だけを付け替えている `applyStorageDelta` とも噛み合わない。

**対応**: `usecases/storage.md` に `relocateFilesForNote` を追加し、`note.moved` の購読で保管ファイルの所有者を移す。

### 2. ジョブを実行系へ送る経路が 2 通りある

`retryJob` は `JobDispatcher.dispatch` を直接呼ぶが、ジョブの新規登録（`storeUpload`、`requestBulkExport`、`requestBackup` など）は `job.enqueued` イベントの発行だけで、`JobDispatcher` を呼んでいない。実装者は「登録時はイベント経由、再試行時は直接呼び出し」という 2 系統を書くことになり、送信漏れや二重送信の原因になる。

**対応**: 送信経路を `job.enqueued` の購読に一本化する。`retryJob` も `Job.retry` が発行する `job.enqueued` に委ね、`JobDispatcher` は購読側のハンドラーだけが呼ぶ。

### 3. `exportNote` が `NoteExportComposer` を呼んでいない

`domains/note.md` に `NoteExportComposer.composeSelfContainedHtml` を定義したが、`usecases/note.md` の `exportNote` は「スタイルと画像を埋め込んだ 1 ファイルを組み立てて」とだけ書き、どのポートを使うかを示していない。

**対応**: `exportNote` の処理フローでポート名を明示する。

### 4. 使われていないポートのメソッドがある

- `ObjectStorage.createUploadUrl` — アップロードはすべてサーバー側で `put` する設計になっており、署名付きアップロード URL を使うユースケースがない
- `ExternalConnection.touch` — 連携の `lastUsedAt` を更新するメソッドだが、呼ぶユースケースがない。`listConnections` は `lastUsedAt` を返すのに、永久に `null` のままになる

**対応**: `createUploadUrl` はポートから削除する。`touch` は `CredentialResolver.resolve` が資格情報を解決したときに併せて更新する旨を明記する。
