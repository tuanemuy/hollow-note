# テストケース: relocateFilesForNote

| 前提条件 | 操作 | 期待結果 | 実装ステータス |
|---|---|---|---|
| 元ファイルとメディア 2 件を持つノートが移動した | 実行する | 3 件の所有者が移動先になり、`storage.fileOwnerChanged` が 3 件発行される | |
| 対象ファイルの列挙 | 解決方法を確認する | `StoredFileRepository.listByNote(noteId)` で引く（`note.moved` の `noteId` から解決し、本文の逆引きはしない） | |
| 取り込んだ外部参照（`purpose: "reference"`）も持つノートが移動した | 実行する | `source` / `media` / `reference` がまとめて付け替えられる | |
| そのノート由来の artifact（PDF 生成物）がある | 実行する | 付け替えの対象にならず、`storage.fileOwnerChanged` も発行されない（`listByNote` は `artifact` も返すため、呼び出し側が `purpose` で `source` / `media` / `reference` に絞る） | |
| 同上 | 除外の理由を確認する | 生成物は容量クォータに算入されないため付け替える意味がなく、付け替えると `applyStorageDelta` が**加算されていない容量を旧主体から減算する**。保有期間の管理も所属ノートではなく `expiresAt` で行い、`collectExpiredArtifacts` が回収する | |
| 同上 | 実行後に artifact の所有者を確認する | 生成時の帰属のまま動かない（サインイン済みの要求では要求者の個人 subject、匿名の PDF 書き出しではノートの所有文脈） | |
| 所有者のアイコン（`purpose: "avatar"`）がある | 実行する | ノートに属さない（`noteId: null`）ため対象にならない | |
| 実行後 | 使用量を確認する | 移動元の保存容量が減り、移動先が増えている | |
| 移動先の保存容量が既に上限を超えている | 実行する | 付け替えは成功する（クォータ強制は取り込み時のみで、移動では `ensureUploadAllowed` を呼ばない） | |
| 既に所有者が移動先と一致している | 実行する | 何もせず、イベントも発行されない | |
| 同じイベントを 2 回受け取る | 2 回実行する | 2 回目は何も起きず、容量が二重に移らない | |
| ノートが既に削除済み | 実行する | `listByNote` が 0 件を返し、何もせず成功する | |
| 一部のファイルが不在 | 実行する | 無視して継続する | |
| 版が競合する | 実行する | 読み直して再適用する | |
| ファイルを 1 件も持たないノート | 実行する | `relocatedCount: 0` が返る | |
