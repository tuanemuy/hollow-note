# テストケース: deleteFilesByOwner

| 前提条件 | 操作 | 期待結果 | 実装ステータス |
|---|---|---|---|
| 利用者が 120 件のファイルを持ち `batchSize: 50` | 実行する | 50 件を削除して同じscopeのcontinuation taskを1件だけ積み、次のAlarm turnで続ける | |
| 対象が `batchSize`（既定 100 件）ちょうど | 実行する | 全件が削除され、継続要求は積まれない（境界値） | |
| 継続が要る | 積まれたイベントを確認する | `deletionOperationId`を保持した購読者1件の`storage.ownerDeleteContinued`だけを積み、受け取った削除eventは再投入しない | |
| 継続要求を受け取る | 処理する | 残っているものを先頭から `batchSize` 件読んで続きを削除する（カーソルは持たない） | |
| 対象が残っているのにそのバッチで 1 件も削除できなかった | 実行する | 継続要求を積まず、失敗として返る（キューの再試行と DLQ に委ねる） | |
| 継続要求が重複配送され 2 系列が並走する | 実行する | 両系列とも「残っているものを読んで消す」だけなので結果は変わらず、対象が 0 件になった系列から順に継続をやめる | |
| 1 バッチを処理する | 件数に比例した往復を要求しないことを確認する | 列挙は 1 回だけ。削除できたファイル 1 件につき `storage.fileDeleted` が 1 件。どちらも `batchSize` の件数に比例した追加の往復を要求しない（バックエンドが発行する文の数はここでは約束しない — [ADR 056](../../adr/056-performance-budget-placement.md)） | |
| `deleteNotesForOwner` の継続 | 形を比べる | 同一である（1 バッチ処理して残りがあれば専用の継続要求を 1 件積む） | |
| ワークスペースのファイルがある | ワークスペースを対象に実行する | そのワークスペースのファイルだけが削除される | |
| 対象が 0 件 | 実行する | `deletedCount: 0` が返る | |
| 1 件の削除が失敗する | 実行する | 記録して継続する | |
| 同じ要求を 2 回実行する | 2 回実行する | 結果が変わらない | |
| アイコンや生成物も所有している | 実行する | 用途によらずすべて削除される | |
| 実行後 | 発行されたイベントを確認する | 1 件ごとに `storage.fileDeleted` が発行される（所有者単位の一括削除メソッドは持たず、`listByOwner` + `deleteFiles` の反復で行い、Usage の減算と実体の回収を 1 件ずつつなぐ） | |
