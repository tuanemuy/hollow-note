# テストケース: emptyTrash

| 前提条件 | 操作 | 期待結果 | 実装ステータス |
|---|---|---|---|
| ゴミ箱に 10 件ある | 空にする | 10 件が完全削除され、`mode: "purged"`、`purgedCount: 10`、`jobIds: []` が返る | |
| ゴミ箱に 10 件、有効なノートが 30 件ある | 空にする | 件数は `countByOwner(owner, "trashed")`、一覧は `listByOwner(owner, "trashed", pagination)` で引くため、有効なノートは 1 件も削除されない | |
| ゴミ箱が空 | 空にする | `mode: "purged"`、`purgedCount: 0`、`jobIds: []` が返る | |
| ゴミ箱に 50 件ある | 空にする | ジョブを登録せず同期削除され、`mode: "purged"`、`purgedCount: 50`、`jobIds: []` が返る（HTTP応答時間とevent fan-outの境界値） | |
| ゴミ箱に 51 件ある | 空にする | 同期削除は行わず、一括削除ジョブ（`bulkDelete`）が 1 件登録され、`mode: "scheduled"`、`purgedCount: 51`（削除を予約した対象件数）、`jobIds` に親ジョブの ID が 1 件返る（境界値） | |
| ゴミ箱に 501 件ある | 空にする | 500 件ごとに分割した一括削除ジョブが 2 件登録され、`jobIds` が 2 件返る（分割単位 500 は子ジョブが別々の実行で処理されるため 1 実行あたりの予算に掛からない。同期のしきい値 50 とは別の制約から来る） | |
| `mode: "scheduled"` が返った | 返った直後のゴミ箱を確認する | まだ 1 件も消えていない（`purgedCount` は予約した対象件数であり、削除し終えた件数ではない） | |
| `mode` ごとの応答 | 画面の文言を確認する | `"purged"` は「N 件を完全に削除しました」、`"scheduled"` は「N 件の削除を開始しました（処理履歴で進捗を確認できます）」と出し分け、後者は `jobIds` を処理履歴への導線に使う（`mode` を持たずに件数だけを返すと後者が虚偽の完了通知になる） | |
| ゴミ箱に 1200 件ある | 空にする | 一括削除ジョブが 3 件登録され（500 / 500 / 200）、`mode: "scheduled"`、`purgedCount: 1200`、`jobIds` が 3 件返る | |
| ゴミ箱に 1200 件ある | 分割した各ジョブの `scope` を確認する | どの分割も入力source ScopeKeyを親子Jobへ使う | |
| ワークスペースの viewer | 空にする | `BusinessRuleError(InsufficientRole)` が投げられる | |
| ワークスペースの editor | 空にする | 成功する | |
| 個人とワークスペースの両方にゴミ箱がある | 個人の文脈で空にする | ワークスペースのゴミ箱は残る | |
| 一部の削除が失敗する | 空にする | 他の削除は継続し、失敗件数が分かる | |
| 同期削除の経路 | `purgeNote` の呼び出しを確認する | 手順の複製ではなくユースケースの呼び出しで、`expectedVersion` には `listByOwner` で引いた各ノートのその時点の版を渡す。`emptyTrash` 自身は `UnitOfWorkProvider.run` を開かず、`purgeNote` が 1 件ごとに確定する | |
| 列挙後・削除前に 1 件が `restoreNote` でゴミ箱から戻された | 空にする | そのノートは版の競合（`ConflictError`）で飛ばされ、`purgedCount` に数えられない。読み直して再適用はしない（戻したばかりのノートを消さないため） | |
| 列挙後・削除前に 1 件が別の経路で完全削除された | 空にする | `NOTE_NOT_TRASHED` / 不在として飛ばして続け、`purgedCount` に数えない | |
| ゴミ箱に 50 件ある | 同期削除の列挙を確認する | `listByOwner` の 1 ページ（`limit` の上限は 100）で収まる。同期のしきい値 50 はページングの上限より小さい | |
