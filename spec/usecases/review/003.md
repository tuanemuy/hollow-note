# ユースケースレビュー 003

対象: `spec/usecases/` 配下すべて

## 1. ジョブが自身の実行に必要な入力を保持できない

`Job` エンティティは `kind` と `target` しか持たないが、ワーカーから呼ばれるユースケースは対象以外の入力を必要としている。

| ユースケース | 必要な入力 | 現在の出所 |
| --- | --- | --- |
| `runRegeneration` | `source`（元ファイル / Drive）、`instruction`、`modelOverride` | 未定義 |
| `runBulkNoteOperationItem` | `operation`（タグ名・公開ステータス・移動先など） | 未定義 |
| `runNoteExport` / `runBulkExport` | `format` | 未定義 |
| `runConversion` | アップロード時に指定された公開ステータス | 未定義 |

いずれも「ジョブを登録したときの指定を、実行時に読み出す」必要があるが、保持する場所がない。実装者はジョブ以外の場所に状態を置くか、引数をどこからか調達することになる。

**対応**: `Job` に `kind` で判別される `payload` を持たせ、登録時の指定を保存する。

## 2. アップロード時の公開ステータスの適用先が定まっていない

レビュー 002 の対応で `storeUpload` に「指定を変換ジョブに引き継ぐ」と書いたが、引き継ぎ先が上記のとおり存在しない。`runConversion` の処理フローにも公開ステータスを適用する手順がない。

**対応**: `payload` に公開ステータスを載せ、`runConversion` の成功時に適用する手順を加える。

## 3. `runRegeneration` を登録するユースケースがない

`runRegeneration` はワーカー側の本体だが、これを登録する入口（IM-06 の「LLM で作り直す」、IN-07 の「元ファイルから再生成」）に対応するユースケースがない。追加指示の長さの検査、連携の有無の確認、多重実行の抑止、実行前の版の保持といった事前処理はここで行う必要がある。

**対応**: `usecases/conversion.md` に `requestRegeneration` を追加する。
