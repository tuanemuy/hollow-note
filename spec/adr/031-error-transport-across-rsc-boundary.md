# 031. RSC ストリーミング境界を越えるエラーは構造で運び、秘匿は 1 か所に集める

## コンテキスト

エラーはそれぞれ `kind` タグ付きの直列化形を持ち、presentation はクラスの列挙ではなく構造でこれを扱う。ところが実装では 2 つの経路でタグが失われた。

1. 開発サーバーは SSR / RSC / server function の並行するモジュールグラフを持ち、同じエラークラスが複製される。`instanceof` による判定は別グラフで生成されたインスタンスに false を返し、メッセージだけを残す組み込みの直列化へ落ちる。結果として**全エラーが「不明」に縮退した**
2. RSC のフラグメント内で throw したエラーはストリーミングのエラーチャネルを通り、素の `Error` として再構築される。`kind` が判別できないだけでなく、server function 境界で行っている秘匿（構造的な直列化と詳細の伏せ字化）を迂回して、生のメッセージがクライアントへ届きうる

## 決定

- 直列化形の判定は `instanceof` ではなく構造で行う（`Error` であり、かつ直列化形が `kind` タグ付きの構造であること）。「presentation は構造的に直列化する」という規律の射程を、自分たちのクラスにも広げる
- ストリーミングフラグメントの生成は専用のヘルパー経由を規約とし、そこが秘匿の境界とサーバーログを一手に担う。フラグメント生成を直接呼ぶ経路は作らない
- 存在判定（見つからない）はフラグメント自身の描画結果として解決する。フラグメントが該当のエラーを捕捉して「見つかりません」の表示を返し、それ以外の失敗だけを throw してルートのエラー境界へ流す

## 検討した代替案

### モジュールグラフを統一してクラスの同一性を保つ

判定を変えずに済む。しかしクラスの同一性はビルド構成（分割数、開発 / 本番の差、HMR）に依存し、壊れても型検査には現れない。構造判定はビルド構成から独立している。

### フラグメント内のエラーをルートのエラー表示側で判別する

エラー処理を境界 1 か所に集められる。しかしストリーミングのエラーチャネルはタグを運ばないため、判別の材料が届かない。

### フラグメントごとに秘匿とログを書く

自由度は高いが、経路ごとに秘匿の有無が変わり、新しいフラグメントを足すたびに漏れる。

## 影響

- `kind` タグがビルド構成に依存せず届く
- 「見つかりません」の表示が、ストリーミングでもフルリロードでも同一になる
- 直列化形と同じ形をたまたま持つ `Error` を誤検出しうる（`kind` の閉集合検査で実質的に排除する）
- フラグメント内の捕捉は「エラーは境界でだけ捕まえる」原則の限定的な例外になる。根拠はストリーミングがタグを運べないことに限る
- ヘルパー経由という規約は lint では強制されず、レビューで守る
