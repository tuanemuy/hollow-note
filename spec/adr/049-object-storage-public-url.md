# 049. 配信 URL の組み立ては `ObjectStorage` に閉じ、公開配信は用途で絞る

## ステータス

承認済み

## コンテキスト

保管したオブジェクトの URL を呼び出し側が組み立てると、application が配信ルートの形（`/storage/...`）を知ることになり、公開ドメインを持つオブジェクトストレージへ移る配備でユースケースまで波及する。既にある期限つきダウンロード URL は用途が違う（短命・ダウンロード用）ので、プロフィールに埋め込むような長命な公開 URL には使えない。

もう 1 つ、オブジェクトの鍵空間は 1 つで、公開してよい用途とそうでない用途（取り込んだ原本、生成物、参照ファイル）が同居する。配信側が用途の線を持たないと、非公開の用途を保管した瞬間に「鍵を知る者への無認可配信」になる。

## 前提

鍵にファイル ID が入り、内容が不変であること（差し替えは必ず別の鍵になる）。鍵の形を組み立てているのが値オブジェクトであること。

## 決定

- **公開 URL の組み立てをポートに持たせ**、呼び出し側はその戻り値を返すだけにする。配備ごとの形（アプリ相対パスか公開ドメインの URL か）はアダプターに閉じる。期限つき URL と公開 URL は別のメソッドとして型で分ける
- 鍵の形を知っているのは鍵の値オブジェクトなので、**鍵から用途を読み戻す派生をその値オブジェクトに置き**、配信側は公開してよい用途以外を 404 に倒す。形式違反も 400 ではなく 404 にする（形の違いを区別すると鍵空間の探索の手掛かりになる）
- キャッシュは **`private`** にする。鍵が不変なので共有キャッシュに載せる利得は再取得の削減だけだが、「削除したら消える」という利用者への約束が前段の共有キャッシュで破れる。ブラウザーキャッシュだけでも実効は変わらない
- 配信応答には `nosniff` とサンドボックス CSP、`Content-Disposition` を付ける。ファイル名は鍵の末尾から作るが、ヘッダーに置く前に安全な文字だけに落とす

## 検討した代替案

### 呼び出し側が配信ルートのパスを組む

実装が最短。しかし配備ごとの URL の形が application に漏れ、ストレージを差し替えるとユースケースが動く。

### 期限つきダウンロード URL を流用する

新しいメソッドが要らない。しかし短命なので、プロフィールに埋め込むような長命な参照には使えない。用途が型で分かれていないと、誤用が静かに壊れる。

### 鍵をエスケープして単一セグメントの動的パラメーターで受ける

ルートの形が単純になる。しかし `%2F` を含むパスは前段のプロキシの正規化で壊れる。複数セグメントのまま受けるほうが安定する。

### 配信ルート側で鍵のセグメントを切り出して用途を判定する

値オブジェクトに手を入れずに済む。しかし鍵の形の知識が 2 か所に増え、組み立て側を変えたときに配信側が置き去りになる。

## 影響

- 公開ドメインを持つストレージへ移る配備では、この配信経路ごと不要になる
- 「公開なのは特定の用途だけ」がコードで守られ、非公開の用途を保管しても配信面が広がらない。将来それらを配信する必要が出たら、同じ経路に所有者検査を足す入口として使える
- 前段に CDN を置く配備では、公開オブジェクトの取得がオリジンに当たり続ける（CDN を入れる判断とストレージを差し替える判断は同じ場面で行われる）
- 鍵の組み立て形を変えると、配信側の用途判定も一緒に直す必要がある
