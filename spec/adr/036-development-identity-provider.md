# 036. 開発用 IdP は代替プロバイダー実装として併設し、選択規則を composition root に閉じる

## ステータス

承認済み

## コンテキスト

外部 IdP との OAuth は「実装本体が外部プロトコル結合」の典型で、動かすには配備済みの資格情報が要る。手元と CI に資格情報が無い状態では、認可往復の分岐（同意・キャンセル・state 不一致・期限切れ・通信失敗）が一度も動かないまま配備される。

選べる形は 3 つある。実プロバイダー実装だけを置いて手動検証に資格情報を必須とする / fake だけを置く / 実プロバイダー実装を本体としつつローカル用の別プロバイダー実装を併設する。fake だけを置くと本物が書かれないまま残り、実装だけを置くと誰も認可往復を動かせない。

## 前提

in-memory 永続化を fake ではなく正規のバックエンドとして扱う立場（[ADR 024](./024-in-memory-adapter-as-first-class-backend.md)）。プロバイダーの選択が composition root に閉じられること。開発用の経路を有効にしてよい配備を判定できること（[ADR 037](./037-node-env-allowlist.md)）。

## 決定

- **開発用 IdP を実プロバイダーの縮退版ではなく、対等なアダプター 2 本目として持つ。** in-memory バックエンドと同じ扱いで、ポート契約を満たす別プロバイダーの実装とする
- **選択規則は composition root の env スキーマ 1 箇所に閉じる。** 開発用の指定があれば開発用 IdP、無ければ実プロバイダーの資格情報が揃っているかを見る、どちらでもなければ**起動に失敗する**。黙って fake に落ちない。資格情報は SSR メタデータを運ぶ設定の器に載せず、composition root がランタイムへ供給する
- **開発用 IdP は同意画面をアプリ内のルートとして持つ。** 認可エンドポイントから直接コールバックへ返す自動承認にすると、「同意する」「キャンセルする」という利用者の分岐が一度も動かない。ルートは有効化フラグが偽なら 404 を返し、判定は composition root が供給するフラグ 1 つを読むだけにする（ルート側で環境変数を直読みしない）。redirect 先は自オリジンのパスに限る
- **開発用 IdP の認可コードは署名しない。** 同意画面（アプリ）とアダプター（コア）は同一プロセスでも別のモジュールグラフに載るので、モジュールスコープの鍵は書き手と読み手で食い違う。代わりに厳格なスキーマ検査と **PKCE 検証**（封筒に code challenge を載せ、交換時に verifier と突き合わせる）を置く。「リダイレクトから盗んだコードだけでは交換できない」という本番と同じ性質が開発時にも成立する
- **PKCE の challenge 導出はこのポートが持つ。** プロトコルが規定する表現なので、保存用ハッシュを担うポートを拡張せず、プロトコルを知っているアダプター側に置く
- **適合スイートは「資格情報の要否」ではなく「ハーネスが認可コードを発行できるか」で割る。** 外部と通信しない部分（認可要求の組み立て、challenge 導出）は全アダプターで常に実行し、コード交換は認可コードを発行できるハーネスを持つときだけ実行する。実行しない登録も残し、スイート名に理由を含める

## 検討した代替案

### fake だけを置く

最短で全経路が動く。しかし外部プロトコル結合の実装が書かれないまま残り、「仮実装を残さない」という完了条件をポート単位で破る。

### 実プロバイダー実装だけを置く

余計なコードが増えない。しかし資格情報を持たない開発機と CI では認可往復が一度も動かず、同意のキャンセルのような分岐は永久に未検証になる。

### 自動承認の開発用アダプター

同意画面のルートを持たずに済む。しかし「同意する / キャンセルする」という往復の要が消え、コールバック側の分岐も動かせない。

### 開発用の認可コードに署名を付ける

改竄耐性が上がる。しかし鍵の受け渡し経路をモジュールグラフ間に作る必要があり、PKCE で得られる保証と重複する。

### 適合スイートを資格情報の有無で gate する

判定が単純。しかし資格情報を入れた瞬間に、実際には何も検証していないケースが「アサーション 0 本の PASS」に化ける。実プロバイダーの認可コードはブラウザーの同意画面を経ないと発行されないので、資格情報は交換系の実行可能性を意味しない。

## 影響

- 資格情報の無い環境でも認可往復の全状態をブラウザーで検証でき、実プロバイダーの実装は仮実装なしで書ける
- アダプターが 2 本になり、選択の分岐が composition root に増える。ビルド無しでソースを直接解決する構成では tree-shaking で開発用実装を落とせないので、有効化のガードは実行時に置く（[ADR 037](./037-node-env-allowlist.md)）
- 開発用の同意画面は任意のメールアドレスを検証済みとして通し、コードも署名されていない。したがって**これが有効な配備は全アカウントが乗っ取り可能**であり、有効化の判定を安全側へ倒すことがこの決定の前提になる
- 実プロバイダーの交換系は、資格情報があっても既定では実行されない（同意画面を経ないとコードが出ない）。実行するにはコード発行手段を注入するハーネスが要る
