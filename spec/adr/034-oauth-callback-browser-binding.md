# 034. OAuth の認可往復は転送境界で開始したブラウザーに束縛する

## ステータス

承認済み

## コンテキスト

認可の開始で発行する `state` はサーバー側の 1 行としか結び付いておらず、**どのブラウザーが開始したか**を持たない。

攻撃者は自分のブラウザーで「外部アカウントで続ける」を押し、自分のアカウントで同意まで進めてから最終ナビゲーションだけを止め、`https://<app>/auth/callback/<provider>?state=S&code=C` を手元に取れる。それを被害者に踏ませると、コールバック画面が自オリジンから消費要求を出すので、`Origin` も `Sec-Fetch-Site` も CSRF トークンもすべて正しく揃い、被害者のブラウザーに**攻撃者のアカウントのセッションが焼かれる**。以降、被害者が書いたノートは攻撃者のアカウントに入る。

[ADR 029](./029-verification-session-binding.md) がメール確認について書いた「通常の CSRF 対策が原理的に効かない」条件がそのまま当てはまる。state ストアの単回消費が防ぐのは、他人の正規フローに別の code を差し込む向きだけで、攻撃者が自分の完成済みフローを被害者のブラウザーへ持ち込む向きは防げない。PKCE も同様で、verifier はサーバーが持っているので攻撃者の側はむしろ正しく揃っている。

## 前提

認可の開始が自オリジンの POST であり、そこで Cookie を焼けること。`SameSite=Lax` により、攻撃者が自分の Cookie を被害者のブラウザーへ持ち込む経路が無いこと。コールバックの消費が単回であること（[ADR 035](./035-oauth-callback-single-route.md)）。

## 決定

[ADR 029](./029-verification-session-binding.md) と同じ分担で**転送境界に閉じる**。フロー状態にもユースケースにもブラウザー束縛の概念を入れない。

1. 開始の応答が束縛 Cookie を焼く。値は `state` そのものではなく **SHA-256**、属性はセッション Cookie に揃えて `HttpOnly` / `SameSite=Lax` / `Path=/`（開発時の平文 http を除き `Secure`）、寿命は `state` 行と同じ
2. 消費の入口は、**ユースケースを呼ぶ前に**「要求本文の `state` の SHA-256 == Cookie」を照合する。不一致・Cookie 不在はどちらも「state 不正」に畳む
3. 破棄は 2 点に置く — 照合を通った直後と、消費要求が起きない往復（プロバイダーが拒否を返した / 引数が欠けた）。後者も**自分が焼いた Cookie だと確認できたときだけ**捨てる
4. 照合に**失敗した**ときは捨てない
5. 生成・照合は転送境界の純関数として置き、Cookie の運搬と分ける

照合を消費より先に置くのは、通っていない `state` を消費させないため。攻撃者の URL を踏んだだけで消費が走ると、正規のブラウザーの側でフローが壊れる。

破棄を無条件にしないのは、`<img src="…/auth/callback/…?error=x">` を踏ませるだけで被害者の進行中フローの Cookie を落とせてしまうため。同じ理由で、照合に失敗した Cookie は「別のブラウザー（＝正規の利用者）が進行中のフロー」のものなので触らない。

Cookie に `state` そのものではなくハッシュを載せるのは、`Path=/` の Cookie が同一オリジンの全要求に相乗りするため。単回消費の資格情報そのものを常時運ばせない。照合に必要なのは同値性だけなので、束縛の強さは変わらない。

連携（既存アカウントへのログイン方法追加）の往復にも同じ束縛を掛ける。こちらは攻撃者のセッションが焼かれる向きは元々成立しないが、被害者に他人の外部アカウントを紐づけさせる向きの `state` すり替えを一段防げる。

## 検討した代替案

### フロー状態の行にブラウザー識別子を持たせる

ユースケースの中で束縛を検査できる。しかしドメインのポートと全バックエンドに transport 由来の概念が入り、束縛の実現手段（Cookie）を差し替えられなくなる。守りたい性質は「攻撃者が被害者のブラウザーへ持ち込めない値がある」ことだけで、それは Cookie の属性が与える。

### CSRF トークン・`Origin` 検証を強める

消費要求を出しているのは自オリジンのページ自身なので、トークンも `Origin` も正しく揃う。攻撃者が偽装しているのは要求ではなく「どのフローを完了させるか」なので、原理的に効かない。

### 照合をユースケースの中に置く

層の分担としては素直に見えるが、照合の前に `state` の取り出し（単回消費）が走るため、踏ませるだけで正規のフローを壊せる。

## 影響

- 「コールバック URL を踏ませるだけでは被害者の認証状態が変わらない」が成立する。攻撃者が被害者のブラウザーへ持ち込めないのは Cookie だけ、という [ADR 029](./029-verification-session-binding.md) と同じ根拠に乗る
- **縮退（受容）**: 束縛 Cookie は 1 本なので、同一ブラウザーで 2 つの認可フローを並行して開始すると先に始めた方が完了できない。「もう一度やり直してください」に倒れるだけで、認証状態は壊れない
- **縮退（受容）**: 別端末で認可を完了する経路（PC で開始してスマートフォンで同意）は成立しない。認可の同意は開始したブラウザーの中で完結するのが通常の導線なので、メール確認の別端末フローと違い実質的な縮退にはならない
- 中断された往復の Cookie は寿命（`state` 行と同じ）まで残る。次の開始が上書きし、期限で消える
- 束縛の成否は「Cookie を焼く行」と「照合の行」の**順序**そのものなので、純関数の単体テストでは守れない。回帰の検知は、実際にエクスポートされている入口を 1 リクエスト分の実行文脈で呼び、Cookie を実物の要求ヘッダー / 応答ヘッダーとして観測するテストが担う
