# 034. OAuth の認可往復は開始したブラウザーに束縛する

## ステータス

承認済み

## コンテキスト

認可の開始で発行する `state` はサーバー側の 1 行としか結び付いておらず、**どのブラウザーが開始したか**を持たない。

攻撃者は自分のブラウザーで「外部アカウントで続ける」を押し、自分のアカウントで同意まで進めてから最終ナビゲーションだけを止め、`https://<app>/auth/callback/<provider>?state=S&code=C` を手元に取れる。それを被害者に踏ませると、コールバック画面が自オリジンから消費要求を出すので、`Origin` も `Sec-Fetch-Site` も CSRF トークンもすべて正しく揃い、被害者のブラウザーに**攻撃者のアカウントのセッションが焼かれる**。以降、被害者が書いたノートは攻撃者のアカウントに入る。

[ADR 029](./029-verification-session-binding.md) がメール確認について書いた「通常の CSRF 対策が原理的に効かない」条件がそのまま当てはまる。state ストアの単回消費が防ぐのは、他人の正規フローに別の code を差し込む向きだけで、攻撃者が自分の完成済みフローを被害者のブラウザーへ持ち込む向きは防げない。PKCE も同様で、verifier はサーバーが持っているので攻撃者の側はむしろ正しく揃っている。

## 前提

認可の開始が自オリジンの POST であり、そこで Cookie を焼けること。`SameSite=Lax` により、攻撃者が自分の Cookie を被害者のブラウザーへ持ち込む経路が無いこと。コールバックの消費が単回であること（[ADR 035](./035-oauth-callback-single-route.md)）。フロー状態の取り出しが原子的であること。振る舞いをポートの契約として規定し、適合スイートで全バックエンドへ強制できること（[ADR 026](./026-port-contract-and-conformance.md)）。

## 決定

束縛の秘密の digest だけをフロー状態に持たせ、Cookie の運搬と不在判定は転送境界に残す。照合そのものは `state` の消費と同一の原子操作の中で行う。

1. 開始の応答が束縛 Cookie を焼く。値は `state` と独立した**一回限りの乱数**（その digest をフロー状態の行が持つ）、属性はセッション Cookie に揃えて `HttpOnly` / `SameSite=Lax` / `Path=/`（開発時の平文 http を除き `Secure`）、寿命は `state` 行と同じ
2. 消費は「束縛が一致したときだけ `state` を削除して返す」条件付きの原子操作で行う。束縛が一致しない要求は行を残したまま「state 不正」に畳み、Cookie 不在は転送境界がユースケースを呼ぶ前に同じ「state 不正」へ畳む
3. 破棄は 2 点に置く — 消費要求が「state 不正」以外で終わったときと、消費要求が起きない往復（プロバイダーが拒否を返した / 引数が欠けた）。後者は**束縛が一致して行を取り出せたときだけ**捨てる
4. 消費要求が「state 不正」で終わったときは捨てない
5. Cookie の運搬（焼く・読む・捨てる）と不在判定は転送境界に置き、値の照合は消費と同じ原子操作に置く

照合が消費と同一の原子操作なので、通っていない `state` は消費されない。攻撃者の URL を踏まされても、正規のブラウザーの側のフローは残る。

破棄を無条件にしないのは、`<img src="…/auth/callback/…?error=x">` を踏ませるだけで被害者の進行中フローの Cookie を落とせてしまうため。同じ理由で、照合に失敗した Cookie は「別のブラウザー（＝正規の利用者）が進行中のフロー」のものなので触らない。

Cookie に `state` そのものを載せないのは、`Path=/` の Cookie が同一オリジンの全要求に相乗りするため。単回消費の資格情報そのものを常時運ばせない。だから Cookie に載せるのは `state` と独立した一回限りの秘密にする — `state` から導ける値にすると、認可 URL とコールバック URL で往復する `state` を握った第三者が同じ Cookie を再現できてしまう。

連携（既存アカウントへのログイン方法追加）の往復にも同じ束縛を掛ける。こちらは攻撃者のセッションが焼かれる向きは元々成立しないが、被害者に他人の外部アカウントを紐づけさせる向きの `state` すり替えを一段防げる。

## 検討した代替案

### Cookie の値を `state` の鍵付き MAC にする

`HMAC(serverKey, state)` ならサーバー側の記憶が要らず、照合は純関数のまま置ける。しかし配備に新しい鍵（あるいは既存鍵の用途分離）が要り、鍵が漏れれば束縛は「`state` から決定的に導出できる値」へ即座に戻る。往復する値とブラウザーにしか無い値が独立でなくなる点は変わらない。

### `state` を Cookie 値の digest にする（`state = sha256(nonce)`、Cookie には nonce）

これもサーバー側の記憶が要らないが、Cookie の値が `state` の原像になるため、Cookie 単体が `state` を含む「より強い資格情報」になる。`Path=/` の Cookie に単回消費の資格情報そのものを常時運ばせない、という決定の向きに逆行する。

### CSRF トークン・`Origin` 検証を強める

消費要求を出しているのは自オリジンのページ自身なので、トークンも `Origin` も正しく揃う。攻撃者が偽装しているのは要求ではなく「どのフローを完了させるか」なので、原理的に効かない。

### 消費した後に照合する（`take` の後で比較する）

層の分担としては素直に見えるが、照合の前に `state` の取り出し（単回消費）が走るため、踏ませるだけで正規のフローを壊せる。却下するのはこの「消費が先に走る」形であって、照合が消費と同一の原子操作になる条件付きの `take` ではない。

## 影響

- 「コールバック URL を踏ませるだけでは被害者の認証状態が変わらない」が成立する。攻撃者が被害者のブラウザーへ持ち込めないのは Cookie だけ、という [ADR 029](./029-verification-session-binding.md) と同じ根拠に乗る
- 束縛が双方向になる。`state` 単体でも Cookie 単体でも認可を完了できず、独立した 2 本が揃ったブラウザーだけが通せる
- 消費済みでも Cookie が残ることがある。「state 不正」は行が消えたかと 1 対 1 ではなく、転送境界からは両者を区別できないので、安全側に倒して捨てない。行が消えている以上その Cookie はもう何も通せず、寿命は `state` 行と同じで次の開始が上書きする
- **縮退（受容）**: 束縛 Cookie は 1 本なので、同一ブラウザーで 2 つの認可フローを並行して開始すると先に始めた方が完了できない。「もう一度やり直してください」に倒れるだけで、認証状態は壊れない
- **縮退（受容）**: 別端末で認可を完了する経路（PC で開始してスマートフォンで同意）は成立しない。認可の同意は開始したブラウザーの中で完結するのが通常の導線なので、メール確認の別端末フローと違い実質的な縮退にはならない
- 中断された往復の Cookie は寿命（`state` 行と同じ）まで残る。次の開始が上書きし、期限で消える
- 束縛の成否は「Cookie に何を焼くか」と「その値をどう渡して消費するか」の**配線**そのものなので、純関数の単体テストでは守れない。回帰の検知は 2 か所が担う — 「束縛が一致しなければ消費されない」は適合スイート、配線は実際にエクスポートされている入口を 1 リクエスト分の実行文脈で呼び、Cookie を実物の要求ヘッダー / 応答ヘッダーとして観測するテスト
