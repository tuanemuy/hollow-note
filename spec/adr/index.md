# ADR 一覧と前提依存マップ

設計上の非自明な判断を記録した Architecture Decision Record の索引。あわせて、**どの ADR がどのプラットフォーム前提に乗っているか**を逆引きできる表を置く。

[idea.md](../idea.md) の「未確定の技術選択（候補）」のとおり、実行基盤・保存先・全文検索の置き場はまだ確定していない。ヘキサゴナルアーキテクチャによりアダプター層の差し替えは安いが、**ADR に記録された判断は前提を差し替えても自動的には剥がれない**。前提を動かすときは、まずこの表で影響範囲を引くこと。

## 前提依存マップ

「依存している前提」は、その ADR の**決定そのもの**が成立するために必要な前提を指す。代替案の不採用理由にだけ前提が使われている場合は、決定は依存しないものとして扱い、その旨を注記する。

| ADR | 依存している前提 | 前提が変わったときの影響 |
| --- | --- | --- |
| 001 認証手段の分離 | 依存なし | — |
| 002 OpenRouter OAuth | 依存なし | — |
| 003 ノートの所属 | 依存なし | — |
| 004 ワークスペースのロール | 依存なし | — |
| 005 非同期ジョブ | 実行基盤の実行時間・CPU 時間の制約と、キューによる配送 | 実行基盤が変わると「何をジョブにするか」の境界そのものが動く。制約が緩ければ同期に戻せる処理が出る |
| 006 HTML の本文モデル | 依存なし | — |
| 007 既定スタイルと Shadow DOM | 依存なし（ブラウザの機能） | — |
| 008 ドメイン境界 | **同一 Unit of Work で束ねられるのは同じデータストアに載る範囲に限られる** | ストアを分けると「中間状態を許容できない後始末は同一 UoW」という一貫性の表が成立しなくなる。強制終端の後始末（Job + Note + StoredFile を同一 UoW で書く）などが結果整合に落ち、途中状態を利用者に見せない保証が失われる |
| 009 読み取りモデル | 「1 つの基盤の上で完結させる」前提と、SQLite の FTS5 | 検索を専用エンジンに出すと `note_search` の存在意義そのものが変わる。タグ絞り込みと関連度順を検索エンジン側が担えるなら、読み取りモデルは一覧の非正規化だけを担う軽いものになる |
| 010 匿名エクスポートとチケット | レート制限を transport 層に置く前提（手段は未定） | 影響は小さい。チケットはステートレスな署名値であり保存先を持たない |
| 011 bigram 検索 | **FTS5 にカスタムトークナイザーを積めないこと**（D1 のような環境では SQLite の拡張をロードできず、組み込みの `unicode61` / `trigram` の範囲で日本語の部分一致を成立させる必要がある） | 日本語アナライザーを持つ検索エンジンなら ADR 011 は丸ごと不要になる。書き込み時の bigram 前処理も、ハイライト生成の自前実装（[database/index.md](../database/index.md) の「ハイライトと抜粋の生成」）も要らなくなる |
| 012 ジョブ実行の回復性 | ステートレスな実行環境と、at-least-once・順序保証なしのキュー | 永続実行基盤（Durable Objects / Workflows / 同種の仕組み）を採れば、リース・リーパー・`beginAssembly` / `renewAssemblyLease`・`attempts` の 0 / 1 による実行権の表現の大半が不要になる |
| 013 サニタイズ方針 | 依存なし | — |
| 014 取り込み結果の供給元 | 依存なし | — |

### 注記

- **001** — 代替案「マネージド認証サービスを使う」の不採用理由に「1 つの基盤の上で完結させたい」という前提が使われている。決定（Identity を User から分離する）自体はどの基盤でも成立するが、前提が変われば代替案の再評価はありうる
- **009** — 代替案「検索だけを外部の検索サービスに委ねる」も同じ理由で不採用にしている。009 は決定そのもの（FTS5 を `note_search` に対応づける）が前提に乗っているため、上表では依存ありとした
- **011** — 011 は 009 の下に積まれている。009 が動けば 011 は自動的に再検討の対象になる

## 前提を動かすときの手順

1. この前提依存マップで影響範囲を確認する
2. 影響のある ADR を改訂するか、破棄して新しい ADR に置き換える
3. 下流（`domains/` → `usecases/` → `database/` → `testcases/`、および `pages/` / `manual-tests/`）へ反映する

**ADR 008 への影響がもっとも広い**。008 はドメインの分割そのものと、ドメインをまたぐ整合性の取り方（何を同一 UoW で束ね、何を結果整合にするか）を定めており、下流のほぼ全文書がここに乗っている。データストアを分割する変更を検討するときは、008 の一貫性の表を先に引き直すこと。

## 未決の技術選択

前提が確定していないため、まだ決めていないもの。

| 項目 | 決める必要があること |
| --- | --- |
| 全文検索の置き場 | 書き込みモデルと同じストアに置くか、専用の検索エンジンに出すか（ADR 009 / 011 の去就がこれで決まる） |
| ジョブ実行基盤 | ステートレスな実行環境 + キューで続けるか、永続実行基盤に載せ替えるか（ADR 012 の大半がこれで決まる） |
| 調整状態の置き場 | レート制限のカウンター・失敗回数、OAuth の一時状態、イベントの重複排除の記録を、主データベースに置くか専用の低遅延ストアに置くか（読んでから書く更新の原子性をどう与えるかがこれで決まる） |
