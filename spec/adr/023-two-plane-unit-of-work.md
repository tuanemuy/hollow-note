# 023. Unit of Work を global 平面と scope 平面に分け、境界を型で強制する

## コンテキスト

[ADR 021](./021-scope-sharded-data-plane.md) は業務データを scope 単位の Durable Object に、制御面と公開投影を global D1 に置くと定めた。この境界を実装側の Unit of Work にどう写すかが問題になる。

単一の `UnitOfWorkProvider.run(fn)` で両方を扱うと、コールバックがどちらの平面のデータを触っているかが型に現れない。平面をまたぐ書き込みや入れ子の `run` は、DO storage の私有性から**実行時にしか失敗しない**。加えて「リポジトリは UoW の中でだけ触る」という原則が JSDoc 頼みになり、コンテナからフルのリポジトリを取り出せば UoW の外でも書き込めてしまう。

一方で、仕様が意図的に UoW の外に置いている書き込みもある。一意性の予約サガ、note route のサガ、ログイン試行の原子カウンター、期限切れセッションの best-effort 削除は、いずれも UoW に属さない。「UoW の外では書かない」を単純な禁止として実装すると、これらが表現できなくなる。

## 決定

### 2 つの provider を別の型として定義する

- `GlobalUnitOfWorkProvider.run(fn)` — global 平面（Identity / directory / routing / global outbox）
- `ScopeUnitOfWorkProvider.run(scope, fn)` — scope 平面。`ScopeKey` を必須引数に取り、コールバックが受け取る context は**その scope に属する repository と、イベントを enqueue する唯一の経路**だけを公開する

平面をまたぐ操作は 1 つの UoW にせず、サガとして書く。ノート作成は「global で route を予約 → scope で commit → global で activate」の 3 段になる。入れ子の `run` は実行時に拒否する。

### コンテナは UoW 外で使ってよいポートだけを載せる

DI コンテナに置く読み取り経路は `Pick<Repository, 読み取りメソッド>` として公開し、書き込みメソッドを型から落とす。UoW の外での書き込みが仕様であるポート（一意性 directory、note route store、ログイン試行 store など）だけをフルシグネチャで載せる。「UoW 外の書き込みはこの列挙だけ」という境界が、コンテナの型そのものになる。

## 検討した代替案

### 単一 UoW のまま始め、平面の分割を後回しにする

初期の実装量は減る。しかし平面の分割はサガの形（予約 → commit → activate）と表裏であり、後から入れると全ユースケースの書き直しになる。分割の遅延で節約できるのは in-memory 実装の模倣コストだけで、取引が合わない。

### 両平面を 1 つの `run` に束ね、分散トランザクションのように見せる

呼び出し側は単純になるが、Durable Object の storage は別オブジェクトや D1 と 1 トランザクションに束ねられない（ADR 021）。実現できない抽象を型で約束することになる。

### コンテナにフルのリポジトリを載せ、規律を JSDoc で守る

実装は最短。しかし「UoW の中でだけ触る」は最も破られやすく、破れたときの症状（部分書き込み・ロールバック漏れ）が最も見つけにくい規律であり、型で落とせるものを文章に委ねる理由がない。

## 影響

- ユースケースは自分がどの平面にいるかを型で意識する。平面をまたぐ操作は必ずサガとして書かれ、中断点が実装に現れる
- UoW コンテキストの形が契約になる。同一トランザクションで行うべき操作（[ADR 027](./027-projection-revision-numbering.md) の投影世代の bump など）は context に載せることで強制する
- コンテナに読み取りメソッドが増えるたび `Pick` の列挙を広げる差分が出る
- in-memory バックエンドでも平面分離・スコープ分離を模倣する実装コストがかかる。単一プロセスでは分離の恩恵が見えにくいが、適合テスト（[ADR 026](./026-port-contract-and-conformance.md)）の検証対象としては同じ価値を持つ
