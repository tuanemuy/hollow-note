# 039. 削除の参加者と必須受領は、配備の全数宣言から導出する

## ステータス

承認済み

## コンテキスト

アカウント削除は、scope 平面の掃除参加者（component）と global 平面の必須受領（receipt）が**全部揃って**初めて終端へ進む。この「全部」の集合をアダプターの定数として焼き込むと、まだそのドメインが存在しない配備では終端に到達できない。

回避策として「存在しない component を無条件 ack するダミー」を置くと、後続の実装が本物の参加者を足したときにダミーを外し忘れた瞬間、「掃除したつもりで消えていない」という検出困難な欠陥になる。

逆に、必須集合を「登録された参加者」からだけ導出する**追加式**にすると、登録漏れが (i) そのドメインへ掃除コマンドが配送されない かつ (ii) 必須集合にも入らない、という形で「黙って完了する」に化ける。ダミーを退けた理由が別経路で復活する。

## 前提

完了の条件が「宣言された集合の全 ack」であること。参加者と受領の列挙型が設計側の正典であり、配備によって値そのものは変わらないこと。

## 決定

必須集合は composition root の**全数宣言**から導出する。

- 宣言は `Record<列挙値, 参加者 | 不在理由>` の形にする。列挙値のいずれかが欠ければ型エラーになるので、値を追加したときも、後続の実装が不在理由を参加者へ差し替え忘れたときも、宣言の存在自体は型が保証する
- **必須集合は「参加者」の側からだけ導出する。** 不在理由は「なぜ居ないか」と引き継ぎ先を持つ値であり、不在であること自体は正当な状態として型に残す
- アダプターと適合スイートは固定値を持たない。宣言集合を受け取り、「宣言された全 ack で完了 / 1 つでも欠ければ衝突」という形で一般化する
- ダミー ack は置かない
- scope 平面の完了を global 平面の受領へ運ぶのは**専用のブリッジ 1 か所**にする。2 つの Unit of Work をネストせず、「scope の commit ack を受けてから global の受領を書く」順に固定する（[ADR 023](./023-two-plane-unit-of-work.md)）
- 再駆動を冪等にするため、掃除の進捗を読む読み取りを 1 本持つ。完了済みへの ack 再送と完了の再宣言は成功する no-op とする

## 検討した代替案

### 存在しない component を無条件 ack するダミーを置く

必須集合を固定したまま終端へ到達できる。しかし外し忘れが「掃除していないのに完了する」という無言の欠陥になり、検出手段が無い。

### 登録された参加者から必須集合を導出する（追加式）

宣言が 1 か所で済む。しかし登録漏れが配送漏れと必須集合の欠落を同時に起こすので、ダミーと同じ失敗が別経路で成立する。

### 必須集合をアダプター側の定数として持つ

実装が単純。しかしバックエンドの数だけ同じ集合が複製され、配備ごとの差を表現できない。

## 影響

- 参加者を足すスライスは、不在理由を参加者へ差し替えるだけで必須集合に入る
- 列挙値の追加はコンパイルエラーとして検出される
- 不在理由のまま放置しても型は通る（不在は正当な状態なので型では禁じられない）。したがって「今どの参加者が不在か」を配備の記録として残す運用が要る
- scope の commit と global の受領のあいだで落ちると受領だけが未記録で残る。再駆動が受領の書き込みをやり直せる形にしておく必要がある（[ADR 043](./043-cross-plane-handover-driver.md)）
