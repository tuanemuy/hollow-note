# 043. 平面をまたぐ引き渡しは、専用の継続行を駆動主体にする

## ステータス

承認済み

## コンテキスト

scope 平面の掃除の最後のターンは、1 つのトランザクションで「component の ack」「barrier の完了」「自分のタスク行の完了」を確定させる。そのあと、別平面・別トランザクションとして global 側の受領と次フェーズの継続を書く。平面をまたぐので、この 2 つを 1 つのトランザクションに束ねられない。

2 つ目のコミットを落とすと、**復旧する主体がどこにも残らない**。タスク行は完了で消えているので backoff は行不在の no-op、掃除フェーズの継続イベントは決定的 id で 1 行に畳まれて再配送されず、終端処理も回収処理も掃除フェーズへは戻ってこない。データは消えているのに操作は永久に「実行中」のままになる。

消えたタスク行を復活させるだけでは直らない。復活した行が再投入するのは掃除の本体で、その先頭の検査は「閉じたばかりの barrier」を必ず拒否するため、上限回数まで失敗して終端へ落ちる毒行になる。イベント駆動のウェーブが同じ状況から復旧できるのは、配送側が進捗を先に読んでコマンド自体を飛ばすからで、タスク行の経路には同じ入口が無い。

## 前提

平面をまたぐ 2 つのコミットを 1 つのトランザクションに束ねられないこと（[ADR 023](./023-two-plane-unit-of-work.md)）。継続イベントが決定的 id で 1 行に畳まれること（[ADR 041](./041-deterministic-continuation-event-id.md) / [ADR 042](./042-outbox-save-id-collision.md)）。受領の記録が冪等であること。

## 決定

引き渡しに**専用の継続行**を与える。barrier を閉じたターンの直後にその行を arm し、その上で global 側の受領を書き、受領が入って初めてその行を完了させる。同じ kind のハンドラーが登録されているので、例外でもプロセス断でも次の tick が**引き渡しだけ**を再実行する。

backoff は「行が無ければ何もしない」を保つ。閉じた本体の行を復活させると毒行になるので、これがこの経路の正しい既定になる。

## 検討した代替案

### 完了したタスク行を復活させる

新しい kind を増やさずに済む。しかし復活した行が再投入するのは本体で、その入口は閉じた barrier を必ず拒否する。上限回数まで失敗して終端へ落ちるだけになる。

### 中央のスイーパーが「受領の無い完了済み barrier」を探す

汎用の回復手段になる。しかし別平面を横断して読む主体を新設することになり、scope を跨いだ列挙という最も避けたい形の読みが増える。

### 引き渡しを本体と同じトランザクションに入れる

最も単純だが、平面をまたぐので不可能。

## 影響

- 引き渡しが失われても駆動主体がデータとして残るので、「プロセスを落として再起動しても未完の継続を拾って完走する」が、barrier を閉じるターンでも成立する
- 再駆動されるのが引き渡しだけなので、本体のユースケースにも入口の検査にも触れずに済む
- barrier を閉じるターンごとに scope 平面のトランザクションが 2 つ増える（arm と完了）
- **残る窓**: 本体のコミットと arm のあいだで落ちると、依然として駆動主体が残らない。塞ぐには本体と同じトランザクションで arm する必要がある。arm は同一 scope への小さな書き込み 1 回なのに対し、塞げた窓は別平面のコミット全体なので、窓は桁で縮んでいる
