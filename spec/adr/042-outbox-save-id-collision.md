# 042. outbox の保存は id 衝突を「先着行をそのまま残す no-op」として契約する

## ステータス

承認済み

## コンテキスト

継続イベントの ID を決定的に導出する判断（[ADR 041](./041-deterministic-continuation-event-id.md)）は、その正しさを「同じ id の再保存は 1 行に畳まれる」という性質に置いている。ところがこの性質は outbox ポートの契約に書かれておらず、適合スイートにも重複 id のケースが無く、特定アダプターの実装特性だけが支えていた。

契約が無いと、次のバックエンドは素の `INSERT`（一意制約違反で業務トランザクションごと巻き戻る）とも上書きとも書ける。上書きは配送済み・隔離済みの行を復活させ、試行回数と再試行予定まで初期化する。どの実装でも現行のテストは通る。

## 前提

決定キーがターンごとに変わること（[ADR 041](./041-deterministic-continuation-event-id.md)）。したがって **id が衝突する = 同じ論理イベントの再保存**であることが設計上の不変条件になる。outbox 行の保持期間が再配送の窓を上回っていること。

## 決定

次をポートの契約として明文化し、適合スイートで固定する。

> `id` は outbox 行の同一性である。既に保存されている id のイベントは skip し、先着行（payload・試行回数・再試行予定・claim・処理済み / 隔離の状態）をそのまま残す。これはエラーではなく、同一バッチの他のイベントは通常どおり保存される。

スイートは「再保存で行が増えない」「再保存が試行回数と再試行予定を戻さない」「処理済み id の再保存が再配送を起こさない」の 3 点を固定する。

## 検討した代替案

### 上書き（upsert）にする

「行が 2 本にならない」は同じく満たせる。しかし処理済み行の復活は、応答喪失 1 回につきチェーンの**残り全部**を再実行させる（復活したターンが後続ターンを再保存し、それも処理済みなので復活する、という連鎖）。隔離した行の試行予算も回復するので、隔離そのものが意味を失う。復活が救えるのは「同じキーの継続が消される」問題だが、それは保存と完了の**順序**に由来するので上書きでも解決しない。

### 一意制約違反をそのまま伝播させる

実装が最も素直。しかし業務トランザクションごと巻き戻るので、再実行が必ず失敗し続ける。

### 呼び出し側が重複を避ける

契約を増やさずに済む。しかし重複が起きうること自体が前提（応答喪失）なので、避けられるのは呼び出し側ではない。

## 影響

- 決定的 ID の不変条件がバックエンド横断の契約として固定され、新しい実装は「衝突時は何もしない」形しか書けない
- 重複排除の有効期間は行の寿命と等しい。処理済み行を回収したあとは同じ id を再び保存できるので、**outbox の保持期間は再配送の窓を上回っている必要がある**
- 「同じ id へ upsert される」と読める設計文書の記述は、「1 行に畳まれる」という意図としては一致するが語が合わない
