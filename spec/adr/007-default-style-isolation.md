# 007. 既定スタイルは装飾を持たない本文にのみ適用し、本文は Shadow DOM で隔離する

## ステータス

承認済み

## コンテキスト

idea.md には「デフォルトのスタイルを当てたいが、装飾された HTML には影響しないようにしたい。デフォルトは GitHub の Markdown スタイル」とある。

本文には 2 種類ある。Markdown や Office ファイルから機械変換された、装飾を持たない素朴な HTML と、元から CSS で装飾された HTML である。前者には読みやすい既定スタイルを当てたい。後者に同じスタイルを当てると、元の見た目が壊れる。

さらに、アプリケーション側のスタイル（Tailwind のリセットなど）が本文に漏れ込むと、装飾された HTML の見た目は本文を隔離しない限り必ず変わる。逆に、本文に含まれる CSS がアプリケーション側に漏れ出す危険もある。

## 決定

- ノートは `styleMode` を持つ。値は `default`（既定スタイルを適用）と `preserve`（元の装飾のみ）の 2 つ
- 取り込み時に自動判定する。本文に `style` 要素、`link rel=stylesheet`、または意味のある量の `style` 属性が含まれる場合は `preserve`、そうでなければ `default` とする
- 判定結果は利用者が後から切り替えられる。ノートごとの設定として保持する
- 本文の描画は Shadow DOM で隔離する。アプリケーション側の CSS は本文に届かず、本文の CSS はアプリケーション側に漏れない
- 公開ページはサーバー側で描画するため、Declarative Shadow DOM（`<template shadowrootmode="open">`）を使う。本文の文字列は HTML の応答に含まれ、検索エンジンから読める
- 既定スタイル（GitHub の Markdown 相当）は Shadow DOM の内側に注入する。`preserve` の場合は注入しない
- 書き出し（EX-01）の HTML でも同じ規則を適用し、`default` の場合のみ既定スタイルを埋め込む

## 検討した代替案

### 本文を包む要素にスコープ付きの CSS を当てる

実装は容易だが、詳細度の勝負になり、元の装飾を確実に守れない。アプリケーション側のリセット CSS の影響も残る。不採用。

### iframe に本文を描画する

隔離は最も強固だが、高さの同期、リンクの遷移、印刷・PDF 生成、テキスト選択、アクセシビリティのいずれもが扱いづらくなる。共有ページの表示品質を落とす代償が大きい。不採用。

### 常に既定スタイルを当てる / 常に当てない

どちらかの本文が必ず不本意な見た目になる。要件が両立を求めているため不採用。

### 判定を自動化せず、利用者に毎回選ばせる

取り込みのたびに判断を強いることになる。自動判定を既定とし、切り替えを残す形にした。

## 影響

- ノートは本文とは別に `styleMode` を保持する
- 変換処理に「装飾を持つか」の判定が加わる
- 本文の描画コンポーネントは Shadow DOM を使うため、サーバー側での描画結果に依存した表示（本文内へのアプリ側 UI の差し込み）はできない
- ノート詳細に、既定スタイルの適用を切り替える操作（所有者のみ）を置く
- 公開ページは Declarative Shadow DOM で描画する。本文から抽出したテキストは説明用のメタ情報にも使う
