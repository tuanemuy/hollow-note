# 038. 外部アカウントの claim は、現行の identity 行と対で読む

## ステータス

承認済み

## コンテキスト

外部アカウントの一意性は key shard の予約ディレクトリが持ち、identity 行は UserId shard にある。両者は別の物理境界にあり、1 つのトランザクションで同時に変えられない。

ログイン方法の解除は identity 行を UserId shard で消し、予約の解放はイベントの購読者へ委ねる。したがって「解除は成功したのに、その外部アカウントでまだサインインできる」窓が必ず一度は開く。実測でも、解除の直後に同じ外部アカウントを提示するとセッションが発行された。

窓は一時的とは限らない。配送は失敗回数の超過で隔離され、解放の受領は保持期限で消える。両方が起きると再配送は「受領が無い」として何もせず、claim は恒久的に有効なまま残る。

逆向きの穴もある。解放側が冪等性の根拠を「その identity ID の行が消えていること」に置くと、再連携で**新しい ID** が採番されるため旧 ID は恒久的に不在になり、旧イベントの再配送が**再連携したばかりの claim を解放する**。結果は「identity 行はあるが claim が無い」状態で、別の利用者がその外部アカウントを奪える。

## 前提

配送が at-least-once で順序保証を持たないこと。identity 行の読みとセッションの insert を同じ shard の同じトランザクションに置けること。

## 決定

claim は「サインインを通す資格」ではなく**索引**として扱い、その鍵を**今**名乗っている identity 行を同じトランザクションで確認する。読み側・書き側・解放側の 3 経路が同じ述語を使う。

- **読み側（サインイン）**: セッションを insert する最終トランザクションの中で当該利用者の identity 一覧を読み、同じ外部アカウント鍵の行が現存しなければセッションを発行しない。トランザクションの外で読むと「読んだあとに解除が commit される」窓が残る
- **解放側（購読者）**: 「その鍵を今名乗る identity が受領の利用者に居ないこと」を条件にする。削除された ID の不在では判定しない
- **書き側（再連携）**: 同じ不一致を同じ判定で検出する
- 拒否は「解除処理が進行中である」ことを表す専用のコードにする。既存の「別の利用者に紐づいています」は、**自分が今解除した鍵**について出ると誤誘導になる。文言は再試行が有効であることを伝える

## 検討した代替案

### 受領に予約行の operation ID を凍結し、解放時に照合する

同じ奪取を防げる。しかしポート・アダプター・適合スイートの変更に波及し、効果は変わらない。判定を application の 1 か所に閉じるほうが小さい。

### claim を無視して、メール経路（新規作成 / 既存への自動リンク）へ落とす

サインインは通る。しかし予約行は残っているので後続の予約が必ず競合し、利用者には「別の利用者に紐づいています」が出る。状態と応答が食い違う。

### 解放イベントの到達を前提に、窓を無視する

配送が確実なら成立する。しかし隔離と受領の保持期限で窓は恒久化しうる。到達に依存しない判定が 1 トランザクションで書ける以上、依存する理由が無い。

## 影響

- 「解除に成功した外部アカウントでは二度とサインインできない」が、解放イベントの到達に依存せず 1 トランザクションだけで成立する
- 読み・書き・解放の 3 経路が同じ述語で判断するようになり、非対称が消える
- サインインごとに identity 一覧の読みが 1 回増える（件数に上限があるので実質定数）
- 解放が恒久的に落ちた場合、その外部アカウントは誰も使えないまま固まる（サインインも再連携も拒否される）。運用で解放を再駆動するまで止まる形を選んだ — 誤って通すより固まるほうが安全側に倒れる
- 同じ鍵を再連携したあとに旧解放イベントが再配送される正常系でも「解放しない」判断が記録される。理由コードで異常系と区別する
