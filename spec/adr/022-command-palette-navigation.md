# 022. 常設サイドバーを持たず、航法をスコープトークンとコマンドパレットに二重化する

## コンテキスト

本サービスの画面は、その大部分が**利用者が作ったのではない HTML** で占められる。変換された本文は独自の見出し階層・色・余白を持ち込むため、UI 側が枠や柱を常駐させるほど本文と競合する。[デザイン方針](../design/index.md) はこの前提から「中央 1 カラム ＋ 呼べば出てくる道具」という構造を採り、**常設サイドバーを置かない**ことを決めた。

一方 [pages/index.md](../pages/index.md) の L-01 は、常設サイドバーがあることを前提に到達性を組み立てていた。サイドバーは「今どの文脈にいるか」の表示と、「その文脈のどこへ行けるか」（ノート一覧・タグ管理・ゴミ箱・処理履歴・設定）の一覧を、常に画面に置くことで両方を無条件に成立させていた。この柱を外すと、次の 2 つが同時に宙に浮く。

1. **現在地の表示** — 個人とワークスペースでは同じ URL 構造・同じ画面が別の中身を出すため、文脈を誤認すると誤ったスコープへノートを取り込む
2. **行き先の一覧** — タグ管理・ゴミ箱・処理履歴・設定は、どの画面からも直接には見えない場所になる

デザイン方針は 2 に対して「**パレットにしか入口がない機能を作らない**」という規則を置いたが、その規則を満たす具体的な入口はどこにも定まっていなかった。⌘K パレットは航法の中心ではあるが、**初回の利用者はその存在を知らない**ため、パレットを唯一の入口にした機能は事実上到達不能になる。

## 決定

**航法を「常時見える 2 つのメニュー」と「すべてに届く 1 つのパレット」に二重化し、両者の役割を帰属で割る。**

### 1. 入口は 3 層で構成する

| 層 | 何を担うか | 実体 |
| --- | --- | --- |
| 常時見える入口 | 現在地の表示と、視覚的にたどれる行き先 | 上部バーのスコープトークン、アカウントメニュー |
| 近道 | 検索・絞り込み・移動・操作をキーボードで一息に | ⌘K コマンドパレット |
| 文脈内リンク | その画面を見ている最中にだけ意味を持つ行き先 | 処理ティッカーの「処理履歴」、空状態の CTA、一覧の行アクション、下端操作バー |

### 2. メニューの帰属で行き先を割る

**行き先が現在の文脈（scope）に属するならスコープトークン、利用者本人に属するならアカウントメニュー**に置く。

| メニュー | 並ぶもの |
| --- | --- |
| スコープトークン | 文脈の切り替え（個人 / 参加中ワークスペース、20 件ずつ追加読込）、ワークスペースを作成、現在の文脈のタグ管理・ゴミ箱、ワークスペース文脈ではワークスペース設定とその公開ページ |
| アカウントメニュー | プロフィール、自分の公開ページ、処理履歴、設定、サインアウト |

処理履歴がアカウント側にあるのは、`/jobs` が文脈を持たず実行者本人に紐づくためである（[pages/index.md](../pages/index.md) の URL の割り当て、[usecases/job.md](../usecases/job.md)）。同じ理由で個人設定はアカウント側、ワークスペース設定はスコープ側に分かれ、[デザイン方針](../design/index.md) §3.9 の「設定のタブ列を個人とワークスペースで分ける」はこの帰属の帰結になる。

この規則は、**サイドバーが 1 本の柱に混ぜていた 2 種類の行き先を分離したもの**である。サイドバーは「切り替え」と「その文脈の行き先」を上下に並べていたが、上部バーには柱がないため、帰属を判断の軸に据えないとどちらのメニューに置いてもよくなり、規則が失われる。

### 3. パレットを唯一の入口にしない（不変条件）

すべての機能は、パレット以外に最低 1 つの視覚的な入口を持つ。**処理ティッカーは実行中ジョブが 0 件のとき要素ごと消えるため、処理履歴の恒久的な入口には数えない**（だからアカウントメニューに置く）。権限で使えない行き先はメニューから消す（無効化して並べない） — ワークスペースの viewer にゴミ箱を出さないのは [ADR 004](./004-workspace-roles.md) の帰結である。

## 検討した代替案

### 常設サイドバーを残す（デザイン側を差し戻す）

到達性は無条件に成立し、既存の spec を書き換えずに済む。しかし本文が画面の主役であるという前提と正面から衝突する — 変換された HTML は左に柱があることを知らないので、柱の分だけ本文が痩せ、本文が持ち込む区切り線と柱の境界が二重の分割線になる。加えてモバイルではサイドバーをドロワーに畳む必要があり、**ブレークポイントで DOM 構造と情報階層が分岐する**。この構造の最大の利点（分岐しないこと）を、既存記述を守るためだけに手放すことになる。不採用。

### すべての行き先をパレットに寄せる

上部バーが最も静かになり、規則も「行き先はすべて ⌘K」の 1 行で済む。しかし初回の利用者はパレットの存在を知らず、知ったあとも「何が呼べるか」を覚えている必要がある。サイドバーを外すことで払う代償は「常時の視認性」であって「到達可能性」ではない、という線を引けなくなる。不採用。

### 行き先をすべてアカウントメニューに集約する

メニューが 1 つで済み、帰属を判断する必要がなくなる。しかしタグ管理・ゴミ箱は**文脈ごとに中身が違う**ため、アカウントの下に並ぶと「どの文脈のゴミ箱を開こうとしているのか」がメニューの位置からは読めない。現在地の表示（スコープトークン）と行き先が離れることで、文脈の誤認という最も高くつく事故の確率が上がる。不採用。

### ノート一覧（P-10）のツールバーに「⋯」を置いて収める

一覧は最も長く滞在する画面なので、そこに置けば実質的に常時見える。しかし**一覧に戻らないと行けない**行き先になり、ノート詳細・設定・処理履歴からは 1 回余分に遷移する。[デザイン方針](../design/index.md) §3.6 が固定した P-10 の構成（タイトル / 件数 / ツールバー / チップ列 / 一覧本体）のうち、ツールバーが画面固有の操作だけを持つという線も崩れる。到達性は共通の枠（L-01）が持つべきで、特定の画面に間借りさせない。不採用。

## 関連する設計

- スコープトークンはこの構造で唯一の現在地表示なので、モバイルでもラベルを省略しない（長い名前は省略記号で詰める）
- 検索は独立した検索ボックスを持たず、パレットの「ノート」セクションが担う。適用した条件は一覧のチップ列に積まれ、チップ列は解除の入口を兼ねる
- 実行中ジョブの可視化はティッカー 1 行に閉じ、バッジ付きアイコンを常駐させない。完了・失敗はトーストで伝える
- 公開レイアウト（L-02）はこの決定の対象外。サインイン前の画面は文脈を持たず、パレットも持たない
