# 015. 実行基盤を Cloudflare Workers + D1 + R2 + Queues に確定し、永続実行基盤は採らない

## ステータス

superseded by [021. scope sharded data plane](./021-scope-sharded-data-plane.md)

## コンテキスト

[idea.md](../idea.md) は実行基盤・保存先・全文検索の置き場を「未確定の技術選択（候補）」として保留していた。保留の代償として、[クロスフェーズ検証 004](../review/cross-phase/004.md) の H-01〜H-05 は**確認済みの実在する問題でありながら直し方を決められず**、[ADR 一覧と前提依存マップ](./index.md) には「未決の技術選択」が 3 項目残っていた。いずれも「上限値が決まらないと分割単位を逆算できない」「原子性を与える手段が基盤に依存する」という形で、基盤の確定を待っていた。

あわせて、ジョブの実行を**ステートレスな実行環境 + キュー + 自前のリース**（[ADR 012](./012-job-execution-resilience.md)）で続けるか、永続実行基盤（Durable Objects / Workflows）に載せ替えるかも未決だった。載せ替えれば ADR 012 のリース・リーパー・組み立ての実行権の大半が不要になる。

## 決定

### 構成を確定する

| 役割 | 製品 |
| --- | --- |
| 実行環境 | Cloudflare Workers |
| データベース | D1（SQLite） |
| オブジェクトストレージ | R2 |
| ジョブとイベントの配送 | Cloudflare Queues |
| 全文検索 | D1 の FTS5 |
| 定期実行 | Workers の Cron Triggers |
| 転送境界の粗いレート制限 | Workers の Rate Limiting binding（[ADR 020](./020-coordination-state.md)） |

**調整状態（レート制限のカウンター・OAuth の一時状態・イベントの重複排除の記録）は主データベースである D1 に置く**。専用の低遅延ストアは設けない（[ADR 020](./020-coordination-state.md)）。

実上限の一覧と、そこから逆算した設計値（行サイズ予算・クエリ予算・キュー構成・cron の割り当て）は [platform/index.md](../platform/index.md) を正典とする。ADR は**どの判断がどの上限に乗っているか**だけを持ち、値そのものを二重に持たない。

### 永続実行基盤（Durable Objects / Workflows）は採らない

ジョブの実行は Queues + D1 + 自前のリースのまま続ける。[ADR 012](./012-job-execution-resilience.md) の決定は**リース・リーパー・`beginAssembly` / `renewAssemblyLease`・`attempts` の 0 / 1 による実行権の表現を含めてすべて維持する**。落とすものはない。

理由は 3 つある。

1. **`Job` は問い合わせ可能な第一級の実体であり続ける必要がある**。処理履歴（JB-01）・進捗・再試行・取り消しに加え、除名 / 脱退 / ワークスペース削除 / 退会に伴う一括取り消しは `listActiveByScope` という**業務述語での検索**に依存する（[ADR 012](./012-job-execution-resilience.md)）。Workflows のインスタンスはこの述語で引けないため、載せ替えても `jobs` 表は索引として残る。状態の正が 2 か所に分かれるだけで、1 か所も減らない
2. **強制終端の 9 経路が同一 Unit of Work であることを崩せない**。[ADR 008](./008-domain-boundaries.md) は「中間状態を許容できない後始末は同一 UoW」と定め、ジョブの終端・`processing` のままのノートの回復・生成物の回収を 1 トランザクションで束ねている。Workflows インスタンスの終了も Durable Object への通知も D1 のトランザクションには入らないため、載せ替えると**この 9 経路が結果整合に落ちる**。利用者が自力で解けない状態（`processing` で固定された本文）を残さないという保証は、ADR 012 の存在理由そのものである
3. **リースが解いていた問題は、Queues の性質がそのまま残す**。Queues は少なくとも 1 回・順序保証なしで配送し、コンシューマーは最大 250 並行、壁時計は 15 分で強制終了される。「`running` を受け取ったワーカーが、生きている別ワーカーの実行中なのか死んだワーカーの残骸なのかを区別できない」という ADR 012 の出発点は、この構成でそのまま成立する

Durable Objects が担いうる「キー単位の直列化」も採らない。必要だった 2 か所は、より安い手段で同じ保証が得られた — 読み取りモデルの投影は**専用キューの同時実行数を 1 にする**ことで（[ADR 016](./016-projection-single-writer.md)）、失敗回数の加算は**D1 の単一 SQL 文の原子性**で（[ADR 020](./020-coordination-state.md)）解ける。どちらも新しいストアを増やさない。

### 確定に伴って ADR 012 の 1 点だけを改訂する

**batch 親の組み立てリースを 60 分から 15 分に短縮する**。ADR 012 は進捗リースと組み立てリースを `attempts` の 0 / 1 で区別しつつ期間を同じ 60 分にしていたが、組み立て（`runBulkExport` の ZIP 生成）を実行するのは Queues のコンシューマーであり、**壁時計 15 分で必ず強制終了される**。組み立てが 15 分を超えて生き続けることは原理的にありえないため、60 分のリースは「死んだ組み立てワーカーの親が最大 60 分滞留する」ことだけを意味する。進捗リース（`attempts = 0`。子の終了報告で延びる）は一括操作全体の所要時間に対応するため 60 分のまま据え置く。

期間の表は [usecases/job.md](../usecases/job.md) の「共通: リース期間と回収の間隔」が引き続き正典で、そちらを 15 分に改める。

## 検討した代替案

### Workflows に載せ替え、ADR 012 のリースとリーパーを落とす

各ジョブを Workflow インスタンスにし、ステップの永続化と自動再試行に任せる案。単体ジョブ（変換・バックアップ・書き出し）には確かによく合い、リース・リーパー・引き継ぎの規則をまるごと削れる。

不採用の決め手は上記 2 の**同一 UoW の要求**である。加えて、一括操作は「親 1 件 + 対象ごとの子」に分解され、子の失敗は他の子に影響せず、失敗した子だけを後から再試行できる（[ADR 005](./005-async-processing.md)）。これを 1 つの Workflow インスタンスで表すと、部分再試行のために `retryFailedChildren` 相当をステップの内側に作り直すことになり、子を個別に取り消す経路（除名時に特定の要求者の子だけを止める）が失われる。子を独立したインスタンスにすれば表せるが、そのとき親子関係と集計を持つのは結局 `jobs` 表であり、Workflows は「キューの代わりに実行を運ぶ層」以上のものにならない。

### Durable Object をジョブごと（またはスコープごと）に置く

キー単位の直列化で二重実行を構造的に防ぐ案。リースは不要になる。しかし DO の状態は D1 のトランザクションに入らないため、上記 2 の問題が同じ形で残る。さらに `jobs` 表と DO の状態が乖離したときの回復手順を新たに設計することになり、いま 1 か所にある「実行中かどうか」の正が 2 か所に増える。取引が合わない。

### Durable Object を読み取りモデルの投影の単一ライターとして使う

H-01 に対しては正しく効く。しかし DO は D1 に書けても**同じトランザクションには入れない**ため、DO は排他制御だけを担う錠になる。キューの `max_concurrency: 1` が同じ保証を設定 1 行で与えるのに対し、こちらはバインディング・クラス・ラウンドトリップが増える。詳細は [ADR 016](./016-projection-single-writer.md)。

### 保存先を D1 以外（Turso / PostgreSQL 互換）にする

行サイズ 2 MB・1 実行 1,000 クエリという D1 固有の上限から解放され、H-02 / H-03 は消える。しかし Workers から使うには外部接続（Hyperdrive や HTTP ドライバー）が要り、`CLAUDE.md` の「1 つの基盤の上で完結させる」構成上の単純さと、D1 の `batch()` が与える暗黙トランザクションを失う。H-02 / H-03 はどちらも**上限から分割単位を逆算すれば消える**種類の問題であり（[ADR 017](./017-content-size-budget.md) / [ADR 018](./018-query-budget.md)）、ストアを替えるほどの理由にならない。不採用。

### 全文検索を外部の検索サービスに出す

[ADR 009](./009-read-models.md) / [ADR 011](./011-bigram-search.md) が不採用理由に挙げていた「1 つの基盤の上で完結させる」前提は、本 ADR で確定した決定になった。したがって外部検索サービスは**前提の側から不採用**となり、再評価の対象ではなくなる。009 / 011 の決定はそのまま維持される。

## 影響

- [idea.md](../idea.md) の「未確定の技術選択（候補）」が「確定した技術選択」になり、[ADR 一覧と前提依存マップ](./index.md) の「未決の技術選択」3 項目がすべて解消する
- 前提依存マップの「前提が変わったときの影響」欄は、**確定した前提に対して決定がどこに乗っているか**を示す欄に役割が変わる。前提を動かす手順そのものは残す（基盤の移行を将来検討する場合に使う）
- 実上限と設計値の正典として [platform/index.md](../platform/index.md) を新設する。`database/index.md` は「D1 を前提とした具体設計」から「D1 の確定設計」になり、冒頭の留保が外れる
- H-01〜H-05 がそれぞれ [ADR 016](./016-projection-single-writer.md) / [017](./017-content-size-budget.md) / [018](./018-query-budget.md) / [019](./019-owner-cleanup-continuation.md) / [020](./020-coordination-state.md) として決着する
- [ADR 012](./012-job-execution-resilience.md) は決定を維持したまま、組み立てリースの期間だけ本 ADR が改訂する。`usecases/job.md` の期間表が 60 分 → 15 分になる
- [ADR 001](./001-authentication-strategy.md) / [009](./009-read-models.md) が代替案の不採用理由に引いていた「1 つの基盤の上で完結させたい」は、候補に基づく前提から**確定した決定**になる。両 ADR の末尾の留保を差し替える
- [ADR 005](./005-async-processing.md) の「上限の具体的な値は基盤によって変わる」が確定値（CPU 5 分 / コンシューマーの壁時計 15 分）に置き換わる。ジョブと同期処理の境界そのものは変わらない — 15 分は LLM 構造化や 500 件の ZIP 組み立てを同期で返せる長さではない
