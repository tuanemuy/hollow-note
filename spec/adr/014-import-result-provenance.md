# 014. 取り込み結果の供給元は帰属で割り、本文・Storage の記録・ジョブの申し送りに分ける

## ステータス

承認済み

## コンテキスト

[ADR 006](./006-html-content-model.md) は「除去した内容を利用者に提示する」ことを決定に含めており、[ADR 013](./013-html-sanitization-policy.md) の許可リスト化でその対象は増えた（CSS の宣言単位の除去など）。同期の経路（[usecases/note.md](../usecases/note.md) の `updateNoteBody`）は出力 DTO に `removed` を持つため成立する。

しかし非同期の経路（`runConversion` / `runRegeneration` / `importExternalReferences`）は結果をジョブとして返す。`Job` が利用者向けの結果として持てるのは `JobFailure` の `reason` だけで、`detail` は [domains/job.md](../domains/job.md) が「運用者向けの文字列」と明記している。しかも `failure` を持つのは `failed` のジョブだけで、取り込みは失敗した参照があっても成功として終端する。

[pages/index.md](../pages/index.md) の P-11 は次の 4 つを表示すると書いているが、このうち供給元が定まっていたのは 1 つ目だけだった。

1. 取り込んだ参照リソースの一覧 — `StoredFileRepository`（`purpose: "reference"`）から引ける
2. 本文に埋め込んだ外部スタイルシートの件数と配布元 — **供給元がない**
3. 取り込めなかった参照と、取り込めずに装飾が失われた外部スタイルシート — **供給元がない**
4. サニタイズで除去された CSS 宣言 — **供給元がない**

さらに、`usecases/conversion.md` の `runConversion` には「公開ハンドル／スラッグが未設定などで適用できない場合は非公開のまま残し、その旨をジョブの `detail` に記録する（ジョブ自体は成功とする）」という記述があるが、`detail` は `JobFailure` のフィールドであり `failure` を持つのは `FailedJob` だけなので、**この記述は型の上で実行不能**である。データベースも `failure_detail` を `status = 'failed'` のときのみ非 NULL としている。

### 器を 1 つ作る案が成立しない理由

当初は「成功したジョブに利用者向けの結果を載せる器（`JobResult` 相当）を足す」か「変換・取り込みの結果を Note 側に保持する」の二択として整理していた。検証の結果、どちらも単独では成立しないことが分かった。

**ジョブに載せられない理由は寿命ではなく帰属である**。[usecases/job.md](../usecases/job.md) は「ジョブは実行者本人にのみ見える。**ワークスペースのノートに対するジョブでも他のメンバーには表示しない**」と定めており、`getJobDetail` も `requestedBy` が一致しなければ `JOB_NOT_FOUND` を返す。P-11 はノートを読める者すべてに開かれた画面なので、ジョブに載せた情報はワークスペースの他メンバーには出ない。しかも経緯を知らない他メンバーにこそ必要な情報である。加えて `deleteJobsForRequester` は退会時に状態を問わずジョブを全削除するため、寿命は「`pruneJobHistory` の保持期間以内、要求者の退会で即時失効」になる。**表示はノートに帰属するのに、ジョブは要求者に帰属する**。

**Note の集約に持たせるのも成立しない**。`Note.updateBody` が受け取る `ProcessedHtml` は外部参照の一覧を含まず（参照の列挙は `HtmlProcessor.extractExternalReferences` の仕事）、集約に参照集合を維持させるとドメインエンティティが HTML を解釈することになる。`importExternalReferences` 自身も `updateBody` を通して本文を保存するため、「本文の書き換えをまたいで解決状態を引き継ぐ」規則を置くと、その唯一の書き込み経路が壊れる。版からの復元は `NoteRevision` が本文しか保持しないため、集合と本文が両方向に食い違う。

**本文からの再計算だけでも足りない**。`extractExternalReferences` は「外部」参照だけを返す契約ではない — `collectOrphanMedia` はサービス内ストレージの URL が本文に現れるかを調べるのにこのポートを使っており、内部と外部の切り分けはポートの外にある。加えて、取得に失敗した参照・一度も試行していない参照・予算超過で打ち切られた参照は、本文上でいずれも「外部 URL がそのまま残っている」という同じ姿になり区別できない。

## 決定

**1 つの器を作るのをやめ、情報を性質と帰属で 3 つに割る。**

| 何を語るか | 供給元 | 誰に見えるか / いつまで |
| --- | --- | --- |
| **どの参照がどうなったか（構造）** | 本文そのもの | ノートを読める者すべて / 恒久 |
| **なぜそうなったか（理由）** | Storage ドメインの取得記録 | ノートを読める者すべて / 恒久 |
| **ジョブ実行中に下した判断** | `SucceededJob.notices` | 要求者本人 / ジョブ履歴の保持期間 |

### 1. 本文がスタイルシートの状態を語る

`HtmlProcessor` が扱うスタイルシートの痕跡を 3 状態に分け、**抽出対象を `data-stylesheet-href` だけに限定する**。

| 状態 | 本文中の表現 | `extractExternalReferences` が拾うか |
| --- | --- | --- |
| 未取り込み（未試行、または利用者が取り込まないと選んだ） | `<style data-stylesheet-href="URL">`（空） | ○ |
| 取り込み済み | `<style data-imported-stylesheet="URL">…CSS…</style>` | × |
| 取得できなかった（失敗・予算超過） | `<style data-stylesheet-unavailable="URL">`（空） | × |

これにより「本文に埋め込んだ外部スタイルシートの件数と配布元」（P-11 の 2）と「取り込めずに装飾が失われた外部スタイルシート」（同 3 の後半）が、**本文から、ノートを読める者すべてに、ジョブの寿命と無関係に**読めるようになる。

ADR 013 は取得できなかった参照を「痕跡ごと落とす」と決めていたが、その根拠は [usecases/storage.md](../usecases/storage.md) が挙げた**再登録ループただ 1 つ**（空の痕跡が残ると以後の保存のたびに同じ参照取り込みジョブが登録される）であった。抽出対象を `data-stylesheet-href` に限定した時点でこの根拠は失効するため、禁止のほうを取り下げる。

`data-*` 属性は許可リストの内側にあるため（ADR 013）、サニタイズ・書き出し・公開ページの描画のいずれでも失われない。

### 2. Storage の取得記録が理由を語る

外部からの取得は Storage の責務である（`ExternalFetchPolicy` / `RemoteResourceFetcher` がそこにある）。したがって**取得結果も産んだ側が持つ**。Note にも Job にも寄せない。

- `noteId` × `url` を鍵に、最後の試行結果（種別・結果・理由・試行時刻）を記録する
- 直近の取り込み 1 回分の要約として、サニタイズで落ちた CSS 宣言を分類ごとに畳んだ形で持つ（P-11 の 4）
- `importExternalReferences` が本文の保存と同一の Unit of Work で書く
- P-11 は本文と記録を突き合わせて描く。**本文にその URL がもう無い記録は表示に現れない**ため、古い記録を掃除する規則が要らない
- 「記録に行があるか」が「試行済みか未試行か」の区別になる。本文だけでは区別できなかった 3 つの姿が、記録の有無で分かれる

読み取りは [ADR 008](./008-domain-boundaries.md) が既に定めた「ノート詳細はアプリケーション層で Note / Tag / Job / Storage のクエリポートを合成する読み取りになる」にそのまま乗る。回収は `note.purged` の購読で、既存の `deleteFilesForNote` と同じ経路に相乗りさせる。

### 3. `SucceededJob.notices` はジョブ実行中の判断だけを語る

`SucceededJob` に `notices` を足す。中身は `visibilityNotApplied`（`runConversion` が公開を適用できずに非公開のまま残した）**のみ**とする。取り込み結果は上の 1・2 が持つため `notices` には入れない。

- これで `runConversion` の「成功ジョブの `detail` に記録する」という実行不能な記述が解消する
- `JobFailure.detail` は運用者向けのまま据え置く
- 可視性は「要求者本人のみ」のままでよい。公開を要求したのは本人であり、他メンバーに見えなくても情報が欠けない（公開されなかったこと自体は `visibility` から分かる）
- `notices` に依存する不変条件は置かない。Job は運搬と刈り取りだけを担う

**`notices` の中身を 1 種に絞ったのは意図的である**。すべての結果をここに載せると、`JobNotice` が Conversion・Storage・Note の 3 ドメインの語彙を吸収し、Job の変更理由がすべてのワーカーの都合に開かれる。

## 検討した代替案

### Note の集約に未解決参照・取り込みレポートを持たせる

「ノート詳細に表示する情報はノートの属性である」という点では最も素直で、可視性も寿命も要件に合う。しかしコンテキストに挙げたとおり、`ProcessedHtml` が参照の一覧を持たないためドメインが HTML を解釈することになり、`importExternalReferences` 自身が `updateBody` を通る以上「解決状態を引き継ぐ」規則が唯一の書き込み経路を壊し、版からの復元で集合と本文が両方向に食い違う。派生情報を本文と別に持つこと自体が [ADR 006](./006-html-content-model.md) の「正データはサニタイズ済み HTML 1 つ」と逆を向いている。不採用。

### すべてを `SucceededJob.notices` に載せる

器が 1 つで済み、`JobRepository` にクエリを 1 本足すだけで動く。しかし帰属が合わない — ワークスペースの他メンバーに出ず、要求者の退会で消える。P-11 は「自分が実行した取り込みのときだけ理由が出る画面」になる。加えて `JobNotice` が 3 ドメインの語彙を吸収する。不採用。

### CSS 宣言の除去記録を永続化しない

保存操作への応答（`updateNoteBody` の `removed`）だけで ADR 006 の約束は果たされている、という整理。しかし [scenario/import.md](../scenario/import.md) の IM-05 が「取り除いた内容は**取り込み結果に示す**」と要求しており、これは利用者が書いた CSS ではなく取り込んだ第三者の CSS が落ちる話なので同期経路の `removed` では満たせない。マニュアルテストの受け入れ条件にもなっている。不採用。

### `styleMode` と本文の齟齬から装飾の喪失を推定する

`styleMode` が `preserve` なのに本文に装飾の実体がなければ「装飾が失われた」と推定できる、という案。記録を一切持たずに済む。しかし [ADR 007](./007-default-style-isolation.md) の `hasDecoration` は `style` 属性の多用も `preserve` の根拠に数えるため、`<style>` の有無では判定できない。[scenario/editing.md](../scenario/editing.md) が正常な操作として認めている「装飾を持たない本文に『元の装飾のみ』を選ぶ」を誤検出し、外部スタイルシート 2 件のうち 1 件だけ失敗した場合は検出できず、さらに推奨している回復手順（ED-11 で既定スタイルに切り替える）を踏むと条件が崩れて案内が消える。不採用。

### 取得結果を Note ではなく読み取りモデルに置く

[ADR 009](./009-read-models.md) の `note_search` に相乗りさせる案。しかし読み取りモデルは一覧・検索・サイトマップの絞り込みのために投影されるもので、ノート 1 件を開いたときにしか使わない情報を載せる場所ではない。投影はイベント駆動で遅延するため、取り込み直後に開いた画面が古い結果を出す。不採用。

## 影響

- `HtmlProcessor.inlineStylesheets` の契約が変わる。成功した痕跡は属性を付け替え、取得できなかった痕跡は要素ごと取り除くのをやめて非抽出の空痕跡として残す。`extractExternalReferences` は `data-stylesheet-href` だけを痕跡として拾う
- [ADR 013](./013-html-sanitization-policy.md) の「取得できなかった場合は参照ごと落とす」という決定を改める。許可リスト方式という ADR 013 の主題は変わらないため supersede はしない
- Storage ドメインに外部参照の取得記録が加わる。ポート・テーブル・`note.purged` での回収が要る。行数は `FetchBudget.maxCount` で上界が決まる
- `Job` のユビキタス言語に `Notice`（成功したジョブが利用者に伝える申し送り）が加わる。`Job.succeed` の引数、`reopenBatch` での破棄、`BatchProgressCalculator.applyTo` の呼び出し、`jobs` 表の列と CHECK に波及する
- `data-imported-stylesheet` / `data-stylesheet-unavailable` は **利用者が HTML モードで手書きできる**。本文は利用者が書き換えられる領域なので、これらは「本文に記録された取り込み元」であって監査記録ではない。再取得・認可・監査の入力に使ってはならない
- これらの属性は公開ページ・HTML 書き出し・PDF に載る。取り込み元の URL は元の文書に元からあった情報であり、`<link>` を消した現行設計では公開本文から消えていた値が戻ることになる。これを許容する
- WYSIWYG モードでの保存は「表現できない要素は失われうる」（ADR 006）ため、`<style>` ごと落ちて件数が 0 になりうる。装飾も同時に失われるので表示は整合するが、`<style>` を残しつつ未知の `data-*` だけを落とす実装では記録だけが静かに消える。P-12 の WYSIWYG 警告の対象に含める
- 匿名ジョブ（`pdfExport`）は `notices` を持たない
