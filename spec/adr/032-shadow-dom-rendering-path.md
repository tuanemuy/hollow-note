# 032. 本文の Shadow DOM は宣言的 template とクライアント側の昇格の二段で描画する

## コンテキスト

[ADR 007](./007-default-style-isolation.md) は本文を Shadow DOM で隔離し、公開ページはサーバー側で描画するので Declarative Shadow DOM（`<template shadowrootmode="open">`）を使うと定めた。本文の文字列が HTML の応答に含まれ、検索エンジンから読めることが理由である。

しかし `<template shadowrootmode>` が実際に shadow root になるのは、**HTML パーサーがその要素を処理した場合だけ**である。認証が要る画面の本文は RSC のストリーミングで届き、クライアントは受け取ったペイロードから DOM API で要素を構築する。この経路では宣言的 Shadow DOM は解釈されず、template は不活性なまま残り、本文が表示されない。

## 決定

本文コンポーネントは `<template shadowrootmode="open">` をマークアップとして出しつつ、クライアントの effect で「shadow root が未生成で template が残っている」状態を検出したら `attachShadow` して内容を移植し、昇格させる。

- HTML としてパースされる経路（公開ページのサーバー描画）では、宣言的にそのまま機能する
- ストリーミングの経路では、effect が同じ結果へ収束する

ホスト要素は `position: relative` を持ち、本文中の絶対配置の基準を本文の内側に閉じる（これは隔離ではなく描画側の責務である）。既定スタイルは shadow の内側の `<style>` として注入し、デザイントークンは CSS カスタムプロパティ経由で継承させる。

## 検討した代替案

### クライアントでのみ `attachShadow` して本文を挿す

ストリーミング経路だけを考えれば単純。しかし公開ページの HTML に本文が含まれなくなり、ADR 007 が Declarative Shadow DOM を選んだ理由（検索エンジンから本文が読めること）が失われる。

### 本文フラグメントだけをサーバー描画の HTML として別経路で流す

宣言的 Shadow DOM がそのまま効く。しかし本文だけデータの取得経路が二重になり、認証・エラー処理・ストリーミングの規約をもう 1 系統維持することになる。

### iframe に本文を描画する

ADR 007 で検討し、高さの同期・リンク遷移・印刷・テキスト選択・アクセシビリティの代償が大きいとして不採用にした判断をそのまま引き継ぐ。

## 影響

- 公開ページと認証必須ページで同じマークアップの形を使い回せる
- ストリーミング経路では本文の表示に JS が必須になる（認証必須の画面なので許容する）
- React の型に `shadowrootmode` がないため、属性の受け渡しにキャストが要る
