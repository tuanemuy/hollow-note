# 005. 時間のかかる処理はすべて非同期ジョブとして扱う

## ステータス

承認済み

## コンテキスト

本サービスには、要求から応答までの時間が読めない処理が複数ある。

- ファイルの変換（特に LLM による構造化と音声認識）
- 参照先リソースの取得と差し替え
- Google Drive へのバックアップ
- PDF の生成と一括ダウンロードの ZIP 生成
- 元ファイルからの再生成

Cloudflare Workers には要求単位の実行時間・CPU 時間の制約があり、これらを同期的に処理すると上限に達する。加えて、一括アップロード（最大 100 件）は 1 件の失敗で全体を止めるべきではなく、利用者が画面を離れても処理が続いてほしい。

## 決定

- 上記の処理はすべて「ジョブ」として登録し、キュー経由で非同期に実行する
- ジョブは進捗と結果を持つ第一級の閲覧対象とする。利用者は処理履歴（JB-01）で状態を確認し、失敗したものを再試行できる
- 一括操作は「親ジョブ 1 件 + 対象ごとの子ジョブ」に分解する。子ジョブの失敗は他の子ジョブに影響しない
- ジョブの登録はノートの作成・更新と同じトランザクション（Unit of Work）の中で行い、アウトボックス経由で確実にキューへ渡す
- 実行は少なくとも 1 回。ジョブの処理は冪等に実装する
- 同期的に返せる操作（HTML / Markdown の単体書き出し、タグ付け、公開設定の変更）はジョブにしない

## 検討した代替案

### 要求の中で同期的に処理する

実装は単純だが、実行時間の上限に達し、一括操作がまったく成立しない。画面を離れると処理が失われる。不採用。

### クライアント側で分割して逐次要求する

各要求は短くなるが、ブラウザを閉じると処理が止まり、進捗の永続化も別途必要になる。結局サーバー側に状態を持つことになる。不採用。

### すべての処理をジョブにする

一貫性はあるが、タグ付けのような即時に返せる操作まで待機を挟むことになり、体験が悪化する。境界を「実行時間が予測できるか」に置いた。

## 影響

- ジョブを表す集約（種別、対象、状態、進捗、失敗理由、実行者）が必要になる
- 画面には「処理中」の状態が常に存在する。ノート一覧・ノート詳細・ヘッダーのインジケーター・処理履歴の 4 か所で表現する
- 失敗の理由は利用者に説明できる語彙で分類する。語彙そのものはここに列挙せず、利用者向けの正を [scenario/jobs.md](../scenario/jobs.md) の JB-01、型としての集合を `JobFailureReason`（[domains/job.md](../domains/job.md)）が持つ。二重管理をやめ、語彙が増えてもこの ADR は追随しない
- ジョブの保持期間（90 日）と生成物の保持期間（単体 PDF は 24 時間、一括ダウンロードの生成物は子・ZIP とも 7 日）を定め、期限切れを回収する仕組みが必要になる。経路による差は `exportNote` の再利用条件が吸収する（[ADR 012](./012-job-execution-resilience.md)）
- 実行中のジョブは、ワーカーの生存を待たずに終端させる経路が 9 つある — 連携失効に伴う一括失敗・連携解除・ゴミ箱への移動・ワークスペース削除・退会・除名・脱退・ロールの降格・利用者自身の取り消し。いずれもジョブの終端とその後始末（`processing` のままのノートの回復と、終端させた batch 親の成功済みの子が持つ生成物の回収）を同一 UoW で伴う。列挙と規則の正典は [ADR 012](./012-job-execution-resilience.md) と [usecases/job.md](../usecases/job.md) の「共通: 強制終端の後始末」に置き、ここでは重複して数え直さない
- リース失効による自動回収（リーパーと引き継ぎ試行の上限超過）も、`processing` のままのノートを回復させる点では同じ後始末を伴う（理由は `timeout`）。生成物の回収だけは行わない — 自動回収が作る `failed` の batch 親は再試行で開き直せるためである（同じく ADR 012）
