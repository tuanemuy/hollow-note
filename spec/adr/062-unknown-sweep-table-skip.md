# 062. run が名指す表をこの配備が掃けないときは、ack で飛ばして run を完走させる

## ステータス

承認済み

## コンテキスト

表順の正本を run のスナップショットに一本化しても（[ADR 061](./061-maintenance-sweep-order-authority.md)）、「表構成を変えるデプロイをまたいだ resume」の残り半分が残る — run のスナップショットが、この配備には sweep の無い表を名指しているケース（表が**減る**デプロイ）。この lane を解放して失敗に数えると、漏れ（lane が claimed のまま残ること）は起きないが、次の cron も同じ lane を取って同じ判定に戻るため、**その run は永久に完走しない**。同じ kind の running run がある限り新しい run は作られないので、以後この kind のスイープ全体が止まる。

ただし「この配備が sweep を持たない表」の原因は 1 つではない。

1. **デプロイ境界越えの resume** — 旧い表集合で作られた run を、表を減らした配備が resume した。次の run はこの配備の表集合で作られるので、この表は 1 run 分で現れなくなる
2. **同一配備内の表集合ドリフト** — run の表集合の供給元と sweep レジストリの供給元は別で、同じ配備の中でもずれうる（表名を既定の表集合に足して sweep 側の union に足し忘れる、綴りを誤る）。この場合、**次の run にも同じ表が現れる**

## 前提

表集合のスナップショットが run 単位で、resume 中も動かないこと（[ADR 061](./061-maintenance-sweep-order-authority.md)）。参照ランタイムが Node + in-memory の 1 つであること（[ADR 025](./025-single-reference-runtime.md)）。

## 決定

未知の表は error ログに記録したうえで `advanceOrAck(completed: true)` で前進させ、返った position を通常どおり処理キューに載せる。原因 1 と原因 2 を実行時に区別しない。

- **失敗には数えない。** 「削除の失敗」ではないため。数えると、表集合が全部未知の run が「この invocation の削除がすべて失敗」の条件に当たって `SystemError(DatabaseError)` を投げ、DB 障害と区別できなくなる
- ack 1 回を 1 command として invocation の予算に数える。表集合が全部未知なら lane は表数ぶん ack を繰り返すので、1 invocation 内で無制限に回らないようにする
- ログの payload は飛ばした表名に加えて `runId` / generation / shardId。この変更後、これが「その run でその表が掃かれなかった」唯一の痕跡になる。**run の表集合は載せない** — 呼び出し側が run について知れるのは開始応答と lane だけで、表集合を返すポートメソッドは無く、足すことは [ADR 061](./061-maintenance-sweep-order-authority.md) が棄却した「表集合を呼び出し側へ配る」案に戻ることを意味する。飛ばした表名と run / lane の特定子があれば痕跡としては足り、表集合は `runId` から後で引ける

## 検討した代替案

### 解放して停滞させ、運用が気づいて手で run を消す

「うるさい故障」として気づける利点はあるが、この配備には掃く手段がそもそも無いので、run を止めても行は掃けない。停滞のぶんだけ悪い。

### 未知表を検出したら run 全体を失敗させる

未知表は障害ではなく配備の状態で、`SystemError(DatabaseError)` の意味（DB 障害）と衝突する。エラーの種別を曖昧にする。

## 影響

- **原因 1（デプロイ境界越えの resume）は解消する。** 表が減るデプロイをまたいでも run が完走し、次の run はこの配備の表集合で作られるので、停滞は 1 run 分で自然に消える。本 ADR が主張する効果はここまで
- 未知表の skip は cron（駆動）経路の振る舞いとして定める。`AuthStateTable` はこの配備の呼び出し箇所で未知表を型エラーにするが、プロセス／デプロイ境界を越えて run の表集合から継続 turn に届く表は止められない。その turn は前進せず、lane は後続の cron が同じ skip で回収する
- 掃く手段が無い表の行は、その run では掃かれないまま run が completed になる。ただし掃く手段が無い以上これは停滞させた場合も同じで、停滞を足さないぶんだけ良い
- **残存条件（原因 2 は解消しない）**: 同一配備内で run の表集合と sweep レジストリがずれた場合、その表は次の run にも現れる。skip を入れる前は「うるさい故障」（run が止まる）だったものが、**恒久的に、静かに、掃かれない表**になる — error ログを誰も見ていなければ、期限切れの認証状態が永久に回収されない。これは sweep レジストリの union が型で捕まえていた失敗モード（登録漏れを「決して回収されない表」ではなく型エラーにする）を、実行時の静かな取りこぼしへ戻すことを意味する。本 ADR はこれを**解決しない**
- 残存条件を塞ぐ手段は composition root の起動時検査だが、参照ランタイム（[ADR 025](./025-single-reference-runtime.md)）ではこの配備を作れない（表集合はバックエンドのオプションで、環境変数からは渡らないため本番経路は常に既定の表集合を使う）。到達不能な失敗モードに対して composition root の持ち分と将来の全バックエンドへの引き継ぎを足す判断は、その配備が現実に作れるようになる時点（環境変数から表集合を渡す、バックエンドが増える）と合わせて行う
