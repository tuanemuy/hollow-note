# 008. ドメインを 9 つに分割し、タグ付けを Tag 側に置く

## コンテキスト

79 のシナリオと 32 の画面を、依存が一方向に流れるドメインへ分割する必要がある。とくに次の 3 点が非自明だった。

1. ノートとタグの関係。ノート一覧はタグで絞り込み、タグ管理はノートへの付与件数を数える。素直に両側から参照すると循環する
2. ファイルの保管（オブジェクトストレージ）と、ファイルから HTML を作る変換。同じ「ファイル」を扱うが関心事が違う
3. 非同期ジョブ。取り込み・再生成・バックアップ・PDF 生成・一括ダウンロードのすべてに現れ、どのドメインにも属さない

## 決定

ドメインを 9 つに分割する。

| ドメイン | 責務 |
| --- | --- |
| Identity | 利用者、認証手段、セッション、確認・再設定トークン |
| Workspace | ワークスペース、メンバーシップ、招待 |
| Note | ノート本体、本文の版、公開設定、共有リンク、所属先 |
| Tag | タグと、ノートへの付与 |
| Storage | 保管ファイル（元ファイル、メディア、取り込んだ参照リソース、生成物） |
| Conversion | ファイル形式の判定、変換方針の決定、変換の実行 |
| Integration | 外部サービス連携（OpenRouter / Google Drive）とバックアップ記録 |
| Job | 非同期ジョブの登録・進捗・再試行・キャンセル |
| Usage | 保存容量と LLM 実行回数のクォータ |

依存方向（すべて ID による参照）:

```
Identity ← Workspace ← Note → Storage ← Conversion
   ↑          ↑         ↑        ↑
   └── Integration ─────┘        │
   ↑          ↑                  │
   └── Usage  │                  │
   ↑          │                  │
   └── Job ───┴──────────────────┘
        ↑
       Tag → Note
```

この図は主要な辺のみを示す。正確な依存一覧は [domains/index.md](../domains/index.md) の依存表を正とする。

循環はない。Note は Tag を知らず、Tag が NoteId を参照する。Job も同じ向きで、Job が NoteId を参照し、Note は Job を知らない。`JobId` を含む値（PDF エクスポートの `ExportTicket`）が必要になる場合は、それが Note の不変条件に関与しないことを確認したうえでアプリケーション層の型として定義し、Note → Job の辺を作らない（[ADR 010](./010-anonymous-export-and-ticket.md)）。

### タグ付けを Tag ドメインに置く

ノートへのタグ付与（`NoteTag`）は Tag ドメインの集約に含める。Note はタグを一切知らない。一覧でノートとタグを一緒に見せるのは読み取りの合成であり、アプリケーション層が両方のクエリポートを呼んで組み立てる。

### 変換を Storage から分ける

Storage は「バイト列を預かって返す」ことだけを責務とする。形式の判定、変換方針の決定、LLM の呼び出しは Conversion に置く。Conversion は Storage を ID で参照し、内容の読み出しはポート経由で行う。

### Job を独立させる

Job は対象を `(targetType, targetId)` の組で多相に参照する。ジョブの状態遷移・再試行回数・親子関係・キャンセル可否は Job の不変条件として閉じ、各ドメインはジョブの存在を知らずに済む。ジョブの実行内容（何をするか）はアプリケーション層のワーカーが担う。

### ドメインをまたぐ整合性の取り方

分割の代償として、1 つの操作が複数ドメインの集約に及ぶことがある。既定は**ドメインイベント経由の結果整合**とし、次の基準を満たすものだけを同一 Unit of Work（同一トランザクション）で束ねる。

| 後始末の性質 | 取り方 | 例 |
| --- | --- | --- |
| 遅延を許せる（途中の状態を見られても矛盾に見えない） | ドメインイベント（結果整合） | ノートの完全削除に伴うタグ付与・保管ファイルの回収、保管ファイルの実体の削除、容量と LLM 実行回数の集計、読み取りモデルの投影 |
| 中間状態を許容できない（片方だけが確定すると、利用者が自力で解けない状態が残る／権限を失った相手にデータが残る） | 同一 Unit of Work | ジョブの強制終端に伴う後始末（`processing` のまま固定されるノートの回復、終端の時点で存在する生成物の破棄）、退会・ワークスペース削除・除名に伴う実行中ジョブの取り消し |

同一 Unit of Work で複数ドメインを書いても依存方向は壊れない。束ねているのはトランザクションの境界であって集約どうしの参照ではなく、各集約は自分の不変条件だけで更新される。ただしこの束ね方が使えるのは同じデータストアに載る範囲に限られ、オブジェクトストレージのような外部資源への書き込みは必ずイベント駆動になる（メタデータを先に消して実体を後から消す `deleteStoredObjects`）。複数ドメインを 1 つの Unit of Work で書くときの合成の規約（`run` を入れ子にしない、共有手順として切り出す）は [usecases/identity.md](../usecases/identity.md) の「共通の約束」に置く。

## 検討した代替案

### タグを Note の集約に含める

ノートの読み書きが 1 集約で完結し、一覧の取得も単純になる。しかしタグのリネーム・統合・削除（OR-08）が「全ノートの更新」になり、タグ管理画面の使用件数の集計もノート全走査になる。タグは独立した寿命を持つため不採用。

### Note と Tag を相互参照する

読み取りは最も素直だが、ドメイン間に循環が生まれ、アーキテクチャ制約に反する。不採用。

### 変換を Note の一部にする

「ノートの本文を作る」という点では自然だが、対応形式ごとの判定・LLM のモデル選択・音声認識といった関心事が Note に流れ込み、Note が肥大化する。変換は入力（ファイル）と出力（HTML 断片）が明確な独立した関心事なので分離した。

### ジョブを各ドメインに分散させる

`ConversionJob` / `BackupJob` / `ExportJob` をそれぞれのドメインに置く案。処理履歴（P-15）が 3 つのクエリの合成になり、共通の再試行・キャンセル規則を 3 か所に複製することになる。不採用。

## 影響

- ノート一覧やノート詳細の取得は、アプリケーション層で Note / Tag / Job / Storage のクエリポートを合成する読み取りになる
- ドメインをまたぐ整合性は、遅延を許せる後始末（ノート削除時のタグ付与の削除など）をドメインイベント経由の結果整合とし、中間状態を許容できない後始末だけを同一 Unit of Work で束ねる（上記「ドメインをまたぐ整合性の取り方」）。Unit of Work は 1 トランザクションで複数の集約・複数ドメインのリポジトリを更新し、そこで生まれたイベントの enqueue までを原子的に行う
- Conversion は Storage の内容を読むためのポート（`FileContentReader`）を自前で定義し、Storage のアダプターがそれを満たす
- Usage は Note / Storage の変更イベントを購読して集計を更新する。クォータ判定は同期的に読む
