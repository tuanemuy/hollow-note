# 058. 台帳 ID の名乗りをコード側に要求するのは適合ケースだけとする

## ステータス

承認済み

## コンテキスト

`spec/inventory/*.md` の各行は ID を持ち、そこから対応する実装やテストへ辿れることが台帳の値打ちである。到達の手段は要素の種類ごとに違う。

- **ADP 行**（ポートメソッド）— [ADR 052](./052-adapter-inventory-granularity.md) が適合スイートのケースに行を採番しないと決めた結果、行を持たないケースと行を持つメソッドを結ぶ手段はケース名（`it` の第 1 引数）の ADP ID しか無い
- **TC 行** — `spec/testcases/{domain}/{usecase}.md` の表の 1 行と 1 対 1 で、定義場所欄がそのファイルを名指しする
- **UC 行** — 「1 ユースケース = 1 テストケースファイル = 1 UC 行」の不変で `spec/usecases/{domain}.md` の節と 1 対 1 に結ばれ、実装ファイル名がユースケース名そのものである

つまり TC と UC は台帳の定義場所欄からファイル名を経由して辿れるのに対し、ADP だけは名乗りが無いと辿れない。一方でコード側には、TC ID を `it` 名に、UC ID をユースケース実装の JSDoc に書いたものと書いていないものが混在している。混在の理由が読めないと、名乗っていない行が「規約の取りこぼし」と読まれ、レビューのたびに同じ論点が立つ。

## 前提

適合ケースに台帳行を採番しないこと（[ADR 052](./052-adapter-inventory-granularity.md)）。TC 行がテストケースファイルの表の行と、UC 行がユースケース節と 1 対 1 であること — この 1 対 1 が崩れれば、TC / UC にも名乗りが要る。

## 決定

- **ID の名乗りをコード側に要求するのは適合ケース（`it` 名の ADP ID）だけとする。** TC ID を `it` 名に、UC ID をユースケース実装の JSDoc に書くことは**推奨するが要求しない**
- **既に名乗っているものは外さない。** 名乗り自体に害は無く、外すと台帳からの到達性が減る
- したがって、同じ台帳の中で名乗る行と名乗らない行が混在する状態は**規約どおりであって欠陥ではない**

## 検討した代替案

### 全 TC / 全 UC に名乗らせる

台帳からコードへの到達性が最大になる。しかし TC 行だけで 2400 行を超えており、一部にだけ掛ければ「新しく採番した分だけが名乗る」という非対称を別の場所に作り直すことになる。全数に掛けるなら台帳の追随とは別の規模の作業になる。

### 名乗りを一律に禁じ、既に名乗っている ID をコードから外す

混在が消えて規約が単純になる。しかし台帳から辿れていたテストとユースケースが辿れなくなる。規約をそろえるために到達性を捨てる向きは採らない。

### ADR 052 の決定に「TC ID は `it` 名で追わない」と書く

規約としては最もはっきりする。しかし 052 の決定は採番の位置と ADP ID の名乗りに閉じており、名乗らせ**ない**ことをそこへ書くと、後から `it` 名に ID を足す判断が規約違反と読まれる。「推奨するが要求しない」という強さは別の決定として持つ。

## 影響

- ADP ID の名乗りが「唯一の追跡手段だから要求される」という理由つきの規約として残り、TC / UC へ機械的に横展開されない
- TC / UC は台帳からコードへ `grep` 一発では到達できず、テストケースファイル名・ユースケース名を経由する 2 段になる。台帳の定義場所欄がその経路を持つので断絶はしない
- 名乗る / 名乗らないがファイルごとに分かれるので、コード側で `TC-` を数えても意味を持たない。計数の正典は台帳側だけになる
