# 003. ノートの所属先は個人または 1 ワークスペースのいずれか 1 つとし、移動を許す

## コンテキスト

個人のノートとワークスペースのノートが並存し、利用者は両方の文脈を切り替えて利用する。ノートの所属と移動の規則を一意に定める必要がある。

これはアクセス制御の根幹に関わる。1 ノートが複数の文脈に属せる場合、「誰が読めるか」の判定が所属の集合に対する探索になり、公開ステータスとロールの掛け算が所属数だけ増える。

## 決定

- ノートは `owner`（個人 or ワークスペース）をちょうど 1 つ持つ
- 所属先は後から変更できる（個人 → ワークスペース、ワークスペース → 個人、ワークスペース A → ワークスペース B）
- 移動できるのは、移動元での編集権限と移動先での編集権限を両方持つ利用者に限る
- 移動してもノートの ID と共有リンクの URL は変わらない。ただしアクセスできる人の範囲は移動先の規則に従って即座に変わる

## 検討した代替案

### 所属先を 1 つに固定し、移動を許さない

アクセス判定は最も単純になるが、「個人で作ったノートをチームに渡す」という自然な流れが作り直しになる。日常的に起きる操作を塞ぐ代償が大きく不採用。

### 1 ノートを複数ワークスペースに同時共有する

柔軟性は最も高いが、公開ステータス（非公開 / 限定公開 / 公開）とワークスペースごとのロールの組み合わせで実効権限を決める必要があり、「このノートは誰に見えているのか」を利用者が把握できなくなる。ワークスペースごとに違う公開設定を持たせるかという追加の判断も生む。不採用。

## 影響

- ノートは `ownerType`（`user` / `workspace`）と `ownerId` を持つ。所有者と作成者（`createdBy`）は別の概念として保持する
- アクセス判定は「ノートの公開ステータス」と「所属先に対する閲覧者の立場」の 2 要素で決まり、探索を伴わない
- 移動時は、移動によって閲覧できなくなる利用者が出る旨を事前に警告する必要がある
- タグは所属先（個人 / ワークスペース）ごとに独立しているため、移動時は同名のタグへ付け替え、移動先に存在しないタグは外れる
- 移動はノート単位と複数選択の一括操作の両方で提供する
- タイムラインは所属先で絞り込むだけで表現でき、個人 / ワークスペースの切り替えが単純なフィルターになる
