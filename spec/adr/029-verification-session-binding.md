# 029. メール確認はセッションの発行を確認要求元のブラウザーに束縛する

## コンテキスト

メール確認のリンクはメールクライアントから GET で開かれる。ページの読み込みでトークンの消費とセッションの発行まで行う素朴な実装には、2 つの問題がある。

1 つは「状態を変更する GET」を作ってしまうこと。単回消費のトークンが、プリフェッチやリンクプレビューの GET で誤って消費される。

もう 1 つはより深刻で、**セッションの発行が「リンクを踏んだ」だけで走る**ことである。攻撃者は自分のメールでサインアップして自分の確認トークン `T` を得たうえで、`https://<app>/verify-email?token=T` を被害者に踏ませればよい。結果、被害者のブラウザーは**攻撃者のアカウントでサインインした状態**になる。本サービスはノートを書くためのものなので、被害者がそのまま書いた内容は攻撃者のアカウントに保存される — 直接のデータ流出経路である。

この攻撃には通常の CSRF 対策が効かない。トップレベル遷移なので `SameSite=Lax` の Cookie は素通りし、確認要求を発するのが自オリジンのページ自身である以上、`Origin` 検証も CSRF トークンも原理的に成立しない。「状態を変更する GET を作らない」という規律は、文面としては満たしていても守ろうとした性質を守れていない。

## 前提

すべての server function 呼び出しに対して同一オリジン検証を実際に強制していること。`FormData` を受ける POST 経路はフレームワークが server function に対して常に開けており（クロスオリジンの `<form>` から直接叩け、プリフライトも起きない）、「アプリ側が `FormData` 経路を書いていない」ことは攻撃者を縛らない。この検証が外れると、下の確認待ち Cookie を被害者のブラウザーに植える経路が開く。

## 決定

1. `/verify-email` の GET はページの描画（「処理中」）だけで状態を変更しない。トークンの消費はマウント後の POST で行う
2. サインアップの応答は確認待ち Cookie を**常に**焼く。値はサインアップ応答のユーザー ID、属性は `HttpOnly` / `SameSite=Lax` / `Path=/`、寿命は確認トークンと同じ。条件分岐を入れると Cookie の有無や形そのものが利用者列挙のオラクルになる（既登録メールのユーザー ID は decoy — [ADR 028](./028-account-enumeration-resistance.md)）
3. セッション Cookie は「トークンの持ち主 == 確認待ち Cookie の値」のときだけ発行し、同時に確認待ち Cookie を破棄する
4. 一致しなくても**メール確認そのものは成立させる**（トークンは消費し、利用者は有効になる）。画面は「確認しました。サインインしてください」の状態へ倒す。トークンが使用済みだった場合とは原因が違うので、別の状態として持つ

`SameSite=Lax` は攻撃者が確認待ち Cookie を被害者のブラウザーへ持ち込む経路を塞ぎ、`HttpOnly` はスクリプトからの書き込みを塞ぐ。攻撃者が被害者に踏ませられるのは URL だけで、Cookie は攻撃者自身のブラウザーにしかない。

## 検討した代替案

### GET 1 発でトークンを消費してセッションを発行する

往復が 1 回で済み、JS も不要。しかし状態を変更する GET であり、誤消費と login CSRF の両方が成立する。

### GET / POST の分離だけを行う

誤消費は防げる。しかし POST が利用者の操作を介さずに走る以上、攻撃の成立条件は変わらない。分離は必要条件であって十分条件ではない。

### 確認 POST に CSRF トークンを付ける

POST を発しているのは自オリジンのページ自身なので、トークンも `Origin` も正しく揃う。攻撃者が偽装しているのは POST ではなく「どのトークンを確認するか」なので、原理的に効かない。

### 確認後は常にサインインさせない

最も単純で安全。しかし同一ブラウザーで完結する通常の導線にも一手増える。束縛が成立する場合だけ自動サインインさせれば、安全性を落とさずに通常の導線を保てる。

## 影響

- 「リンクを踏ませるだけでは被害者の認証状態が変わらない」が成立する。誤消費の防止と状態変更 GET の不在も維持される
- セッションの上書きが起きないので、サインイン済みの利用者が確認リンクを踏んでもセッションを失わない
- **縮退（受容）**: PC でサインアップして携帯でメールを開く別端末フローでは自動サインインせず、「確認できました → サインインしてください」に倒れる。確認自体は完了しているので、サインインするだけで先へ進める。Cookie を消した / 期限切れの同一ブラウザーでも同じ経路になる
- **縮退（受容）**: 確認待ち Cookie は 1 本なので、同一ブラウザーで続けてサインアップすると先のサインアップの確認リンクは自動サインインしなくなる。これも「確認済み・サインインが必要」に倒れるだけで、確認そのものは成立する
- presentation が「確認待ち」という状態を Cookie 1 本ぶん持つ。ユースケース側は無変更で、束縛は transport 境界に閉じる
