# 054. 外部アカウントの一意性は、予約ディレクトリだけが担保する

## ステータス

承認済み

## コンテキスト

同じ外部アカウント（provider ＋ provider 上の識別子）が 2 人のユーザーに紐づかないことは、認証の基本的な不変条件である。これを強制する場所として候補が 2 つあった。

- **identity 行のリポジトリ**（`IdentityRepository`）— 行を書く側が重複を弾く
- **一意性の予約ディレクトリ**（`IdentityUniqueDirectory`）— 索引を確保する側が弾く

設計文書は前者のエラーケースに `ConflictError("PROVIDER_ACCOUNT_ALREADY_LINKED")` を挙げていたが、実装は後者だけが検査を持つ。どちらかに決めないと、バックエンドを書く人は「両方に置くべきか」を毎回自分で判断することになり、置いた側と置かなかった側で振る舞いが分かれる。

両方に置く形も検討に値するが、その場合は同じ不変条件が 2 か所で強制され、予約の操作 ID 体系（[ADR 048](./048-uniqueness-reservation-operation-id.md)）の外に検査が 1 つ増える。予約と補償の対応が取れない検査が混ざると、失敗時にどちらの記録を巻き戻せばよいかが決まらない。

## 前提

外部アカウントの claim が索引であって資格ではなく、読み側が現行の identity 行を同一トランザクションで照合すること（[ADR 038](./038-provider-account-claim-and-identity-row.md)）。一意性予約の操作 ID が合成で決定的に導出されること（[ADR 048](./048-uniqueness-reservation-operation-id.md)）。

## 決定

- **provider account の一意性の担保は予約ディレクトリに一本化する。** `PROVIDER_ACCOUNT_ALREADY_LINKED` はディレクトリ側のエラーケースとして契約し、identity 行のリポジトリの契約からは落とす。ポート定義の JSDoc も同じ側にそろえる
- **契約を弱めた側は責務の移転を残す**（[ADR 046](./046-port-contract-divergence.md)）。ディレクトリ側の記述に「provider account の一意性はここが唯一の担保である」と明記する。索引の一意性を索引の持ち主が担保する形は、claim を索引として扱う立場と自然に整合する

## 検討した代替案

### リポジトリ側にも一意性検査を足す

行を書く経路が単体で安全になる。しかし同じ不変条件が 2 か所で強制され、予約の操作 ID 体系の外に検査が 1 つ増える。予約 → 行の書き込みという順序があるので、後段の検査が発火するのは前段が壊れたときだけであり、そのとき何を巻き戻すかは決まっていない。

### 両方に置いてよいことにする

バックエンドの自由度が上がる。しかし「JSDoc だけを読んで実装したものが適合スイートを通る」（[ADR 026](./026-port-contract-and-conformance.md) の決定 1）が成立しなくなり、バックエンドごとに拒否の出どころが変わる。

## 影響

- JSDoc だけを読んだ実装者が到達する振る舞いと、適合スイートが通す振る舞いが一致する
- identity 行のバックエンド実装者は、provider account の一意性制約を DB 側に置いてもよいが、契約としては要求されない。逆に、置かなくても適合する
- 一意性の強制がポート契約として残ること（[ADR 028](./028-account-enumeration-resistance.md) の前提）は、ディレクトリ側の契約で満たされる
- ディレクトリが担保するのは**全利用者にまたがる**一意性である。1 利用者の identity 集合の中に同じ `(provider, providerAccountId)` が 2 件並ぶかどうかは別の問いで、そちらは `IdentityPolicy.findOAuth` が見る（[ADR 060](./060-conditional-unique-claim-teardown.md)）。担保元はこの決定から動かない
