# 037. `NODE_ENV` に依存する安全判定は allowlist で書く

## ステータス

承認済み

## コンテキスト

開発専用の危険な機能（開発用 IdP — [ADR 036](./036-development-identity-provider.md)）の無効化と、Cookie への `Secure` 付与を、どちらも「`NODE_ENV === "production"` なら」という denylist で書いていた。denylist は production **以外のあらゆる値**を通す。

実測では `NODE_ENV=staging` と `NODE_ENV=`（空文字）のいずれでも本番形の起動に成功し、開発用の同意画面が 200 を返した。空文字は起動口の `process.env.NODE_ENV ??= "production"` が既定へ戻せない（`??=` は空文字を nullish と見なさない）ため、未定義変数を参照する配備マニフェスト（`NODE_ENV=$UNSET_VAR`）で普通に起きる。配備側の `NODE_ENV` は我々の管理下にない。

## 前提

開発の正規経路が `NODE_ENV=development` を立てること。本番形の起動口が、配備者の申告を待たずに自分で `NODE_ENV=production` を宣言すること（宣言は読み込むバンドルの実体と一致する）。ビルド時に畳み込まれる参照（リテラル比較）と実行時に読む参照（env スキーマ）で、値が効く経路が違うこと。

## 決定

危険側の免除は allowlist で書く。**`development` のときだけ免除し、他のすべての値（未設定・空文字・`test`・`staging` を含む）では拒否 / 付与する。**

- 「分類できない配備は安全側へ倒す」を規則そのものにする。denylist は「危険な値を数え上げられている」ことを前提にするが、その前提は成り立たない
- 免除の理由を判定の向きと一致させる。`Secure` を外す理由は「開発時の平文 http」であって「production ではない」ではない
- 起動を止めるときは、失敗メッセージに**観測した値**を含める。空文字のケースでは、値が見えないと原因に辿り着けない
- 判定がビルド時に畳み込まれるのか実行時に読まれるのかを、why コメントとして判定のすぐ横に残す。畳み込みの有無が読めないことが繰り返しの誤読を生む

## 検討した代替案

### denylist を維持し、危険な値を数え上げる

変更が小さい。しかし列挙は配備側が渡しうる値に追いつかない。「安全な値を数え上げる」ほうが集合として閉じている。

### 専用のフラグ（`APP_ENV` など）を新設する

`NODE_ENV` のツール的な意味と、配備の分類を分けられる。しかし env が 2 系統になり、両者が食い違ったときにどちらが正かの判断が新たに要る。ツールチェーンが `NODE_ENV` を見続ける以上、二重管理は消えない。

### 起動口の宣言だけに頼る

宣言を通る経路では正しく効く。しかし宣言を通らない起動経路が 1 つでもあれば破れるので、ガードの前提として使えない。宣言は「production バンドルと実行時 env の一致」を保つ役割に留める。

## 影響

- 本番形の起動は `NODE_ENV` の値によらず開発専用機能を拒否する。実測で production / staging / 空文字 / 未設定の 4 通りすべてが起動時に失敗し、開発用の指定が無い本番形は起動して当該ルートが 404 を返す
- 「配備先では絶対に有効にしない」という運用上の約束が、配備者の申告ではなくコードで裏づけられる
- 本番形で開発専用機能を検証する経路は `NODE_ENV=development` を明示する 1 通りだけになる
- `test` などで起動する運用を将来入れるなら、allowlist を広げる判断を明示的に行う
