# 024. in-memory 永続化を正規のバックエンドとして扱い、トランザクションを undo ログで実装する

## コンテキスト

外部プロセスなしで動く永続化が要る。開発サーバーの実行基盤になり、ユースケースのテストを unit の速度で回せる。

しかしテスト方針は「リポジトリ / UoW / Clock の fake を作らない」と定めていた。トランザクションや楽観ロックの in-memory 模倣は integration テストの代替にならず、契約を検証しないモックを増やすだけになるからである。in-memory 実装を素朴に持ち込むと、この方針と正面から衝突する。

もう 1 つの問題はトランザクションの模倣方法である。全テーブルのスナップショットを取って失敗時に差し替える素朴な実装は、UoW の外で発行される原子的操作（route の予約、ログイン試行のカウンター、OAuth state の取り出し — [ADR 023](./023-two-plane-unit-of-work.md)）が open な UoW と交錯したとき、**無関係な確定済みの書き込みまで巻き戻す**。

## 決定

### `adapters/memory/` は fake ではなくバックエンドの 1 つとする

他のプロバイダーと同格のアダプター群として扱う。fake との違いは 2 つ。

1. 共有適合スイート（[ADR 026](./026-port-contract-and-conformance.md)）を、実バックエンドと同一の条件で通す義務を負う
2. DI で本番と同じ経路で配線され、開発サーバーの実行基盤になる

テスト方針は「fake を作らない」の趣旨（契約を検証しない場当たりのモックを禁じる）を保ったまま、「適合テストを通るアダプターはバックエンドの 1 つ」と読み替える。

### トランザクションは undo ログ + 実行文脈で実装する

全テーブルを「mutation のたびに undo エントリーを積む Map ラッパー」とし、トランザクション文脈を非同期実行文脈（`AsyncLocalStorage`）で運ぶ。UoW のコールバックと同じ文脈から出た書き込みだけが undo ログに載り、失敗時は逆順の undo でその UoW 自身の書き込みだけを巻き戻す。別文脈からの書き込み（UoW 外ポート）は直接適用され、並行するロールバックの影響を受けない。

行は必ず新しいオブジェクトで置き換える（in-place の変更は undo が効かない）。UoW 同士は直列化して single-writer 分離を近似し、入れ子の `run` は文脈検査で拒否する。

### 暗号 / Intl 系のアダプターも当面ここに同居させる

パスワードハッシュ、セキュアトークン生成、共有トークン保護、タイムゾーン解決は永続化契約とは無関係で、プロバイダー別のグループ分けからは別ディレクトリが素直である。しかしバックエンドが 1 つしかない現時点で分離しても得られるのは import パスの整理だけなので、同居のまま置く。2 つ目のバックエンドが実在する時点で分離を再検討する。

## 検討した代替案

### テスト用の fake としてテストディレクトリに置く

方針との衝突は起きない。しかし適合スイートを通す義務を負わないため、バックエンド差し替えの検証に使えず、開発サーバーの実行基盤にもならない。結局「契約を検証しないモック」そのものになる。

### スナップショット + 差し替えでトランザクションを模倣する

実装は最も短い。しかし UoW の外で発行される原子的操作と交錯したときに、無関係な確定済みの書き込みを失う。この交錯は仕様が要求している形（予約サガ・原子カウンター）なので、例外ではなく通常経路で起きる。

### 暗号系を最初からプロバイダー別ディレクトリに分ける

配置としては正しいが、いま移動すると import の波及だけが発生し、分離の判断材料（2 つ目のバックエンドが何を必要とするか）は得られない。

## 影響

- ユースケースのテストが外部プロセスなしで走り、開発時の起動に外部依存がない。データはプロセスの寿命だけ生き、再起動で白紙に戻る
- SQL 制約、パラメータ上限、トランザクション分離といった実バックエンド固有の挙動は in-memory では検出できない。「適合スイートを通った」を本番保証と誤認しない運用が要る
- 行の immutable 規約（必ず新オブジェクトを set する）がアダプター全体の前提になる
- UoW を直列化するため、長時間の UoW は他をブロックする（in-memory では許容する）
- `adapters/memory` から暗号実装を import する形は誤解を招きうる。命名（`createNodeSecureTokenGenerator` など）と本 ADR で緩和する
