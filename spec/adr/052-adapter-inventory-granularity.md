# 052. 台帳の 1 行はポートメソッドに対応させ、ID は行位置ではなく行の識別子とする

## ステータス

承認済み

## コンテキスト

`spec/inventory/*.md` は `spec/domains/` `spec/usecases/` `spec/testcases/` を生成元とする台帳で、`| ID | 要素 | 定義場所 | 実装されるべき振る舞いの要点 |` の 4 列と「1 行 = 1 要素」という不変を持つ。ポートについては 1 行 = 1 メソッドで、エンティティやドメインサービスは 1 行が全振る舞いを畳む。

この台帳には 2 方向の圧力がかかる。

1 つは**適合スイートのケース**。1 つのメソッドに複数のケースが相乗りし、なかには「membership item は cleanup レーンが走って初めて完全 ack になる」のように 3 メソッドのどの 1 行にも収まらない横断的な主張もある。ケースごとの行を作れば「どこまでがメソッドで、どこからがケースか」の判断が毎回必要になり、ケース単位の spec を新設する案は [ADR 026](./026-port-contract-and-conformance.md) が既に棄却している（共有スイート自体を契約の実行形とし、対応は `describe` 名に ADP ID を含める命名規約で追う）。

もう 1 つは**新規要素の追加位置**。台帳の行はポート定義の出現順に並んでいるが、ID は `spec/` 本文・計画・レビュー記録から参照される識別子でもある。出現順の位置に挿入して以降を繰り下げると、既存の参照がすべて別の要素を指すようになる。`spec/inventory/test.md` の TC ID はとくにこの誤解を招きやすい — テストケースファイル名の辞書順にブロックが並んでおり、`spec/testcases/*/*.md` の表自体には ID が 1 つも書かれていないため、「ID は行位置で決まる」と読める余地がある。

## 前提

契約の正本がポート定義にあり、検証が共有適合スイートで、ADP 行との対応を `describe` 名の命名規約で追うこと（[ADR 026](./026-port-contract-and-conformance.md)）。

## 決定

- **適合スイートのケースには ID を採番しない。** ケースが主張する契約はポート定義の正本（`spec/domains/*.md` のポート説明段落）に書き、台帳は既存行の「実装されるべき振る舞いの要点」欄で追随させるだけにする。台帳のヘッダーには生成規則を 1 行明文化する（「1 行 = 1 ポートメソッド。適合スイートのケースは行にせず `describe` 名の命名規約で追う」）
- **採番しないのは適合ケース**（既存メソッドに相乗りする主張）**であって、新規ポートメソッドには通常どおり採番する。** 採番は各群の末尾に足し、出現順に挿入して既存 ID を繰り下げない。並び順と ID 順は一致しなくなるが、台帳の軸は ID であって行位置ではない — **ID は行位置ではなく行の識別子**である。エンティティやドメインサービスのように既存の 1 行が全振る舞いを畳んでいる単位に振る舞いが増えた場合は、行を足さず要点欄で追随させる
- **同じ規則を `spec/inventory/test.md` の TC ID にも当てる。** TC ID はテストケースファイル名の辞書順に振られてきたが、**ID は行位置ではなく行の識別子**なので、新設したテストケースファイルの TC 行は辞書順の位置に挿入せず**群の末尾に採番する**。既存 ID の指す要素を動かさないことが優先する。**既存のテストケースファイルに行を足す場合も同じで、既存ブロックの中へ挿入せず末尾に採番する**

## 検討した代替案

### 適合ケースごとに新しい ID を採番する

ケース 1 本ずつを ID で追跡できる。しかし「1 行 = 1 ポートメソッド」の不変が壊れ、以後どの主張が行になるかを毎回判断することになる。横断的なケースはそもそもどのメソッドの行にも属さない。

### ケース単位の行を全ポートに展開する

台帳と適合スイートが 1 対 1 になる。しかしスイート全体を台帳へ二重管理することになり、[ADR 026](./026-port-contract-and-conformance.md) が「実行形を正とする」と決めた理由と正面から反する。

### ポート定義の出現順に挿入して以降を繰り下げる

台帳が読みやすくなる。しかし既存 ID の参照がすべて別の要素を指すようになり、ID の意味が「安定した識別子」から「行番号」に落ちる。

### 新規メソッドも採番せず、既存行の要点欄に相乗りさせる

行が増えない。しかし 1 行が 2 メソッドを指すことになり、この ADR が守ろうとしている不変そのものを壊す。

### TC は辞書順に挿入して ID を振り直す

ファイル名と ID の対応が保たれる。しかし DOM / ADP / UC で棄却したのと同じ理由で、既存の参照が全部ずれる。TC ID だけ別の規則にする根拠も無い。

## 影響

- 台帳の生成規則が保たれ、契約は「実装者が読むポート定義」に集まる
- 適合ケース 1 本ずつを ID で追跡することはできない（`describe` 名の命名規約で追う既存方針のまま）
- 台帳の行順と ID 順が一致しない箇所が生まれる。読み手は行位置に意味を読まない
- 新しいバックエンドの実装者は「実装すべきメソッドの全数」を台帳から数えられる
