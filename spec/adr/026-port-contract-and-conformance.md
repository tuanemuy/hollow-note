# 026. ポート契約の正本はポート定義に置き、共有適合スイートで検証する

## コンテキスト

永続化ポートはバックエンドを差し替える前提で設計してある（in-memory → scope Durable Object + D1）。ところが契約の実体 — 原子性、条件付き更新、サガの中断点、keyset の継続、楽観ロック、リースの失効と回収 — はポートごとの JSDoc と spec に散在し、検証はバックエンドごとのテストに重複していた。

共有のハーネスがないと、新しいバックエンドは「動くが契約を満たさない」状態でも通る。逆に、契約の記述をテストだけに置くと、実装者はテストを走らせるまで必要な振る舞いに到達できない。実際、リース失効時に claimed のレーンを pending へ戻す回収（これが無いと停止したオーナーのレーンを誰も再取得できず、処理が永久に完了しない）は、適合スイートだけが規定していてポート定義からは読み取れなかった。

## 決定

### 1. 契約の正本はポート定義に置く

インターフェースと JSDoc だけを読んで、実装者が必要な振る舞いに到達できること。適合スイートだけが規定している振る舞いを残さない。liveness に関わる状態遷移（リース失効時のレーン回収、失効していないリースには触れないこと、回収時に位置と cursor を保持すること）は、スイートではなくポート定義に書く。

### 2. 検証は共有パラメタライズドスイートで行う

`adapters/conformance/` に `describeXxxContract(name, makeBackend)` 形式のスイートを置き、各バックエンドはスイートを import して 1 行で実行する。ケースの根拠は spec のポート契約文とし、テストケース仕様を別ドキュメントに二重記述しない。**スイート自体が契約の実行形**である。

### 3. スイートが契約化するのは観測可能な結果だけ

ポートの利用者から見える結果 — 双方の commit が確定すること、途中状態が他方から観測されないこと、リレーの起動が各 1 回であること — だけを assert する。実行順序や分離の実現手段（プロセス内 mutex による直列化か、バッチ flush か、楽観制御か）は契約から外し、バックエンド固有のローカルテストへ置く。対話型トランザクションを持たない D1 はコールバックの実行が交錯しても仕様上正しく、そこをスイートで凍結すると正しい実装が落ちる。

### 4. 適合バックエンドの契約に UoW とリレー起動の観測点を含める

Unit of Work の実行境界とイベントの enqueue、リレーの起動回数は、バックエンド差し替えで最も壊れやすく、壊れたときの影響が最も大きい契約である。適合バックエンドはこれらを観測可能にする（リレー起動を数える配線を持つ）ことを要求する。

### 5. 同型の違反は同一のエラー種別に写す

`resolveMany` などのバッチ上限超過は `SystemError(DatabaseError)` に統一する。入力上限の超過は並行状態の衝突ではなく呼び出し側のプログラミングエラーであり、利用者への再試行案内も意味を持たない。`ConflictError`（presentation で 409 になる、並行衝突専用）は使わない。エラーの契約はポート定義の記述に含める。

## 検討した代替案

### テストケース仕様を spec に新設する

網羅の管理はしやすい。しかしポート契約が spec の 2 か所（契約文とテストケース）とコードに三重で書かれ、必ず乖離する。契約の実行形をコードに置けば、乖離した瞬間にテストが落ちる。

### バックエンドごとに独立したテストを書く

バックエンド固有の挙動は書きやすい。しかし契約の解釈が実装ごとに分岐し、「同じ契約を満たしている」ことの検証にならない。差し替え可能性という前提そのものが検証されない。

### 実装の観測できる振る舞いをすべてスイートで凍結する

回帰は最大限に捕まえられる。しかし仕様上正しい別実装がスイートに落ちるため、バックエンドを足すたびにスイートを緩める交渉が発生し、「契約」と「たまたまの実装特性」の区別が失われる。

## 影響

- 新しいバックエンドの追加は「スイートを import + セットアップ + 観測用の配線」で検証される
- スイートはテストランナーに結合する。ランナーを替える場合は書き直しになる
- 新しいケースをスイートに足すたび「これは観測可能な結果か、実装特性か」の判断が要る。この規律は lint では強制されず、レビューで守る
- in-memory バックエンドの直列化保証のように、契約ではない実装特性はローカルテストが唯一の防御になる
- バッチ上限超過が 500 系になるため、呼び出し側の実装ミスが監視上「システム障害」として計上される。アラート閾値の設計時に留意する
