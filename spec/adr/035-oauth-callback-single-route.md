# 035. OAuth コールバックは 1 ルートで受け、分岐は消費した `state` の intent だけで決める

## ステータス

承認済み

## コンテキスト

同じコールバック URL に複数の用途が着地する — サインイン、既存アカウントへのログイン方法の追加、外部サービス連携。分岐の根拠として使える面は URL のパス、クエリー、現在のセッションの有無のいずれかだが、クエリーは攻撃者が操作でき、セッションはフロー開始時点と一致する保証がない。プロバイダー側に登録する redirect URI を用途ごとに分けると、登録の運用が用途の数だけ増える。

## 前提

フロー状態の取り出しが原子的な単回消費であること。intent がフロー開始時にサーバーが決めた値であること。

## 決定

- 分岐根拠は取り出したフロー状態の **intent のみ**とする。ルートは 1 本で、パスに含まれる provider は表示・ログ用途に留め、フロー状態の provider と不一致なら「state 不正」に倒す
- application にディスパッチャーを置き、intent でユースケースを選ぶ。ユースケース自身も仕様どおりの入口（自分でフロー状態を取り出す形）を保つ。1 回の要求で走る入口はどちらか一方だけなので二重消費は起きない
- 応答は intent で判別する共用体にする。セッション Cookie を焼くのは**サインインの arm だけ**で、他の arm は Cookie に触れない。用途を足すときは arm を 1 つ増やす
- **intent が判らない時点の表示は intent 中立にする。** キャンセル・照合失敗・交換失敗では intent を知る手段が無い（知る唯一の手段が消費済みのフロー状態）。文言と戻り先を片方の用途に固定すると、もう片方から来た利用者を誤った場所へ流す。戻り先は認証状態に応じて分岐する入口（トップ）に倒す
- 再試行の導線は「再試行が意味を持つと判るとき」だけ出す。単回消費を通り抜けた後の失敗を同じ引数で再送しても必ず「state 不正」になるので、再試行できるのは (a) 要求がサーバーに届いていないと構造的に判る場合と (b) 認可そのものをやり直す場合に限る。(a) の判定はエラー契約を連れているかどうかで行い、例外の型や文言には依存しない

## 検討した代替案

### 現在のセッションの有無で分岐する

追加の状態を持たずに済む。しかしフロー開始時の意図と一致する保証がなく、「サインイン中かどうか」でユースケースが変わる曖昧さが残る。開始時に決めた intent のフローを別のユースケースへ着地させられる。

### 用途ごとにコールバックのパスを分ける

分岐が URL に出て読みやすい。しかしプロバイダー側の登録 redirect URI が用途の数だけ増え、パスは攻撃者が選べる面なので結局フロー状態との突き合わせが要る。

### 消費せずに intent だけを覗く読み取りを足す

失敗時の表示を intent 別にできる。しかし「intent を読めるのは単回消費の取り出しだけ」という閉じ方が緩み、覗ける経路がもう 1 つ増える。得られるのは失敗画面の文言だけで、取引が合わない。

## 影響

- 用途の追加は判別共用体の arm 1 つで済み、ルートもプロバイダー登録も増えない
- 開始時の intent と違うユースケースを呼ばせる経路が構造的に無くなる
- 戻り値が判別共用体になるので、画面側にも intent の分岐が 1 つ増える
- 中立化した戻り先は、用途によっては 1 クリック多い導線になる（キャンセルからサインインフォームへ戻る場合など）。行き止まりを作らないことを優先した帰結として受容する
