# 002. LLM 連携は OpenRouter の OAuth のみをサポートする

## ステータス

承認済み

## コンテキスト

画像・音声・テキストレイヤーのない PDF は、機械的な変換だけでは意味のある HTML にならない。これらを扱うには LLM（および音声認識）が必要になる。

一方で、サービス側が LLM の利用料を負担するとコスト構造が読めなくなる。idea.md でも「OpenRouter 等の LLM プロバイダーと OAuth 連携する」と、利用者自身の契約を使う前提が示されていた。

## 決定

- LLM 連携は OpenRouter の OAuth（PKCE）のみをサポートする
- 連携によって取得したユーザー固有の API キーを暗号化して保存し、そのユーザーのノート変換にのみ使用する
- API キーを画面から直接入力させる導線は設けない
- 未連携のユーザーには LLM を要する変換を提供せず、機械的な変換のみを行う（アップロード自体は成功させ、ノートは「要 LLM 連携」の状態で保存する）
- 連携を解除すると保存済みの鍵は即座に破棄する。生成済みノートの内容は残る

## 検討した代替案

### 任意プロバイダーの API キーを直接入力させる

OpenRouter を使っていない利用者も取り込めるが、プロバイダーごとにモデル名・料金・エンドポイント・レート制限の差異を吸収する必要があり、鍵の平文入力を扱う責務も増える。OpenRouter が複数プロバイダーへのルーティングを既に担うため、得られる柔軟性に対して負担が大きい。不採用。

### サービス側の鍵で LLM を実行し、利用量で課金する

利用者は連携なしで全機能を使えるが、課金基盤が必須になり、idea.md の範囲を大きく超える。不採用。

### OAuth と API キー入力の併用

移行期の受け皿としては有効だが、鍵の出所ごとに検証・失効・エラー処理が二重になる。単一の連携経路に絞る判断とした。不採用。

## 影響

- `ExternalConnection` は `google_drive` と `openrouter` の 2 種類を持つ
- LLM を要する変換は「連携済みか」を事前条件として持ち、未連携時は専用のエラー（連携導線への誘導つき）を返す
- 鍵が失効・無効化された場合の再連携フローが必要になる。変換ジョブは `providerAuthFailed` として失敗し、ノート側に再連携を促す状態を持つ
- モデル選択（構造化用モデル / 音声認識用モデル）はユーザー設定として持ち、既定値をサービス側で定義する
