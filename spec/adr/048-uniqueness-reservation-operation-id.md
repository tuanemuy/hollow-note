# 048. 一意性予約の操作 ID は合成で導出し、ログには出さない

## ステータス

承認済み

## コンテキスト

一意キー（メールアドレス・ハンドル・外部アカウント）の予約は「予約 → 本体の commit → 活性化」の 3 段で進む。応答喪失後の再試行が**同じ予約行を掴み直せる**ことが回復の前提なので、予約の操作 ID は再導出可能でなければならない。

設計文書上の表記はハッシュだが、導出するのは application 層である。ハッシュ実装を application に持ち込むか、ハッシュを渡すためだけにポートを 1 本増やすかの二択になり、どちらも横断的関心事の扱いから外れる。

一方、鍵の正規化値はメールアドレス・ハンドル・外部アカウント ID の生値そのものである。合成した ID をそのまま失敗ログへ載せると、ディレクトリの一時障害が 1 回起きるだけで利用者のメールアドレスがログ基盤へ流れる。ログは DB と保持期間も権限境界も違う。

## 前提

種別が区切り文字を含まない閉じた列挙であること。自由文字列である鍵が末尾に来ること。所有者の一致をディレクトリが別に検査すること（ID を推測できても他人の鍵は動かせない）。

## 決定

- 導出は **`親操作 ID:種別:正規化鍵` の合成**で行う。要求されている性質は「決定的であること」と「同一の親の中で種別・鍵ごとに異なること」の 2 つだけで、不可逆性は要らない。親を持たない操作も同じ規則で `操作名:主体 ID` を親として合成し、再試行が同じ行へ収束するようにする
- **この ID をログに出さない。** ログ用の同一性は `{ 親操作 ID, 種別 }` として別に持つ。親 ID は主体と操作までは特定でき、鍵の値を含まない。この規律を導出関数の JSDoc に残し、「ディレクトリ呼び出しの引数から出ない値」として位置づける
- 決定的 ID の帰結として、**同一主体の並行要求は同じ予約行に相乗りする**。したがって楽観ロックで敗れた側は**補償解放しない** — 予約の所有者は進行中の別の試行であって、敗者ではない。それ以外の失敗（不変条件違反・対象不在・ドライバー障害）は「この操作全体が進んでいない」ことを意味するので、従来どおり即時に解放する

## 検討した代替案

### ハッシュで導出する

ID の長さが固定され、鍵が読めなくなる。しかし application 層にハッシュ実装が入り、決定性の根拠が「合成の一意性」から「衝突困難性」へ移る。再導出する側とのアルゴリズム互換も新たな制約になる。

### 予約の戻り値に「新規確保か相乗りか」を持たせ、補償側で分岐する

補償の条件をポートの語彙で表現できる。しかしポート定義・アダプター・適合スイート・共有手続きの型がすべて動き、同じ仕組みを使う他のユースケースも巻き込む。直したいのは「決定的な親 ID を持つ 1 つのユースケースの補償条件」であって、ポートの語彙ではない。

### ID をハッシュ化してログ問題も同時に解く

ログに鍵が出ない形にはなる。しかし決定性の根拠を移す代償を、ログのために払うことになる。ログに出す同一性を別に持つほうが、両方の性質を保てる。

## 影響

- 応答喪失からの再開が予約層でも成立し、孤児になった予約行を次の試行が必ず掴み直す
- 予約行の ID 列が固定長でなくなる（実バックエンドでは長さの見積もりが要る）
- 予約 1 件につき親 ID を重複して持つ。その代わり、鍵を含む ID を安易にログへ回す道が塞がる
- 補償しない経路では、勝者が同じ鍵を触らなかった場合に予約が有効期限まで残る。恒久的な不整合を有限時間の過剰予約に置き換える取引で、「解放が届かなくても有効期限まで鍵が止まるだけ」という既存の許容範囲の内側にある
