# 065. 条件付き書き込みの道具は書き込みの意味で選び、guard 敗北は読み経路が返す答えへそろえる

## ステータス

承認済み

## コンテキスト

原子適用の単位が「文の束を一度に当てる」形のバックエンドでは、条件付き `UPDATE` が 0 行に当たっても単位は成功する。判定と適用のあいだに別の writer が入ったことを呼び出し側へ伝える手段は、単位ごと中断させる guard 文（[database/index.md](../database/index.md) の `_occ_guard`）しかない。

そこから 2 つの問いが出る。**どの書き込みに guard を積むか**と、**guard が外れたとき呼び出し側に何を返すか**である。素直な答え — 書き込みには一律 guard を積み、外れたら一律 `ConflictError` にする — はどちらも観測できる形で誤る。

- 可換な集合への追加（account deletion manifest の receipt 追加のように、互いに独立した継続の鎖が撃つ ack）に敗者を作ると、交差した ack の片方が落ちる。ack は terminal turn を通過済みで二度と撃たれないので、完了判定が永久に偽のままになる
- 一律の翻訳は、ポートが**戻り値で表現している状態**を例外へ格上げする。「不在 / 別 user / token 不一致はすべて no-op」と列挙で契約されたメソッドが、相手が着地しただけで投げる。呼び出し側が outbox consumer なら負け続けた event は quarantine されうる。同じ operation の並行リプレイ（配送は at-least-once）に負けただけで失敗になる経路も同型である

参照バックエンドは UoW を直列化するのでこの割り込みに到達せず、共有適合スイートは単一スレッドのバックエンドも通す必要があるので、この差はスイートからは観測できない。

## 前提

契約の正本がポート定義とその JSDoc で、検証が共有適合スイートであること（[ADR 026](./026-port-contract-and-conformance.md)）。契約と実装が食い違ったら正本のある側へ倒すこと（[ADR 046](./046-port-contract-divergence.md)）。

## 決定

### 1. 道具は書き込みの意味で選ぶ

- **可換な集合への追加**は、文そのものを冪等にする。guard を積まず、敗者を作らない。交差した 2 つの追加はどちらも残るのが正しい答えである。早期 return は往復の節約として置いてよいが、正しさをそこに依存させない
- **状態遷移**は、読んだ行像に対する compare-and-set にする。guard の述語は行の同一性（鍵・現在の状態・版・operation ID）で組み、同じ条件を `UPDATE` の `WHERE` にも置く。遷移ごとに書き分けない

### 2. guard 敗北の翻訳は、その呼び出しの読み経路が同じ条件で返す答えへそろえる

敗北経路でだけ読みを撃ち直し、答えを再導出する。読みが no-op を返す条件なら return、`false` を返す条件なら `false`、戻り値で「他者が持っている」を表現できるなら例外ではなくその戻り値。**ポートが戻り値で表現している状態を例外へ格上げしない。**

どの索引・どの guard が外れたかを駆動側のメッセージから見分ける必要はない — 読み直した答えが自動的に区別する。払うのは敗者だけで、勝者の往復は変わらない。

### 3. 契約を動かす条件

読み経路の答えへそろえられる敗北は、バックエンド固有の原子性の話であってポート契約の変更ではない。ポート JSDoc も共有適合スイートも動かさない。

そろえられず、呼び出し側へ新しい失敗として届く敗北（同時 claim、投影スナップショットの交差）は、ポート JSDoc のエラー契約行へ「**投げうる**失敗」として足す。「投げねばならない」ではないので、直列化で排他を得ているバックエンドは追記後も契約を満たす。アダプター内で畳めない理由（staged なバックエンドでは guard が commit 時に発火し、呼び出しフレームには畳む場所が無い／負けた差分適用が勝者の索引を壊す）も契約の一部として書く。耐性は呼び出し側に置き、耐える対象は契約行が名指したコードに限る。

### 4. 観測はバックエンド固有テストに置く

読みと適用のあいだへ対抗 writer を 1 度だけ割り込ませる形で書く。共有適合スイートには足さない — 単一スレッドのバックエンドはこの割り込みを原理的に観測できない。

## 検討した代替案

### 敗北を一律 `ConflictError` にする

store の形は完全にそろい、翻訳の分岐が消える。採らないのは上記のとおり、ポートが列挙で契約した no-op や、戻り値で表現された「他者が持っている」状態まで例外になるためである。敗者の答えが「直列に実行されていたら得たはずの答え」から外れる。

### 述語ごとに guard を分けて翻訳を変える

guard を 2 本に割れば述語ごとに翻訳を選べそうに見えるが、駆動側のエラーは制約の**種別**しか運ばないのでどちらが外れたかを区別できない。敗北経路で読みを 1 本撃ち直すほうが安く、索引名への依存も増えない。

### すべての条件付き書き込みを条件付き `UPDATE` だけで表す

`WHERE` に条件を置けば 0 行更新で済むので guard 文が要らない。採らないのは、0 行更新が中断にならない以上、負けたことを呼び出し側が知る手段が無いためである。戻り値が「行が変わった」と食い違い、read-your-writes のオーバーレイにも storage が受け取らなかった行像が残る。

## 影響

- 状態機械を持つ store は「guard を 1 つも持たない」形を取れない。新しい制御表を足すときは、書き込みごとにどちらの意味かを決めることになる
- 敗北経路の読み 1 本ぶんコストが増える。払うのは敗者だけである
- 単位ごと適用するバックエンドを新しく足す実装者は、契約を読むだけでは翻訳を決められない — 本 ADR がその決め方である
- staged なセッション（UoW の中）で敗者になった場合の翻訳は、commit 時の既定（`OPTIMISTIC_LOCK_FAILURE`）のままである。読み直しが走るのは autocommit の形だけ。staged 経路でも読み経路の答えへそろえるには、commit が「どの書き込みの guard が外れたか」をポートへ返す仕掛けが要る
